### 1.2 手机端（V45 已补齐）

**方式 A：手机浏览器 / PWA（现在就能用，零发版成本）**

浏览器打开站点即可：全站响应式（≤640 手机断点），底部四 Tab
（广场 / 发布 / 消息 / 我的，消息带未读红点），触控目标 ≥44px、
输入框 16px（不会一聚焦就整页缩放），刘海与手势条安全区已适配。

可「添加到主屏幕」以独立窗口启动（`manifest.webmanifest`，standalone +
maskable 图标）。Service Worker 只缓存应用外壳，**API 一律不缓存**——
任务状态、合约状态、钱包余额读到陈旧值会让用户基于错误信息决定付钱，
宁可报错也不能撒谎；断网时显示离线兜底页而非浏览器错误页。
有新版本时提示「刷新」，避免旧外壳打新接口。

**取证拍照**：执行留痕支持拍照/相册附图，客户端压缩（长边 1280、JPEG 0.8）
后上传。压缩不是优化是必需——手机直出常有 3~8MB，弱网下执行者传不上去，
而交付凭证传不上去等于没有证据。图片走 `StorageProvider` 抽象，
接对象存储/CDN 只改环境变量。

**方式 B：原生 App（React Native / Expo）**

## 二、后端并发设计（现状 + 生产化路径）

### 2.1 现在真实具备的并发安全手段

| 手段 | 位置 | 防什么 |
|---|---|---|
| **幂等键 + 请求指纹** | `core/idempotency.py` | 网络重试重复扣款；同 key 不同金额（吞单）；跨操作串味 |
| **状态机白名单** | `task/service.py::transition` | 并发双击导致重复放款——第二次必落在非法流转上 |
| **事务边界整体回滚** | `core/db.py::get_db` | 任一步失败则整笔回滚，不留半截状态 |
| **DB 唯一约束** | `contracts.task_id UNIQUE` 等 | 一任务一合约的最后一道防线 |
| **限流（滑动窗口）** | `core/ratelimit.py` | 注册/登录/改密/换绑的暴力尝试 |
| **对账不变量** | `risk/service.py::reconcile` | 五条硬不变量兜底，不平自动开工单+告警 |

这套组合已被 **550 个测试**覆盖，其中 `test_concurrency_guards.py` 专门验证
「重复接受报名 / 重复托管 / 重复交付 / 重复验收 / 重复里程碑放款」全部拒绝且零副作用。

### 2.2 多副本并发安全（V42 已补齐，见 [18-concurrency.md](specs/18-concurrency.md)）

此前是 **SQLite 单文件 + 单进程 + 无行锁**：单进程安全，多副本下
「两个进程同时读到 `status=funded` 各自放款」这类竞态在应用层拦不住。
现已补齐三层防护：

| 层 | 实现 | 作用 |
|---|---|---|
| **行锁（悲观）** | `core/locks.py::lock_contract` / `lock_wallets` | 多副本下把「读-判断-写」串行化 |
| **乐观锁** | `Contract.lock_version` / `WalletAccount.lock_version`（`version_id_col`） | 拿不到行锁时，并发 UPDATE 也只有一个能提交，另一个 409 |
| **状态机白名单** | `task/service.py::transition` | 即使串行到达，重复操作仍被状态判断拒绝 |

要点：
- **切 Postgres 只改一个环境变量**，业务代码零改动：
  ```bash
  PLATFORM_DATABASE_URL=postgresql+psycopg://user:pass@host/db
  ```
  连接池参数（`PLATFORM_DB_POOL_SIZE` / `MAX_OVERFLOW` / `POOL_RECYCLE`）已参数化。
- **加锁顺序统一**：先合约、后钱包，多钱包按 `user_id` 升序——从根上杜绝死锁。
- **SQLite 自动降级**：`supports_row_lock()` 探测方言，本地开发不受影响
  （已开 WAL + `busy_timeout`）。
- **限流**：`RateLimiter` 协议 + 内存/Redis 双实现，配 `PLATFORM_REDIS_URL` 即切；
  Redis 故障连续达阈值自动降级为内存并在 `/readyz` 中可见——限流不该拖垮登录。
- **定时任务单实例**：`JobLock` 表 + `job_slot()` 依赖，全部 14 个 job 端点已接入；
  执行完即释放，崩溃靠 TTL 抢占。调度表与端点**同源**（`app/core/jobs.py`），
  cron 直接读它，并有测试从 OpenAPI 自动发现端点双向核对——**漂了 CI 就红**
  （V57：此前手抄的表漂出三处，其中资金对账 job 从来没被架起来过）。
- **探针**：`/healthz`（存活，不查依赖）、`/readyz`（DB + 限流后端，不满足 503）。

覆盖测试：`tests/test_conc_hardening.py`（真多线程）验证并发验收只放款一次、
并发托管只扣一次、并发提现不透支、丢失更新被拒、job 不重复执行。

### 2.3 事件投递（V53 已补齐，见 [28-event-delivery.md](specs/28-event-delivery.md)）

此前 `core/events.py` 是十七行同步派发、**没有任何隔离**。`task.completed` 上
挂着 6 个派生 handler，和真正的放款在同一个事务同一个请求里——
用探针复现过：把知识卡片 handler 改成抛异常（卡片生成走 LLM，超时很正常），
**验收接口直接崩，执行方一分钱拿不到**。锦上添花拖死了存在理由。

现在的模型：

| 机制 | 作用 |
|---|---|
| **SAVEPOINT 隔离** | 每个 handler 在嵌套事务里跑，失败只回滚它自己那一段 |
| **事务性发件箱** | `publish()` 在业务事务内写 `outbox_events`，业务回滚则事件不存在 |
| **投递记录唯一约束** | `(event_id, handler)` 唯一——「恰好一次」靠数据库，不靠代码自觉 |
| **`retry` 必填声明** | 新增 handler 必须回答「隔一段时间自动补做还对吗」，不答就注册失败 |
| **`critical` 例外** | 存证入链这类失败**必须**让业务事务失败：签了字却没链上记录，等于证据能力有洞 |
| **drain job + 死信** | 任何副本都能补做任何副本发布的事件（这就是 SEC-040 要的跨副本能力） |

刻意**没有**引入 Kafka/Redis：发件箱在同一个库同一个事务里，天然没有两阶段提交
问题；真要上 MQ，让它从发件箱消费即可，业务代码一行不用改。顺序不能反。

同样刻意**没有**把派发改成全异步：通知与经验卡片在同一请求内落库，用户刷新就能
看到；异步只是失败后的兜底，不是默认路径。

**仍待做**：
- **地理检索**：现在是全表扫 + Python 算距离，规模化需换 PostGIS 或 geohash 索引。

**容量参考**：单机 Postgres + 4 个 uvicorn worker，这套读写比下支撑
日均十万级任务量没问题；瓶颈会先出现在 AI 分解（外部 LLM 调用）和地理检索
（现在是全表扫 + Python 算距离，⚠️ 规模化需换 PostGIS 或 geohash 索引）。

## 三、安全性

### 3.1 已实现（每项都有测试）

**账号与认证**
- 密码 **PBKDF2-HMAC-SHA256，12 万次迭代 + 随机盐**（`core/security.py`）
- 自签 token 绑定会话 id，**会话可吊销**（改密/换绑/重置密码后全端下线）
- 三入口限流一致：注册 3/60s、短信登录 5/60s、**密码登录 5/60s**
- 新设备登录站内提醒；换绑手机需「新号验证码 + 旧密码」双验证

**授权**
- 资源级鉴权：任务/合约/会话/纠纷都校验「你是不是当事人」，非当事人 403
- 管理端 `require_admin`；**内部 cron 端点独立令牌** `X-Job-Token`（与用户身份正交）
- 越权测试集中在 `test_hardening.py`，覆盖跨用户读取报名/合约/会话/导出

**资金**
- 整数分记账、只增流水、三态账本（可用/托管/冻结）
- **五条对账硬不变量**：全局守恒 / 托管有据 / 冻结有据 / 平台佣金有据 / **代扣税款专户有据**
- 提现风控：日限额、**单笔或当日累计**达 ¥1 万冻结进人审、必须先绑实名一致的收款账户
  （V55：改造前只判单笔，连提 5 笔 ¥9,999 可以 ¥49,995 零人审出账）
- 幂等指纹防吞单/串味；防重放守卫覆盖全部关键资金动作

**审计与存证**
- **管理员操作审计**（封禁/裁决/结算/提现审批全留痕，可按动作查询）
- **SHA256 存证哈希链**：合约关键动作入链，改一行必须重写整条后继链才不被发现
- 对账不平自动开差错工单 + 通知全体管理员

**内容与风控**
- 敏感词机审（任务/内容/评论）、举报队列、封禁影响面预览 + 对手方告知
  （V58：审核队列与用户页两条封禁路径**副作用逐项对等**，此前队列那条只把
  `is_banned` 置 True，对手方的托管资金就这么被无限期困住）
- 下架任务会通知发布者（带原因）与已报名者；已成交任务不可被审核单方作废
- IM 站外引导识别（防跳单）、陌生人私聊条数上限、消息撤回保留审计副本
- 位置脱敏（精确地址仅成交双方可见）、30 天后清除打卡坐标

### 3.2 边界防护（V47 已补齐）

此前最大的洞不是「没加密」，而是**限流只按账号维度**——攻击者每次换手机号，
计数器永远是 1，批量注册与撞库完全不受影响；而且限流只有 7 个手写调用点，
新端点默认裸奔。现在补齐三层：

| 层 | 位置 | 挡什么 |
|---|---|---|
| 网关 | `deploy/nginx.prod.conf` | 建连洪水、慢速攻击；三档 IP 令牌桶（普通/写/**认证最严**） |
| 中间件 | `core/guard.py::WriteRateLimitMiddleware` | 所有写操作按 IP 兜底——**新端点默认受保护** |
| 端点 | `core/guard.py::guard` | 认证类端点账号 + IP **双维度**，任一超限即拒 |

**客户端 IP 必须取对**（`core/clientip.py`）：常见错误是取
`X-Forwarded-For` 的第一个 IP，那是客户端可以随便伪造的——攻击者每次带一个
不同的假 IP，按 IP 的限流与封禁就全废了。正确做法是只信任反代注入的**最后一跳**。
因此生产必须设 `PLATFORM_TRUSTED_PROXY_HOPS=1`（prod 自检会强制检查），
否则应用只看到容器网关 IP，会把全站用户当成同一个人限流。

**自动封禁（V56 起跨副本一致）**：认证失败窗口内达阈值即临时封禁 IP。
封禁与失败计数**落 `security_events` 表**，不再是进程内 dict——
改造前三副本部署下攻击者换个连接就能绕过、有效阈值被放大三倍、
管理员解封只解了一个副本（被误封的公司出口 IP 之后还有 2/3 概率被拒，
用户报「有时候能登录有时候不能」，客服根本复现不出来）。

**升级阶梯是三档，不是两档**：正常 → **要求人机验证** → 封禁。
中间这一档（V56 新增）很关键：没有它，手滑输错几次密码的真人
和撞库脚本得到的处置完全一样。验证码是给被误伤的人一条自证的路，
不是多加一道墙——接上真实供应商后误封率会明显下降。
默认 `PLATFORM_CAPTCHA_PROVIDER=none` 是直通（不验证任何东西），
但触发事件照样留痕，所以没接供应商时风控趋势也看得见。

`/admin/security` 可查看全局封禁并**人工解封**；解封入口**刻意不受封禁限制**
——误封整个公司出口 IP 时管理员很可能就坐在那个 IP 后面。

**其余已就位**：TLS 强制跳转 + HSTS（仅 prod 下发）、安全响应头
（nosniff / frame DENY / CSP / Referrer-Policy）、生产关闭 `/docs`、
`/metrics` 与 `/jobz` 仅内网可达、上传文件带 `nosniff` + sandbox CSP。

### 3.3 ⚠️ 仍需补的

| 项 | 现状 | 要做什么 |
|---|---|---|
| **TLS 证书** | 配置已就位 | 证书需你提供（ACME/Certbot 或云厂商），`up.sh` 会检查 |
| **WAF / CC 防护** | 无 | 云厂商 WAF 或 CDN 层防护，应用层挡不住大流量 DDoS |
| **人机验证** | ✅ V56 服务端 + V59 端到端（SDK/网页/配置端点）已打通 | 配 `PLATFORM_CAPTCHA_PROVIDER` **和 `PLATFORM_CAPTCHA_SITE_KEY`** 接第三方；**只配前者不配后者，生产会拒绝启动**——网页渲染不出挑战，用户会被锁在门外 |
| **依赖扫描** | 无 | CI 加 `pip-audit` / `npm audit` |
| ~~跨副本封禁共享~~ | ✅ V56 已修：封禁与失败计数落 `security_events` 表 | —— |

## 四、一键部署

### 4.1 本地/单机（现在就能跑）

```bash
docker compose up --build
# Web: http://localhost:8080   API 文档: http://localhost:8000/docs
```
数据持久化在 `platform-data` volume（SQLite 文件）。

灌演示数据：
```bash
docker compose exec server python -m scripts.seed_demo
# 生成用户/任务/闭环/圈层/动态，账号密码 pass123456
```

### 4.2 生产部署（一条命令，DEP-001~003）

```bash
cp deploy/.env.example deploy/.env   # 逐项填写，标【必须修改】的不改会被拒绝
./deploy/up.sh                       # 自检 → 迁移 → 起栈 → 等 /readyz
./deploy/up.sh --scale 3             # API 起 3 副本（worker 仍固定 1 副本）
```

`deploy/up.sh` 起栈**前**会拦下这些错误上线：弱 JWT 密钥、默认 job token、
弱数据库密码、CORS 仍是 `*`、四个供应商仍是 mock/local。这些不是建议，是红线；
预发演练确需跳过时用 `ALLOW_INSECURE=1`，且脚本会显式警告。

栈的构成（`deploy/docker-compose.prod.yml`）：

| 服务 | 说明 |
|---|---|
| `db` | Postgres 16，数据在 `pgdata` volume |
| `redis` | 分布式限流后端（CONC-021） |
| `migrate` | **一次性**容器跑 `alembic upgrade head`，避免多副本并发建表 |
| `api` | 可 `--scale N`；健康检查用 `/readyz` 而非 `/healthz`，未就绪不导流量 |
| `worker` | **固定 1 副本**跑 `scripts/cron.py`；即便误起多份，job 端点还有 DB 执行锁兜底 |
| `web` | Nginx 托管前端 + 反代 API |

### 4.3 迁移、备份与恢复

```bash
# 迁移（生产唯一建表路径；ENV=prod 下 create_all 会直接报错）
docker compose -f deploy/docker-compose.prod.yml run --rm migrate

# 备份（建议 crontab 每日）：pg_dump + 存证链 head 快照
./deploy/backup.sh

# 恢复：导入后**强制**跑资金四不变量 + 存证链校验，不过则明确失败
./deploy/restore.sh backups/db-20260822T030000Z.sql.gz
```

存证链 head 单独存一份的理由：它是「历史未被篡改」的独立锚点。
只备份数据库的话，一旦数据被篡改后又备份，你手里就没有能反驳的证据了。

**恢复演练**是这套东西唯一有意义的验证方式——没演练过的备份等于没有备份。

### 4.4 可观测与告警

| 端点 | 用途 | 鉴权 |
|---|---|---|
| `/healthz` | 存活探针，不查任何依赖 | 无 |
| `/readyz` | 就绪探针：DB + 限流后端 + 迁移版本 | 无 |
| `/version` | git sha / 版本 / 环境 | 无 |
| `/metrics` | Prometheus：请求量、延迟分位、**托管中金额 / 待提现 / 未结纠纷** | `X-Job-Token` |
| `/jobz` | 各 job 上次成功时间与最近错误 | `X-Job-Token` |
| `/api/v1/events/health` | 待补做与死信的事件投递数（按 handler 聚合） | `X-Job-Token` |
| `/api/v1/events/dead-letters` | 需人工处理的投递明细 | 管理员登录 |

指标带令牌的理由：资金口径数字不该对公网裸奔。

**必配告警**（DEP-043）：
- 资金对账不平 / 存证链断裂 —— 最高优先级，直接推值班手机
- **`platform_jobs_never_run` > 0** —— 有应有的 job **从来没跑过**。
  V57 之前监控对这种情况完全免疫：`/jobz` 只遍历已有记录，没跑过的没有行，
  于是在列表里干脆不存在。冒烟每次打印「0 个 job 有记录」，
  看起来太像一切正常了——**空列表不是好消息，是没人在跑**。
- `platform_jobs_stale` > 0 或 `/jobz` 中任一 job `seconds_since_success`
  超过其**自身周期**的 3 倍 —— job「静默不跑」比报错更危险
  （自动验收停摆＝资金永久卡在托管）
- 提现失败率突增、5xx 突增、`/readyz` 连续失败
- **`platform_event_dead_letters` 大于 0**（V53 新增）——
  死信堆积是「有功能已经悄悄坏了」的最早信号：业务面上一切正常，
  用户只是少收了通知、经验没入库、后继子任务没自动发出来，
  没有任何接口会报错，只有这个数会涨。每条死信都代表一个**未发生的副作用**，
  需要人判断是否补做（`/api/v1/events/dead-letters` 看明细）。

日志是结构化 JSON，带 `request_id`（入站生成或透传），
并对手机号 / 证件号 / 银行卡自动打码——出事时排查日志，不能因为日志本身再泄一次。

**上线检查清单**：

## 五、社区、市场与营销运营

### 5.1 冷启动：先解决「鸡生蛋」

双边市场最大的坑是两边都空。**不要两边同时推**，按顺序来：

**第一步：把供给端做厚（先招工人，不招雇主）**
- 选 **1 个城市 × 1~2 个高频品类**（推荐：保洁 / 跑腿代买 / 搬家）。
  不要一上来铺全品类全城市——密度不够就没有履约体验。
- 目标：**单个商圈 50~100 个实名执行者**。低于这个密度，发单等不到人接，
  雇主第一次体验就崩了。
- 获取渠道：同城群、蓝领招聘平台、家政/跑腿公司谈整队入驻、地推。
- 钩子：**平台补贴前 N 单佣金**（现在 `fee_bps` 已支持按信用等级折扣，
  可直接给新人 0 佣金），加「保证金免缴」。

**第二步：需求端小范围做透**
- 平台方**自己当第一批雇主**发真实单（这不丢人，是标准做法），
  确保执行者有钱赚、留得住。
- 然后定向邀请：写字楼物业、小区业主群、小微商户。
- 关键指标：**任务被接单率 > 80%**、**平均接单时长 < 30 分钟**。
  达不到就继续加供给，不要扩张。

### 5.2 已经内置、可直接用的增长工具（V46 已补齐）

运营可在管理后台独立完成「注资 → 建活动 → 建券 → 投放 → 看报表」，无需研发介入。

| 能力 | 端点 | 要点 |
|---|---|---|
| 补贴池注资 | `POST /admin/subsidy-pool/fund` | 冷启动时平台还没佣金收入，得先注资 |
| 建活动（预算硬顶） | `POST /admin/campaigns` | **超顶自动停投**，不靠人盯 |
| 建券 | `POST /admin/coupons` | 定额/比例二选一；比例券强制带封顶 |
| 券报表 | `GET /admin/coupons` | 发放/核销/成本/核销率 |
| 供需健康度 | `GET /admin/market-health` | 城市×类目标出 supply / demand 缺口 |
| 北极星指标 | `GET /admin/north-star` | 成单数、GMV、新用户首单转化、纠纷率 |
| 用户侧 | Web `/rewards` | 新人任务进度、领券、我的券、邀请战绩 |

**补贴的资金铁律**：一分补贴都不凭空产生。所有补贴走
「平台账户 → 用户可用余额」并落 `subsidy` 流水，平台余额不足即核销失败，
绝不透支。资金第 4 不变量已相应扩展为
「平台可用 == Σ佣金 + Σ注资 − Σ结算 + Σ补贴净额 + Σ调整净额」，
每个增长用例结尾都断言四不变量成立——**补贴永远能追到出资方**。

**防薅规则**（都有测试兜底）：
- 未实名不得领券（否则批量注册即可薅）
- 一人限领、一单一券（DB 唯一约束兜底）、限量发放
- 合约取消 → 券退回可再用 + 补贴款退回平台（不让用户白丢券，也不让白拿钱）
- 邀请奖励**完成首单才发**（注册即奖是刷号的邀请函）
- 同收款账户 / 同实名 / 互为邀请 → 奖励 blocked 转人工，不发钱

**合规红线（GRW-060，代码层面硬约束）**：
邀请奖励**仅一级**——邀请人的邀请人不获任何奖励，代码里根本不去追溯上级；
战绩接口显式返回 `levels: 1`，页面也写明「不存在多层级返利」。
多层级分销是法律红线，不是产品选项。

### 5.3 社区运营节奏

**日常**
- 每天看 `admin/funnels`：接单率掉了就补供给，验收纠纷多了就查品类标准。
- 纠纷 SLA 已有自动升级（7 天），但**人工仲裁必须 24h 内响应**——
  纠纷处理体验直接决定口碑，这是不能省的人力。
- 每周挑 1~2 个优质闭环案例，让执行者发到社区，平台给流量。

**社群（圈层）玩法**
- 按**技能**建圈：保洁师傅圈、设计师圈——沉淀专业交流，圈内成交有信任加成。
- 按**地域**建圈：某商圈/某小区——密度就是履约速度。
- 圈主给权益（优先派单、佣金折扣），让圈主自己拉人。

**内容与获客**
- 让老手写「XX 任务怎么做才不返工」的案例文 → 既是 SEO 也是新人培训。
- 把「AI 分解」做成传播点：用户输入一句「我要搬家」，
  平台自动拆成 3 个可执行子任务并报价——这是**很强的演示钩子**，
  适合做短视频/直播演示。

### 5.4 变现与定价

- 当前抽佣 **8%**（`PLATFORM_FEE_BPS` 可配），高信用执行者有折扣。
- 冷启动期建议：**前 3 个月 0 佣金**换密度，靠融资/自有资金补贴。
- 成熟后的收入结构：佣金 + 保证金沉淀 + 会员（优先派单/低费率）+
  企业版（批量发单、对公结算、发票）+ 增值（认证徽章、置顶曝光）。
- 平台收入已有实收口径与结算接口（`/admin/platform-finance`），
  财务对账不用另做系统。

### 5.5 风险与合规（别忽视）

- **资金合规**：托管资金属于用户备付金，**必须接持牌支付机构做账户隔离**，
  自己拿账户池收钱是红线。
- **劳务关系**：明确平台是信息中介、执行者是独立承揽人，
  合约模板要写清（现在 `contract/service.py` 的 terms 已含框架，需律师定稿）。
- **税务（V54 已落地机制，但方案必须你来定）**：执行者收入需代扣代缴。
  平台向自然人支付报酬即为**扣缴义务人**（《个人所得税法》第九条），
  应扣未扣会被处应扣未扣税款 **50% 至 3 倍**的罚款。
  代码提供三条路，`PLATFORM_TAX_MODE` **不显式选一条，生产就不让启动**：

  | 路径 | 配置 | 税负 | 前提 |
  |---|---|---|---|
  | 劳务报酬预扣预缴 | `withholding` + `labor_income` | 20%~40% 累进 | 无需执行者办手续 |
  | 经营所得委托代征 | `withholding` + `commissioned_collection` | 通常 0.5%~1.5% | ⚖️ **须先与税务机关签委托代征协议**——没有协议按低税率扣是另一种违法 |
  | 自行申报 | `self_declared` | 执行者自负 | 执行者是个体户/企业**且能开票**；平台不校验发票就付款，企业所得税前列支会被否 |

  代扣的钱进**独立专户**（不与平台佣金混同），由 `finance/jobs/remit-tax` 缴库，
  第五条对账不变量盯着它。执行者在「我的-税务」可查代扣明细
  ——注意那是**代扣明细不是完税证明**，客服口径不要说错。
- **人身安全**：线下任务已有到场打卡、行程分享、紧急联系人（GEO-021/023/024），
  运营上还要有**保险**（意外险/责任险）和黑名单联动。
- **资质品类**：法律/医疗/电工等已有职业资质准入（ACC-022），
  运营必须严格审核证件，别为了 GMV 放水。
- **反洗钱（V55 已内置识别，但制度与人必须你来配）**：
  ⚖️ 反洗钱是**制度 + 人**，不是一段代码。平台侧做的是「只有平台看得见」的那部分——
  拆分提现、快进快出、多账号共用收款卡，这些存管机构只看资金流是看不出来的。
  合规官在 `/admin/aml/activities` 复核，**平台不自动对外报送**（报送要人判断要签字）。

  **客服口径红线**：《反洗钱法》第五条要求对反洗钱工作信息保密。
  用户问「我提现为什么被卡住」，只能答「需人工复核」，
  **绝不能**说「你被风控/被标记为可疑」——那既违法，也等于告诉对方下次怎么规避。

  另：反洗钱要求交易记录保存 **5 年**，与用户的删除权冲突时反洗钱法优先
  （PIPL 第四十七条把「法律另有规定」列为删除义务例外），注销页须如实告知。
- **账号注销（V60 已内置闸门，但有两件事运营必须知道）**：
  ① 注销闸门按**钱包三态之和**拦截。用户抱怨「明明余额是 0 却注销不了」，
  多半是有一笔提现正在人工复核（钱在冻结态）——**先去把复核处理掉**，
  别去改代码绕过闸门：改造前正是这里放行了一笔 ¥15,000，
  复核驳回后钱退回一个再也登不上的账户，永久搁浅。
  ② 注销**不是全删**：按 `app/modules/account/deletion.py` 的处置表，
  真实姓名与银行卡号脱敏保留（反洗钱调档用，脱敏后不足以再打款），
  交易流水与证件摘要原样保留，画像类字段清空。
  五年留存期满后的物理删除**还没有实现**（ACCDEL-041），到期前须补上。
- **发票口径**（V54）：平台只能开**平台服务费**发票（佣金部分）。
  执行者的劳务报酬发票平台**没有开票资格**，要么执行者自开、要么走代开渠道。
  客服遇到「帮我开全额发票」的要求必须拒绝——那是虚开，不是服务。
- **协议更新（V52 已内置，但有个运营动作不能忘）**：改
  `PLATFORM_AGREEMENT_VERSION` 会让**所有用户**在下一次发布/报名/托管/提现前
  被要求重新同意。所以顺序必须是「先把新协议文本上线，再改版本号」——
  反过来做，用户会被要求同意一份他看不到的新协议。
  日常修错别字**不要**动版本号，只有实质性变更才动。
- **撤回同意是有后果的**（LAW-032）：用户在 我的→协议与个人信息授权 里
  撤回支付项会当场解绑收款账户、撤回证件项会停用接单与提现。
  客服会收到「我怎么突然提不了现」的工单，**先问一句是不是撤回过授权**，
  重新授权入口在同一个页面。
