# 商用上线流程：手续、审批、与等待期间能做什么

> **这份文档不是法律意见。** 它的骨架取自代码里**已经硬编码成启动拦截**的那几条
> 上线红线（`server/app/vendors/registry.py::startup_check`），以及每一条拦截
> 当时写下的理由。具体的资质名称、门槛、办理时限与适用地区，**必须由法务/合规
> 顾问按你实际的经营地与业务形态确认**——下面标注 ⚠️ 的地方都是这一类。
>
> 这份文档回答三件事：
> 1. **不做完什么就不能收真钱**（代码会拒绝启动，不是靠人记）；
> 2. 这些手续大致的**依赖顺序**（谁必须先拿到）；
> 3. **等批复的那几个月**能做什么，不必干等。

## 0. 一页速查：代码拒绝启动的全部条件

`PLATFORM_ENV=prod` 时，下面任何一条不满足，**服务直接拒绝启动并打印原因**。
这是刻意的「难用」：把上线前必须完成的对接变成硬拦截，而不是一行只有开发者
看得见的日志。

| # | 环境变量 / 条件 | 拦住它的理由 |
|---|---|---|
| 1 | `PLATFORM_LEDGER_BACKEND=custody` | 平台自建账本托管用户资金涉嫌**资金池与二清**（无证从事支付结算） |
| 2 | `PLATFORM_TAX_MODE` ∈ {`withholding`,`self_declared`} | 向自然人支付报酬即为**扣缴义务人**；应扣未扣可被处应扣未扣税款 50%~3 倍罚款 |
| 3 | `PLATFORM_TAX_PROVIDER ≠ none`（当选 `withholding`） | 声明了要代扣却没配扣缴规则，等于没扣 |
| 4 | `PLATFORM_SIGNATURE_PROVIDER` 非 `platform`/`sandbox-ca` | 平台见证签名不构成《电子签名法》的**可靠电子签名** |
| 5 | `PLATFORM_NOTARY_PROVIDER` 非 `local`/`sandbox-notary` | 自算哈希链没有真实**司法采信力** |
| 6 | `payment` / `sms` / `kyc` / `moderation` / `oauth` 全部非 mock | 这五项是 P0：模拟实现上线即事故（`oauth` 的 mock 等于「客户端说自己是谁就是谁」） |
| 7 | 配了 `ANTHROPIC_API_KEY` 时，`PLATFORM_LLM_MODEL` 在在售型号表内 | 过期型号会让每次分解静默回落模板，而平台看起来完全正常 |
| 8 | `PLATFORM_CAPTCHA_SITE_KEY`（当 `PLATFORM_CAPTCHA_PROVIDER` 会真的拦人） | 渲染不出挑战 = 用户永远交不出令牌 = 连错几次密码就被锁在门外 |
| 9 | `PLATFORM_DATABASE_URL` 指向 Postgres | 生产不得用 SQLite |
| 10 | `PLATFORM_JWT_SECRET` / `PLATFORM_JOB_TOKEN` 非默认值 | 默认密钥等于没有密钥 |
| 11 | `PLATFORM_CORS_ORIGINS ≠ *` | 收紧到白名单域名 |
| 12 | `PLATFORM_EXPOSE_DOCS` 关闭 | 生产不暴露 API 文档 |
| 13 | `PLATFORM_TRUSTED_PROXY_HOPS` 已设 | 反代后取不到真实 IP，按 IP 的限流与封禁会全部失效 |
| 14 | `PLATFORM_API_WORKERS` × (池 + 溢出) ≤ `PLATFORM_DB_CONNECTION_BUDGET` | 连接耗尽不是某个接口变慢，是 `FATAL: sorry, too many clients already`——**每一个接口同时 500，包括健康检查**，于是编排器开始重启容器，而重启后它又去抢同样多的连接。拦的是一类具体改动：把 worker 从 2 调到 8、或副本从 1 加到 3，而池参数没动 |

自查命令（不需要真的起服务）：

```bash
cd server && PLATFORM_ENV=prod python -c "
from app.vendors.registry import startup_check
try:
    startup_check(); print('可以上线')
except Exception as e: print(e)"
```

## 1. 手续与审批：依赖顺序

下面的**顺序**是有讲究的——每一层都被下一层依赖，跳过去会返工。
⚠️ 标注的项目请让法务确认当地的具体资质名称与门槛。

### 第 0 层：主体

| 事项 | 为什么必须先做 |
|---|---|
| 公司主体设立、经营范围 | 后面每一项申请都要主体资质；经营范围写错要变更 |
| 对公账户 | 存管机构、支付通道、税务都要它 |
| ⚠️ 平台经营相关的经营许可/备案 | 视业务形态与地区而定，需法务确认清单 |

### 第 1 层：让网站/App 能对外提供服务

| 事项 | 依赖 | 备注 |
|---|---|---|
| 域名实名 + ⚠️ ICP 备案（如适用） | 主体 | 未备案的域名在部分地区无法解析 |
| ⚠️ 等级保护测评（如适用） | 主体 | 涉及个人信息的平台通常需要 |
| App 开发者账号（Apple / Google / 各安卓市场） | 主体 | 审核周期以周计，**越早注册越好** |
| 隐私政策与用户协议定稿 | ⚠️ 法务 | 代码里已有版本化与变更重新同意机制（`PLATFORM_AGREEMENT_VERSION`） |

### 第 2 层：钱（**这层没通，一分真钱都不能收**）

| 事项 | 依赖 | 对应代码 |
|---|---|---|
| ⚠️ 与**持牌资金存管机构**签约 | 主体 + 对公账户 | 红线 #1；接完设 `LEDGER_BACKEND=custody` |
| ⚠️ 持牌**支付通道**签约（含提现/打款） | 同上 | 红线 #6 的 `payment` |
| **个税方案定案**：平台代扣，还是执行方自行申报开票 | ⚠️ 税务顾问 | 红线 #2/#3。两条都合法，但**必须显式选**——默认的 `none` 意味着「没人想过这件事」 |
| 税款专户（若选代扣） | 税务方案 | 代码已把代扣税款与佣金分账，有第五条对账不变量钉着 |
| ⚠️ 反洗钱内控制度、合规官指定、可疑交易报送流程 | 主体 | 代码已有可疑活动识别与复核台（V96），**但报送与否由合规官判断，平台不自动对外报送** |

> **为什么这一层必须先于开放注册**：一旦有真实用户充值，平台自建账本
> 就已经在托管别人的钱了。代码用拒绝启动来防止这件事发生，
> 不要用改代码的方式绕过它。

### 第 3 层：身份与内容

| 事项 | 对应代码 |
|---|---|
| ⚠️ 实名核验（eKYC）服务商签约 | 红线 #6 的 `kyc`。代码已做证件号摘要查重（防一人多号） |
| 短信服务商 + ⚠️ 短信签名/模板报备 | 红线 #6 的 `sms`。报备通常需要数个工作日 |
| ⚠️ 内容安全服务商 | 红线 #6 的 `moderation`。代码已把图片与文本都接到统一抽象 |
| 第三方登录应用审核（微信/Apple 等） | 红线 #6 的 `oauth` |
| ⚠️ 未成年人保护措施 | 代码已有未成年人实名拦截 |

### 第 4 层：法律效力（可后补，但影响纠纷时的证明力）

| 事项 | 对应代码 | 不做的后果 |
|---|---|---|
| ⚠️ 第三方 CA（可靠电子签名） | 红线 #4 | 合约只有平台见证签名，**证明力弱**；代码已如实标注这一点，没有冒充 |
| ⚠️ 司法链/公证处存证 | 红线 #5 | 哈希链只能自证未被平台篡改，**没有第三方背书** |
| ⚠️ 仲裁机构或诉讼路径约定 | ESCA-050 | 平台处理决定**不是仲裁裁决**，代码里刻意没有这样称呼 |

### 第 5 层：可选但强烈建议

| 事项 | 不做的代价 |
|---|---|
| 人机验证服务商（`captcha`） | 限流 + 自动封禁能挡住大部分自动化攻击，但误封率明显更高 |
| 推送通道（`push`） | 「答辩期还剩 12 小时」这类**错过就无法挽回**的通知只存在于站内，等于没发 |
| 对象存储/CDN | 本地磁盘存图，扩副本即失效 |
| 语义向量模型（`embedding`） | 缺省词袋不是语义模型，知识库检索质量低 |

## 2. 等批复的时候做什么

审批以月计，代码不必干等。按价值排序：

1. **沙箱全链路自检**（今天就能跑）
   ```bash
   cd server && python -m scripts.sandbox_check   # 合规态 28 项
   cd server && python -m scripts.smoke           # 真实交易 + 分账
   ```
   两条都绿，说明**契约已经对齐**：供应商到位后只改环境变量。
   接完真实供应商再各跑一遍，仍绿即说明对接正确。

2. **把 72 号台账里「卡在我们自己」那一类做掉**
   见 [specs/72-status-ledger.md](specs/72-status-ledger.md) §2.2。
   最该先做的三条：**约 88 个两端都没人调用的 SDK 方法逐条过筛**
   （每次抽查都掉出实质缺陷）、管理后台剩余四条（审计日志尤其——
   *谁批了那笔三万块现在只能查数据库*）、提现复核的四眼原则。

3. **App 提审材料与真机验证**（APPB-051 / APP-071）
   开发者账号下来之后第一件事就是在真机上跑一遍，
   **现在所有 App 行为都由扫描闸门与单测覆盖，没有一次点击发生在真实设备上**。

4. **压测与演练**：备份恢复演练脚本已有（`scripts/restore_drill.py`），
   在真实 Postgres 上跑一次；按 `deploy/alerts.prom.yml` 接上告警。

5. **文案与协议定稿**：1197 处界面文案未抽取（I18N-050），
   条款是中文模板而非律师起草文本（IPC-050）。这两件事律师在审的时候可以并行。

## 3. 上线当天的部署步骤

```bash
# 1. 配置（把 13 条红线逐条填对）
cp deploy/.env.example deploy/.env && vi deploy/.env

# 2. 启动自检 → 迁移 → 起栈（脚本内已按此顺序）
./deploy/up.sh

# 3. 验活
curl -fsS https://<域名>/healthz            # 存活
curl -fsS https://<域名>/readyz             # 就绪（含 DB/Redis）
curl -fsS -H "X-Job-Token: $PLATFORM_JOB_TOKEN" https://<域名>/api/v1/jobz   # 18 个 job 在册

# 4. 真实环境闭环（用真实供应商跑一笔小额）
cd server && python -m scripts.smoke
```

**回滚**：`deploy/up.sh` 之前先 `deploy/backup.sh`；恢复用 `deploy/restore.sh`，
它与生产用的是同一份校验实现（V44 立的规矩：恢复校验不能是另写一份）。

## 4. 上线后第一周盯什么

| 指标 | 为什么 |
|---|---|
| `llm_decompose_fallback_total` | 不为 0 说明模型调用在失败而平台在静默降级（V97 新增） |
| 五条资金对账不变量（日终 job + 告警） | 这门生意的心跳 |
| 提现复核队列长度 | 积压意味着用户的钱冻着没人放行 |
| 可疑活动待复核数 | 合规官的工作量，也是报送时限的压力来源 |
| `/jobz` 的「从未跑过」清单 | 排期与端点不一致时这里会先露出来 |
| 纠纷开案率与答辩缺席率 | 缺席率高通常意味着通知没真的触达 |

## 5. 明确的红线：不要这样绕

- **不要**为了上线把 `LEDGER_BACKEND` 留在 `internal`。那不是配置问题，
  是业务不能这样做。
- **不要**把 `TAX_MODE` 设成一个「先跑起来再说」的值。两条路都合法，
  没选是唯一不合法的状态。
- **不要**改 `startup_check` 让它放过某一条。每一条拦截旁边都写着理由，
  要绕之前先把那段理由读完。
