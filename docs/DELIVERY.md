## 二、已钉死的核心契约（全部有测试）

**业务闭环**：发布 → AI 分解（预算守恒）→ 推荐（可解释）→ 报名/邀约 →
合约生成 → 双签 → 托管 → 执行留痕/打卡 → 交付 → 验收/自动验收 → 放款抽佣 →
互评 → 信用 → 经验入库 → 参考价。

**安全与资金不变量**：
- 状态机白名单穷举：非法流转全拒（`test_state_machine`）
- 资金三不变量（全局守恒/托管有据/冻结有据），随机生命周期 fuzz（`test_money_property`）
- 防重放：重复接受/托管/交付/验收/里程碑全拒且零副作用（`test_concurrency_guards`）
- 变更单守恒：加价补托管/减价退款/多轮随机改价（`test_change_order_money`）
- 分期×纠纷交叉：部分放款后只分剩余、冻结期禁放款（`test_milestone_dispute_cross`）
- 多人任务名额预算守恒 + 自动验收边界（`test_multiperson_autoaccept`）
- 存证哈希链防篡改：自洽伪造/删行/脱链全被定位（`test_anchor_chain`）
- 幂等（Idempotency-Key）、限流、资源级越权拒绝（`test_hardening`）

**迭代中修复的产品级缺陷**（测试先行暴露）：
存证链重复注册膨胀、刷单阈值差一、多人任务余数蒸发（每单丢分钱）、
dispute 响应缺复核基数字段、圈层创建者角色丢失等。

| V92 TEAM/APP/CLI | 没有人被告知。本来是去补 App 那三个页面的，补之前先看了一眼团队审批这条线到底通不通：员工提交一笔超额支出，老板驳回并写明理由——**两端都是沉默的**。审批人没收到任何通知（全仓 37 处 `notify()`，`team` 模块一处都没有），所以员工的活被卡住、而**卡住他的那个人从头到尾不知道**，申请可以一直躺着；发起人也没收到任何通知，不知道被驳回了，更不知道为什么。最刺眼的是第二条：服务端**强制**要求写驳回理由（`reason_required`），认真地把它存进 `decision_reason`，**然后不送给任何人**——连 `decide` 的响应里都没有它。**「必须写」和「送到了」是两件事**：这是 V89（V77 强制选知识产权归属却不返回）、V91（服务端说「请先绑定收款账户」却没有任何端能绑）之后的第三次。强制写理由的立意是对的——不写理由的驳回是权力，不是管理；但理由的价值全在于**被驳回的人读到它**，他要据此决定是改金额、改用途还是去谈。送不到，这条强制就只是给审批人加了一道手续。所以补两条通知（提交→通知 owner 与 admin，发起人自己除外；审批完成→通知发起人并带上理由），并把 `decision_reason` 回给调用方。刻意**没有**把它们放进 `MUST_REACH`：申请不会因为没人看就作废，理由也一直躺在列表里可查——**V90 那张表的标准是拿来做减法的，不是每次都用来做加法**，全做成不可关，用户会连真正重要的几条一起屏蔽掉。接着才是三个页面：新通知在手机上会变成一件更糟的事——**通知把人叫来了，而他点进去无路可走**（V91 APP-066 的同一条教训），所以 `app/TeamCoopDev.tsx` 把团队（额度/预算池/申请/审批含必填驳回理由/执行/发票）、合作体（份额/贡献/确认/风险揭示）、开发者（API Key 一次性明文与吊销、Webhook 与签名说明）一起补上，挂在「我的」下而不是再加第八个 Tab；按钮可用性一律读服务端的 `can_decide` / `invoice_block`，客户端不重写判断（**第二份实现必然抄漏**）。最后把规则变成闸门：`NOTICE_ACTIONS` 表——(类别,标题) → 动作的 SDK 方法 → 必须做得到的端 → **这条通知在叫他做什么**，V91 手写的那条单独断言并入表中。红验时还抓到自己的一处虚假绿：「发起人不收『等你审批』」那条测试拿 member 当发起人，而 member 根本不在 owner/admin 名单里，**压根没碰到那行排除逻辑**——改成 admin 超额申请才真的钉住 |
| V91 PAY/APP/CLI | 钱能进不能出。本来是去给 App 补三个页面的，补之前先量了一下 App 到底能用到多少能力：共享 SDK **245 个方法，Web 用到 135，App 只用到 33**。Web 独有名单里第一个刺眼的词是 `withdraw`——App 的钱包页有充值、**没有提现**。那 Web 呢？Web 有提现按钮，按下去 `400 {"code":"no_payout_account"}`「请先绑定收款账户」；而 `grep -rn "bindPayoutAccount" web/src app/` **没有任何输出**。合起来就是：**钱能进，不能出**——Web 的提现按钮每一次点击都返回 400，且全仓没有任何界面能解决这个 400；App 连按钮都没有。这不是某个页面缺失，是资金闭环缺了返程，对应用商店还是另一层风险（一个能收钱、不能退钱的 App 会被直接打回）。这是 **V88 的孪生**：V88 的结论是「服务端的必填如果没变成类型上的必填，就只是一句口头约定」，这一条是**服务端的「请先 X」，如果 X 在客户端没有入口，那这句话不是提示，是死路**；CLI-064 立过半条规矩（把拦截理由原样显示），**第二半是那个理由得有地方去解决**。所以补两端的收款账户绑定（回显服务端给的脱敏卡号，并把「收款人须与实名一致」提前说出来——`Me` 上没有 `real_name`，填不了默认值只能提示）、App 的提现与账单流水（科目中文名走共享 SDK，不在端里另写一份）。顺带掉出两条：SDK 的 `withdraw` 返回类型里**没有 `message` 字段**，而大额进人审时服务端给的中性话术就在那儿——于是 AML-030/031 要求原样显示的那句话，**没有任何界面显示得了**；以及 App 此前只能「看」协议状态不能同意，一次协议更新就把 App 用户卡成只读（发布/接单/资金全被 409 挡住）。还清了上一批自己挖的坑：V90 的必达通知写着「可在任务详情页申请人工核验」，而 `requestVerification` 当时只在 `web/src/AgentPanel.tsx` 出现过一次——**通知里指的路，必须在收到这条通知的端上走得通**。最后照 V90 的办法把规则变成闸门：`REMEDY_UI` 声明表（错误码 → 补救的 SDK 方法 → 必须有入口的端 → **理由**），扫两端源码逐条验；表自身也被验（码服务端还在抛、方法 SDK 上还有），扫描器先自检（扫得到已知成员、扫不到编造的名字）。闸门第一版把注释也扫了，于是**解释「不许说风控」的那句注释自己先红了**——改成只扫用户看得见的文案，这正是 V89 那条「假报警多的闸门会被人关掉」 |
