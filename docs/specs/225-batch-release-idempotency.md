# 225 批量放款接入通用幂等键

> 状态：本批实现（V252）。编号 SC-016。
> 来源：146 号 spec「没做的」——「批量放款的幂等键：现在靠『只放已交付的』与『合计核对』防重复；接入通用幂等键（104 号 spec 那一套）排进待办」；BACKLOG V252。
> 只增不减：不带 `Idempotency-Key` 的请求行为不变（已经装在手机上的旧版 App 不带）；`releaseDelivered` 的前三个参数不变，第四个可选。
> 写明的行为变化：带键时，同一个键的重试回放第一次的结果；同一个键换了内容（期号集合或合计不同）回 `idempotency_key_conflict`。

## 0. 要解决的问题

发布方点「放款已交付的 N 期」，请求到了服务端、钱放了，但手机信号断了、响应没回来。他再点一次：服务端说「第 1 期不是待验收」——钱其实放出去了，可这句话让人以为失败了，于是去找客服。钱没有放两次（放过的期状态已变），但用户看到的结果是错的。充值、提现早在 104 号就解决了这件事，批量放款没接。

## 1. 业界怎么做

Stripe 的幂等键：同一个键的重试返回第一次的结果，键对应的参数变了就拒绝。104 号 spec 已经照此实现（先占键再动钱、失败不缓存、24 小时过期），本批直接复用。（本批没有另找外部来源。）

## 2. 数据

不加表：复用 `idempotency_records`，作用域 `contract.release_delivered`，指纹是合约号、排序后的期号与合计——期号顺序不同也是同一次操作。

## 3. 接口

| 接口 | 变化 |
|---|---|
| `POST /contracts/{id}/milestones/release-delivered` | 可选请求头 `Idempotency-Key`：命中且指纹一致回放第一次的结果；指纹不同 `idempotency_key_conflict`；第一次失败（如合计对不上）不缓存，同一个键改对了会真的再试一次 |

为什么不强制：资金类在 104 号是强制带键，但这个接口已经有旧版 App 在用。不带键时「放过的期第二次会被拒」本来就挡住了重复放款，强制只会让旧版直接 400。两端新版都带键。

SDK：`releaseDelivered(contractId, idxs, expectedTotalCents, idempotencyKey?)`；`OperationKey.run(intent, fn)`（取键 → 执行 → 成功或明确被拒换新键，网络断了或 5xx 保留键）。

## 4. 两端

- **Web** 任务详情「放款已交付的 N 期」与 **App** 分期块「确认放款」：都用 `OperationKey.run`，意图是「合约号 + 期号 + 合计」。服务端出错或断网后再点一次是重试（同一个键）；放成功或被明确拒绝后，下一次是新操作。

## 5. 隐私、授权与边界

键按用户隔离（104 号）；授权与「只放已交付、合计核对、冻结不放」等规则都在 `run()` 里照旧执行，回放只发生在第一次已经成功之后。
