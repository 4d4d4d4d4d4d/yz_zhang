# 176 一单多次上门的逐次回报

> 状态：本批实现（V203）。编号 SCN-120。
> 来源：173 号 spec 第 7 节「没做的」——「一单多次上门的逐次回报：喂猫一单 7 天、每天两次，每次的打卡与照片清单（喂食、换水、铲屎、门窗）现在只能靠留言」；BACKLOG V203；宠物上门照看包的方法「每次上门按这个顺序」。
> 只增不减：进展记录、到场打卡、交付验收都不变；上门回报是进展记录里新的一种（`kind=visit`），证据包与纠纷照常能看到。
> 写明的行为变化：发布时多两项可选（上门几次、每次要做的事），不填与原来完全一样。

## 0. 要解决的问题

- 宠物包（173 号）的教练方法写着「喂食、换水、铲屎各拍一张照片并在平台回报」，平台上却没有「回报」这个东西：接单人只能写自由文字留言，发单人要自己对着清单数，14 次上门里漏了哪次没人知道。
- 出了事（猫生病、主人说没来）时，纠纷里缺的正是「每次做了什么」的结构化记录。

## 1. 业界怎么做

| 做法 | 说明 |
|---|---|
| 宠物照看平台的「每次上门报告」 | 照看人每次上门后提交一份报告：喂食、换水、清理、照片、备注，主人实时收到（173 号引用的行业报道与法大大的建议：服务内容写清、留存记录以便厘清责任 <https://www.fadada.com/article/Basics-020870>） |
| 家政按次打卡 | 到岗、离开在平台打卡，有分歧以平台记录为准（家庭事务包，153 号） |

本批取：发单人写清单，接单人每次勾清单 + 备注 + 照片，平台按清单顺序算出「做了 / 没做」，每次通知发单人。

## 2. 数据

- `tasks.visits_planned`（0~60，0 表示不按次）、`tasks.visit_checklist`（最多 8 项，每项最多 20 字，去空白去重）。
- `progress_logs.checked`：这次勾了清单里的哪几项（`kind=visit`）。
- 迁移 `c1d220260041`（SQLite 与 Postgres 都 `upgrade head && check` 过）。

## 3. 接口

| 接口 | 说明 |
|---|---|
| `POST /tasks` | 多 `visits_planned`、`visit_checklist`；清单项超过 20 字拒（`visit_item_too_long`） |
| `POST /tasks/{id}/visits` `{done, note, images}` | 只有接单的人、只在执行中；`done` 只能是清单里的项（`visit_item_unknown`）；什么都没有拒（`visit_empty`）；图片只认本平台上传地址。返回第几次、做了的、没做的（按清单顺序）；通知发单人「第 n/计划 次上门回报：已做…；没做…」 |
| `GET /tasks/{id}/visits` | 成交双方与管理员：计划几次、回报几次、一共漏几项、每次的做了 / 没做 / 备注 / 照片 |
| 名额与周期单 | 带着同样的次数与清单 |

SDK：`reportVisit`、`taskVisits`、`TaskVisits`、`TaskVisit`；`Task` 与 `TaskCreateInput` 多两个字段；3 个错误码进 i18n。

## 4. 两端

- **Web 发布页**：「要上门几次」「每次要做的事（用顿号分开）」，不填不带。
- **Web 详情页**：成交双方看到「上门回报 · 3/14 次」、一共漏了几项、每次一行；接单人在执行中多一组清单勾选、备注、拍照（沿用 `PhotoPicker`）和「交这次的上门回报」。
- **App 发布页**：同样两项。
- **App 详情页**：`VisitsBlock`（`app/visits.tsx`）同一块；拍照沿用资质页的取图方式（压缩、超过 2MB 不传）。

## 5. 隐私、授权与边界

- 回报（含照片）只给成交双方与管理员（对象级授权表登记）；照片只认本平台上传地址。
- 平台只把回报**记下来并告诉发单人**，不替发单人验收、不按回报次数自动扣钱或放款——钱的事仍是发单人确认。
