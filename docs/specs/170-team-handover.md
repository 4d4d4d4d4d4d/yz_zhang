# 170 团队成员离开时的交接

> 状态：本批实现（V197）。编号 TEAM-054（53 号 spec「成员离职后其发起的在途任务如何转交」）。
> 注：62 号 spec 第 5 节也用了 TEAM-054 这个号（「月份按 UTC 切」），那条已经做完并有测试；本 spec 指 53 号里的那一条。
> 来源：53 号 spec 第 7 节「没做的」；BACKLOG V197；企业客户上线必问。
> 只增不减：移出成员的权限（只有 owner）、不能移出 owner 都不变；`DELETE /teams/{id}/members/{uid}` 的响应在 `removed` 之外多交接字段，多一个可选的 `handover_to`。

## 0. 要解决的问题

- 以前移出成员只是把他标成不在职：他发起的、还在审批里的支出申请照样挂着——批下来他还能执行，钱就进了一个已经离开的人的钱包。
- 他用团队的钱发的任务还在跑，团队里没人知道还有哪些没收尾，他自己也没收到任何说明。

## 1. 业界怎么做

| 做法 | 说明 |
|---|---|
| 离职时的权限回收与工作交接 | 企业 SaaS（如飞书、钉钉的离职交接）在移出成员时把他名下的待办、文档、审批交给指定接手人 |
| 合同主体不随人走 | 签了约的事，签约方是谁就是谁；换主体要另签（转让 / 变更协议），不能由一方单方面改 |

## 2. 数据

不新增表：关闭的申请写进已有的 `team_spend_requests`（状态 `expired`，理由追加「发起人已移出团队，申请自动关闭」）。

## 3. 接口

| 接口 | 说明 |
|---|---|
| `DELETE /teams/{id}/members/{uid}?handover_to=` | 只有 owner；接手人默认是操作的 owner，指定时必须是团队在职成员（`handover_not_member`），不能是被移出的人（`handover_to_self`）。返回 `removed`、`closed_requests`（被关掉的申请编号）、`in_flight_tasks`（用团队的钱发的、还没做完的任务：编号、标题、状态、金额）、`handover_to`；通知接手人在途任务清单，通知离开的人哪些仍要他收尾 |

SDK：`removeTeamMember(teamId, uid, handoverTo?)` 返回 `TeamMemberRemoved`；`teamHandoverDetail()` 给两端同一句交接说明（老服务端没有这些字段时返回空串）。

## 4. 两端

- **Web 团队页、App 团队成员**：移出后照旧显示「已移出」，下面单独一行交接说明（关掉几个申请、哪些在途任务要跟进、合约仍由原成员履行）。

## 5. 隐私、授权与边界

- 合约不转：签约的是原成员本人。交接给的是「知道还有这些事、去跟进」，不是把别人的合约换到自己名下。
- 已执行的支出不追回：钱已经划给他用于发任务（审计有记录）；未用完的怎么退回团队属于报销与结算口径（TEAM-070）。

## 6. 闸门与红验

| 闸门 | 测试（`server/tests/test_team_handover.py`） | 红验 |
|---|---|---|
| 关掉他没执行的申请（待批与已批未执行）、不动别人的；列出在途任务（做完的不列）；合约主体不变；通知接手人与离开的人；关掉的申请不能再执行 | `test_removal_closes_open_requests_lists_in_flight_tasks_and_tells_both_sides` | 只关待批 → 红；做完的也列 → 红；不通知接手人 → 红；不通知离开的人 → 红；关掉所有人的申请 → 红 |
| 接手人默认 owner；指定的必须是在职成员、不能是他自己 | `test_default_taker_is_the_owner_and_handover_must_be_an_active_member` | 不查接手人 → 红；不拦自己 → 红 |
| 两端 | `web/src/TeamMembers.test.tsx`、`app/appGaps.test.tsx`（原有「已移出」断言不变） | — |

## 7. 没做的

- **TEAM-069 在途任务换签约主体**：要做成「三方确认的变更」（原成员、接手人、执行方都确认），不能单方面换（欠）。
- **TEAM-070 已划给成员但没用完的钱退回团队**：要先定团队支出的报销与结算口径（欠）。
