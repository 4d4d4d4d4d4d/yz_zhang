# 40 那些从来没验证过的东西（DRILL）

> 我在上一次状态汇报里把这一类单列出来，说它是我最没底的部分：
> 压测、告警、备份恢复演练、依赖扫描——**一次都没做过**。这一批把它们做掉。

## 0. 这一批修的是什么

前面几十批修的都是「代码里有个洞」。这一批不一样：代码可能是对的，
但**没有任何证据**。四件事各自的形态：

| 项 | 改造前的状态 |
|---|---|
| 备份恢复 | `backup.sh` / `restore.sh` 写得很仔细，但需要完整 Postgres + docker compose 生产栈，且 `restore.sh` 会停下来等人敲 `yes`。**从来没有被恢复过一次。** |
| 告警 | `/metrics` 暴露了指标，**没有任何东西在消费它**。没有规则文件，没有值班通道。 |
| 压测 | 并发**正确性**有测试钉着，**容量一无所知**：不知道能扛多少 QPS、不知道 p95 是 20ms 还是 2s。 |
| 依赖扫描 | 无。 |

### DRILL-001 一份没有恢复过的备份，不是备份，是一个关于备份的假设

`restore.sh` 里那段恢复后一致性校验写得很对——导入完必须跑资金五不变量
与存证链校验，不过就明确报失败，「不给人『大概好了』的错觉」。

但它是一个 heredoc，嵌在一个需要完整生产栈 + 人工确认才跑得到的脚本里。
**一段从没跑过的校验代码，和没有校验没有区别。**

### DRILL-002 写告警规则的过程本身就抓到一个洞

我写完 `deploy/alerts.prom.yml` 去核对指标名，发现最重要的三条——
资金对账不平、定时任务静默、上传审核积压——引用的
`platform_reconcile_ok` / `platform_jobs_unhealthy` /
`platform_uploads_pending_review` **`/metrics` 根本不暴露**。

告警规则不会因为指标名写错而报错。**它只是永远沉默。**
一个「配了却从不告警」的监控比没有监控更危险：没有监控时你知道自己是瞎的，
配错了的监控让你以为自己被盖住了。

这和这一路修下来的那类缺陷是同一个形状——**写错了不会报错的声明**。

### DRILL-003 依赖扫描第一次跑就有真东西

```
11 vulnerabilities (6 moderate, 4 high, 1 critical)
```

但数字本身会误导，必须分清**哪些真的发给用户**：

- `npm audit --omit=dev` → **2 moderate，全部是 react-router**。这是唯一进
  浏览器的那部分。
- 其余 9 条（vitest / vite / esbuild / postcss / nanoid / browserslist）都是
  构建工具链，影响的是开发机与 CI，不是用户。

其中 react-router 的两条：一条是 SSR hydration 的构造器注入——我们是纯客户端
SPA，不适用；另一条是 `<Link>` / `useNavigate` 的反斜杠开放重定向，
要求把用户可控字符串当作跳转目标。我核对了全部调用点，全是字面量或
`/tasks/${来自自家 API 的数字 id}`，**当前没有暴露面**。

但「当前没有」不是一个可以维护的状态——下一个写 `nav(returnUrl)` 的人
就把它带回来了。所以直接升到 react-router 7 把问题消掉，
而不是写一份「暂不受影响」的说明。

## 1. 设计判断

**判断一：恢复后的校验提成一个模块，演练与生产跑同一段代码。**
不是为了「整理代码」，是为了让 CI 里跑的那段校验**就是**半夜恢复生产库时
跑的那段。两份实现迟早会漂移，而漂移的那一天你正在恢复生产库。

**判断二：压测脚本不设阈值断言。**
容量取决于机器。在 CI 的共享 runner 上写死一个 p95 阈值，只会变成一条
时不时误报、然后被人注释掉的断言。脚本的职责是**给出数字**，判断由人来做。

**判断三：依赖扫描分两档。**
发给用户的依赖（`--omit=dev`）是硬闸门——这些代码会进浏览器。
构建工具链只报告不阻断——否则一条「Vitest UI 服务监听时可被读文件」
（一个我们从不启用的功能）会把整条流水线卡死，然后被人加 `|| true` 绕过，
最后连该拦的也不拦了。

**判断四：告警指标名必须被机器核对。**
这是本批唯一一条真正的新闸门，也是这批里唯一一个「写错了不会报错」的地方。

## 2. 条目

### 备份恢复

- **DRILL-010** `server/scripts/consistency_check.py`：恢复后一致性校验的
  唯一实现（资金五不变量 + 存证链）。`deploy/restore.sh` 改为调用它。
- **DRILL-020** `server/scripts/restore_drill.py`：造一笔真实闭环交易 → 备份
  → **删库（删文件，不是清表）** → 恢复 → 跑同一段校验 → 核对余额原样回来。
  进 CI，每次 push 都跑。
- **DRILL-021** 演练造数据必须走真实 HTTP 管线，不直接塞库——
  直接塞出来的数据可能本来就不满足不变量，那样演练是在校验一个假数据。

### 告警

- **DRILL-040** `deploy/alerts.prom.yml`：4 组 8 条规则，覆盖资金不平、
  托管只增不减、实例不可达、5xx 占比、p95 劣化、job 静默、事件死信、
  审核积压。每条都必须有 `severity` 与 `summary`——没有 severity 值班的人
  无法分流，没有 summary 半夜被叫醒的人看不懂。
- **DRILL-041** `/metrics` 补出 `platform_reconcile_ok`、
  `platform_jobs_unhealthy`、`platform_uploads_pending_review` 三个指标，
  并加测试断言：**告警规则里出现的每一个指标名都必须真的被暴露**。
- **DRILL-042** 指标端点对单个聚合出错必须容错——一个聚合炸了就整体 500，
  会让**所有**告警一起瞎掉。算不出来的按最坏情况（`reconcile_ok 0`）上报。

### 压测

- **DRILL-030** `server/scripts/loadtest.py`：纯标准库（不引入 locust/k6——
  CI 里多一个依赖就多一个不跑的理由），输出吞吐、错误率与 p50/p95/p99。
  读写两个场景。

### 依赖扫描

- **DRILL-050** CI 新增 `dependency-audit`：`pip-audit` +
  `npm audit --omit=dev --audit-level=moderate`（阻断）+ 全树 `npm audit`（仅报告）。
- **DRILL-051** 升级到 react-router 7 / vite 7 / vitest 5，
  全树 `npm audit` 归零。

## 3. 实测结果（写下来，以后好比）

本机（容器，SQLite 单文件，uvicorn 单 worker）：

| 场景 | 并发 | 吞吐 | p50 | p95 | p99 | 错误率 |
|---|---|---|---|---|---|---|
| read（任务详情） | 16 | 129 rps | 121ms | 175ms | 199ms | 0 |
| write（发布任务） | 16 | 87 rps | 60ms | **769ms** | **1872ms** | 0 |

两点解读：

1. **写路径的长尾是 SQLite 单写锁的签名**（p50 60ms → p99 1872ms，30 倍）。
   生产是 Postgres + 行锁，这个数字不能外推——但它说明「写会排队」这件事
   在当前配置下是真的。
2. **读的 p50 121ms 偏高**，单条 GET 不该这么久。可能是中间件链
   （限流/封禁查库）或详情接口的多次查询。本批不追，记为 DRILL-060。

**这些数字是地板，不是容量规划。** 换机器、换 Postgres、加副本之后必须重测。

## 4. 已知缺口

- **DRILL-060 读路径 p50 偏高未定位。** 需要 profiling，不在本批。
- **DRILL-061 演练只覆盖 SQLite 路径。** `pg_dump` / `psql` 那条真实生产路径
  仍未被自动验证——它需要 docker compose 起 Postgres，CI 可以做但会显著
  拉长流水线。演练证明的是「恢复完要校验」这个判断是活的，
  不是「pg_dump 一定能用」。
- **DRILL-062 告警规则未经 promtool 校验。** 本环境没有 Prometheus。
  结构与指标名有测试钉住，但 PromQL 表达式的语义正确性没有。
  落地前必须跑 `promtool check rules deploy/alerts.prom.yml`——
  规则文件头部写了这句。
- **DRILL-063 没有值班通道。** 规则写了，但 Alertmanager 的接收端
  （电话/短信/IM）需要你配。规则不响到人身上等于不存在。
- **DRILL-064 没有渗透测试。** 边界防护是我自己写自己测的，
  这种自查有系统性盲区。这一条代码解决不了，需要外部审计。
