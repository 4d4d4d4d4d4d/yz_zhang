# 190 对象响应完整运行时校验：复核后不做

> 状态：本批复核（V218）。编号 APP-098。

还要不要再加一层：按 `types.ts` 为每个对象响应生成运行时校验器，所有字段都看？

## 1. 业界怎么做

- 用 zod / io-ts 一类库在边界上做运行时校验，类型从 schema 推出来（<https://zod.dev/>）。前提是 **schema 是唯一的类型源**；在已有 3000 多行手写 `types.ts` 的项目里补，等于维护两份类型，或者重写类型层。
- 另一种做法是从 OpenAPI 生成客户端与校验器。本项目服务端已有 OpenAPI，但 SDK 是手写的，而且有大量面向界面的派生类型（如 `TaskTreeChild`、`TaskDaySummary`），生成的类型替代不了。

## 2. 结论：不做

1. **能拦住的问题，测试期已经拦住了。** 字段名错、少字段、多字段，响应形状闸门在合并前就会红；运行时校验只能在用户手机上发现同样的问题，而且发现得更晚。
2. **剩下的畸形来自版本错配或中间层**（代理返回的错误页对象、老服务端少新字段）。这类响应要么整个不像样（`hasLists` 已经接住），要么只少一个新字段，按「字段可能没有」写的页面照常显示。全字段校验会把后一种也判成「不像样」，**反而让本来能显示的块消失**。
3. **成本不对称**：引入校验库要给两端各加一份依赖和包体积（App 冷启动敏感），并维护第二份类型源；自写生成器要解析 TypeScript 类型（联合类型、交叉类型、可选字段），这是一个独立的小项目，收益只是把「这一块崩了换成兜底」变成「这一块显示说明」——185 号已经对风险最高的块做了后者。

## 3. 重开条件

出现以下任一情况就重开（新编号，不复用 APP-098）：

- 渲染出错上报（184 号）里同一类错误连续两周出现在不同页面，且原因都是对象响应少字段；
- SDK 改成从 schema 生成（那时校验器是顺带的）；
- 开放给第三方的客户端（开放 API）需要在客户端侧校验。
