
# 113 调外部服务时不挂着数据库事务（CONC-067）

> 状态：本批实现（V138）。设计见 [111 号](111-audit-industry-and-remaining-design.md) 第 4.1 节。
> 承接用户的商业化要求：「实际商业化的一些问题，例如部署的并发……也考虑解决一下」。

## 0. 量过之后

台账 CONC-067 一直写着「长事务没查：调供应商时有没有把事务一起挂住」。这次量了：
引擎事件记录每个线程有没有打开着的事务，包住全部供应商实现，跑全量测试——

> **2956 次供应商调用里，2917 次（98.7%）发生在一个打开着的事务里。**

| 调用 | 次数（在事务里 / 全部） | 在哪 |
|---|---|---|
| 实名核验 `kyc.verify` | 1245 / 1245 | 实名接口（先写了单独同意） |
| 内容审核 `moderation.check` | 858 / 859 + 58 + 58 | 发任务、发内容、改空间（拿着行锁）、图片、AI 产出 |
| 充值下单 `payment.create_charge` | 513 / 513 | 充值（与幂等占键、订单同一个事务） |
| 存储读写删 | 92 / 92 | 上传、读取、处置删除、注销删证件影像 |
| 提现出款 `payment.create_payout` | 36 / 37 | **在钱包行锁里调银行** |
| 短信 `sms.send_code` | 30 / 30 | 发验证码 |
| 向量化、税额、存管分账、推送 | 12 + 8 + 3 + 2 | 检索、放款事务里、放款事务里、事件 handler 里 |

在 Postgres 上，每一次等供应商的时间里，这个请求都占着一条池连接（`idle in transaction`）与它拿过的行锁。
供应商一慢，连接池先耗尽——**与这个供应商毫无关系的接口一起挂**；提现那一处还更糟：
银行慢的那几秒，这个人的钱包锁一直陪着银行等。业界的说法很直接：*never call APIs inside database transactions*
（transactional outbox：意图与业务一起落库并提交，事务外调用，回来回写；重试靠幂等键）。

## 1. 守卫（每一次都查，不靠人记得）

- `core/txguard.py`：引擎的 begin / commit / rollback 事件按线程记「打开着的事务」与「这个事务写没写过」
  （`SELECT … FOR UPDATE` 也算写——行锁被提前提交放掉是另一种静默错误）。
- 注册表发出去的每个供应商实现都包一层 `Guarded`：方法被调用时若线程挂着事务——
  **开发 / 测试直接抛错**（整套后端测试因此就是这条闸门），**生产只记日志与指标**
  `vendor_call_in_transaction_total{call}`，照常执行：防御性检查不能把用户的请求打挂。
- 模型客户端不经注册表，在分解网关里显式过守卫。
- 进程内的规则计算（税额规则）标 `in_process`，守卫放行；闸门核对这些模块不引任何网络库。

## 2. 三种改法（按调用点的性质，不是一刀切）

| 性质 | 改法 | 调用点 |
|---|---|---|
| **只读过、再调用** | `vendor_base.release(db)`：只读事务直接提交、连接还回池里（写过的一律不替调用方提交） | 内容审核（发任务 / 发内容 / 评论 / 空间——空间改成**拿锁之前**审）、图片审核、存储读、签发直传、向量化、模型调用 |
| **意图必须先落库** | 显式提交点 `vendor_base.checkpoint(db, 理由)`，**每一处都登记理由**（闸门） | 实名（单独同意先于处理且独立成立）、短信（码先落库再发）、充值下单、出款两阶段、编排逐步分发、事件补做 |
| **事后的副作用** | 业务**提交之后**再做；业务回滚了就不做 | 推送（事件 `after_commit` 订阅者）、存管分账指令（同）、删存储文件（`on_commit`） |

## 3. 原来靠「失败就整笔回滚」得到的保证，现在逐条显式给出

挪出事务不是换个位置。每一处原来的隐含保证都要重新写出来，否则是用一种静默错误换另一种。

### 3.1 出款两阶段（最重要的一处）

改造前的注释写着「宁可提现失败重来，也不能账扣了钱没打出去」——它只护住了一个方向：
银行打出去了、而我们的提交失败（或超时、根本不知道打没打），就是**钱出去了账没扣**。

现在：

1. 锁内：可用 → 冻结，记下出款单 `sending`，**提交**；
2. 事务外调银行，按出款单号幂等（银行侧与 VendorCall 都按单号去重）；
3. 成功：另开事务划出冻结、记一条 `withdraw` 流水（与改造前完全相同，AML 的计数不受影响）；
4. **明确失败**：即时提现解冻退回、出款单 `failed`；人审提现回到待审、钱留在冻结，管理员可以再批——
   **都先落库再报错**；
5. **结果不明**（超时 / 网络）：钱留在冻结、出款单留在 `sending`、接口返回 `processing`；
   **不能当失败退回**——银行那边可能已经打出去了，退回等于让他能再提一次。
   `/wallet/jobs/resolve-payouts`（十分钟一次）按同一个单号重试，不会打两次。

日终对账的第三条不变量（冻结有据）随之数 `pending / awaiting_second / sending` 三种状态。
**顺带修掉一个既有的误报**：大额提现一审通过、等第二位管理员确认的那段时间（`awaiting_second`），
钱一直在冻结里，而对账只数 `pending`——会报「冻结不符」。日限额也同样漏数了这两种状态。

### 3.2 充值

订单与幂等占键先落库再调渠道。渠道**明确拒绝**：订单置 `failed`（此前要么回滚掉、要么永远 `pending`）。
无论哪种失败，`replay_or_run` 都把还没有结果的占键删掉——**失败不缓存**的语义不变：
同一个键重试会真的再试一次，而不是被 `idempotency_in_progress` 卡 24 小时。

### 3.3 推送与存管指令：业务回滚了就不发

此前推送 handler 在业务事务的保存点里同步跑：**放款最后回滚了，「已到账」的推送照样发出去了**。
现在 `subscribe(..., after_commit=True)` 的 handler 不在业务事务里跑：投递记录先写成 `deferred`，
业务提交之后另开会话投递；业务回滚则作废；提交之后、投递之前进程挂了，drain 过一阵子（60 秒）补做。
存管分账指令同理：指令本身（结算单）与内部账本变动同生共死地落库，提交后下达；
超过 30 分钟没下达的进日终对账（`custody_instruction_overdue`）。

**过程里踩到的一个坑**：SQLAlchemy 的会话 `after_commit` 事件在**保存点释放时也会触发**——
实测 handler 的 SAVEPOINT 一提交就到了投递函数里，外层事务还开着，新会话看不见刚写的投递记录，
推送就悄悄没发（只在「事件 handler 里又发通知」这条路径上出现；直接发通知的测试是绿的）。
改成只在没有嵌套事务时才投递；作废也只在**最外层**回滚时作废——某个 handler 的保存点回滚，
不能把别的 handler 排好的推送一起丢掉。

### 3.4 删文件

人工处置删除违规图片、注销删除证件影像：改成业务提交之后删（处置或注销回滚了，文件不该已经没了）。
处置接口返回的 `file_removed` 因此表示「已安排在提交后删除」。

## 3.5 全量跑一遍才看见的（守卫在测试里抛错，整套测试替我找）

- **每个 job 从头到尾跑在同一个打开着的事务里**：`job_slot` 抢锁那条写没提交，一直挂到 job 结束——
  job 里调的任何供应商（向量化、出款补偿……）都在事务里。改成抢到锁立刻提交：别的副本马上看得见
  「有人在跑」，job 从干净的会话开始；失败时显式放锁（锁已提交，回滚不会再顺带放掉它）。
- **每个 API Key 请求从鉴权开始就是一个「写过的」事务**：鉴权时写 `last_used_at`。改成当场提交。
- **调用留痕本身也是一条写**：一个请求里先后调两个供应商（上传 → 图片审核 → 拒绝时删文件），
  第一次调用的留痕会让第二次放不掉连接。调用前事务是干净的，留痕就单独提交——
  顺带让**失败的调用留痕不再随请求回滚一起消失**。
- **机器发布拿着额度锁调内容审核**：改成拿锁之前审；同一个会话里审过的同一段文字不再审第二次。
- **AI 助理运行**：running 记录先落库（它本身就是防重复触发的并发闸，提交之后别的连接才看得见），
  再等模型；内容审核挪到改运行记录的任何字段之前。

## 3.6 我自己第一版里的一个「一次意图、两次打款」

并发提现测试偶发失败：余额少了两笔，成功的响应只有一个。追下去：
一笔提现过了提交点（钱已冻结、出款单已落库），结账时撞上并发修改（SQLite 没有行锁，靠版本号），
于是**报了一个错**。报错的后果是：

1. 客户端用同一个幂等键重试；
2. 幂等占键在失败时会被放掉（失败不缓存）——重试变成**第二笔**提现；
3. 而第一笔的出款单还停在 `sending`，补偿 job 会把它打出去。

一次提现意图，打了两次款。改法是把语义说清楚：**过了提交点之后，除了银行明确拒绝，任何意外都只能是
「处理中」，不能是一个报错**；结账也在受保护的这一段里当场提交（留到请求结束再提交，那一刻撞上并发修改
时银行那边钱已经打出去了）；失败分支里先回滚再碰任何 ORM 属性（会话可能处于「待回滚」，读属性会再抛一次——
第一版的兜底分支就是这样把自己也弄崩的）。修完连跑十次全过。

同一类问题在幂等上也有一处：占键现在先于结果提交，所以「有占键、还没结果」是常态——
并发同键的后到者**等它一会儿**（上限 `PLATFORM_IDEMPOTENCY_WAIT_SECONDS`，默认 15 秒）再回放同一个结果，
FIN-072「并发同键都拿到同一个 200」保持成立；先到者失败放了键，后到者接着做；等不到才 409。

## 5. 这一批没做的

- **热词读取时的逐词审核**（`CONC-067b`）：`_public_terms` 每次最多 30 次内容安全调用；现在不挂事务了，
  但调用次数本身没减。应当按词缓存审核结论（词表变化很慢）。
- **出款单的银行侧查询**：补偿 job 用「同单号重试」得到结果，依赖银行接口按单号幂等；
  接真实银行时要换成「按单号查询」——那是供应商接入时的事（GO-LIVE 红线 6）。
