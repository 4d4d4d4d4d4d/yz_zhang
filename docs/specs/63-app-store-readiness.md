# 63 App 上：一个发不出任务的按钮，和四条会被直接打回的必查项（APP-060~066）

> 探针复刻了 App `PublishScreen` 发出的那个请求体：
>
> ```
> APP PUBLISH: 400 {"code":"ip_assignment_required",
>                   "message":"请选择交付成果的知识产权归属…"}
> ```
>
> **App 上的「发布」按钮，每一次点击都返回 400。**

## 0. 为什么它能坏这么久

V77 把 `ip_assignment` 改成必填时，做得很仔细：改了 Web 的发布页、改了
314 个测试、改了四个闭环脚本，还加了一条闸门测「客户端确实发了这个字段」。

**那条闸门只看 Web。** App 不在它的视野里，而 App 也没有任何测试——
CI 对 App 只做 `tsc --noEmit`，而漏一个字段**不是类型错误**：

```ts
createTask(input: Partial<Task> & { title: string; category: string; … })
```

`Partial<Task>` 让每个业务字段都可选。类型系统看着这段代码，
认为它完全正确。

> **服务端的「必填」如果没有变成类型上的「必填」，那它只是一句口头约定。**

## 1. APP-060 把必填变成类型必填

改 SDK 的签名，让 `ip_assignment` 成为**必需参数**：

```ts
createTask(input: Partial<Task> & {
  title: string;
  category: string;
  ip_assignment: IpAssignment;   // ← 漏了就编译不过
  …
})
```

这比再加一条「检查客户端有没有发」的测试好，理由有三条：

1. **它覆盖所有客户端**，包括以后写的那个。测试只覆盖被想到的那些。
2. 它在**写代码的时候**就红，不是在 CI 里红。
3. 它**不需要有人记得**去写那条测试——而 V77 就是记得写了，只是只写了一半。

同时在 core 的测试里留一条**类型层面的钉子**：

```ts
// @ts-expect-error ip_assignment 必填：漏了就编译不过（App 曾经就漏了）
client.createTask({ title: 'x', category: '跑腿' });
```

`@ts-expect-error` 是双向的：要是哪天字段又变回可选，这一行**自己**会变成
一个「未使用的 ts-expect-error」错误。**它不只钉住现在，也钉住以后。**

## 2. APP-061~064 四条审核必查项

`app/STORE_CHECKLIST.md` 里四行全是 `⚠️ 待接入`：

| 项 | 服务端 | App |
|---|---|---|
| 账号注销 | `POST /users/me/deactivate` | ⚠️ 没有入口 |
| 内容举报 | `POST /reports` | ⚠️ 没有入口 |
| 拉黑用户 | `POST /users/{id}/block` | ⚠️ 没有入口 |
| 协议与隐私政策 | `legal` 模块 | ⚠️ 没有入口 |

这四条不是「最好有」：**缺任何一条，应用商店会直接打回**，
而前三条在 Web 上早就有了——差的只是 App 上那几个按钮。

做的时候有两个地方不能省：

### APP-061 注销要先说清楚后果

Web 上注销是一段带确认的流程（ACC-006：脱敏保留而不是删库，
有钱/有在途合约时拦住）。App 上不能做成一个「注销」按钮直接调接口——
服务端会拦，但**用户看到的是一个莫名其妙的报错**，而不是「你还有
一笔托管中的资金」。所以 App 上同样要把服务端给的拦截理由原样显示出来
（与 CLI-064 同一条）。

### APP-062 举报要能选类型

`POST /reports` 收 `target_type` + `target_id` + `reason`。
做成一个只发 reason 的「举报」按钮，运营侧收到的是一堆不知道在说什么的工单。

## 3. APP-065 这一批**没有**做 App 的三条线页面

原计划（UI-078）是把合作体、团队、开发者三页搬到 App。这一批没做，
因为探针把优先级改了：**一个发不出任务的按钮和四条会被打回的必查项，
比三个新页面重要得多**。三条线的 App 页面继续挂着。

## 4. 验收点

| 编号 | 验收点 |
|---|---|
| APP-060 | `createTask` 漏 `ip_assignment` **编译不过**（类型层面的钉子，双向） |
| APP-060 | App 的发布页能选归属，发出的请求服务端接受 |
| APP-061 | App 上能注销，且拦截理由原样显示 |
| APP-062 | App 上能举报（带类型），能拉黑 |
| APP-064 | App 上能读到用户协议与隐私政策 |
| — | `STORE_CHECKLIST.md` 里的状态跟着改，不留假的「待接入」 |

## 5. 这一批没做的

- **APP-065**：合作体 / 团队 / 开发者三页仍未搬到 App。
- **APP-066**：App 仍然没有单元测试，只有 `tsc`。这一批把最关键的一条
  （必填字段）提升成了类型约束，但**「点了按钮会不会 400」这类问题，
  类型系统答不了**。真要答，需要在 App 侧跑一个打真实后端的冒烟，
  而这需要真机/模拟器环境，本容器里做不到——如实记着。
