# 54 开放 API 与 Webhook（API / HOOK）

> 来自需求回顾的 P2 缺口：「开放 API / Webhook（做 agent 生态的前提，
> 现在一个 api_key 机制都没有）」。
>
> 现状实测：全站唯一的身份是**用户会话 token**（`Bearer <自签 token>`，
> 绑 `sid`，改密即全端下线）。那是给**人**用的：会过期、会被吊销、
> 绑定登录设备。**机器拿不到也不该拿这种凭证。**

## 0. 为什么会话 token 不能当 API Key 用

最省事的做法是「让集成方存一个用户 token」。三条都不成立：

1. **会话会被吊销**。用户改一次密码，对方的集成第二天就全挂了——
   而他们完全不知道为什么。
2. **权限全有**。会话 token 能提现、能改密、能注销账号。
   集成方只想读任务列表，凭什么给他一把能把钱转走的钥匙。
3. **没法审计**。出问题时分不清是本人操作还是集成方调的。

所以 API Key 是**另一类主体**，不是用户凭证的别名。

## 1. API-001 Key 只存哈希，且**只在创建时显示一次**

与密码同一条道理：库里存 `sha256(key)`，明文只在创建响应里出现一次。

这意味着「忘了就找不回来」——必须在创建时把这句话讲清楚，
并提供**轮换**（生成新 key、旧 key 立刻失效）。

**为什么不存可逆加密**：能解出来就意味着有人能解出来。
找回的便利，不值得拿「库被拖走时所有集成方的凭证同时泄露」去换。

## 2. API-002 Scope 是白名单，默认什么都不能做

```
tasks:read     读任务
tasks:write    发布/编辑任务
wallet:read    读余额与流水
webhooks:manage  管理自己的 webhook
```

**没有 `wallet:write`，也没有提现相关的任何 scope**——
这一批**不给 API Key 任何动钱的能力**。

理由：出金是这个平台上唯一不可逆的动作。集成方的 key 泄露的概率远高于
用户密码泄露（它躺在 CI 变量、日志、截图里），而一次错误出金是追不回来的。
需要程序化出金的场景，等有真实需求、且能配上白名单收款账户与二次确认时再说。

**scope 校验在依赖层做，不在每个端点里写 if。** 写 if 的那种做法，
新端点默认是「没检查」，而不是「拒绝」——这与 V47 限流那个洞同一形状。

## 3. API-003 Key 的权限**不能超过**它所属用户

Key 是用户授权给机器的一个**子集**，不是一个独立的权限来源。
所以每次请求仍然要解析出用户、仍然要过封禁/注销/实名检查。

一个被封禁的用户，他的 API Key 必须同时失效——否则封禁只封了人，没封住机器。

## 4. HOOK-001 Webhook 要签名，且要防重放

平台推送给集成方的请求，对方怎么知道确实是平台发的？

- `X-Platform-Signature: sha256=<hmac(secret, timestamp + "." + body)>`
- `X-Platform-Timestamp`，超过 5 分钟的拒收（防重放）
- 签名用**每个 webhook 独立的 secret**，不是全局的

**时间戳必须进签名**，不然攻击者可以拿一个旧请求原样重放，
签名照样对得上。

## 5. HOOK-002 投递失败要重试，且要能被看见

复用 V53 建的发件箱：webhook 投递是 `OutboxEvent` 的一个消费者，
不是另一套异步机制。

- 指数退避重试（1m / 5m / 30m / 2h / 12h）
- 连续失败达阈值 → **自动停用**并通知拥有者
- 每次投递留记录：状态码、耗时、响应片段

**自动停用是必须的**：一个挂掉的 endpoint 会让重试队列无限堆积，
拖慢所有人的投递。但停用必须**通知到人**——悄悄停掉比不停更坏，
对方会以为平台没有事件。

## 6. HOOK-003 不在 webhook 里发敏感数据

事件体只带**标识与状态**（`task_id`、`status`、`at`），
不带手机号、不带精确地址、不带金额明细。要详情就用 API Key 回查。

理由：webhook 的接收端是我们控制不了的。一个写进对方日志的手机号，
就是我们泄露的手机号。

## 7. 验收点

| 编号 | 验收点 |
|---|---|
| API-001 | 明文 key 只在创建时返回一次；库里只有哈希；轮换后旧 key 立刻失效 |
| API-002 | 无 scope 的调用被拒；scope 不足被拒且说明缺哪个；**没有任何动钱的 scope** |
| API-003 | 用户被封禁/注销后其 API Key 同时失效 |
| API-004 | API Key 不能调用用户会话专属的端点（改密、提现、注销） |
| HOOK-001 | 签名正确且包含时间戳；超时的请求被拒（对端可验证） |
| HOOK-002 | 失败重试并留投递记录；连续失败自动停用**且通知拥有者** |
| HOOK-003 | 事件体不含手机号/地址/金额明细 |

## 8. 这一批没做的（明确记账）

- **API-050**：**没有按 key 的独立限流**。当前走既有的 IP + 账号限流。
  按 key 限流需要一套配额模型（不同集成方不同额度），留待有真实用量。
- **API-051**：没有 OAuth 授权码流程（第三方代表用户访问）。
  当前的 key 是**用户给自己的机器用的**，不是给第三方应用代表用户用的。
  两者的信任模型不同，混在一起做会两边都不对。
- **HOOK-050**：只支持平台 → 外部的推送，没有做入站 webhook（外部触发平台）。
- **HOOK-051**：事件类型只开放了任务与合约的几个关键状态，不是全量。
  全量开放要先逐个审事件体里有没有敏感字段——**开放一个没审过的事件
  比不开放更危险**。
