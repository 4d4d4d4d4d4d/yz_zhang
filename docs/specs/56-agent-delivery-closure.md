# 56 Agent 交付闭环与产出审核（AGT-051 / AGT-060~067）

> 缺口来自一次探针：把 48/49 号 spec 建起来的 agent 链路**从 HTTP 口上完整走一遍**
> （邀请 → 选人 → 签约 → 托管 → 执行 → 交付）。前五步都通，第六步通不了。
>
> ```
> RUN STATUS: succeeded | OUTPUT: 交付内容：已完成。
> DELIVER as requester: 403 {'detail': {'code': 'forbidden', 'message': '仅执行者可提交验收'}}
> TASK STATUS after run: in_progress
> ```
>
> **一个由 agent 执行的任务，在生产里永远交付不了。** 钱躺在托管里，
> 任务停在 `in_progress`，两边都没有任何按钮能往前走。

## 0. 为什么测试全绿却漏了这个

`test_agt019` 里有这么一段，注释写得明明白白：

```python
# agent 是平台自有的，没有登录态（也不该有），所以交付与验收走服务层
with SessionLocal() as db:
    t.delivered_at = t.created_at
    task_service.transition(db, t, "pending_acceptance")
    _complete_task(db, t)
```

这句注释**两个分句都对，合起来是个洞**：

- 「agent 没有登录态」——对，而且不该有（AGT-017）。给一个 AI 发 token
  只会让它的所有动作都长得像人的动作。
- 「所以测试走服务层」——**错在这个「所以」**。测试绕开 HTTP 只说明了
  测试能绕开；生产里没有人能绕开。

这是一条通用教训，值得写进规矩：**当一个测试为了「走通」而绕过了
入口层，绕过去的那段就是没有被测的那段。** 注释解释了为什么绕，
却没有人问一句「那生产里谁来走这一步」。

同一形状此前出现过三次（V59 验证码、V61 纠纷陈述、V64 media_urls）：
**服务端建了闸门，客户端没有任何路径能满足它。** 这次是反过来的版本：
服务端建了闸门，**连服务端自己都没有路径去过它**。

## 1. 判断：交付由谁发起

三条路：

| 方案 | 做法 | 否决理由 |
|---|---|---|
| A 给 agent 发 token | agent 像人一样 POST `/deliver` | 违反 AGT-017。一个能签发的 token 就是一个能泄露的 token，而它背后是平台的钱包 |
| B 发布方代按「提交交付」 | 放宽 `deliver` 的身份校验 | **让收货方替发货方声明「我交付了」**。纠纷时这条记录属于谁？且放宽后人类任务也跟着松了 |
| C 平台代发起 | 执行成功即由平台提交交付 | 选它 |

**选 C。** 理由：agent 的执行结果**平台自己看得见**（`AgentRun.output` 就在库里），
交付这个动作的实质是「把产出交出去并请求验收」，而平台本来就是 AI 执行任务的
**责任主体**（AGT-017 已经写进合同条款了）。让责任主体发起交付，身份是自洽的。

方案 B 看着更省事，但它改的是 `deliver` 的身份校验——那条校验同时管着
**几百万条人类任务**。为了一个 AI 的特例去放宽一条通用的身份闸门，
是这一批最该避免的交换。

### AGT-060 平台代交付

新增服务层单一入口 `agent.service.submit_agent_delivery(db, task, note="")`：

- 执行者不是 agent → 返回 False，**什么都不做**（这条闸门只管 agent）
- `delivery_block(db, task)` 非空 → 返回 False，不交付
- `task.status` 不是 `in_progress` → 返回 False（幂等，见 AGT-062）
- 否则：落一条 `ProgressLog(kind="delivery", user_id=agent 的 user.id)`，
  内容是产出正文；`task.delivered_at = now`；`transition → pending_acceptance`

**`user_id` 写 agent 的 user 行，不写发布方。** 纠纷证据链里必须能看出
这份交付物是谁交的；写成发布方就是在证据里撒谎。

### AGT-061 闸门仍然权威，代交付不是后门

`submit_agent_delivery` **调用 `delivery_block`**，不重写它的判断。
判据不过 / 置信度不足 / 还在执行中 / 执行失败——四种情况一条都不许交付。

这是本批最容易做错的地方：加一条「平台可以代交付」的路径，如果它绕过
`delivery_block`，那 48/49 两批建的闸门就全部作废了。**新开的路必须比
原来的路更窄，不能更宽。**

### AGT-062 幂等

`agent-run` 可以被发布方重复触发（AGT-014 只挡并发，不挡串行重试）。
代交付必须幂等：已经 `pending_acceptance` 或已 `completed` 的任务，
再调一次**不产生第二条交付记录、不重置 `delivered_at`**。

### AGT-063 核验通过后自动交付，`revised` 用修正稿

`escalated` 的 run 被人核验通过后（VER-022），闸门解除——但此前**没有任何东西
去推那一下**。核验人提交 `approved`/`revised` 之后，任务还是停在 `in_progress`。

所以 `submit_outcome` 结论为解除类（`approved` / `revised`）时，紧接着调用
`submit_agent_delivery`。

**`revised` 时交付物是核验人的修正稿，不是 agent 的原始产出。** 这条不是
细节：修正稿之所以存在，正是因为原始产出不合格。把原始产出交出去，
等于让发布方验收一份已经被判定为不合格的东西，而他还要为核验费买单。

实现上有一个 V76 踩过的坑要避开：`delivery_block` 里的
`verification_unblocks_delivery` 是**再查一次库**，而会话是 `autoflush=False`。
`submit_outcome` 刚在内存里把 `status` 改成 `done`，不 `flush` 的话那次查询
看不见它，代交付会被自己刚解除的闸门挡住。

### AGT-067 判据失败的 run，只有「已修正」能解锁

顺着 AGT-063 查下去，发现同一形状的第二个死胡同：`delivery_block` 里
`failed` 分支排在核验分支**前面**，所以发布方自费给一个判据没过的 run
下了核验单、核验人交了一份**重新过了判据**的修正稿——任务照样交付不了，
钱花了，闸门纹丝不动。

但也不能简单地把核验分支提前，那会让 `approved` 也解锁 `failed` 的 run，
等于**让一个人点一下就覆盖掉平台的客观判据**（AGT-030 的整个立论就是
「不让执行方自己判卷」，换成核验人判也一样）。

分开定：

| run 状态 | `approved` | `revised` |
|---|---|---|
| `escalated`（只是置信度不足） | 解锁 | 解锁 |
| `failed`（判据没过） | **不解锁** | 解锁 |

`revised` 能解锁 `failed`，靠的不是核验人的权威，而是 VER-030 已经强制
**修正稿要重新跑一遍平台判据**、不过就报错。也就是说客观判据一次也没有
被绕过——变的是那份被判的文本。

### AGT-064 交付物进证据链

交付正文落在 `ProgressLog` 里，纠纷证据导出（`/legal/disputes/{id}/evidence-export`）
自然就带上了。这不需要新代码，但需要一条测试钉住——`AgentRun` 表和
`progress_logs` 表是两本账，只在 `AgentRun` 里有产出的话，纠纷侧看不见。

## 2. AGT-051 产出过内容审核

48 号 spec 的「没做的」里记着这条：

> **AGT-051**：agent 产出**不过内容审核**。`files` 与 `task` 都接了 moderation，
> agent 的 output 没接——这是 V64 那个洞的同一个形状。

现在它不再是「记一笔」，因为本批刚把产出接到了交付上：**在此之前，
未经审核的产出只有当事人看得见；从这一批起，它会成为交付物、进证据链、
被验收，并在纠纷里被引用。** 接上交付的同时必须接上审核，否则这一批
是在给一个已知的洞加流量。

### 三档结论，三种处理

| 供应商结论 | 处理 | 理由 |
|---|---|---|
| `reject` | run → `failed`，**产出不入库** | 与 UMOD-011 对称：被拒的内容不留痕迹 |
| `review` | run → `escalated`，产出保留 | 本地/沙箱实现看不了图；扔掉会让非生产部署完全不能用 |
| 供应商故障 | 同 `review` | 见下 |

**供应商故障时不放行、也不销毁，而是升级人审。** 与 UMOD 的 fail-open
判断在方向上一致（不因第三方抖动而销毁内容），但这里**不 open 到直接交付**：
上传物的用途是自证，挡住它伤的是被侵害方；而 agent 产出的用途是**换钱**，
放过它伤的是发布方与平台自己。同一个「第三方挂了怎么办」，两个场景答案不同，
**分界线是「代价落在谁身上」**。

`reject` 时产出不入库，但 `moderation_labels` 落库——否则运营侧面对
「我的任务失败了」的工单，只能看到一句「未通过审核」，无法回答为什么。

### AGT-065 审核先于判据

审核在拿到 output 之后**立即**执行，排在验收判据与置信度之前。
一份违规的产出，判据过没过不重要。

顺带一条实现约束：送审的文本不进 vendor 调用日志（只记字符数）。
把待审文本抄一份到日志里，等于给违规内容多开一个落点。

## 3. 验收点

| 编号 | 验收点 |
|---|---|
| AGT-060 | agent 执行成功后，任务**从 HTTP 口**走到 `pending_acceptance`，发布方能验收放款 |
| AGT-061 | 判据不过 / 置信度不足 / 执行失败 → 代交付不发生，任务仍在 `in_progress` |
| AGT-062 | 重复触发执行只产生一条 `delivery` 记录，`delivered_at` 不被重置 |
| AGT-063 | 核验 `approved` → 自动交付；`revised` → 交付物是**修正稿** |
| AGT-064 | 交付正文出现在纠纷证据导出里 |
| AGT-067 | `failed` 的 run：`approved` 不解锁，`revised` 解锁 |
| AGT-051 | 产出命中违禁词 → run `failed` 且 `output` 为空、labels 落库、不交付 |
| AGT-065 | 违规产出即使判据全过也失败（审核先于判据） |
| AGT-066 | 审核供应商故障 → run `escalated`，不交付，可走人工核验解锁 |
| — | 人类执行者的 `deliver` 路径行为不变（回归） |

## 4. 这一批没做的

- **AGT-070**：代交付没有为「AI 已交付，请验收」定制通知文案。
  事件已 `publish`（`task.pending_acceptance`），走的是通用模板。
- **AGT-071**：`review` 结论目前靠发布方自己去下核验单。自动下单（平台付费）
  更顺，但会让「审核供应商抖一下」直接产生平台成本，先观察。
- **AGT-072 / VER-052（下一批）**：查这一批时顺手发现的——**48、49 两号 spec
  从头到尾没有一个字提客户端**，`packages/core` 里也没有任何 agent / 核验单的
  方法。也就是说：发布方无法在 Web 上邀请 AI 助理，核验人无法看到、接下、
  提交任何一张核验单。服务端完整，端上零入口。
  这与 V59/V61/V64/V77 是同一个形状，但更彻底——那几次是「闸门没人能满足」，
  这次是**整条功能线没有任何客户端表面**。单独成批（它要动 SDK + Web 两侧）。
- 编排器接 agent（原 AGT-053）与经验回流喂回提示词（VER-051）仍未做。
