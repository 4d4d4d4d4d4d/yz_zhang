# 242 按期间的成交额与代扣税额

> 状态：本批实现（V269）。编号 FIN-062。
> 来源：144 号 spec「没做的」——「按期间的成交额（GMV）与代扣税额：GMV 要按放款流水跨用户汇总，代扣税额在独立专户（与平台收入分开），各自出表时口径要和财税确认后再做」；223 号再次登记；BACKLOG V269。
> 只增不减：144 号的平台收支期间报表、导出与 223 号锁账都不变；本表是新的一张，不改任何既有字段。
> 写明的行为变化：新增 `GET /admin/platform-finance/gmv-tax`（财务角色）；后台「按期间」下多一张表。

## 0. 要解决的问题

144 号的期间报表只有平台自己的收支（佣金、结算划出、补贴）。财务月结还要两组数：这个月平台上成交了多少，以及代扣了多少个税、缴库了多少、还剩多少待缴。以前只能导出全部流水自己加。

## 1. 业界怎么做

撮合平台的经营报表通常把 GMV 与平台收入分开报（GMV 是交易额，收入只是其中的佣金）；代扣代缴的税款单独列示、按期核对「已扣 / 已缴 / 待缴」。口径由财务定，系统把口径写在报表上。（本批没有另找外部来源。）

## 2. 口径（写进响应的 `basis`，逐条）

- **成交额（GMV）按放款算**：期间内验收放款给执行者的金额 + 同一笔里扣的平台佣金（即从托管里放出去的总额）。没放款的托管不算；退回发布方的另列「退款」；纠纷裁决分给执行者的另列「纠纷分账」；都不计入成交额。
- **代扣税额**按税款专户流水：期间内代扣进专户的金额与笔数、缴库划出的金额；「期末待缴」是专户到期末的余额。
- 被代扣人数与对应收入取自完税明细（只记扣了税的支付）。
- 期间按北京时间自然月 / 季度、按记账时间归属。本表不受锁账影响（锁账只管平台收支表）。
- 响应带 `draft_note`：「口径草稿：对外申报、报送前请财税负责人确认口径」——钱与申报的事 AI 只出草稿，人确认。

## 3. 数据

不新增表：读钱包流水（`escrow_release`、平台账户的 `fee`、`dispute_split`、`refund`、税款专户的 `tax_withheld` / `tax_remit`）与完税明细 `tax_withholdings`。每个期间固定 4 次查询，期间数上限沿用 144 号。

## 4. 接口

| 接口 | 说明 |
|---|---|
| `GET /admin/platform-finance/gmv-tax?granularity=&start=&end=` | 财务；参数、默认范围、校验与 144 号的期间报表相同 |

每期：`gmv_cents`、`release_count`、`executor_net_cents`、`fee_cents`、`dispute_split_cents`、`refund_cents`、`withheld_cents`、`withheld_count`、`withheld_people`、`withheld_income_cents`、`remitted_cents`、`tax_pending_cents`。SDK：`platformGmvTax`、`PlatformGmvTaxPeriods`、`PlatformGmvTaxRow`。登记：后台角色表、后台端点覆盖表、功能面清单。

## 5. 两端

- **Web 后台「平台财务 · 按期间」**：平台收支表下面多「成交额与代扣税」：草稿提示、每期一行、口径可展开；跟着上面的月 / 季切换。
- **App**：后台只在 Web，不涉及。

## 6. 隐私、授权与边界

只有财务角色（及超级管理员）可看；只给合计，不列个人（被代扣人只给人数）。
