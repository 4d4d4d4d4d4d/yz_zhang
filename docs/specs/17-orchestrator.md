# 17 · 编排循环（Agent Harness）：把「发任务给人」当作工具调用

> 心智模型：**Mission ≈ 一次 agent run，MissionStep ≈ 一次 tool call**，
> 而 tool 的实现体不是函数，而是本平台既有的
> 「发布任务 → 智能合约托管 → 他人执行 → 验收放款 → 纠纷兜底」这一整条链路。
> 人是工具，合约是调用协议，验收是返回值校验。

## 1. 为什么这样设计

agent harness 的四要素在本平台都有天然对应物：

| harness 概念 | 本平台实现 | 已有保障 |
|---|---|---|
| tool call | 发布任务并招募（`publish_task`） | 状态机白名单、类目准入、防调包编辑 |
| 调用协议/契约 | 合约生成 + 双签 + 资金托管 | 一任务一合约、托管守恒、存证哈希链 |
| observation | 任务验收结果（completed/cancelled/驳回/纠纷） | 验收/驳回上限、自动验收、纠纷答辩期 |
| 错误处理 | 生成「修复步」重新分发 | 迭代上限、预算护栏、人工停机 |

因此**不需要新造一套执行与结算体系**——编排层只负责「决定下一步调用什么工具」，
钱、法律、争议仍走既有的、已被 258 个测试钉死的链路。

## 2. 循环（一次 tick）

```
plan（首轮：AI 分解目标 → 步骤）
  → observe（读取各步对应任务的真实状态 → observation）
  → evaluate（完成度 = 已验收步/有效步；汇总问题）
  → 若有失败步：生成修复步（原步标记 superseded）
  → dispatch（把 pending 步真实发布为任务 = 调用工具）
  → 停机判定（全部达标 succeeded / 触及护栏 failed|blocked）
```

- **ORC-001** 创建目标 `POST /missions`（goal、预算上限、迭代上限、验收标准）
- **ORC-002** 推进一轮 `POST /missions/{id}/tick`；批量心跳 `POST /missions/jobs/tick-all`（需 job 令牌）
- **ORC-003** 编排状态机（与任务状态机同治理）：
  `planning → running → {blocked ↔ running} → succeeded|failed|cancelled`，非法流转 409
- **ORC-005** 完成度：`completion_pct = done / 有效步数`（superseded 不计入分母，
  否则任何一次失败都会让编排永远无法达到 100%）

## 3. 护栏（ORC-004，本模块第一性要求）

agent 会**自动花真钱**，所以护栏先于功能：

| 护栏 | 作用 | 触发行为 |
|---|---|---|
| `budget_cap_cents` | 累计已承诺预算硬上限 | 超出则 `blocked` 挂起等人工，绝不越线 |
| `ORC_PLAN_RESERVE_BPS`（默认 30%） | 规划只用上限的 70%，其余留作重试预留金 | 否则首轮用满、修复步永远无钱可发 |
| `max_iterations` | 迭代上限 | 触顶且仍有未决失败 → `failed` 停机 |
| 人工停机 `POST /missions/{id}/cancel` | 随时中止 | 未成交挂单一并下架 |
| 所有权隔离 | 仅 owner/管理员可查看与推进 | 他人 403 |

资金动作**不绕过**既有链路：每个分发步都是真实任务，仍需发布方托管、执行方交付、
验收放款，因此资金守恒、对账不变量、平台佣金口径、审计留痕全部继续适用。

## 4. 法律与合约衔接

- 每个 step 分发出去的任务，成交后走 **SC-001 合约生成 → SC-002 双签 → SC-003 托管**；
- 争议走 **DSP 全套**（冻结、答辩期两造兼听、仲裁分账、申诉窗口）；
- 编排目标本身可视为「委托说明」，其下各子合约独立可导出（SC-010）与存证（SC-011）。

## 5. 未做（有意留白）

- 多种 tool（目前仅 `publish_task`）：后续可加 `verify_by_third_party`、`ai_review` 等；
- 依赖 DAG 编排（当前步之间并行分发，依赖关系由 AI 分解的 `depends_on_idx` 承载，
  尚未在编排层强制串行）；
- 自动裁决/自动验收：**有意不做**——资金裁决必须有人类经手，与 DSP-009 一致。
