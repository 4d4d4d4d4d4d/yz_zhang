# 71 进了人审，就再也出不来（PAY-040/041 / AML-040 / CLI-077）

> 豁免理由写着「在管理后台做」。管理后台里没有这一条。

## 0. 探针

V91 把提现这条路接通了——在那之前没有任何端能发起提现，所以「大额进人审」
这条分支是理论上的。接通之后它变成了活的，于是：

```
WITHDRAW: 200 {"status":"pending_review","request_id":1,
               "message":"该笔提现需人工复核，通常 1 个工作日内处理完成",
               "available_cents":2000000,"frozen_cents":3000000}
WALLET  : {'available_cents': 2000000, 'escrow_cents': 0, 'frozen_cents': 3000000}
用户收到的通知: []
```

¥30000 进了 `frozen_cents`。而：

```
withdrawRequests: web=0 app=0
decideWithdraw  : web=0 app=0
```

**管理后台里没有提现复核台。** 有用户列表、有举报处置、有封禁、有指标——
没有这一条。端点是通的（探针手工打 `/approve` 成功了），
**只是没有任何界面能打它**。

用户那一侧同时是全静音的：他看到「通常 1 个工作日内处理完成」，
然后钱要么回来要么不回来，**平台一个字都不说**。三万块。

## 1. 为什么这条能漏这么久

V82 的覆盖闸门有一张豁免表，里面写着：

```python
"/wallet/withdraw-requests/{x}/approve": "提现人审是风控岗位的动作，在管理后台做",
"/wallet/withdraw-requests/{x}/reject": "提现驳回同样是风控岗位的动作，不是用户按钮",
```

理由是对的——**那确实不该是用户按钮**。但这句话同时是一个承诺：
「在管理后台做」。而**没有任何东西核对过那个地方是否真的有这一条**。

更结构性的一层：同一个闸门里写着

```python
if "/admin" in rel or "/jobs" in rel:
    continue          # 运营后台与调度端点不面向普通客户端
```

也就是说，**整个管理后台在我建的所有闸门的覆盖范围之外**。
而真正动钱的决定大半发生在那里：放款审批、纠纷裁决、可疑活动复核、
税款缴库。用户侧被一层层闸门盯着，运营侧一条都没有。

**一张豁免表如果没人核对它的理由，它就只是一句无人负责的承诺。**

## 2. PAY-040 复核台要给够判断的依据

改造前队列每行只有 `id / user_id / amount_cents / status / created_at`。
一个风控岗要为三万块做放行判断，拿到的是一个用户 ID。

补上：昵称、是否实名、注册时间、历史已提现累计，以及
**这笔申请命中的 AML 标记**——那些标记 V55 就在写库了（`record_withdrawal_flags`），
而此前没有任何地方读它们。

两侧措辞的分界要一直守住（AML-030/031）：

| 看的人 | 能看到什么 |
|---|---|
| 合规官 / 风控岗 | 命中了哪几条、明细、金额 |
| **用户** | **只有中性话术**，不含任何「为什么」 |

## 3. PAY-041 裁决要告诉用户，而且驳回不能说原因

- 批准：钱已在路上（说清打款去向是脱敏后的哪张卡）。
- 驳回：**中性**——「未通过复核，已退回可用余额」。
  不给原因不是敷衍，是《反洗钱法》第五条的保密义务，
  而且说了就等于教对方下次怎么规避（V55 立的那条）。

这两条归 `funds` 类。`notify()` 的既有规则里 `funds` 本来就**不可被开关关掉**，
所以**不需要进 `MUST_REACH`**——表是给「本该可关却不能关」的那些用的。

## 4. AML-040 合规官的队列也没人读

`/admin/aml/activities`、`/stats`、`/review` 三个端点 V55 就建好了，
**SDK 里一个都没有**（它们在 `/admin` 下，被闸门跳过了）。
可疑活动躺在库里，没有任何人能复核、也没人能标「已报送」。
本批把它们接进 SDK 与控制台。

## 5. CLI-077 闸门：把「在管理后台做」变成会红的承诺

两条新规则：

1. **豁免理由里说「在管理后台做」的端点，管理后台必须真的调它。**
   扫 `CLIENT_EXEMPT` 的值，凡出现「管理后台」「后台」字样的，
   其对应的 SDK 方法必须在 `web/src/pages/Admin.tsx`（或其引用的组件）里被调用。
2. **`ADMIN_CONSOLE` 声明表**：运营侧必须可达的能力 → 为什么。
   判定标准：**这件事只有运营/风控能做，而不做就有人的钱或权利卡住。**
   不满足的（报表、指标一类）不进表。

这两条合起来，补上「管理后台整体在闸门之外」这个缺口。
不追求把整个后台纳入——**先把卡住钱的那几条钉住**。

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| PAY-040 | 管理后台有提现复核台，能列出待审并批准/驳回 |
| PAY-040 | 队列行带昵称/实名/注册时间/历史提现与**命中的 AML 标记** |
| PAY-041 | 批准与驳回都通知用户；**驳回文案不含任何原因** |
| PAY-041 | 这两条是 `funds` 类（既有规则即必达），**不进 `MUST_REACH`** |
| AML-040 | 可疑活动列表与复核在 SDK 与控制台里可用 |
| CLI-077 | 豁免理由说「在管理后台做」的端点，后台真的调它——否则红 |
| CLI-077 | `ADMIN_CONSOLE` 每条在后台可达 |

## 7. 这一批没做的

- **不做四眼原则**：批准提现仍是一个管理员一个人点。真实风控要求
  大额双人复核（maker-checker），这条记下来，它需要模型层支持。
- 复核台没有分页与筛选（金额区间、时间、命中类型），队列长了不好用。
- `platformFinance` / `settlePlatform` / `adminAuditLog` / `banImpact` 仍无界面。
  审计日志尤其要补：**谁批了这笔三万块，现在只能查数据库**。
- 管理后台整体仍未纳入覆盖闸门，只钉住了 `ADMIN_CONSOLE` 里声明的几条。
