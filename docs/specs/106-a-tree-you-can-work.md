
# 106 拆到能干活为止的树：实现（AI-DEC-040~048）

> 状态：本批实现（V132）。设计见 [96 号](96-decompose-into-a-tree-that-can-be-worked.md)，本篇记实现、偏差与验证。
> 承接用户 2026-10-10：「任务拆解借鉴 todolist 生成过程，生成树类脉络够细够具体的任务，
> 这样有些 AI 可以闭环，有些需要求助其他专家」。

## 0. 改之前

一次提案只产出**一层**（同层 DAG），且没有任何字段说这一步谁能干。用户拿到的是一层待办，
不是一棵能开工的树。

## 1. 数据：一棵树存在提案里

`decompositions.tree`（JSON，≤ 60 个节点）存整棵树；每个节点带父节点、深度、同级依赖、
四条判据的材料、停止原因、执行主体与依据。`revision` 做比较并交换——逐层展开与逐步编辑
都是「读整棵树 → 改 → 写回」，两个窗口同时改时后写的会整个覆盖先写的。
V132 之前的一层提案 `tree` 为空，照原路走；`items` 对树形提案是第一层的只读视图，老客户端照读。

## 2. 规则（与 96 号逐条对应）

| 编号 | 实现 | 偏差与理由 |
|---|---|---|
| AI-DEC-040 叶子判据 | 交付物、验收标准、单一责任主体、预算 ≥ 最小可托管额，四条齐了才是叶子；缺哪条写在 `missing` 里 | 「可估」落成「预算够托管」：94 号的子类分布还没有（KB-070），拿不到带样本量的区间 |
| AI-DEC-041 逐层 | `POST /decompositions/{id}/expand` 一次长一层（或只拆点名的几步），每层落盘；`GET /tasks/{id}/decomposition` 读回进行中的那份 | 模板只有一层：模板拆不深就说「模板只能拆一层」（`template_limit`），不硬编更深的步骤 |
| AI-DEC-042 依据 | 「AI 可闭环」= 平台 Agent 在该类目**成功且任务已被验收**至少 3 次（可配）；不够就 `unknown` 并写出差几次 | 模型说 machine / expert 而查不到依据时也是 `unknown`——`needs_machine` 本批不会出现，没有可核对的产能登记（SPACE-025） |
| AI-DEC-043 否决 | 类目资质表里 `required_cert` 非空：直接 `needs_expert`，不看模型、不看历史 | 无 |
| AI-DEC-044 去处 | `needs_expert` 确认后是该类目的任务，资质门槛照常拦（无资质报名 → `certification_required`）；`unknown` 在确认前必须选「交给人做」或一个要资质的类目；`ai_closable` 的叶子到任务页用既有的 Agent 入口 | 96 号写的是「`unknown` 落到运营队列」。改成**让发布方自己选**：运营不了解这个人的项目，而发布方知道；确认被拦住时 409 点名是哪几步、各差什么 |
| AI-DEC-045 保险 | 深度 5、节点 60、预算碎片、无进展、模型调用 20 次、依赖不成立、审核不过——停下都写原因（`stop_note`），触发次数进 `/metrics`（`decompose_stop_total{reason}`） | 多了 `invalid_output` 与 `moderation` 两种停法 |
| AI-DEC-046 资金 | 只有叶子发布；中间步骤是草稿态容器，不发布、不托管；每一层子步骤预算之和 ≤ 上一级；前置完成后，后继**容器**下面没有前置的叶子才发布；全部完成后容器与总任务逐级结项 | 无 |
| AI-DEC-047 每层审核 | 每一层的每个子步骤都过机审与金融合规；一层里有一步不过，这一层整层不落盘 | 无 |
| AI-DEC-048 来源 | 每个节点带 `source` 与 `fallback`；模型不可用回落模板时，页面顶部说「AI 模型暂时不可用，以下按平台模板拆出」 | 无 |

**AI 不动钱**：拆解模块不许 import 钱包、合约、支付代码（AST 闸门）。

## 3. 两端

- **web**：`/tasks/:id/decompose`。树按层嵌套；每个叶子写出谁来做与依据；缺判据的写「还差：…」；
  停下的写原因；「判不了」的步骤就地给「交给人做」与「需要持证专家：选类目」。有没说清的步骤时
  「确认」按钮不可点，并列出是哪几步。发布页提交项目型任务后直接进这一页；任务页给发布方「继续拆解」。
- **App**：本批没有（APP-077，下一批）。

## 4. 顺带修掉的：只在 Postgres 上才有的 500

在本地 Postgres 上跑拆解测试撞见：`knowledge.find_template` 用
`KnowledgeCard.decomposition != []` 过滤——SQLite 上能跑，**Postgres 没有 `json <> json`
这个运算符**。没有种子模板、也没命中关键词的类目（例如「法律咨询」），**生产上一发起分解就 500**，
而所有测试都是绿的，因为测试库是 SQLite。

修法：查出最近 20 张卡在 Python 里判断。并且：

- 新增 `test_postgres_portability`：SQL 过滤里不许拿列和 `[]` / `{}` 字面量比较（AST 扫描，
  自检里原样放进这一行）；
- 拆解的两组测试进 CI 的 Postgres job（V130 建的那一步）。

## 5. 闸门

`test_decompose_tree.py`（32 条）：模板层直接是叶子；四条判据各自；逐层落盘与读回；
只拆一步；历史依据（含 0 次时说出 0 次）；资质否决（哪怕模型说 AI、哪怕 Agent 闭环过）；
总任务带资质时每一步都要专家；模型编的类目不采信；`unknown` 必须解决、两种解决都真实、
用户不能空口标「AI 可闭环」；专家步骤确认后被资质门槛拦；七种停法各自；每层预算；
深层违禁词与金融表述被拦且整层不落盘；回落看得见（假网关与真网关两条）；并发编辑 409；
只有发布方能动；删子树清依赖；**两层的树从确认一路做到总任务结项**；旧的一层提案照常确认；
AI 不动钱；迁移里的种子字段与代码一致；四个新端点的真实响应与 SDK 声明一致；停止原因进指标。

web 10 条（`Decompose.test.tsx`）；真浏览器联调新增「项目型任务逐层拆解并确认发布」。

**红验十一条**：资质否决排在判定之后 / 没有历史也标 AI / 回落不标 fallback / 只有根节点过审核 /
预算只校验第一层 / 容器也发布 / 写回不比较版本 / 去掉深度保险 / 后继容器不往下发布叶子 /
叶子不要求验收标准 / 把 `json != []` 写回查询（可移植性闸门）——都红。其中两条第一次是绿的：
「后继容器不往下发布叶子」与「叶子不要求验收标准」——**测试没有覆盖那两条路径**
（端到端那条里的后继步骤恰好是叶子；没有一步是「有交付物、没验收标准」的）。补了用例再红验才红。

web 页第一版把 `node={n}` 写在 `{...props}` 之前，props 里带着上一级的 node 把它盖掉——
子步骤被画成父步骤、无限递归，测试进程直接崩掉。「子步骤画在父步骤里面」那条用例就是为它留的。
