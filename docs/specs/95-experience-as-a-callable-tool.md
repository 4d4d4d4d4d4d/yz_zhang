
# 95 经验要变成能被调用的工具（KB-080~KB-089 / AGT-080~AGT-085）

> 状态：**设计，未实现**。本篇是可实现规格，不表示已交付。
> 依赖：94 号（经验按子类生长——本篇的输入是子类，不是样本）、
> 06 号（KB-020~022 消费侧 API）、61 号/orchestrator（Agent 编排）、
> 88 号（经验资产：有来源、有适用条件、有验证结果、有使用权限）
> 承接用户 2026-10-10 的设计意见：
> 「攒经验完全可以作为检索数据库或者 skilltool 工具给后续复用」

## 0. 今天「复用」到哪一步了

V86 那一批做了「经验回流喂回提示词」。量一下它的实际形态：

- 经验以**文本**形式拼进分解提示词；
- 复用的唯一方式是**模型读到它**；
- 平台不知道哪条经验被用了、用了之后结果是好是坏。

所以今天的复用是**单向的、不计量的、不可验证的**。
用户这次说的是另一件事：经验应当成为**两种可被调用的东西**——
一个**检索数据库**（问它"这类活儿怎么做"），
和一个**工具**（直接拿来执行那一步）。

这两件在工程上的区别很实在：
**检索返回文本，工具返回结果。** 前者的失败是答得不准，
后者的失败是做错了事——所以后者必须带权限、预算与回滚。

## 1. 三层：证据 → 结论 → 工具

```
样本（knowledge_cards）         ← 93/83 号已有：闭环后清洗入库
   ↓ 聚类（94 号）
子类（knowledge_clusters）      ← 共识流程 + 分歧 + 分布 + 样本量
   ↓ 蒸馏（本篇 KB-080）
可复用单元（reusable_units）    ← 有输入输出契约、适用条件、验证状态
   ↓ 注册（本篇 AGT-080）
Agent 工具表（agent_tools）     ← 可被编排器调用，带权限与预算
```

**蒸馏这一步不能跳。** 子类是统计描述（「这类活儿通常七步，其中第三步
有两种做法」），而工具需要确定的输入输出。把子类直接塞给 Agent 当工具，
等于让它在运行时自己决定走哪条分歧——那是把判断推给了最不该判断的地方。

## 2. 可复用单元是什么（KB-080）

四种，按「它替谁做了多少事」排列，**风险递增**：

| 类型 | 它是什么 | 调用方 | 失败的后果 |
|---|---|---|---|
| `price_hint` | 报价/工期区间 | 发布流程、分解估价 | 报价偏了，用户可改 |
| `checklist` | 验收检查清单 | 验收页、核验台 | 漏检一项 |
| `procedure` | 分解模板（步骤树） | AI-DEC-012 | 拆出来的树不对，用户要改 |
| `skill_tool` | **可执行**的一步（如「按这份清单生成验收报告草稿」） | 编排器 / 个人 Agent | **真的做错事** |

每个单元必须带的元数据（88 号 spec 对经验资产的四条要求，逐条落到字段）：

| 要求（88 号原话） | 字段 |
|---|---|
| 有来源 | `cluster_id` + `sample_ids`（证据可回溯） |
| 有适用条件 | `applicability`：类目、城市、预算区间、以及**排除条件** |
| 有验证结果 | `validation`：离线评测结果 + 线上使用后的实际结果对照 |
| 有使用权限 | `scope`：`private` / `project` / `platform`，与 `reuse_license` |

`applicability` 里的**排除条件**是刻意要求的：
一个只说「适用于什么」的单元，会在它不适用的场合被照样调用。

## 3. `skill_tool` 的边界（AGT-080~083）

这是本篇唯一会**动真格执行**的一类，所以单独立规矩。沿用 88 号对 Agent
的要求（「每个 Agent 应展示代表谁、能访问什么、能花多少、哪些动作要确认，
以及如何撤销权限」），落成四条：

| 编号 | 要求 |
|---|---|
| AGT-080 | 工具注册必须声明：读哪些数据、写哪些数据、是否花钱、是否对外发消息 |
| AGT-081 | **不许写资金、不许签约、不许转移权益**。这三件由人确认——与 04 号 spec 的「人机协同底线」同一条 |
| AGT-082 | 每次调用留痕：谁的 Agent、用了哪个单元的哪个版本、输入输出摘要、耗时与成本 |
| AGT-083 | 产出一律是**草稿**：标注「由经验单元 X 生成，未经人工确认」，并可一键丢弃 |

**为什么草稿是硬要求**：经验来自历史闭环，而历史闭环里有纠纷与返工
（94 号的 `outcome_mix` 就是为此存在）。一个把历史做法直接当成当前动作的
工具，会把上一次的错误复制到下一次——而且因为它"有经验撑着"，
看起来比随便猜更可信。

## 4. 复用要计量，否则贡献分成是空话（KB-083~085）

88 号 spec 第 55 行写着「知识贡献需要署名，商业复用可试验按实际使用结算
贡献收益」。要兑现这句话，必须先能数清楚：

| 编号 | 要求 | 判据 |
|---|---|---|
| KB-083 | 每次调用记录 `unit_id` + `version` + 调用场景 + 调用方 | 调用表可按单元聚合 |
| KB-084 | 调用结果回流：用了这个单元之后，那一单**闭环了没有、返工了没有** | 单元的 `validation` 随真实结果更新 |
| KB-085 | 贡献归因：单元 → 子类 → 样本 → 贡献者（任务双方 / 核验人 / 写经验帖的人） | 一次调用能列出它的受益贡献者清单 |

**KB-084 是这一组里最容易被省掉、也最不能省的一条。**
没有它，「经验」只会单调增长：每次调用都被记成一次成功复用，
而平台无从知道某个单元其实在拉低闭环率。
这与 94 号 `outcome_mix` 同一条道理——**只统计成功的系统学不会任何东西。**

## 5. 对外接口（KB-086~088）

| 编号 | 接口 | 说明 |
|---|---|---|
| KB-086 | `GET /knowledge/units?category=&kind=&q=` | 可复用单元检索（用户侧「这类活儿怎么做」） |
| KB-087 | `GET /knowledge/units/{id}` | 单元详情：适用与排除条件、验证结果、样本量、贡献者（按授权） |
| KB-088 | `POST /agent/tools/{unit_id}/invoke` | 调用 `skill_tool`（受 AGT-080~083 约束，产出草稿） |

两端都要够得到前两个（CLI 可达闸门）。第三个是 Agent 侧动作，
由编排器与个人 Agent 页面调用，**不做成一个用户可以随便点的按钮**。

## 6. 商业上线要求

| 要求 | 为什么是上线门槛 | 判据 |
|---|---|---|
| **复用授权与训练授权分开** | 06 号开头与 88 号都写着「检索复用与模型训练分别授权」。这不是两种说法，是两份同意 | 单元的 `reuse_license` 与 `train_license` 是两个独立位；缺任一位时对应用途直接拒绝 |
| **撤回要能生效** | PIPL 的撤回权（V119 已做入口）必须穿透到经验层 | 贡献者撤回后：该样本退出子类统计、受影响单元降级为待复核、已生成的草稿不追回但要标注来源已撤回 |
| **署名与分成口径先定** | 没定口径就上线计量，等于先收钱后定规则 | 分成规则文档 + 用户可见的贡献明细页；**真实分账接入前不开启商业复用** |
| **工具不碰钱** | AGT-081；资金路径已被 GO-LIVE 红线 1~3 管着 | 闸门扫描：`skill_tool` 的实现不得 import wallet/contract 的写接口 |
| **成本可控** | 04 号 E 节已要求；工具调用会放大 token 消耗 | 每个单元声明预估成本；超预算拒绝并升级给人 |
| **退化态要说出来** | 94 号已立：`semantic=false` 时不生长知识图谱 | 退化态下 `skill_tool` 不可调用（只允许 `price_hint`/`checklist` 这类只读单元） |

## 7. 闸门

| 闸门 | 内容 |
|---|---|
| KB-080a | 单元必须带来源、适用条件（含排除）、验证状态、授权位，缺一不得注册 |
| AGT-081a | `skill_tool` 的实现不得触达资金/签约/权益写入（AST 扫描，不靠人自觉） |
| AGT-083a | 工具产出一律带「未经人工确认」标注，且可丢弃 |
| KB-084a | 调用结果回流真的更新了 `validation`，失败的调用会把单元推向待复核 |
| KB-085a | 一次调用能列出受益贡献者清单，且清单里不含未授权的人 |
| CLI-078 | `units` / `unit 详情` 两端可达 |
| KB-089 | 贡献者撤回授权后，统计与单元状态**真的变了**（不是只在表里改个位） |

## 8. 这一篇没做的

- **不做自动蒸馏**：第一版 `procedure` / `checklist` 由运营从子类里确认生成
  （沿用 V103 的队列机制）。全自动蒸馏要先有 KB-084 的回流数据来证明蒸馏
  质量，而那需要先上线一段时间——**顺序不能反**。
- **不做跨平台经验导入**：外部案例没有闭环证据，进不来这套体系。
- **不做个人 Agent 的完整形态**：那是 SPACE-026，本篇只定它能调什么。
- **不开启商业复用分成**：见第 6 节，口径与分账未就位。
