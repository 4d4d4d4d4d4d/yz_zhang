
# 140 发单时就提示创作类需求的九项

> 状态：本批实现（V166）。编号 SCN-106。
> 来源：137 号 spec「没做的」SCN-106：需求单体检要先启用场景包再问助手；BACKLOG V166。
> 只增不减：任务画像（126 号）原有字段与「说明完整度」的口径一字不改；新加的 `brief` 字段对非创作类的单是 `null`。

## 0. 要解决的问题

自由创作者的扯皮多半出在需求单里没写的那几项（137 号场景卡 A）。137 号把「需求单体检」做成了场景包助手的工具，
但那要创作者先启用场景包、再把甲方原话贴进来——问题已经发生了。更早、成本更低的地方是**发单页**：发布方写海报需求时，就告诉他九项里还缺什么。

## 1. 业界怎么做（带来源链接）

- 设计接单平台的发布流程普遍是结构化的需求表单（例如 99designs 的 design brief，<https://99designs.com/how-it-works>），把用途、尺寸、风格参考等拆成必答或建议项。
- 本平台不加必填（不挡发布），而是沿用 126 号的「边写边提示」：写到了就不提示，没写的给一句该补的话。

## 2. 数据

无新表。`POST /profiles/task-draft` 与 `GET /tasks/{id}/profile` 的响应多一个 `brief`：

| 字段 | 内容 |
|---|---|
| `brief` | `null`（不是创作类）或 `{items, missing}` |
| `items[]` | `{name, ok, ask}`：九项按 137 号的顺序（用途、数量、尺寸规格、文件格式、交期、改稿次数、版权授权、参考、预算） |
| `missing` | 没写的项数 |

## 3. 规则

| 编号 | 内容 |
|---|---|
| SCN-106a | 什么算创作类：类目是「设计 / 文案 / 视频剪辑 / 剪辑 / 摄影 / 插画 / 动画」之一，**或者**要求的技能（按 135 号概念表归到规范名）或从说明里认出的技能是品牌设计、平面设计、UI 设计、视频剪辑、摄影、文案之一 |
| SCN-106b | 九项用 137 号同一个 `brief_check`（一份实现，两处用）；表单里填了的也算写到：预算 > 0 算「预算」，有截止时间算「交期」 |
| SCN-106c | 只是提示，不计入「说明完整度」，也不挡发布 |

## 4. 两端

- **Web 发布页**（`DraftHints`）与 **App 发布页**（`DraftHints`）：「说明完整度」那一块下面多一段「创作类需求一般写清九项，已写 X/9。还可以补：」，只列没写的项和该补的话。

## 5. 隐私、授权与边界

只看发布方自己正在写的草稿；不落库。任务详情的画像沿用原来的可见性规则（126 号）。

## 6. 闸门与红验

6 处变异全部变红（`scratchpad/mut166.py`）：

| 闸门 | 红验 |
|---|---|
| 表单里填了预算 / 截止时间算写到 | 去掉 → `test_form_fields_count_as_written` 红 |
| 按技能认创作类 | 只看类目 → `test_skill_concepts_make_it_a_creative_job…` 红 |
| 技能先归到规范名（「VI设计」→ 品牌设计） | 不归一 → 同上红 |
| 创作类才有九项 | 恒不给 → `test_design_draft_lists…` 红 |
| Web 只列没写的 | 全列 → `Profiles.test.tsx` 红 |
| App 只列没写的 | 全列 → `app/profiles.test.tsx` 红 |
| 说明完整度口径不变 | `test_other_jobs_have_no_brief_and_completeness_is_unchanged`；`test_profiles.py` 原有断言照旧通过 |
| 响应形状 | `TaskProfile`、`TaskBrief`、`TaskBriefItem` |

## 7. 没做的

- **SCN-110 任务详情上给接单的人看九项**：现在任务详情的画像只显示风险、技能、价格位置；接单前看一眼「这单没写版权、没写改稿次数」对创作者很有用，但要先想清楚会不会让发布方觉得被公开挑错（措辞与是否只给报名者看）。
- 发单表单直接加「用途、尺寸、改稿次数、版权」结构化字段：知识产权归属已经是必选（52 号），其余要等发单表单改版一起做。
