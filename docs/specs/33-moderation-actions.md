# 33 · 处置动作的单一实现（MOD）

> 补 [12-platform-foundation.md](12-platform-foundation.md) RISK-002/006 与
> OPS-013 之间掉下去的那条缝。

## 先说清楚发现了什么

**封禁一个用户，在这个系统里有两条路，做的事完全不一样。**

`POST /admin/users/{id}/ban`（OPS-013 那条，写得很仔细）：

1. 先算**影响面**：在途合约、涉险托管金额、未成交挂单；
2. 通知每一笔在途合约的**对手方**——被封的人无法再交付/验收，
   对手方得知道要赶紧取消或发起纠纷，否则托管资金被无限期困住；
3. 关闭该用户挂单上的**待处理报名**并通知报名者；
4. 走 `transition()` 把挂单下架；
5. `record_audit` 留痕。

`POST /admin/reports/{id}/resolve` 且 `action="ban_user"`（审核队列那条）：

```python
user.is_banned = True
db.add(user)
```

**就这两行。** 上面五件事一件都没做。

而审核队列**恰恰是审核员日常真正在用的那个界面**——写得仔细的那条路
反而在另一个页面上，用得更少。

### 后果不是「少了点提示」

- 在途合约的对手方**永远不会被告知**：他的钱还在托管里，
  而对面那个人已经被平台封了、永远不会来验收。OPS-013 整节就是为了防止
  这件事，结果最常用的入口把它完全绕开了。
- 报名者继续等一个**永远不会有人来选他**的任务。
- 处置**不进审计日志**——而这个函数的 docstring 写着「处置留痕
  （RISK-002/006）」，运维手册也写着「管理员操作审计（封禁/…全留痕，
  可按动作查询）」。**又是一句说谎的话。**

### 顺带还有一处绕过状态机

同一个函数里下架任务用的是：

```python
task.status = "cancelled"      # 而不是 transition(db, task, "cancelled")
```

`transition()` 是整套状态机设计的**唯一合法变更入口**：它做白名单校验、
统一审计、并派发 `task.cancelled` 事件。绕过它今天只是少了个事件
（当前订阅者恰好会提前返回），但**下一个给 `task.cancelled` 加订阅者的人
——比如托管退款——会发现它在这条路径上根本不触发**。

而且发布者**不会收到任何通知**：任务就这么消失了，不知道为什么，
也就无从申诉。

## 33.A 根因

和 [32 号 spec](32-job-orchestration.md) 是同一类问题的另一种形态：
**同一件事被写了两遍，其中一遍抄了近道。**

- 32 号是「同一份清单抄在两处」→ 漂移；
- 这里是「同一个动作实现在两处」→ **能力不对等**。

两者都不会报错，所以都能长期存在。区别只在于：漂移的清单错在调度，
而不对等的处置错在**用户的钱和知情权**。

## 33.B 单一实现（P0）

- **MOD-001** 每个处置动作只能有**一个**实现，放在 `admin/service.py`：
  `ban_user_with_impact()` / `takedown_task()` / `takedown_content()`。
  端点只负责鉴权、取参、调它。
- **MOD-002** 任何路径的封禁都必须完整执行五步：算影响面 → 通知对手方 →
  关闭待处理报名并通知 → 下架挂单（走 `transition()`）→ 记审计。
  「哪条路进来的」不该改变用户拿不拿得到通知。
- **MOD-003** 下架任务必须走 `transition()`，并**通知发布者（含原因）与
  已报名者**。任务无声消失，用户既不知情也无从申诉。
- **MOD-004** **每一次**处置都记审计，包括 `dismiss`。
  驳回同样是决定：谁在什么时候驳回了哪条举报，是事后复盘的关键。
  只写 `report.handled_by` 不够——审计日志按动作查询时看不到它。

## 33.C 机器强制的护栏（P0）

- **MOD-010** 测试断言**两条路径产生相同的副作用集合**：
  同样的封禁，从审核队列进和从用户页进，对手方通知、报名关闭、挂单下架、
  审计记录必须一模一样。这是本 spec 的核心用例。
- **MOD-011** 全仓库扫描：`task.status = ` **只允许**出现在 `transition()` 内部。
  状态机的「唯一入口」是靠约定维持的，而约定不会报错——
  写成测试才拦得住下一次。

## 33.D 验证（P0）

- **MOD-020** 从审核队列封禁 ⇒ 在途合约对手方收到通知（缺口的直接反面）。
- **MOD-021** 从审核队列封禁 ⇒ 待处理报名被关闭、报名者收到通知。
- **MOD-022** 从审核队列封禁 ⇒ 未成交挂单被下架，且**经由状态机**。
- **MOD-023** 两条封禁路径的副作用逐项对等。
- **MOD-024** 下架任务 ⇒ 发布者与报名者都收到带原因的通知。
- **MOD-025** 每种处置（含 dismiss）都能在 `/admin/audit-log` 按动作查到。
- **MOD-026** 全仓库不存在绕过 `transition()` 的任务状态赋值。

## 验收标准

- 同一个业务动作，无论从哪个入口触发，**副作用完全一致**；
- 任何影响用户资金或权利的处置都有通知与审计；
- 「唯一入口」不再只是注释里的约定，而是有测试盯着的事实。
