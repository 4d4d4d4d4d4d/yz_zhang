
# 96 拆到能干活为止，并说清每一步谁能闭环（AI-DEC-040~AI-DEC-049）

> 状态：**设计，未实现**。本篇是可实现规格，不表示已交付。
> 依赖：04 号（AI-DEC-010~015 现有分解）、94/95 号（子类与可复用单元是模板来源）、
> 03 号（任务状态机）、05 号（预算与托管）、51 号（资质）
> 承接用户 2026-10-10 的设计意见：
> 「任务拆解感觉可以借鉴 todolist 生成过程，主要要生成树类脉络够细够具体的
> 任务，这样有些 AI 可以闭环，有些需要求助其他专家」

## 0. 现状（读过实现的）

`decompose/models.py` 里一次提案的结构是：

```python
# items: [{title, description, required_skills, budget_cents, depends_on_idx: [int]}]
items: Mapped[list] = mapped_column(JSON, default=list)
```

也就是说：

1. **一次提案只产出一层**。它是同层之间的 DAG（`depends_on_idx`），
   不是树。多层只能靠「对某个子任务再发起一次分解」实现
   （AI-DEC-014，默认最多 3 层），每一层都要用户再点一次。
2. **没有任何字段说这一步谁能干**。只有 `required_skills` 一个字符串数组，
   而它是**匹配用的标签**，回答不了「这一步平台 Agent 能不能自己闭环」。
3. 所以今天的产物是**一层待办**，而用户要的是**一棵能直接开工的树**。

另外量到一件相关的事：`propose` / `editDecomposition` /
`confirmDecomposition` / `taskTree` 四个方法 **web 有、App 一个都没有**
（见 72 号台账新增的 `APP-077`）。本篇定的是结构；端上补齐是另一批。

## 1. 「够细够具体」要有判据，不能靠感觉（AI-DEC-040）

一个节点可以停止继续拆分，当且仅当它同时满足四条：

| 判据 | 说明 | 为什么 |
|---|---|---|
| **交付物可指认** | 说得出交出来的是什么（一份图、一次上门、一台样机） | 说不出交付物的节点无法验收，也无法托管 |
| **验收判据可判** | 有人能在不懂全局的情况下判断它是否完成 | 这正是子任务能独立结算的前提（05 号） |
| **单一责任主体** | 一个人/一个 Agent/一台设备能负责到底 | 两个人共同负责的节点在出问题时无法归责 |
| **预算与工期可估** | 能给出区间（来自 94 号子类分布，带样本量） | 估不出来说明还没拆到位，或者平台没见过这类活儿 |

四条里任一条不满足 → **继续拆**。四条都满足 → **叶子**。

这替换掉「默认最多 3 层」那个数字：深度限制是**防失控的保险**，
不是停止条件。把保险当判据用，结果是复杂任务在第三层被迫停下，
留下一堆没人能验收的半成品节点。保险仍然要有（见第 5 节）。

## 2. 像生成 todolist 那样逐层展开（AI-DEC-041）

借用户给的类比，落成一个可实现的循环：

```
队列 ← [根需求]
while 队列非空且未触发保险:
    取一个节点
    查 94 号子类：这类活儿的共识流程是什么（带样本量与分歧）
    据共识 + 节点上下文，提出它的直接子步骤
    对每个子步骤判第 1 节那四条
        四条全满足 → 标为叶子，附执行主体判定（第 3 节）
        否则        → 入队，继续拆
```

两处与「让模型一次吐出整棵树」的关键差别：

- **每层都过一次子类检索**。模型一次生成整棵树时，深层节点是它凭
  上下文编的；逐层展开则每一层都能拿到「平台见过的同类活儿怎么做」。
  这也是 95 号 `procedure` 单元的调用点。
- **每层都落盘**。树是增量生长的，用户可以在第二层就打断、改写、
  然后让它接着往下拆。一次性生成的整棵树，用户只能全盘接受或全盘重来——
  而 04 号 spec 的 AI-DEC-011 已经要求「AI 结果仅是草稿」，
  **草稿的意义就在于能被改**。

展开过程对用户必须是**可见且可打断的**：每完成一层就呈现一层。
一个转圈三十秒然后甩出四十个节点的界面，用户无法判断该信哪一部分。

## 3. 每个叶子都要说清谁能闭环（AI-DEC-042）

这是用户这次提的核心——「有些 AI 可以闭环，有些需要求助其他专家」。
每个叶子带一个 `executor_kind` 与**判定依据**：

| `executor_kind` | 含义 | 判定依据（必须可查，不能是模型自说自话） |
|---|---|---|
| `ai_closable` | 平台 Agent 能自己做完 | 该子类下 Agent 历史闭环记录（95 号 KB-084 的回流数据）；无记录则**不得**标此类 |
| `needs_human` | 要人做，但无资质门槛 | 默认值 |
| `needs_expert` | 要具名资质的人 | **类目资质表**（`task/service.py` 里的 `required_cert`：法律咨询→律师、电工维修→电工…）。这是硬依据，不是判断 |
| `needs_machine` | 要设备/产能 | 机器授权与产能登记（OPC-MACHINE 文档、SPACE-025） |
| `unknown` | 判不了 | **必须允许这个值存在**，见下 |

**`unknown` 是刻意保留的。** 一个只有四个确定分类的枚举，会迫使判定逻辑
在没有依据时随便挑一个——而挑错的方向是不对称的：把 `needs_expert`
误判成 `ai_closable`，结果是**无资质地做了需要资质的事**
（法律咨询、电工、燃气维修——平台已经在接单侧拦着的那些）。
所以规则是：**判不出来就标 `unknown` 并升级给人**，
与 04 号 spec「遇到不确定性升级给人」一致。

反向的硬约束（AI-DEC-043）：
**`required_cert` 非空的类目，永不得标 `ai_closable`。**
这条不走判定逻辑，直接按类目表否决——
因为这是平台已经在接单侧用资质拦住的同一批活儿，
在拆解侧放行等于从另一个门绕进去。

## 4. 「求助其他专家」要是一个动作，不是一句提示（AI-DEC-044）

标成 `needs_expert` 之后，用户必须能**就地**把这个节点发成一个
面向该资质的任务：带着父任务上下文、子类给的预算区间、以及
验收判据，落到现有的发布 + 匹配 + 资质门槛链路上。

这是 66 号 spec 那条规矩在拆解场景的一次应用：
**服务端判断出「这里需要律师」，而界面上只写一句「建议咨询专业人士」，
等于平台知道答案却让用户自己去找门。**

同理，`needs_machine` 落到机器授权链路，`unknown` 落到运营队列。
**每一种判定都要有去处**——没有去处的分类只是给用户增加了一个坏消息。

## 5. 保险（AI-DEC-045）

逐层展开必须有停机保证。四条，任一触发即停止并交给人：

| 保险 | 阈值 | 触发后 |
|---|---|---|
| 最大深度 | 默认 5（可按类目配） | 停止该支，标注「已达深度上限，请人工判断是否继续」 |
| 最大节点数 | 默认 60 | 同上，整棵树停 |
| 预算碎片 | 子节点预算 < 父预算的 2% 且 < 平台最小托管额 | 不再拆：**托管不了的节点拆出来没有意义** |
| 无进展 | 某节点拆出的子步骤与自身判据集合无变化 | 停止该支（防模型原地复述） |

前两条的**默认值与实际触发率都要可观测**：一个经常在深度 5 上截断的类目，
说明那一类的判据或模板不对，而不是用户的需求太复杂。

## 6. 树与资金、状态机的关系（AI-DEC-046）

沿用 05 号与 AI-DEC-030，不新造机制，但把两件事写明：

- **只有叶子成为可发布任务**。中间节点是组织结构，不独立托管、不独立结算，
  否则同一笔钱会在父子两层各托管一次。
- **父节点的完成由子节点推导**，不手工置位（现有 `_on_task_completed`
  已是这个形状，保持）。
- 预算自上而下分配、剩余回父节点预算池（AI-DEC-030 已定）；
  **树形分配要保证任一层子节点预算之和 ≤ 父节点预算**，
  这条现有 `validate_items` 只在单层上做过，多层要逐层做。

## 7. 商业上线要求

| 要求 | 为什么是上线门槛 | 判据 |
|---|---|---|
| **资质不得绕过** | AI-DEC-043。无资质承接法律/电工/燃气是行政违法风险 | 闸门：类目表里 `required_cert` 非空的，拆解结果中 `ai_closable` 必须为空 |
| **AI 不动资金** | 04 号 E 节已立；GO-LIVE 红线 1~3 管着资金路径 | 拆解只产出草稿，确认由人；AST 闸门禁止拆解模块 import 资金写接口 |
| **模型降级要可见** | GO-LIVE 红线 7：过期型号会让每次分解**静默回落模板**，而平台看起来完全正常 | 拆解结果必须带 `source`（模型 / 模板 / 子类共识）并在界面显示 |
| **高风险需求先拦** | AI-DEC-003 已定（分解前过内容安全） | 逐层展开的**每一层**都要过，不只根节点——第三层才出现的违规内容同样要拦 |
| **成本上限** | 逐层展开比单次生成贵 | 每棵树的 token 预算上限；超限停止并说明，不静默截断 |
| **可解释** | 用户要能问「为什么这一步需要律师」 | 每个判定带依据来源（类目表 / 历史记录 / 运营判定） |

## 8. 闸门

| 闸门 | 内容 |
|---|---|
| AI-DEC-040a | 叶子必须四条判据齐全；缺任一条的节点不得标为叶子 |
| AI-DEC-041a | 逐层展开可被打断，已落盘的层不丢 |
| AI-DEC-042a | `ai_closable` 必须有历史闭环依据，无依据时降为 `unknown` |
| AI-DEC-043a | `required_cert` 非空的类目永不出现 `ai_closable`（按类目表否决，不走判定） |
| AI-DEC-044a | `needs_expert` / `needs_machine` / `unknown` 三种都有可点的去处 |
| AI-DEC-045a | 四条保险各自真的会停，且停止原因对用户可见（不是静默截断） |
| AI-DEC-046a | 任一层子节点预算之和 ≤ 父节点预算（多层递归校验） |
| AI-DEC-047 | 每层都过内容安全，不只根节点 |
| AI-DEC-048 | 结果带 `source`，模型不可用时回落到模板**会显示出来** |

红验要点：AI-DEC-043a 要能被「把资质类目标成 ai_closable」弄红；
AI-DEC-048 要能被「回落模板时不标 source」弄红——
后者正是 GO-LIVE 红线 7 担心的那种「看起来完全正常」。

## 9. 这一篇没做的

- **不做对话式澄清**（AI-DEC-001 仍未实现）：逐层展开需要上下文，
  而澄清是获取上下文的更好方式。但那是一条独立的交互线。
- **不做甘特/关键路径**（AI-DEC-021 母任务驾驶舱）：树有了之后才谈调度。
- **不做跨子任务产出物共享**（AI-DEC-024）：要先有授权模型。
- **不改 App**：`propose` 等四个方法 App 仍无调用，记台账 `APP-077`。
- **不做自动重新招募**（AI-DEC-023）。
