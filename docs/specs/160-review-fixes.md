# 160 功能检视：CORS 暴露响应头与工单进导出和注销处置

> 状态：本批实现（V189）。编号 CORS-001、ESCA-055。
> 来源：用户 2026-10-15「检视一下功能是否健全」。对 V178~V185 做了代码检视，并用真服务端（alembic 迁移出来的 Postgres、真 HTTP）走了 25 个关键步骤；发现两处缺口，当批修掉。
> 只增不减：只多响应头声明、导出多一段、注销多处置两类数据；接口与行为不变。

## 0. 检视做了什么

- **真服务端走查**（`scratchpad/walk160.py`）：客服工单（提单 → 先回一句 → 主管指派 → 超时升到第 2 级 → 提单人看到进度 → 数据导出）、全站公告（按城市预览 → 发送只到上海的人 → 已读率 → 撤回后用户那条显示理由 → 定时后取消）、开放 API（建 Key → 剩余次数与配额头 → 用量页含账号合计）、审计（链头锚定 → 自检完整 → 直接改库后自检指出断点）、场景雷达（3 个人问到租房问题 → 雷达出现「租房买房」→ 库里不存原文）。全部通过。
- **代码检视**发现下面两处，都是「测试里看不出来、上线才会咬人」的类型：

## 1. 发现与修复

| 编号 | 问题 | 后果 | 修复 |
|---|---|---|---|
| CORS-001 | 跨域中间件没有声明 `expose_headers` | 网页与 API 不同源部署时，浏览器不让脚本读 `X-Total-Count`：后台审计日志、提现复核台的「共 N 条 / 第几页」显示为空；开放 API 的剩余次数、`Retry-After` 浏览器里读不到。测试用的是同源客户端，看不出来 | 声明客户端要读的响应头 `EXPOSED_HEADERS`（总条数、重试、限流与配额剩余、请求编号）；新加客户端会读的头要同时登记在这里 |
| ESCA-055 | 客服工单（标题、内容、客服往来）不在 `/users/me/export` 里，注销也不处置；法律问答「答不上」的分析事件注销后仍带着用户编号 | 数据可携带权与删除权（个人信息保护法第四十五、四十七条）缺一块；工单里常写着地址、卡号等个人情况 | 导出多 `tickets`（含往来）；注销时没转成纠纷的工单清空文字（转成纠纷的按纠纷材料留存），分析事件去掉与人的关联（聚合数保留） |

## 2. 数据

不加表、不加迁移。

## 3. 规则与接口

| 编号 | 内容 |
|---|---|
| CORS-001-1 | 所有响应的 `Access-Control-Expose-Headers` 包含：`X-Total-Count`、`Retry-After`、`X-RateLimit-Limit`、`X-RateLimit-Remaining`、`X-Quota-Limit`、`X-Quota-Remaining`、`X-Account-Quota-Remaining`、`X-Request-ID` |
| ESCA-055-1 | `GET /users/me/export` 多 `tickets`：标题、内容、状态、时间与往来（往来只写「客服 / 我」，不写是哪位管理员） |
| ESCA-055-2 | 注销：没转成纠纷的工单标题改为「（已注销用户的工单）」、内容与回复清空；转成纠纷的保留；该用户的分析事件 `user_id` 置空 |

## 4. 两端

不涉及界面：导出文件两端都有入口（V119），内容由服务端给；响应头是浏览器层面的修复。

## 5. 隐私与边界

- 转成纠纷的工单保留，是因为纠纷材料要按法定期限留存（ESCA-001 工单与纠纷互相能找到）。
- 分析事件只去掉人，不删行：雷达等聚合数不受影响。

## 6. 闸门与红验

6 处变异全部变红（`scratchpad/mut160.py`）：去掉 `expose_headers`、不清工单文字、不清往来、转纠纷的也清、不去掉分析事件的人、导出里去掉工单 → `tests/test_review_fixes_160.py` 对应用例红。
