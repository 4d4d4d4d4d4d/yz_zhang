
# 104 幂等键：从「支持」到真的护住钱（FIN-071 / FIN-072 / FIN-073）

> 状态：本批实现（V130）
> 依赖：14 号（14.6「所有写操作支持 Idempotency-Key，资金类强制」）、05.B（资金幂等）、
> 98 号（Stripe 对照表：FIN-071 / FIN-072）、99 号（MONEY_WRITE_PROTECTION）

## 0. 起点与探针

台账里两条「上线前必须做」：幂等记录不过期（FIN-071）、并发同键会 500（FIN-072）。
修之前先打了一次探针——同一个用户、同一个键、6 个线程同时充值：

```
concurrent same key [500, 500, 500, 500, 500, 200]
balance 5000 (expect 5000)
long key 1st 200
long key retry 500
```

钱是对的，但**六个请求都把钱动了一遍**：原流程是「查 → 跑 → 记」，大家都查不到，
都执行了充值，然后在记录幂等键时撞唯一约束，靠整个事务回滚才没多入账。
用户看到的是**钱包页上的「服务器错误」**，而且他不知道钱动没动——于是他会再点一次。

同一次探针还查出两件台账里没有的：

- **超过 80 个字符的键查不到自己**：存的是 `key[:80]`、查的是完整的 key。每次重试都
  重跑一遍再撞约束——这个键的幂等保护从来没有成立过。
- **两端从来没有发过这个头**（记为 FIN-073）。14.6 写着「资金类强制」，服务端却把空键
  当成「不要幂等」直接执行，SDK 的 `topup` / `withdraw` 也没有这个参数。
  **这条保护对真实用户一次都没有生效过**：网络超时后再点一次「提现」，服务端看到的
  就是两笔毫不相干的提现。99 号 spec 的 `MONEY_WRITE_PROTECTION` 表把充值与提现登记为
  「靠幂等键」——它核对了服务端接了这个头，没有核对有没有人发。

## 1. 服务端

### 1.1 先占键，再动钱（FIN-072）

```
INSERT ... ON CONFLICT (user_id, key) DO NOTHING   ← 占键（空结果）
  └ 落空：同键请求已提交 → 读它的结果原样回放（指纹不同 → 409 冲突）
run()                                              ← 动钱
UPDATE ... SET response = <结果>                    ← 同一个事务里补上结果
```

Postgres 上，后到的插入在唯一索引上**等前一个事务提交**，然后落空、读到结果、回放——
**钱只动一次，所有人都拿到同一个 200**。前一个回滚了（动钱失败），后到的插入就成功，
真的去做一次。失败不缓存：`run()` 抛异常时整个请求回滚，占位随之消失，同一个键重试
会真的再试。

**为什么不是 V112 钱包那样的 SAVEPOINT**：第一版就是那么写的，测试当场红了。
pysqlite 不会在 SAVEPOINT 之前发 BEGIN；占键是这个事务的第一笔写入时，RELEASE 就
等于提交——**空结果的占位行在动钱之前就落库了**：并发的人读到空结果（JSON 解析失败，500），
动钱失败时占位也不回滚（之后同一个键永远是空结果）。`ON CONFLICT DO NOTHING` 两种库都
支持，不需要 SAVEPOINT，也不毒化外层事务。

### 1.1b 只在 Postgres 上才看得到的那个错

占键的第二版用 `rowcount == 1` 判断插入是否落空。SQLite 上全绿；在本地起一个
Postgres 16 跑同一组测试，**连单独一笔充值都是 409**——psycopg 驱动下这条 ORM 插入
报回来的 rowcount 不是 1，于是每一笔都被当成「别人先占了」。照那样上线，
**生产上的充值与提现会全部失败**。改成 `RETURNING id`：有行回来才算占到。

这件事的教训比修法重要：**资金并发这组测试只在 SQLite 上跑，等于没在生产引擎上跑。**
CI 的 Postgres job 现在单独起一个库跑这三个文件（`test_idempotency_concurrency` /
`test_money_duplicate_protection` / `test_idempotency_fingerprint`），并有一条闸门
钉住那一步在、且没有 `|| true`。

### 1.2 过期（FIN-071）

`PLATFORM_IDEMPOTENCY_RETENTION_HOURS`，默认 24（Stripe 的语义）。两端在「这一次操作」
得到确定结果之前一直用同一个键，之后换新键——重试发生在几秒到几分钟内，不会跨天。

**过期在读的时候就生效**：`replay_or_run` 读到过期记录就删掉、把这个键当新的用。
清理 job（`/wallet/jobs/purge-idempotency`，一天一次，单实例锁）只负责让表不无限增长——
它晚跑、漏跑，语义都不变。

### 1.3 键的长度与强制（FIN-073 服务端那半）

- 充值与提现**不带键 → 400 `idempotency_required`**；超过 80 个字符 → 400
  `idempotency_key_invalid`（不再截断）。
- 强制之后，一个忘了带键的新客户端会在开发时就拿到 400，而不是上线后悄悄地把双击
  变成两笔充值。

## 2. 两端：一次操作一个键（FIN-073 客户端那半）

共享 SDK 新增 `OperationKey`，两端各个资金按钮各持有一把：

| 情况 | 键 |
|---|---|
| 网络断了、超时、5xx、`idempotency_in_progress` | **保留**——请求可能已经到了，下一次点击是重试，服务端回放 |
| 成功，或服务端明确拒绝（4xx） | **换新**——下一次是新操作 |
| 用户改了金额 | **换新**——那是另一件事；否则会撞上 `idempotency_key_conflict`，那句话是写给开发者的 |
| 双击 | 两下读到的是同一个键（换键发生在结果回来之后）→ 服务端回放第一下 |

`topup` / `withdraw` 的键是**必填参数**：漏传在 TypeScript 里就编译不过。
键生成优先 `crypto.randomUUID`，React Native 的 Hermes 上没有时退回 `Math.random`——
键按用户隔离，它要的是不撞，不是不可猜。

## 3. 闸门

| 闸门 | 内容 |
|---|---|
| FIN-072a | 6 个线程同键充值：全部 200、同一个订单号、只入账一次 |
| FIN-072b | 5 个线程同键提现：全部 200、只扣一次 |
| FIN-072c | 结构：占键在 `run()` 之前；用 `ON CONFLICT`；**不用 SAVEPOINT** |
| 长度 | 81 个字符被拒且没动钱；80 个字符的键能回放 |
| FIN-073a | 充值与提现不带键 → 400 且没动钱 |
| FIN-073b | 失败不缓存：余额不足被拒后，同键重试**真的提现了**（只看状态码不够——被缓存的东西也可能以 200 回放） |
| FIN-071a | 保留期内回放；过期后（清理 job 还没跑）当作新键 |
| FIN-071b | 清理只删过期的；在调度表里；要 job 令牌 |
| 99 号表 | 「靠幂等键」的资金接口必须走 `require_key`（强制），不只是接了这个头 |
| SDK | 键格式与唯一性（含没有 `crypto` 的退路）；`OperationKey` 四种情况；两个方法把键放进请求头 |
| 两端 | 网络断了再点 → 同一个键；成功后再点 → 新键；（web）改金额 → 新键 |
| Postgres | CI 的 Postgres job 单独建库跑这组测试；本地 Postgres 16 上三轮全绿；全链路验收在 Postgres 上跑了六轮 |
| 联调 | 真浏览器在真服务端上充值成功（服务端对不带键的请求直接 400，所以这一步走通就证明构建产物真的带着键） |
| 脚本 | 冒烟、全链路验收（新增「不带幂等键的充值被拒」）、沙箱自检、恢复演练、演示数据都带键，前三个实跑通过 |

**红验**：服务端六条（退回先跑再记 / 不强制 / 读时不判过期 / 清理不看时间 / 截断长键 /
占位先提交）、客户端五条（网络错误也换键 / 金额变了不换键 / 每次点击现生成键 / 成功后不换键 /
App 失败后也换键）、联调一条（构建产物不带键）——都红。

红验里两条探针是坏的，记下来：一条把 `"{}"` 写进占位——请求失败时整个事务回滚，什么也没缓存，
它测的不是「失败被缓存」；另一条在独立会话里提交失败结果，在 SQLite 上与主事务互等写锁死锁。
**但第一条暴露了测试本身的弱点**：如果失败真的以 `{}` 被缓存并以 200 回放，只看状态码的
断言会是绿的——所以补了「钱真的出去了」。真实的回归形态（占位先提交，即第一版的 SAVEPOINT 行为）
另用一条变异钉住，三条红。

## 4. 这一批没做的

- **4xx 不缓存**与 Stripe 不同（Stripe 缓存 4xx 结果）。这里选择不缓存：余额不足被拒之后
  充了值再用同一个键重试，用户的意图就是「再试一次」，回放旧的拒绝是错的。两端在 4xx 后
  本来就会换新键，这个差别只影响直接调 API 的人。
- **开放 API 的机器写操作**有自己的幂等表（`MachineAction`），它先取 API Key 行锁再查，
  并发同键是串行的、不会 500；它的记录同时是审计日志，**不过期是有意的**，不在本批清理范围内。
- **在 Postgres 上跑全链路验收时撞见的另一件事**：六轮里有一轮「注销后登录态失效」红了——
  注销返回 200 之后紧接着的请求仍然通过了鉴权。病因不在本批：FastAPI 0.142 里 `yield`
  依赖的收尾代码（`get_db` 的 `commit()`）**默认在响应发出之后才执行**，客户端可能在提交
  之前就拿到 200 并发出下一个请求；提交若失败，客户端已经被告知成功了。这对钱是同一类问题
  （「充值成功」先于入账提交送达）。记台账 `CONC-070`，下一批（V131）单独修。
