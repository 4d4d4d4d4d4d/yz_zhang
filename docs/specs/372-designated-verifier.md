
# 372 发单人点名核验人（VER-050）

> 状态：本批实现（V399）。编号 VER-050。
> 来源：台账 VER-050「核验人是发布方挑还是平台派单，只做了平台派」（欠）；BACKLOG V399。
> 只增不减：
> - `verification_orders` 多一列 `designated_verifier_id`（迁移 `c1d220260093`，SQLite 与 Postgres 都 `upgrade head && check` 过）；
> - `POST /tasks/{id}/verification` 多认一个可选请求体 `{verifier_id}`。
> 不点名的与原来完全一样：升级的单平台付、平台派；主动申请的发单人付、平台派。

## 0. 要解决的问题

AI 执行的任务没把握时，要转人工核验（49 号）。原来只有一种派法：
- 平台把单子挂出来；
- 有资格的人来接：实名、信用分够、在这个类目有完成记录。

行业项目里，发单人往往有自己信得过的懂行的人：
- 公司里的工程师；
- 合作多年的顾问；
- 认识的老师傅。

平台派来的陌生人，他未必认；他认的人，在平台上又可能没有这个类目的完成记录，接不了。

## 1. 业界怎么做

审稿与代码评审工具都允许「指定评审人」，同时保留「由系统分配」。指定的评审人仍受利益冲突规则约束，比如不能评自己的提交。这是常见的公开产品做法，本轮没有引用外部链接。

## 2. 规则

| 项 | 规则 | 为什么 |
|---|---|---|
| 谁能点名 | 只有发单人，在申请人工核验时点名 | 与原来「仅发布方可发起核验」同一条 |
| 谁付钱 | 点名了就由发单人付，trigger 记为 `designated`；置信度不足升级的单也一样 | 平台付费的单如果任由发单人点人，等于拿平台的钱给熟人发报酬 |
| 被点名的人要满足什么 | 不是 AI、实名、没被封、不是本单当事人、不是付费方、信用分够 | 这些是安全底线，一条不少 |
| 免哪一条 | 「本类目完成记录」 | 发单人替他担保懂行；这正是点名的意义 |
| 谁能接 | 只有被点名的人；别人的核验台看不到这一单，硬接 403 `verifier_not_designated` | 看不到，也就不泄露是谁家的单 |
| 通知 | 被点名的人收到「有人点名请你核验」，写明报酬和截止 | 不通知的话，对方根本不知道有这单 |
| 没接怎么办 | 走原来的截止退回：截止前没接，自动退回给发单人 | 不新增机制 |

点名时当场就查一遍资格。查不过的，返回 400 `verifier_not_eligible` 并写明原因（比如「需先完成实名认证」），别等对方来接才发现接不了。编号不存在返回 404 `verifier_not_found`。

单一判断来源：接单端点、可接列表、点名时的预查，都读 `verifier_block` 这一个函数。

## 3. 接口

- **`POST /tasks/{id}/verification`**，请求体可选 `{verifier_id: 正整数}`，`extra=forbid`；
- **响应**：多 `designated_verifier_id`；
- **`GET /verification-orders`**：点名了别人的单不出现；
- **`POST /verification-orders/{id}/claim`**：点名了别人的单 403。

## 4. 两端

- **SDK**：
  - `requestVerification(taskId, verifierId?)`：不传与原来一样不带请求体；
  - 类型多一个字段；
  - `parseVerifierId`：空着是不点名，正整数是编号，其他算填错；
  - `verifyTriggerLabel`：三种来路说清谁付费；
  - `DESIGNATE_VERIFIER_HINT`；
  - 两个新错误码进 i18n。
- **Web 任务详情的 AI 助理面板**：
  - 「申请人工核验」旁多一个「点名核验人（用户编号，可不填）」输入框，下面一句说明：只有他能接，核验费由你付，对方要实名、不是当事人；
  - 乱填不发请求，说清怎么填。
- **Web 核验台**：点名来的单写「发布方点名请你核验（发布方付费）」。
- **App 任务详情的 AI 助理块**：同样的输入框与说明。

## 5. 隐私、授权与边界

- 点名用的是用户编号，不暴露手机号。
- 点名的单只有被点名的人看得到；任务详情与 AI 产出，仍然只有发单人与接单的核验人能看（原有授权不变）。
- 防刷：点名了就自己付钱，不能用平台的钱给熟人发报酬。
