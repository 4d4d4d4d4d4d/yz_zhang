# 70 算得很清楚的钱，没有人能动（SC-007 / SC-004 / GEO-021 / TASK-065）

> 「加了两个房间，多给你 100」——这句话在这个产品里没有任何地方可以落地。

## 0. 探针

V93 清了「两端都没人调用」名单里危及人身与账号的那几条，剩下约 95 条
如实记成了缺口。这一批回到那份名单，挑出**直接动钱或关乎举证**的：

```
proposeChange      web=0 app=0
acceptChange       web=0 app=0
rejectChangeOrder  web=0 app=0
defineMilestones   web=0 app=0
checkin            web=0 app=0
myApplications     web=0 app=0
exportEvidence     web=0 app=0
```

服务端逐条实测——**全都是通的**：

```
PROPOSE CHANGE: 201 {"id":1,"status":"pending","new_amount_cents":30000}
ACCEPT CHANGE : 200 {... "amount_cents":30000 ...}       ← 差额自动补托管
CHECKIN       : 400 {"code":"too_far","message":"距任务地点 4205 米，超出打卡范围"}
MY APPLICATIONS: 200 [{"application_id":1,"task_id":2,"status":"pending", ...}]
DEFINE MILESTONES(已签): 409 {"code":"milestones_locked", ...}
```

## 1. 变更单：三层都缺，不只是缺个按钮

`SC-007` 变更单是这里面最重的一条。服务端做得很完整——改价、差额
**多退少补**、版本 +1、任务预算同步，而且有资金守恒测试（`test_change_order_money`
跑多轮随机改价）。但整条路对用户不存在，而且缺的**不只是按钮**：

| 层 | 状态 |
|---|---|
| 提案 / 接受 / 拒绝的**入口** | 两端都没有（V91 那类缺陷） |
| **列出**变更单的接口 | **服务端根本没有**。对方拿不到 `order_id`，就算有按钮也点不了 |
| **通知**对方有变更单待处理 | 没有（V92 那类缺陷：没有人被告知） |

三层是叠在一起的：**只补按钮不补列表，按钮点不了；补了列表不补通知，
没人知道该去看。** 这一批三层一起补。

没有变更单的实际后果：任务范围一变，双方只剩两条路——
取消（要按违约规则算补偿）或发起纠纷。**一件本该是「好商量」的事，
产品逼着他们走对抗路径。**

## 2. SC-004 分期：定义窗口只在双签前，而没有任何端能定义

成交时服务端默认建一个「全部交付」的单里程碑，分期要在**双签前**
由发布方重新定义（签署后 `milestones_locked`，得走变更单）。
`defineMilestones` 两端都没人调用——**于是生产环境里每一份合约都只有一期**。

网页上那张里程碑表的渲染条件是 `milestones.length > 1`，
**永远不成立**：分期的交付/验收按钮是一段跑不到的代码。

## 3. 其余三条

- **GEO-021 打卡**：到场留痕带距离校验（探针实测 4205 米被拒）。
  没有入口 ⇒ **到场证据链从来没有产生过一条**。这条只做 App：
  浏览器里的定位在上门场景里没有意义。
- **TASK-065 我的报名**：报完名，用户在产品里找不到自己报过哪些单。
  接口有、分页测过、没有界面。
- **LAW 证据包**：`exportEvidence` 是纠纷当事人自己留底的唯一手段
  （V50 特意做了「诚实标注证明力边界」）。没有入口。

## 4. 客户端不重算准入

变更单谁能接受，服务端已经判了（`not_counterparty`：提案人自己不能接受）。
新的列表接口按 `can_decide` 的老办法把判断算好给客户端
（TEAM-021 / UI-075 立的那条：**第二份实现必然抄漏**）。

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| SC-007 | `GET /contracts/{id}/change-orders` 返回变更单列表，含 `can_decide` |
| SC-007 | 提案后**对方收到通知**；裁决后**提案人收到通知** |
| SC-007 | 两端都能提案、接受、拒绝；接受后金额与托管随之变化且守恒 |
| SC-004 | 双签前发布方能定义分期，合计不等于合约金额时服务端拒绝、理由原样显示 |
| GEO-021 | App 上执行方能打卡，超距时**原样显示服务端的距离与理由** |
| TASK-065 | 两端都能看到「我的报名」 |
| LAW | 纠纷当事人能导出证据包 |
| CLI-075 | 以上能力进 `MUST_BE_REACHABLE`，缺任何一条即红 |

## 6. 这一批没做的

- 变更单只支持**改金额**，不支持改工期/范围描述——服务端本来就只有金额。
  真实的「加了两个房间」通常同时要改工期，这条记下来。
- 分期**只能在双签前**定义。签署后要改仍然只能走变更单（整体改价），
  没有「把第二期拆成两期」这种结构性变更。
- 打卡没有防作弊（模拟定位）。距离校验只是第一层。
- 剩余约 88 个两端都没人调用的 SDK 方法仍未逐条过筛。
