# 46 App 侧视频沉浸流（VID / CNT-014）

> 补 45 号 spec 留下的 PRLX-042：`VideoFeed` 此前只在 Web 上，
> App 侧的沉浸流要用 `expo-av`，属于加依赖，当时没做。

## 0. 这个场景错一次的代价

短视频流最容易做错、而且**错了最致命**的一条是：**同时播多个**。

每个解码中的视频占一份硬件解码器与几十 MB 内存。滑过十条就能把中低端机
打到 OOM 或直接黑屏——而且它不会在开发机上出现，只在用户手里出现。

所以这一批几乎所有设计都围绕一件事：**任何时刻有且只有一个 `<Video>` 在播。**

做到它需要三件事同时成立，缺一件都不够：

1. **按当前页判定 active**：`shouldPlay={index === activeIndex && …}`。
2. **可见性阈值要高**（`itemVisiblePercentThreshold: 90`）。
   阈值低了会在滑动中途短暂判定两条都可见，于是两个视频同时起播——
   这是"看起来做对了但没做对"的典型。
3. **离开页面时显式 `pauseAsync()`**。依赖卸载来停播在快速滑动时不可靠：
   RN 的回收时机不保证，而回收之前它还在解码。

外加虚拟化（`FlatList` + `removeClippedSubviews` + `windowSize={3}`）——
视频比图片吃内存得多，离屏的整棵子树必须卸掉。V70 里 `Discover` 用
`ScrollView` 是可以的（PRLX-043 记着要换），这里**不可以**。

## 1. 与 Web 版同一套判断，不同的实现

| 能力 | Web（V69） | App（本批） | 判断是否一致 |
|---|---|---|---|
| 流量提醒 | `navigator.connection` | `expo-network` | ✅ 取不到就按「可能是流量」 |
| 断点续播 | `localStorage` | `AsyncStorage` | ✅ 存本地、不跟账号跨设备、快看完不记 |
| 倍速 | `playbackRate` | `rate` + `shouldCorrectPitch` | ✅ |
| 上下滑 | 触摸 + 键盘 | `pagingEnabled` + `snapToInterval` | ✅ |

**判断一致、实现不同**是这里的要点：同一条规则在两端各写一遍是必然的
（API 不一样），但**规则本身不能漂**。所以两边的兜底方向也一致——

- 流量：取不到网络类型 → **按蜂窝处理**（代价是用户的钱，往保守一侧倒）。
- 动效：取不到 reduce-motion → 按关闭处理（代价只是少点效果）。

这两条方向相反，依据是**代价落在谁身上**，不是"保守一点总没错"。

## 2. 本批新增的两条判断

### VID-030 自动播放也受「减弱动态效果」约束

V70 把这个开关用在了视差上。**自动播放的运动画面对前庭敏感人群同样是诱因**，
WCAG 也明确要求自动播放可关闭。所以开了开关就不自动播，改成显示一个
「播放」按钮——并且**如实说明原因**（「已按系统设置关闭自动播放」），
因为悄悄不播，用户会以为 App 坏了。

### VID-031 iOS 静音开关不该让沉浸流变哑巴

`expo-av` 默认遵从 iOS 的物理静音开关。对短视频流这是错的默认值：
用户会以为视频坏了。`Audio.setAudioModeAsync({ playsInSilentModeIOS: true })`。

## 3. 条目

- **VID-001/002/003** 有且只有一个在播：active 判定 + 90% 可见阈值 +
  离页显式暂停。
- **VID-004/005** `FlatList` 虚拟化、`removeClippedSubviews`、
  `windowSize={3}`；`pagingEnabled` + `snapToInterval` 一屏一条。
- **VID-010** 流量提醒：`expo-network`，取不到按蜂窝处理，默认不自动播。
- **VID-020/021** 断点续播：`AsyncStorage`，不足 3 秒不记，
  **恢复只做一次**（每次 status 更新都恢复会让播放不停往回跳）。
- **VID-030/031/032** reduce-motion 关闭自动播并说明原因；
  iOS 静音开关不静音；倍速不变调。
- **VID-040** 接入 App「视频」tab。
- **VID-041** 新依赖必须声明在 `app/package.json`。

  这条单独立一项，因为**解析闸门看不见它**：esbuild 不做模块解析，
  少写一个依赖在本环境完全无感，到真机上是「打开就崩」。
  已实测：把 `expo-av` 从 package.json 删掉，这条变红。

## 4. 已知缺口

- **VID-050 三个新依赖都没有真机验证。** `expo-av` / `expo-network` /
  `@react-native-async-storage/async-storage` 都是各自场景的标准选择，
  但本环境装不了也跑不了。**源码断言能保证「写法是对的」，
  保证不了「装上能跑」**——首次真机运行前请先 `npx expo install` 对齐版本。
- **VID-051 没有预加载下一条。** 成熟的沉浸流会预取下一个视频的首段，
  否则每次滑动都要等首帧。但预加载与「只播一个」有张力（预加载也占解码器），
  要做得先想清楚用 `preload` 还是只预热网络连接——本批不做。
- **VID-052 没有封面图。** 视频加载前是黑屏。需要服务端抽首帧（CNT-042），
  依赖转码服务。
- **VID-053 直传上来的视频还没走完审核闭环。** `sign-upload` 会把它标成
  `review`，但没有回调/异步扫描把结果写回（UMOD-050 同源）。
