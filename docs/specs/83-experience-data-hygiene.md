
# 83 经验数据的清洗与累积（KB-060 / KB-061 / VER-060）

> 状态：本批实现（V108）
> 依赖：06 号（AI 知识库）、49 号（人类核验与经验回流）、
> 52 号（协议与个人信息授权）、61 号（经验喂回提示词）

## 0. 探针

「经验数据如何清洗累积」这个问题，先去看它现在**实际**是怎么做的。

两条管线：

1. `task.completed` → `KnowledgeCard`（类目/城市/价格/工期 + 标题）
2. 人工核验结论 → `VerificationLesson` → `lessons_prompt()` → **agent 的系统提示词**

两处的注释都写着脱敏：

```python
class KnowledgeCard(Base):
    """KB-001 闭环任务经验卡（脱敏后的结构化经验）。"""

def _record_lesson(...):
    """脱敏：不写 user_id、不写精确地址、不写金额。"""
```

探针拿一个真实形状的标题跑了一遍：

```
PROBE 落库的 title: 给王芳家搬钢琴 朝阳区幸福小区3号楼502 联系13800138000
PROBE   含手机号: True   含姓名: True   含门牌号: True
PROBE 别的用户读经验卡: 200    别人能读到含手机号的卡: True

PROBE 拼出来的系统提示词：含手机号 True、含姓名 True、含地址 True
```

也就是说：**一个客户的电话与门牌号，(a) 通过经验卡端点给了别的用户，
(b) 通过提示词给了第三方模型。**

这不是数据质量问题。《个人信息保护法》第六条（最小必要）与第十九条
（目的限制）在这里是直接命中的：为了「撮合与履约」收集的地址与电话，
被用到了「训练/提示另一单的 AI」上，还给了不相关的第三人看。

**注释里的「脱敏」，没有任何东西在做。** 这是这一路第六次同一个形状
（V96 的「在管理后台做」、V99 的「必须换人」、V101 的 `can_invoice`、
V103 的 `SUPPORT_SLA_HOURS`、V106 的 eslint 豁免），而这一次的代价
是个人信息。

## 1. 三条处理原则

### KB-060a 最可靠的脱敏是不采集

经验卡的用途是**按类目与城市看价格与工期**。用户打的标题对这个用途没有
必要，而它是这条链上唯一的自由文本。所以不再存它，改存派生值：

```python
title=f"{task.category}·{task.city or '不限城市'}"
```

先问「这个字段为什么在这里」，再问「怎么洗干净」——顺序反过来会洗出
一堆半干净的字段。

### KB-060b 数字整段抹掉，不用日志那种掩码

日志里 `138****8000` 是对的：运维要靠头尾把几条日志对上。
而经验数据的去处是别的用户与第三方模型，**末四位加城市常常已经足够
定位到人**。所以经验侧整段替换。

同一个原因，**行政区留着、小区与门牌抹掉**：价格与工期随地段变，
区是经验里有用的部分；精确到一个小区、一户人家就不是了。

### KB-060c 写入点做，读出点再做一遍

写入点是主防线（不脱敏的路径不存在）。读出点（`lessons_prompt`）再做一遍，
两个理由：

- 库里还有写入点修好之前落下的行；
- 这段文本的去处是第三方模型，**多一道防线的成本是一次正则，
  漏出去的成本是一条个人信息**。

## 2. 姓名：说清楚守得住什么、守不住什么

姓名没法靠正则认出来。这一批的做法是**用平台已知的当事人姓名去替换**
（`party_names()` 取双方的 `real_name` 与昵称）——比写一个「中文姓名识别」
准得多，也不会把「王府井」当成人名。

但它有明确的边界：**核验人自己打的字里出现第三方姓名（「客户李强投诉」），
去不掉**——平台不知道「李强」是谁。

这条边界写成了一条测试（`..._third_party_names_cannot_be_caught`），
理由是：**不能让下一个人以为这里已经完全匿名化了**。那种误解比漏本身
更危险，它会让人放心地把这段文本送到更多地方去。

残余风险的兜法：核验结论**只进模型提示词，不给其他用户看**；
需要更强保证时的路是命名实体识别或者干脆禁止自由文本进提示词，
记在 72 号台账。

## 3. 累积：去重与权重

`lessons_prompt` 此前把查出来的行逐条拼进去。同一个核验人对同类任务
写同一句结论（很常见），拼出来就是三条一样的经验——
**模型会把它当成「这是最重要的一条」**。现在按内容去重（不是按 id）。

同时不再把任务标题带进提示词：类目已经限定了「同类」，标题是这条链上
最脏的一段，而它对「下次别再犯」这个用途没有贡献。

## 4. KB-061 已经落库的那些

写入点修好之后，库里还留着修好之前的行——探针就是在这些行上复现的。
所以有一条**一次性脚本**：

```
python -m scripts.scrub_experience --dry-run   # 先看会改什么
python -m scripts.scrub_experience             # 真的改
```

逐条打印改动：这是动用户数据的脚本，**不留痕的批量改写是最不该有的东西**。

刻意**不做成定时任务**：那会让人以为「脏数据会被自动处理」，从而放心地
继续写脏数据——而真正该拦的是写入点，那里已经有闸门了。

## 5. 闸门

| 闸门 | 内容 |
|---|---|
| KB-060 写入点（AST） | 经验类表的自由文本字段，赋值必须来自 `scrub_text(...)` 或派生值 |
| KB-060 承诺核对（AST） | 函数里**任何地方**（docstring 或注释）写了「脱敏」，函数体内必须有 `scrub_text` |
| KB-060 行为 | 脏标题走完闭环后，库里、别人读到的卡里、**真实 agent 提示词里**都不含个人信息 |
| KB-060 边界 | 不过度脱敏：行政区、金额、城市必须保留（假报警多的脱敏会把经验洗成没用的东西） |
| VER-060 | 同一条经验不重复进提示词 |

第二条是这一批的关键：写入点这次修好了，**下一个人加一个 `note` 字段、
或者再建一张经验表，就又会原样入库**。用 AST 扫构造调用的关键字参数，
而不是正则——正则读不懂「这个参数的值是什么表达式」。

扫注释而不是只扫 docstring，也是被自检逼出来的：第一版只扫 docstring，
自检当场说「只找到 1 个声称脱敏的函数」——因为知识库那一处的承诺
原本就写在**注释**里，而那正是这一批要修的原始案例。

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| KB-060 | 经验卡不存自由文本，标题是派生值，价格与工期仍在 |
| KB-060 | 别的用户从经验卡端点读不到手机号/姓名/小区 |
| KB-060 | 真实 agent 提示词里不含手机号/小区/门牌，而经验内容仍在 |
| KB-060 | 号码整段抹掉（不留末四位）；邮箱、门牌、小区名去掉 |
| KB-060 | 行政区、城市、金额**不被**抹掉 |
| KB-060 | 当事人姓名按平台已知姓名替换；「王府井」这类地名不误伤 |
| KB-060 | 写入点 AST 闸门：新字段绕过脱敏即红 |
| KB-060 | 承诺闸门：注释说脱敏而函数里没有 `scrub_text` 即红 |
| VER-060 | 重复经验只进提示词一次 |
| KB-061 | 一次性脚本能把已落库的行洗干净，且逐条打印 |

## 7. 这一批没做的

- **第三方姓名去不掉**（见第 2 节）。要做得靠 NER，或者把自由文本从
  提示词里彻底去掉——两条都是产品判断，不是一次重构。
- **没有时效**：一年前的价格经验与上周的同权重。`price_reference`
  应当按时间加权或只看近 N 个月，那要先决定 N 是多少（与运营有关）。
- **没有质量过滤**：核验人随手写的「不行」也会进提示词。要过滤得先有
  「什么算一条有用的经验」的判据。
- **经验卡没有去重**：同一个发布方反复发同类任务会积累很多几乎相同的卡，
  拉低 `price_reference` 的代表性。
- 向量索引（KB-011）**没有跟着脱敏重算**：改了 `title` 之后旧向量与
  新文本不对应。现在的向量只用于检索排序，影响可控；真正接上语义检索前
  要重跑一遍 `kb_reindex`。
