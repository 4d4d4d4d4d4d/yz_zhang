# 194 任务详情上给接单的人看需求九项

> 状态：本批实现（V221）。编号 SCN-110。
> 来源：140 号 spec「没做的」——「任务详情上给接单的人看九项……要先想清楚会不会让发布方觉得被公开挑错（措辞与是否只给报名者看）」；191 号第 3 节排序；BACKLOG V221。
> 只增不减：画像接口与其中的 `brief` 字段不变（V166 起就在返回）；任务详情的画像块原有内容不变，只在下面多一段。

## 0. 要解决的问题

V166 起，发布页会按创作类需求的九项（用途、数量、尺寸规格、文件格式、交期、改稿次数、版权授权……）提示发单人还缺什么。但单发出去以后，**接单的人**在任务详情上看不到这份清单。他得自己读说明、自己想到要问「改几次」「版权怎么算」；没想到的，往往做完才发现对不上。

140 号留下的顾虑：直接把「这单缺了什么」亮给所有人看，发单人会觉得被公开挑错。

## 1. 业界怎么做

137 号 spec（创作者场景包）整理过的业界做法是：开工前把范围、交付物、修改次数、版权这几件事问清楚、写进约定。本批不另找外部来源，沿用那一份：同一份数据，**写成接单的人该问的问题**，不写「发单人漏了什么」。

## 2. 数据

无新数据。用 `GET /tasks/{id}/profile` 已有的 `brief`（九项各自写到没有、没写时该问的那句话）。

## 3. 接口

无新接口。共享 SDK 新函数 `briefHint(brief, isCreator)`：

| 谁在看 | 标题 | 每一行 |
|---|---|---|
| 接单的人（不是发单人） | 「说明里没写的 N 项，报名前可以先问问发单人：」 | 「改稿次数：包含几次修改？超出的怎么算（建议走变更单）？」 |
| 发单人自己 | 「创作类需求一般写清九项，已写 X/Y。还可以补：」 | 同上 |

九项都写到、不是创作类、响应不像样（`items` 不是数组）时返回 null，不显示。行数按 `items` 数，不信 `missing` 字段。

## 4. 两端

- **Web** 任务详情「这单的画像」下面多一段「需求九项」；
- **App** 任务详情的画像块下面同样多几行。
- 两端都按「我是不是发单人」换说法。

## 5. 隐私、授权与边界

- 能看画像的人本来就能看到任务说明（公开招募中的单，或者双方），九项是从说明里读出来的，不多公开任何信息。
- 措辞上不写「缺」「漏」「不完整」，写成「报名前可以先问问」；发单人自己看到的仍是「还可以补」。
