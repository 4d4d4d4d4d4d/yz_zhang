# 67 没有人被告知：团队审批的两端沉默，与只有网页看得见的三条线（TEAM-060/061 / APP-069 / CLI-074）

> 平台**强制**审批人写下驳回理由，然后把这段话送给了谁也没有。

## 0. 探针

员工提交一笔超出本月额度的支出，老板驳回并写明理由：

```
REQUEST : 201 {"id":1,"status":"pending","needed_approval":true,
                "reason":"超出你本月额度（额度 ¥100.00，已用 ¥0.00，剩余 ¥100.00），需管理员审批"}
OWNER 收到的通知 : []
DECIDE  : 200 {"id":1,"status":"rejected"}
STAFF 收到的通知 : []
```

两端都是沉默的：

1. **审批人不知道有东西等他批。** 员工的活被卡住，而卡住他的那个人
   从头到尾没被告知。这笔申请可以在那儿躺到下个月。
2. **发起人不知道被驳回了，更不知道为什么。** 而这条最刺眼的是——
   服务端**强制**要求写理由：

   ```python
   if not approve and not reason.strip():
       raise bad_request("驳回必须写明原因", "reason_required")
   ```

   平台认真地把这段话收上来，存进 `decision_reason`，**然后不送给任何人**。
   连 `decide` 的响应里都没有它。发起人只有主动再去拉一次支出列表才看得到。

全仓 37 处 `notify()`，`team` 模块**一处都没有**。

## 1. 「必须写」和「送到了」是两件事

这是 V89 那条的第三次出现：

> V77 强制发布方选知识产权归属，但 `ip_assignment` 不返回——
> **「必须选」和「看得见」是两件事，只做前一件，公平没有兑现。**

V91 是第二次（服务端说「请先绑定收款账户」，而没有任何端能绑）。
这次是：**平台强制收集的一段话，收件人永远看不到。**

强制写理由的立意是对的——不写理由的驳回是权力，不是管理。
但理由的价值全在于**被驳回的人读到它**：他要据此决定是改金额、改用途，
还是去跟老板谈。送不到，这条强制就只是给审批人增加了一道手续。

## 2. TEAM-060 / TEAM-061 补两条通知

| 时点 | 通知谁 | 为什么 |
|---|---|---|
| 提交超额申请 | 该团队的 **owner 与 admin**（发起人自己除外） | 没人知道就没人批；被卡住的是同事的活 |
| 审批完成 | **发起人** | 批了他才知道可以执行；驳回了他要拿到**理由**才知道下一步做什么 |

同时把 `decision_reason` 补进 `decide` 的响应——**让调用方当场就能显示**，
而不是逼它再拉一次列表。

### 这两条**不**进 `MUST_REACH`

V90 立那张表时写死了判定标准：**错过它，用户会失去一个他本可以行使的
权利，或者失去一笔钱。** 审批通知不满足——申请不会因为没人看就作废，
理由也一直躺在支出列表里可查。

把它也塞进必达表很省事，但那正是 V90 警告过的：
**把所有通知都做成不可关，用户会连真正重要的那几条一起屏蔽掉。**
标准写下来是为了用它做减法，不是每次都用来做加法。

## 3. APP-069 三条线的界面，App 上一个都没有

V84 把合作体 / 团队 / 开发者三页做在了网页上。App 至今没有。
于是上面那条新通知在手机上会变成一件更糟的事：
**通知把人叫来了，而他点进去无路可走。**

这正是 V91 APP-066 的教训（V90 的通知指了一条 App 上不存在的路），
所以这一批必须把通知和界面一起做——**先发通知、界面下批再补，
等于先把人叫醒再告诉他没事可做。**

App 侧补三块，挂在「我的」下面（不再加 Tab——七个已经够多了）：

- **团队**：余额、我的月度额度与已用、预算池、申请支出、
  **审批（批准/驳回，驳回必须填理由）**、执行、企业信息与发票状态。
  按钮可用性一律读服务端的 `can_decide` / `invoice_block`，
  客户端不重写判断（**第二份实现必然抄漏**，UI-075 立过）。
- **合作体**：我的合作体、份额、贡献提交与确认、风险揭示。
- **开发者**：API Key（创建只显示一次的明文、轮换、吊销）、
  Webhook（创建、投递记录）。

## 4. CLI-074 闸门：通知里让你做的事，两端都得做得到

V91 立了 `REMEDY_UI`（服务端的「请先 X」→ X 的入口必须存在）。
这一条是它在通知侧的孪生：

```python
NOTICE_ACTIONS = {
    ("team", "支出待审批"): ("decideTeamSpend", ("web", "app"),
                            "通知就是叫他来批的；点进去没有审批入口，这条通知等于白发"),
    ...
}
```

判定标准：**这条通知的正文让收件人去做一件事，那件事就必须在
收到通知的端上做得到。** 不要求收件人做任何事的通知（纯周知）不进表。

APP-066 那条（必达通知指向人工核验）也一并纳入，
它本来就是这条规则的第一个实例，只是当时是手写的单条断言。

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| TEAM-060 | 超额申请提交后，owner 与 admin 收到通知；**发起人自己不收** |
| TEAM-061 | 审批后发起人收到通知；驳回的通知里**带着那段被强制写下的理由** |
| TEAM-061 | `decide` 的响应里有 `decision_reason` |
| TEAM-062 | 这两条**不**进 `MUST_REACH`（可被通知开关关掉），并有测试钉住这个判断 |
| APP-069 | App 上能打开团队、审批支出、看合作体份额、管 API Key 与 Webhook |
| CLI-074 | `NOTICE_ACTIONS` 每条的动作入口在声明的端上都存在 |
| CLI-074 | 扫描器扫不到已知成员时自己先红 |

## 6. 这一批没做的

- **TEAM-063**：申请没有超时与催办。躺三个月也不会有人再被提醒一次。
- **TEAM-064**：通知只发给 owner/admin **全体**，没有轮值或指派。
  团队一大，这就是群发骚扰。
- **APP-070**：App 仍然没有单元测试，CI 只跑 `tsc`；三页的行为由
  Python 扫描闸门与共享 SDK 的类型覆盖，**这不等于在真机上点过一遍**。
- **APP-067/068**：站内信与任务邀约在 App 上仍然缺席。
- 合作体页只做到「看得见 + 提交/确认贡献」，
  分配（`distributeVenture`）仍只在网页上——那一步动钱，
  **界面没做全比做一半更诚实**。
