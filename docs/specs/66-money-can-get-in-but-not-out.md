# 66 钱能进不能出：一个所有端都点不动的提现按钮（PAY-030 / APP-065~066 / CLI-073）

> 本来是去给 App 补三个页面的。补之前先量了一下 App 到底能用到多少能力，
> 量出来的东西比「缺三个页面」严重得多。

## 0. 探针

先量覆盖面：共享 SDK 上 **245 个方法**，Web 用到 135 个，**App 只用到 33 个**，
105 个能力是 Web 独有。Web 独有名单里第一个刺眼的词是 `withdraw`——
App 的钱包页有「充值 ¥100」，**没有提现**。

那 Web 呢？Web 有提现按钮。按下去：

```
WITHDRAW: 400 {"detail":{"code":"no_payout_account","message":"请先绑定收款账户"}}
BIND    : 200 {"bound":true,"kind":"bank","account_no":"6222****0000"}
WITHDRAW2: 200 {"status":"done","available_cents":40000,"payout_ref":"mock-po-..."}
```

提现本身是通的——**前提是先绑收款账户**。而：

```
$ grep -rn "bindPayoutAccount\|getPayoutAccount" web/src app/
（无输出）
```

**全仓没有任何一个客户端调用过绑定收款账户。**

于是完整的结论是：

| 端 | 充值 | 提现 |
|---|---|---|
| Web | 有 | 有按钮，**每一次点击都返回 400**，且没有任何界面能解决这个 400 |
| App | 有 | **连按钮都没有** |

**钱能进，不能出。** 这是整个产品里最严重的一条——它不是某个页面缺失，
是资金闭环缺了返程。而且它对应用商店是另一层风险：
一个能收钱、不能退钱的 App 会被直接打回。

## 1. 这是 V88 的同一个形状，只是这次是钱往外走

V88 修的是「App 上一个每次点击都返回 400 的发布按钮」，当时的结论写成：

> **服务端的「必填」如果没有变成类型上的「必填」，那它只是一句口头约定。**

这一条是它的孪生：**服务端的「请先 X」，如果 X 在客户端没有入口，
那这句话不是提示，是死路。** 用户看到「请先绑定收款账户」，
然后在整个 App 和整个 Web 上找不到任何一处可以绑定。

CLI-064 立过半条规矩：**把服务端给的拦截理由原样显示出来**
（不然用户看到的是一个莫名其妙的报错）。V88 在 App 注销按钮上兑现了它。
但原样显示只是第一半——**第二半是那个理由得有地方去解决**。

## 2. PAY-030 收款账户绑定入口（Web + App）

服务端早就建好了（`PUT /wallet/payout-account`，带 AML 账户聚集检查、
卡号脱敏返回）。要补的只是两个客户端的入口：

- 展示当前绑定状态（`GET`，返回的是脱敏卡号 `6222****0000`——**照此显示，
  不要试图回显完整卡号**，服务端本来就不给）；
- 未绑定时，提现入口旁边直接给绑定表单，而不是让用户自己去翻设置。

## 3. APP-065 App 钱包：提现 + 账单流水

- 提现：金额、绑定状态、以及**大额进人审时的中性提示**——
  服务端返回 `status: "pending_review"` 并带一句中性话术，
  App 要原样显示。**绝不能自己编一句「你的提现触发了风控」**：
  AML-030/031 的 tipping-off 约束是给所有端的，不只给 Web。
- 账单流水（`ledger`）：App 此前钱包页只有三个数字，没有任何一笔流水。
  「余额少了一百块」而看不到为什么，是最容易变成工单的一类问题。
  科目名走共享 SDK 的 `ledgerKindLabel`（V84 立的那条：
  **账本科目与共享 SDK 中文名双向相等**），不在 App 里另写一份中文。

## 4. APP-066 人工核验入口（兑现 V90 刚写下的那句话）

V90 给 AI 交付的待验收通知加了这句：

> 「如需人工把关，可在任务详情页申请人工核验。」

而 `requestVerification` 只在 `web/src/AgentPanel.tsx` 被调用过一次——
**App 的任务详情页没有这个入口**。这条是上一批自己挖的：
必达通知里指了一条路，那条路在一半的端上不存在。

**通知里承诺的动作，必须在收到这条通知的端上做得到。**

## 5. CLI-073 闸门：「请先 X」必须有 X 的入口

补三个入口容易，问题还是**下一条怎么办**。所以照 V90 的办法立表：

```python
REMEDY_UI = {
    # 服务端错误码 -> (能解决它的 SDK 方法, 哪些端必须有, 为什么用户必须能自己解决)
    "no_payout_account": ("bindPayoutAccount", ("web", "app"),
                          "不绑就永远提不出钱，而服务端只会重复说「请先绑定」"),
    "verification_required": ("verifyIdentity", ("web", "app"), "..."),
    ...
}
```

闸门扫描 `web/src/**` 与 `app/*.tsx`，要求每个条目的 SDK 方法在声明的端上
**真的被调用**。值仍然是**理由**而不是 `True`——与 `MUST_REACH` 同一条：
判定标准得写下来，否则半年后没人知道该往表里加什么。

扫描器自己先红：断言它能在已知位置扫到一个已知成员，扫不到就报错，
而不是安静地放行（V82 的教训——**扫不到等于全绿，是最糟的一种绿**）。

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| PAY-030 | Web 与 App 都能绑定收款账户，绑定后提现成功 |
| PAY-030 | 绑定状态显示的是服务端返回的脱敏卡号 |
| APP-065 | App 钱包有提现入口，大额进人审时原样显示中性话术 |
| APP-065 | App 钱包显示账单流水，科目中文名来自共享 SDK |
| APP-066 | App 任务详情能申请人工核验 |
| CLI-073 | `REMEDY_UI` 每条的补救入口在声明的端上都存在 |
| CLI-073 | 扫描器扫不到已知成员时自己先红 |

## 7. 这一批没做的

- **APP-067**：App 仍然没有站内信（`conversations`/`messages`/`sendMessage`）。
  线下服务的执行方要联系发布方，目前只能靠任务描述里的电话。
- **APP-068**：邀约（`myInvitations`/`acceptInvitation`）在 App 上收不到。
- **APP-069**：合作体 / 团队 / 开发者三页仍然只有 Web（原计划的 V91）。
- **APP-070**：App 依然没有单元测试，CI 只跑 `tsc`；本批的 App 行为由
  Python 扫描闸门与共享 SDK 的类型约束覆盖，**这不等于跑过一次真机**。
- 105 个 Web 独有能力里其余的部分没有逐条过筛，只挑了「卡住钱和权利」的。
