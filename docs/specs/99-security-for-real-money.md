
# 99 安全：谁能碰谁的东西（SEC-060~069）

> 状态：**设计，未实现**（已有部分见第 1 节）。
> 依赖：12 号（风控）、31 号（安全事件）、74 号（四眼原则）、
> 98 号（并发与容量）、GO-LIVE.md

## 0. 先说已经有的，再说缺的

不先盘清已有的，这一篇会变成一份把现状说得过于悲观的清单。
逐条量过的已有能力：

| 已有 | 证据 |
|---|---|
| 安全响应头全套 | `app/core/headers.py`：CSP、`X-Content-Type-Options`、`X-Frame-Options: DENY`、`Referrer-Policy`、`Permissions-Policy`、HSTS（生产）；上传下载另有 `default-src 'none'; sandbox` |
| 写路径按 IP 限流 | `WriteRateLimitMiddleware` 兜住「新端点忘了加限流」，并刻意放行安全处置路径——**补救入口不能被它要补救的东西挡住** |
| 跨副本封禁 | V56 把进程内 dict 改成落库（注释此前说落了 DB 而实际没有） |
| 真实人机验证 | V59 端到端打通；且启动拦截「配了会拦人的 provider 却没有 site key」 |
| 大额出款四眼原则 | V99：两个不同管理员先后确认，且二审必须换人（`same_arbiter`） |
| 资金重复保护 | V123（98 号 spec）：声明表 + 真的打两次 |
| 密钥不入库不写日志 | 全仓只从环境变量读；启动拦截默认 `JWT_SECRET` / `JOB_TOKEN` |
| 反代后取真实 IP | 启动拦截 `TRUSTED_PROXY_HOPS` 未设——否则按 IP 的限流与封禁全部失效 |
| 运营动作留审计 | `adminAuditLog`，V98 给了界面，明细带金额 |

**这些不是「安全做完了」。** 它们覆盖的是传输层、速率、与少数高危动作。
缺的那一类恰好是业界列为 API 安全第一位的那个。

## 1. 缺的第一位：对象级授权没有系统性验证（SEC-060）

量出来的数字：

```
/api/v1 端点            292 个
其中带路径参数的        146 个   ← 每一个都可能被换成别人的 id
碰到 403/forbidden 的测试文件  68 个
```

68 个文件里确实有大量越权断言（「仅任务当事人可生成文书」这类），
但**没有任何记账说明这 146 个里哪些做过「换成别人的 id」的验证**。
于是和 V122 的响应形状闸门同一个形状：看起来覆盖了，实际覆盖率无人知晓。

业界把这一类叫 BOLA（Broken Object Level Authorization），
并一致指出它为什么最难被发现：**它返回的是正常的 200 和一份有效数据**——
只检查「有没有报错」的扫描器会直接放过。要验它必须知道「哪个对象属于谁」，
也就是**用两个账号互相去拿对方的东西**。还有一条常被误解的：
把 id 换成 UUID **不解决**这个问题，那只是让枚举变慢。

设计：

| 编号 | 内容 |
|---|---|
| SEC-060 | `OBJECT_SCOPED_ENDPOINTS` 声明表：146 个带参端点逐条写明「这个 id 属于谁」与「谁可以碰」（值是归属规则，不是布尔） |
| SEC-060a | 两账号穷举：对每条可自动构造的端点，用 B 的 token 去拿 A 的对象，断言 403/404 而**不是 200** |
| SEC-060b | 刻意公开的（公开空间、广场任务、类目表）写明理由并豁免——**一个满口假警报的闸门会被人关掉** |
| SEC-060c | 覆盖记账：声明表必须覆盖全部带参端点；新增一个带参端点而没进表 → 红 |
| SEC-060d | 不只测 GET。写路径（PUT/DELETE/POST 子资源）同样要验——**读到别人的数据是泄露，改掉别人的数据是事故** |

实施顺序刻意从**钱与身份**开始：合约、钱包、提现、纠纷、证件影像、
私聊会话。内容类（空间条目、评论）其次。

## 2. 缺的第二位：权限是按角色还是按关系，没有一处写清（SEC-061）

当前授权判断散在各 router 里，形态有三种：

- `user.id not in (task.creator_id, task.executor_id)` → 按**关系**；
- `user.is_admin` → 按**角色**；
- 团队/合作体里按**成员档位**（owner/admin/member）。

三种混用本身没问题，问题是**没有一份总表**说明某个资源的某个动作属于哪一种。
后果很具体：V122 查出 `legalDocument` 要求「仅任务当事人」，
而同一批里 `exportEvidence` 要求「仅纠纷当事人或管理员」——
两者的差别是有意的还是偶然的，读代码读不出来。

| 编号 | 内容 |
|---|---|
| SEC-061 | 授权矩阵：资源 × 动作 × 判据（关系/角色/档位），与代码对账 |
| SEC-061a | 管理员能做的每一件事都要留审计（已有 `adminAuditLog`，缺的是「全覆盖」的闸门） |
| SEC-061b | 「管理员可以读任何人的私聊/证件影像吗」这类问题必须有明确答案并写进矩阵——**沉默等于默认可以** |

SEC-061b 是其中最该先回答的：平台持有证件影像与私聊内容，
而「哪些运营角色在什么条件下能看」如果没有明文，
在合规审计时是答不出来的，在出事时也无法追责。

## 3. 缺的第三位：没有外部视角（SEC-062）

当前所有安全结论都来自**我们自己写的测试**。而自己写的测试只覆盖
自己想到的攻击面——V112 的钱包 500 就是这样：1195 条测试全绿，
而「第一次读一个只读接口」不在任何人的怀疑名单上。

| 编号 | 内容 |
|---|---|
| SEC-062 | 外部渗透测试（上线门槛，`COMMERCIAL-READINESS.md` 已列但未排期） |
| SEC-062a | 依赖漏洞审计接进 CI 并定期复核（10-08 的 npm 报告 90 项含开发依赖，未逐条处置） |
| SEC-062b | 密钥轮换演练：能不能在不停服的情况下换掉 `JWT_SECRET`（现在换掉等于所有人被登出） |

## 4. 还要考虑的几件（设计，按后果排序）

| 编号 | 内容 | 后果 |
|---|---|---|
| SEC-063 | **上传文件的内容校验**：现在靠扩展名与 CSP sandbox，没有魔数校验与病毒扫描 | 平台替用户分发一个恶意文件 |
| SEC-064 | **SSRF**：空间条目是用户提交的外部链接。服务端**刻意不抓取**（88 号 spec 已写明），这条是为了防止将来有人加「预览抓取」时忘了它 | 内网探测 |
| SEC-065 | **日志脱敏**：有没有把手机号、证件号、token 写进日志，没有系统性检查 | 日志成为第二份个人信息库 |
| SEC-066 | **会话与设备**：已有设备会话与改密码，但缺「改密码后旧 token 全部失效」的验证 | 账号被别人继续用 |
| SEC-067 | **越权提权**：`is_admin` 能否被任何用户侧接口写到（创建/更新用户的请求体里） | 任何人变管理员 |
| SEC-068 | **错误信息不泄露内部结构**：统一错误信封已有，但 500 的堆栈在生产是否外露，没验 | 攻击面情报 |

SEC-067 与 V124（`createTask` 接受 `id`/`status` 等服务端不该收的字段，
台账 `SYNC-050b`）是同一类——**请求体多收一个字段的代价，取决于那个字段是什么**。
`status` 是业务错乱，`is_admin` 是整站失守。所以那一批应当连带把
「哪些字段永不接受」做成声明表。

## 5. 商业上线要求

| 要求 | 为什么是门槛 | 状态 |
|---|---|---|
| 对象级授权有覆盖记账 | 业界列为 API 安全第一位，且它返回 200 不报错 | **未做**（SEC-060） |
| 授权矩阵有明文 | 合规审计要答「谁能看证件影像」 | **未做**（SEC-061） |
| 外部渗透测试 | 自己写的测试只覆盖自己想到的 | **未做**（SEC-062） |
| 密钥轮换可执行 | 泄露时要能换，而不是只能停服 | **未做**（SEC-062b） |
| 依赖漏洞逐条处置 | 90 项未处置 | **未做**（SEC-062a） |
| 日志不含个人信息 | PIPL；也是出事后的二次泄露面 | **未做**（SEC-065） |

**这一页上没有一条是「代码写完就算」的。** SEC-060/061 要写声明表并逐条对账，
SEC-062 要外部团队与时间窗口——它们和资金存管、实名供应商一样属于
上线前的工程＋外部资源，不是功能开发。

## 6. 这一篇没做的

- **不做 WAF 规则设计**：网关已有限流，WAF 是部署期选型。
- **不做零信任架构改造**：当前是模块化单体，服务间没有网络边界可谈。
- **不自建漏洞扫描**：用现成工具，别写第二份。
- **不在这一篇里改代码**：它是一份带判据的清单，实施按 SEC-060 → 061 → 062
  的顺序各自成批——**先把「谁能碰谁的东西」数清楚，再谈别的**。
