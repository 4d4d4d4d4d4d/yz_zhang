# 30 · 反洗钱与可疑交易（AML）

> 落地 [25-financial-compliance.md](25-financial-compliance.md) 的 FIN-040。

## 先说清楚现在的洞（已用探针复现）

现有提现风控两条：单日累计限额 ¥5 万、**单笔** ≥¥1 万转人审。

探针跑了一遍：同一个账号连续提现 **5 笔 ¥9,999**——

```
五笔 ¥9999 提现结果： [(200,'done'), (200,'done'), (200,'done'), (200,'done'), (200,'done')]
进入人审的笔数： 0
```

**¥49,995 出账，零人审。** 因为门槛判的是「单笔」，而拆分是绕过单笔门槛
最古老、最简单的手法（structuring / smurfing），恰恰是反洗钱监测的头号目标。

这个洞不需要任何技术手段就能利用：把金额减 1 元，多点几次。

## 30.A 一件必须先说清楚的事

⚖️ **平台不是反洗钱义务主体的全部答案。** 《反洗钱法》与《非银行支付机构
反洗钱和反恐怖融资管理办法》约束的是**金融机构与支付机构**；
本平台接存管后，直接的报送义务在持牌机构一侧。

但这**不等于平台什么都不用做**：

1. 存管机构只看到资金流，**看不到业务语义**——哪笔钱对应哪个任务、
   双方是不是同一个人的马甲、任务是不是虚构的。这些只有平台知道，
   也只有平台能识别。识别出来交给存管方/合规官，是平台该做的部分。
2. 未接存管时（`LEDGER_BACKEND=internal`，生产已被禁），平台自己就是资金
   归集方，风险全在自己身上。
3. 具体阈值、报送格式与频次由监管要求和存管方决定，**代码把它们做成可配置**，
   不写死。

所以本 spec 的定位是：**做平台能做且只有平台能做的那部分——
业务语义层面的可疑识别、留痕、转人审、可导出**，
而不是假装能替代持牌机构的报送系统。

## 30.B 阈值判定：从「单笔」改为「累计」（P0）

- **AML-001** 人审门槛按**滚动窗口累计**判定，不再只看单笔。
  单笔 ≥ 大额阈值，**或**当日累计 ≥ 大额阈值，都要转人审。
  这条直接修掉探针复现的洞。
- **AML-002** 阈值可配：`LARGE_WITHDRAW_CENTS`（单笔）、
  `AML_DAILY_REVIEW_CENTS`（当日累计）、`AML_REPORT_CENTS`（大额报告线）。
- **AML-003** ⚠️ 累计判定必须在**同一个钱包锁内**完成。
  并发提现时分别读到「还没超」再各自放行，是这类阈值最经典的绕过方式，
  而它和拆分是同一个洞的两种利用姿势。

## 30.C 可疑形态识别（P0）

代码只识别**平台看得见而存管方看不见**的东西：

- **AML-010 拆分规避（structuring）**：滚动窗口内多笔金额接近但都低于
  单笔门槛。「接近」按阈值的百分比判定，不写死金额。
- **AML-011 快进快出**：充值后短时间内几乎原样提现，中间没有真实成交。
  这是资金过账的典型形态——平台被当成了通道。
- **AML-012 高频对敲**：已有 `is_suspicious_pair`（同一对用户反复成交）。
  本批次把它的产出接进统一的可疑记录，而不是只开一张举报工单。
- **AML-013 收款账户聚集**：多个不同用户绑定同一个收款账户。
  一人多号已由证件号摘要查重拦住，但**收款账户**这一维度此前没人看。
- **AML-014 名单筛查**：`SanctionsProvider` 抽象（制裁/涉恐名单），
  mock + sandbox 两个实现；生产必须接真实名单库。

## 30.D 留痕与报送（P0）

- **AML-020** `SuspiciousActivity` 记录：主体、形态、触发依据（含具体数值）、
  关联交易、状态（待复核/已复核-无问题/已复核-待报送/已报送）。
- **AML-021** **绝不自动对外报送**。报送是合规官的动作，需要人的判断与签字；
  代码只负责识别、留痕、生成可导出的材料。自动报送既不合规也不负责任。
- **AML-022** 管理端可查、可复核、可导出。
- **AML-023 记录保存期**：客户身份资料与交易记录自业务关系结束起保存 **5 年**。
  ⚠️ 这与 [26 号 spec](26-legal-enforceability.md) 的删除权（LAW-032）
  **真实冲突**，且反洗钱法优先——PIPL 第四十七条本身把「法律、行政法规
  另有规定」列为删除义务的例外。注销流程必须如实告知用户哪些数据依法保留。

## 30.E 不得泄露（P0，最容易做错的一条）

- **AML-030** 《反洗钱法》第五条：对依法履行反洗钱职责获得的客户身份资料和
  交易信息应当**予以保密**；提交可疑交易报告的情况**不得泄露**
  （tipping-off）。
- **AML-031** 因此**给用户看的文案必须中性**：提现转人审时只能说
  「该笔提现需人工复核」，**不能**说「因涉嫌可疑交易被标记」。
  同理，可疑记录不得出现在任何面向用户的接口里——包括数据导出
  （LAW-032 的导出权同样让位于此）。
- **AML-032** 这条要有测试盯着：用户可见的响应与导出里**不出现**
  可疑标记、形态名或触发依据。写得再对，一句手滑的错误提示就前功尽弃。

## 30.F 验证（P0）

- **AML-040** **拆分五笔 ¥9,999 → 第 N 笔起转人审**（探针的反面，本 spec 核心）。
- **AML-041** 并发提现下累计阈值不被绕过（同锁内判定）。
- **AML-042** 快进快出被识别并留痕。
- **AML-043** 多用户共用收款账户被识别。
- **AML-044** 可疑记录**不出现在**用户可见响应与数据导出里（不得泄露）。
- **AML-045** 提现转人审的用户提示是中性措辞，不含「可疑」「反洗钱」等字样。
- **AML-046** 可疑记录只有管理员可读；普通用户 403。
- **AML-047** 正常用户的正常提现**不被误伤**——风控做得太紧等于停业。

## 验收标准

- 拆分、快进快出、账户聚集三种最基础的形态都能被识别并留痕；
- 阈值判定在锁内，并发拿不到便宜；
- 任何面向用户的出口都不泄露可疑标记；
- 平台不自动对外报送，只产出供人复核与报送的材料。

## 必须由用户提供（代码无法替代）

- ⚖️ 合规官与内控制度（反洗钱是**制度 + 人**，不是一段代码）
- ⚖️ 与存管方确认的报送口径、阈值与频次
- 制裁/涉恐名单数据源订阅
- 员工反洗钱培训与留档
