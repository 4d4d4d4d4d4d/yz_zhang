
# 324 经验质量过滤

> 状态：本批实现（V351）。编号 KB-063。
> 来源：现状台账 KB-063「经验没有质量过滤：随手写的『不行』也会进提示词」，原记「要先有『什么算一条有用的经验』的判据」；BACKLOG V351（第三十二轮排期，分数 36）。
> 只增不减：核验结论照旧全部入库。核验人写什么、核验流程、脱敏、去重、条数上限、时效（323 号）都不变。只是喂给 agent 前多一道筛。

## 0. 要解决的问题

核验人没通过一单时写的理由，会被拼进下一单同类任务的 agent 系统提示词（VER-051）。随手写的「不行」「不满意」「质量差」也一样进去：

- 对下一单没有指导价值，模型不知道该避免什么；
- 还占掉 5 条名额里的一条，把真正有用的旧经验挤出去；
- 「被判定不通过：不行」这样的句子还会让模型过度保守。

## 1. 业界怎么做

用户反馈与评论系统普遍会过滤「低信息量」内容：太短、只有情绪词、没有具体对象的，不进摘要、不进训练。本批没有另找外部来源。

## 2. 规则

- **判据（什么算一条有用的经验）**：理由或修正方向至少一处说得出「哪里不对」或「怎么改」。具体是：
  - 去掉标点和空白后至少 6 个字（「不行！！！！！」只算 2 个字）；
  - 不在空话表里。空话表包括两类：
    - 短的：「不行」「不满意」「质量差」「重做」「还可以」……
    - 够 6 个字却仍然没说哪里不对的：「做得不好请重做」「完全不符合要求」「不是我想要的」……
- **只筛喂给 agent 的那一步**：从近 12 个月的结论里多取 4 倍候选，筛掉空话后取前 5 条。这样新写的空话不会把有用的旧经验挤出去。
- 理由是空话但修正方向具体的，照样喂。修正方向本身就是经验。

## 3. 数据 / 接口

- 不新增表与接口。
- `verify.service.lesson_useful(reason, revision)`、`LESSON_MIN_CHARS = 6`、`VAGUE_LESSONS`。

## 4. 两端

不涉及界面。核验人写理由的地方不拦：写什么是他的事，筛只发生在喂给模型之前。

## 5. 隐私、授权与边界

只减少喂进第三方模型的文本，不增加。
