# 80 里面那一层也要对上（CLI-071 / CLI-072）

> 状态：本批实现（V105）
> 依赖：60 号（形状对齐闸门）、64 号（声明了却不返回）

## 0. 探针

64 号 spec 自己记着这两条盲区，从 V89 一直挂到现在：

> - **CLI-071**：嵌套对象里的字段类型不比（只比顶层）。`members: Array<{…}>`
>   里面写错仍然抓不到。
> - **CLI-072**：请求体仍然只比字面量对象；透传 patch 的调用跳过。

两条都当场复现。把 `TeamDetail` 里嵌套的两个字段同时改错：

```ts
members: Array<{ user_id: number; role: number; spend_limit_cents: boolean }>
//                                      ^^^^^^               ^^^^^^^
// 服务端返回的是 string 和 number
```

```
15 passed in 14.59s
```

**两个字段都写错，形状闸门全绿。**

请求体那半边：

```
比对了 73 条，跳过 11 条：
  PATCH /users/me                  body=patch
  POST  /tasks                     body=input
  PATCH /tasks/{x}                 body=patch
  POST  /missions                  body=body
  ...
```

闸门报「比对了 73 个请求体」，听起来很齐全，而**另外 11 条从来没人看**。

## 1. CLI-071 嵌套怎么比

`_matches` 此前遇到 `list` 与 `dict` 一律返回 `True`。现在：

- 数组：取出元素类型（`Array<X>` / `X[]`），逐个元素比（只看前 5 个——
  同一列表里的元素形状一致，全比一遍只是更慢）。
- 内联对象：解析成字段表，用**与顶层同一套政策**比三个方向
  （少了声明的必选键 / 多了没声明的键 / 类型对不上）。
  「只查一边的闸门，另一边就是自由的」。
- 具名 interface 作为嵌套类型时，展开它的字段再比。

### 宽容的边界要写清楚

**一个假报警多的闸门会被人关掉**（V80 的教训），所以下面几种一律放过：

| 情况 | 为什么放过 |
|---|---|
| 空数组 | 无从比较 |
| `Record<string, X>` | 键未知 |
| 解析不出来的具名类型（别名、泛型实例化） | 不猜，那是编译器的活 |
| 超过两层 | 自引用类型会让闸门转不出来——**闸门要能停** |

最后这条不是偷懒：两层已经覆盖这个仓里实际出现的形状
（`Array<{...}>`、`{ wallet: {...} }`），而无限递归遇到自引用会挂。

写这一条时**我自己的测试抓到了我自己的假警报**：`Array<SomeAlias>`
里那个别名解析不出来，第一版会因此报错——正是我刚在上面写下要避免的东西。

## 2. CLI-072 请求体是变量时，类型标注就是契约

那 11 条被跳过的 body 都是参数名，而**参数都有类型标注**：

```ts
editTask(id: number, patch: Partial<{
  title: string; description: string; budget_cents: number; ...
}>)
```

所以能比：**SDK 可能发出去的每个键，必须是服务端 schema 认的**。
这正是 V82 那个 `addCertification` 的形状（SDK 发的键服务端不认，调用必 422）。

解析器认四种写法：内联 `{...}`、`Partial<...>`、`Pick<Iface, 'a' | 'b'>`、
具名 interface。结果：**11 条里 9 条现在真的在比**，剩下 2 条进声明表：

| 路由 | 为什么解析不了 |
|---|---|
| `POST /tasks` | 参数是 `Partial<Task> & {...}`，比创建 schema 宽得多（`id` / `status` / `created_at` 都在里面），逐键比会是一堆假警报 |
| `POST /tasks/{x}/applications` | 请求体里有条件展开（`...(bidCents ? { bid_cents } : {})`），静态读不出稳定键集合 |

第一条顺手暴露了一个真问题：**`Partial<Task>` 让调用方可以传 `id`、`status`
这些服务端不该接受的字段**。这不是闸门该用假警报去逼的事，是 SDK 的签名
该收窄——记进 72 号台账的 `SYNC-050` 那条线。

## 3. 验收点

| 编号 | 验收点 |
|---|---|
| CLI-071 | 数组元素里的类型写错 → 红 |
| CLI-071 | 嵌套对象少了必选键 / 多了没声明的键 → 都红 |
| CLI-071 | 空数组 / `Record<>` / 解析不了的别名 / 超两层 → 放过（不报假警报） |
| CLI-071 | 切分不许切进括号里（`Array<{ a; b }>; c` 不能被 `;` 切开） |
| CLI-072 | 变量请求体用参数的类型标注比，可能发出的键必须被服务端认 |
| CLI-072 | 解析不了的必须在声明表里写明理由；表里不许留已不存在的路由 |

## 4. 这一批没做的

- **必填项没法从 patch 类型推**：`Partial<{...}>` 里一切都是可选的，
  所以这条闸门只查「多发」不查「漏发」。漏发要么靠字面量那条闸门
  （73 条已覆盖），要么靠端到端测试。
- **`Partial<Task>` 的签名没收窄**：那是行为变更（会让现有调用方编译报错），
  该单独一批做，记在台账里。
- 嵌套比较**只到两层**，更深的形状仍然放过。
- 没有从 OpenAPI **生成** TS 类型。64 号当时判断「要比就得真正解析 TS 类型
  表达式，到那一步不如从 OpenAPI 生成」——这一批证明了中间还有一档
  （一层半的解析器足够抓住实际发生的漂移），生成那条路依然值得做，
  但它会改变类型的写法与审阅方式，属于另一批。
