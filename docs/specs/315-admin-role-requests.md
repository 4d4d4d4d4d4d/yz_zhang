
# 315 临时提权的申请与审批流

> 状态：本批实现（V342）。编号 SEC-061i。
> 来源：171 号 spec「没做的」——「临时提权的申请与审批流：现在由超级管理员直接给；更严的做法是本人申请、另一位超级管理员批」；BACKLOG V342。
> 只增不减：超级管理员直接临时授予、提前收回、整组设置角色都照旧（规则抽成一份共用，行为与审计一字不变）；只多一条「申请 → 批准 / 驳回」的路。

## 0. 要解决的问题

临时角色（V198）只能由超级管理员主动给：要用的人没有地方说「我需要什么、为什么、要多久」，只能私下找人；给的人也留不下一条「谁要的、谁批的」的记录。

## 1. 业界怎么做

特权访问管理（PAM）的即时提权普遍是「本人发起申请、写明理由与时长 → 审批人批准 → 限时生效 → 到点自动收回」，申请人不能自己批（与 171 号「即时 / 限时提权」同一出处的做法）。（本批没有另找外部来源。）

## 2. 规则

- 任何管理员都能申请临时角色：角色、时长（1~720 小时）、理由；规则与直接授予相同——不能申请超级管理员、要至少有一个长期角色、已经长期有的不能申请。同一角色有一条待批的就不能再申请（409 `role_request_pending`）。提交后通知每一位超级管理员（不通知别的管理员）。
- 超级管理员看全部（待批的在前，再加最近处理过的 20 条），其他管理员只看自己的。
- **批准**：只有超级管理员；**不能批自己的申请**（403 `role_request_self`）；批的那一刻**再按规则查一遍**（申请之后可能已经长期给了）；然后走与直接授予同一份逻辑——从批准时起算时长，审计写「申请 #N：理由」，通知本人。
- **驳回**：只有超级管理员，要写理由（2 字以上），通知申请人。处理过的不能再处理（409 `role_request_decided`）。

## 3. 数据 / 接口

- 新表 `admin_role_requests`（迁移 c1d220260079，SQLite 与 Postgres 都验过）。
- `POST /admin/role-requests`（任何管理员）、`GET /admin/role-requests`（任何管理员，按身份过滤）、`POST /admin/role-requests/{id}/approve`（超级管理员）、`POST /admin/role-requests/{id}/reject`（超级管理员）；都登记进角色表与后台入口表。
- 共享 SDK：`AdminRoleRequest`、`requestTemporaryAdminRole` / `adminRoleRequests` / `approveAdminRoleRequest` / `rejectAdminRoleRequest`；三个新错误码进 i18n。

## 4. 两端

- **Web 后台「管理员与角色」**：不是超级管理员的多「临时角色申请」：选角色（只列自己没有的、不含超级管理员）、小时数、理由，写了理由才能提交；下面列自己的申请与状态。超级管理员看到待批的申请，「批准」「驳回」（问理由）。
- **App**：没有管理后台，不涉及。

## 5. 隐私、授权与边界

动权限的批准与驳回只给超级管理员；申请与列表对所有管理员开放但只看自己的；全程进审计（申请、批准即授予、驳回各一条）。
