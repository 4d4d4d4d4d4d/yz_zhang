# 48 平台自有 Agent 的执行层（AGT）

> 缺口来自需求回顾：产品定位是「AI 驱动的任务协作平台」，但实测下来
> **LLM 只用在「拆解」一个点上**——`orchestrator/service.py:52` 里唯一的
> tool 是 `publish_task`，也就是编排器只会把活派给**人**。
> 「调用特定领域 agent」这一项，代码里一行都没有。
>
> 约束（用户确认）：**agent 是平台自有的，平台买特定 API 接口**。
> 不做第三方 agent 市场，没有外部运营者账户。

## 0. 一个必须先定的架构判断：agent 是不是 User

两条路：

- **A 平行实体**：`Agent` 独立建表，独立的接单/结算/评价链路；
- **B 复用 User**：agent 有一行 `User`，照常签合约、进托管、被评价、被封禁。

**选 B。** 理由不是省事——是整套托管、纠纷、信用、账本、风控**全部以
`user_id` 为键**。做成平行实体，等于把它们各写第二遍，而第二遍必然抄漏。
这正是 V58 修过的那个形状：**同一个动作两条路，最常走的那条抄了近道**。

具体：`contract.executor_id`、`wallet_accounts.user_id`、`reviews.ratee_id`、
`disputes` 的当事人、封禁与信用分——**一处都不用改**就对 agent 生效。

代价是 `users` 表多一类行。用 `is_agent` 标记，并在所有「人」的语义处
显式排除（见 AGT-018）。这个代价是可控的、明摆着的；平行实体的代价是
**隐性的、要靠记得**。

## 1. 平台自有带来的三个确定性

因为 agent 是平台的，不是第三方的，三件在 marketplace 模式下很难办的事
直接变简单：

| 事 | 第三方 agent 市场 | 平台自有（本方案） |
|---|---|---|
| **责任主体** | 运营者？平台？要分层协议 | **就是平台**，写进合同条款 |
| **收益去向** | 分给运营者，要做提现与开票 | 归集到平台账户 |
| **成本** | 运营者自负，平台看不见 | **平台买 API，成本可落库** |

第三条是这一批一个被动的好处：**毛利可算**。

```
单次毛利 = 任务收入 − 这次调用的 API 成本
```

没有这个数字，「让 agent 接单」到底是赚是赔，谁也说不清。所以
`AgentRun.cost_cents` 是必填字段，不是可选的观测指标。

## 2. 硬约束：不做这几条，agent 会去接它接不了的活

### AGT-010 只能接远程任务

`task.is_remote` 为假的任务，agent **一律不得接**。

这条排在第一位，因为它是最容易忘、后果最直接的一条：平台上有大量
保洁、跑腿、到场维修。这些任务同样有 `category`、同样有预算、同样
在招募中——**没有这条闸门，agent 会报名一个上门保洁单**，然后交付一段文字。

发布方的钱被托管、时间被浪费、最后走纠纷退款。一次就够毁信任。

### AGT-011 领域必须命中

`task.category` 必须在 `agent.domains` 里。agent 是「特定知识领域的」，
一个法律 agent 不该去接代码任务——它会输出看起来像那么回事的东西，
而这比明确拒绝更坏。

### AGT-012 预算上限

`task.budget_cents > agent.max_task_budget_cents` 拒绝接单。

理由是**赔付能力**：agent 搞砸一个 200 元的文案任务，平台退款认栽；
搞砸一个 5 万元的项目，损失的不只是钱。高价值任务应当由人来做，
或者至少由人来核验（这是 V74 的事）。

### AGT-013 置信度低于阈值不许交付

每次 run **必须**上报 `confidence_bps`。低于 `agent.confidence_threshold_bps`
时，run 落 `escalated` 状态，**并且 `deliver` 端点拒绝这个任务的交付**。

这条是整个 agent 层的安全阀。一个不报置信度、或者报了但没人拦的 agent，
和一个总是说「我做完了」的执行者没有区别。

> 注意这条的**失败方向**：拿不到置信度时按**最低**处理（即必然升级），
> 不按最高。与流量提醒那条同向——代价落在别人身上时，往保守一侧倒。

V74 会把 `escalated` 接到人类专家核验上。**这一批先把闸门建起来，
但不建一条没有出口的死路**：升级后发布方可以取消合约走既有退款链路，
不会把钱卡住。

### AGT-014 同一任务同时只能有一个 run 在跑

重复触发不重复扣费、不产生两份交付。用「该任务是否存在 running 的 run」
做并发闸，而不是靠前端不让点两次。

### AGT-015 失败不假装成功

LLM 不可用（无 Key / 超时 / 输出不合规）时，run 落 `failed` 并记下错误，
**不产出一份空交付、也不降级成模板**。

这里与任务分解的处理**故意不同**：分解失败降级到模板是合理的，模板分解
仍然有用、且发布方会自己看一眼再确认。而**交付物降级成模板就是拿废品
换钱**。同一个「降级」二字，在两个场景里的正确答案相反。

### AGT-016 成本必须落库

见第 1 节。`cost_cents` 由 provider 返回或按配置估算，**不允许为空**。

### AGT-017 责任主体写进合同条款

合同里加一条：

> 执行方为平台自有 AI 助理「<名称>」，平台为本任务履约的责任主体。

写进**当事人合意**，不是只写在平台规则里——定性写进合同才有对抗力
（与 FIN-022 同一条理由）。

### AGT-030 验收标准必须可判定，而且**不能让 agent 给自己判卷**

需求原话是「测试用例通过什么算验收」。这条抓住了 AI 执行任务与人执行任务
最本质的区别：**人做的活靠信任与商誉兜底，AI 做的活只能靠客观判据兜底。**

所以任务加结构化验收项 `acceptance_criteria`，每一项有类型：

| 类型 | 判定者 | 例子 |
|---|---|---|
| `auto` | **平台**执行判据 | 输出必须是合法 JSON / 必须包含某字段 / 必须匹配正则 / 长度区间 |
| `manual` | 发布方（或 V74 的人类核验者） | 「文风符合品牌调性」 |

**关键判断：`auto` 项由平台判，不由 agent 自报。**

这条不这样做，整个机制就是空的——让执行者自己声明「我通过了验收」，
和让它自己声明「我很有信心」是同一种无效。置信度（AGT-013）已经是
自报的了，正因为自报才需要一个**独立的客观闸门**压在它上面。

判据的执行放在平台侧 `agent/criteria.py`，agent 拿不到判据的实现，
只拿到任务描述。

### AGT-031 全部 `auto` 判据通过，才允许提交交付

任一 `auto` 项不通过 → run 落 `failed`，**`deliver` 端点拒绝**，
并把逐项结果落库给发布方看。

`manual` 项不阻断交付，但会原样带进验收界面，让发布方逐条看着勾——
把「怎样算做完」在**开工前**讲清楚，比事后争议便宜得多
（这条判断沿用 AIO-001，只是从 mission 推广到 task）。

### AGT-032 争议升级阶梯：客服 → 纠纷 → 法务

需求原话是「靠客服纠纷，再不行法务」。三级在代码里**都已经存在**，
但它们是三个互不相识的模块——`support/`（工单）、`dispute/`（纠纷）、
`legal/`（协议与法律文书）之间**没有任何一条路把用户从一级送到下一级**。

这一批把阶梯连起来，并明确每一级的入口、时限与出口：

| 级 | 入口 | 时限 | 出口 |
|---|---|---|---|
| 0 自助 | `support.ask` 知识库问答 | 即时 | 解决 / 转工单 |
| 1 客服 | `support` 工单 | `SUPPORT_SLA_HOURS` | 解决 / **转纠纷** |
| 2 纠纷 | `dispute` 两造兼听 + 裁决 | 答辩期 + 裁决期 | 裁决自动执行 / **申诉** |
| 3 法务 | 申诉复核 + 仲裁/诉讼指引 | — | 出具争议处理报告与存证 |

**新增的是「转」这个动作本身**：工单转纠纷时要把工单上下文带过去
（否则用户要把话重说一遍），纠纷升法务时要能导出完整证据链
（合同全文哈希、签署留痕、交付记录、逐条验收结果、agent 的 run 记录）。

**agent 任务在这条阶梯上没有豁免**：平台是责任主体（AGT-017），
被诉的就是平台自己。这一点必须在代码里成立，不能只写在文档里——
所以测试要验证「针对 agent 执行的任务能正常开纠纷并走到裁决」。

### AGT-018 agent 不进普通推荐池

`matching.recommend()` 的召回条件是「实名 + 开启接单 + 非发布者」。
agent 会全部满足，于是**每一个保洁单的推荐列表里都会出现 AI 助理**。

召回处显式排除 `is_agent`，只在任务满足 AGT-010/011/012 时才把匹配的
agent 追加进候选。

### AGT-019 收入归集到平台账户

验收放款走既有链路进 agent 的钱包，再由 `transfer(kind="agent_payout")`
归集到平台账户。**不为 agent 另开一条放款路径**——那是 AGT 这一批最容易
破坏既有五条资金不变量的地方。

新增两个账本科目 `agent_payout_in` / `agent_payout_out`，按 SYNC-002
必须同时在 `LEDGER_KINDS` 与 SDK 文案表里声明，否则 CI 红。

## 3. 数据模型

```python
class AgentProfile(Base):          # 一个 agent = 一行 User + 一行 profile
    user_id: PK                    # 指向 users.id，is_agent=True
    name / domains(JSON) / model / system_prompt
    cost_per_run_cents             # 平台买 API 的单次估算成本
    max_task_budget_cents          # AGT-012
    confidence_threshold_bps       # AGT-013
    is_active
    runs_total / runs_succeeded / runs_escalated / runs_failed

class AgentRun(Base):
    id / agent_user_id / task_id / contract_id
    status                         # running / succeeded / escalated / failed
    confidence_bps / output(Text) / cost_cents / error
    created_at / finished_at
```

## 4. 端点

| 端点 | 权限 | 说明 |
|---|---|---|
| `POST /admin/agents` | admin | 注册平台 agent（自动建 User 行） |
| `GET /admin/agents` | admin | 列表，带**累计毛利** |
| `PATCH /admin/agents/{uid}` | admin | 停用/改阈值/改上限 |
| `GET /agents` | 登录 | 用户可见的 agent 目录（不含 prompt 与成本） |
| `POST /tasks/{id}/agent-apply` | 发布方 | 让匹配的 agent 报名（走既有 Application） |
| `POST /tasks/{id}/agent-run` | 发布方/系统 | 成交后触发执行 |
| `GET /tasks/{id}/agent-runs` | 当事人 | 执行记录与置信度 |

**`agent-apply` 由发布方主动触发**，不自动派单。理由：让 AI 接自己的活
是一个需要知情的选择，静默派单等于替用户做主。

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| AGT-010 | 非远程任务 agent 报名被拒 |
| AGT-011 | 类目不在 domains 里被拒 |
| AGT-012 | 预算超上限被拒 |
| AGT-013 | 置信度低于阈值 → run=escalated 且 deliver 被拒；升级后仍可取消退款 |
| AGT-014 | 同一任务并发触发只跑一个 run |
| AGT-015 | LLM 抛异常 → run=failed，不产出交付、不降级模板 |
| AGT-016 | 每条成功的 run 都有非零 cost_cents |
| AGT-017 | 合同条款含责任主体声明 |
| AGT-018 | 保洁类到场任务的推荐列表里不出现 agent |
| AGT-019 | 放款后 agent 钱包归零、平台账户进账，五条资金不变量仍成立 |
| AGT-020 | agent 走完整合约链路（报名→选人→签约→托管→交付→验收） |
| AGT-030 | `auto` 判据由平台执行；agent 自报通过但判据不过时仍然失败 |
| AGT-031 | 任一 `auto` 判据不过 → deliver 被拒，逐项结果对发布方可见 |
| AGT-032 | 工单可转纠纷并带上下文；纠纷可导出完整证据链；agent 任务能正常开纠纷 |

## 6. 这一批没做的（明确记账）

- **AGT-050**：`escalated` 目前只是「拦住 + 可退款」，**没有接到人类专家**。
  核验单任务类型、置信度→专家路由、核验结果回流经验库是 V74。
- **AGT-051**：agent 产出**不过内容审核**。`files` 与 `task` 都接了 moderation，
  agent 的 output 没接——这是 V64 那个洞的同一个形状，本批先记下。
- **AGT-052**：成本是**按配置估算**，不是从 provider 返回的真实用量。
  真实用量要等接到具体 API 的 usage 字段。毛利数字因此是估算。
- **AGT-053**：没有 agent 之间的编排（一个任务串多个领域 agent）。
  `orchestrator` 的 tool 仍然只有 `publish_task`，把 `run_agent` 加进去
  是下一层的事。
- **AGT-054**：`decompose/llm.py` 里写死的模型标识 `claude-opus-4-8` 已过时，
  本批统一改为可配置并更新默认值。
