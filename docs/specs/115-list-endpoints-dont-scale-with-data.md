
# 115 列表接口的查询次数不随数据量增长（CONC-066）

> 状态：本批实现（V140）。设计见 [111 号](111-audit-industry-and-remaining-design.md) 第 4.3 节。
> 容量证明（CONC-062）不在本批：留在台账，商业上线前在真实 Postgres 上做。

## 0. 怎么查的

此前两次 N+1 都是撞上的（V118 私聊、V128 内容流）。这次系统地查：
`tests/test_list_query_counts.py` 以一个「普通用户」的视角造 k=2 与 k=6 两份世界
（别人的任务、我的报名、收藏、我发的任务与收到的报名、关注、作品、私聊、好友请求、圈层、空间、工单、提现），
对**每一个**不带路径参数的列表 GET 接口各请求一次、用引擎事件数 SQL 条数。
**k=6 比 k=2 多出一条以上就红**；有意随数据量增长的写进 `GROWS_ON_PURPOSE` 并写理由（目前只有 PIPL 数据导出）。
接口清单从 OpenAPI 自动扫，新加的列表接口自动进闸门。

## 1. 查出来的三处

| 接口 | k=2 → k=6 | 原因 | 改法 |
|---|---|---|---|
| `/conversations` | 8 → 20 | `participants` 是 JSON 列表、查不了索引：**把全平台会话读出来在 Python 里挑**；每个会话再各查一次未读、一次最后一条 | 新增 `conversation_members`（按 user_id 索引，flush 事件自动与 participants 对齐，迁移从现有数据回填）；未读一条分组查询、最后一条一条 `max(id)` 子查询 |
| `/conversations/unread-count` | 同上 | 逐会话计数 | 一条聚合 |
| `/contents/mine` | 6 → 14 | 逐条查作者与关注状态 | 复用内容流的 `_ListCtx` 一次取齐 |
| `/circles` | 4 → 10 | 逐个圈查「我在不在里面」 | 一次取齐我在这一页圈里的成员身份 |

改完全部列表接口在 k=2 与 k=6 下条数相同（允许 +1）。

## 2. 闸门与红验

| 闸门 | 红验 |
|---|---|
| 列表接口条数不随 k 增长 | 还原任意一处 → 对应接口出现在红的清单里 |
| 自检：世界不是空的（任务、内容流都有数据，没有 5xx） | 造空世界 → 红 |
| 扫描器能扫到 ≥30 个列表接口 | — |
| 成员表回填：迁移在已有会话上跑，成员行与 participants 一致 | 已在 SQLite 上降级 / 升级验证 |

## 3. 没做的

- **CONC-062 容量证明**：Postgres 上的压测、池等待、三次连跑与 PgBouncer 事务模式配置。
  需要独立的压测环境，留在台账。
- 带路径参数的列表（某个任务的报名、某个会话的消息等）由各自的分页测试覆盖，不在这条扫描里。
