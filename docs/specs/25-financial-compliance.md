# 25 · 资金合规与分账（FIN）

> ## 先说结论：当前实现**不能这样上线**
>
> 现在的形态是「用户充值进平台自建账本 → 平台记账托管 → 平台自行分账放款」。
> 这在国内是明确红线：
>
> - **资金池**：用户的钱沉淀在平台控制的账户里；
> - **二清**：平台在持牌机构与最终收款人之间做了一次「拆分并转付」，
>   属于无证从事支付结算业务。
>
> 账本写得再严谨、不变量校验得再全，都不改变这个定性——
> **问题不在代码质量，在资金的法律路径**。
>
> 本 spec 定义合规形态，以及从现状迁移过去的改造点。
> 标 ⚖️ 的条目**必须有持牌机构与法律意见才能落地**，代码只能把接口留好。

## 25.A 合规形态：平台不碰钱（P0）

唯一合规的资金路径是**钱不经过平台**：

```
付款方 ──→ 持牌机构的存管/备付金账户（资金在此沉淀，平台无支配权）
                │
                └── 平台只发「分账指令」（收款方、金额、事由）
                          │
                          └──→ 持牌机构执行 → 收款方
```

- **FIN-001** ⚖️ 接入**持牌机构的担保交易/资金存管产品**，
  平台角色降级为「交易信息中介 + 分账指令方」。
- **FIN-002** 平台内账本**语义降级**为「指令与对账的镜像」：
  不再是资金的事实来源，而是**与存管方对账的依据**。
  现有整数分账本、只增流水、四不变量全部保留并继续有价值——
  它们从「记我的钱」变成「核对方的钱」。
- **FIN-003** `PaymentProvider` 语义改造（V43 已有接口，需改语义）：
  - `create_charge` → 「发起付款到**存管账户**」，而非平台账户
  - 新增 `split_settle(order_no, splits[])` → 「向存管方下达分账指令」
  - 新增 `query_balance(sub_account)` → 「查询存管子账户余额」
- **FIN-004** 每笔资金变动记录**存管方流水号**，无流水号的账目视为异常并告警。
- **FIN-005** 日终对账：拉取存管方对账文件与本地镜像逐笔核对，
  差错自动生成工单（复用现有 `reconcile` 与差错工单机制）。

## 25.B 分账与分利（P0）

- **FIN-010** 分账指令模型 `SettlementOrder`：
  一笔交易 → 多个收款方（执行者、平台佣金、可能的税费代扣），
  金额之和必须等于订单金额，**整数分、不允许尾差蒸发**。
- **FIN-011** 里程碑分账：现有 `Milestone` 分期改为「每期一条分账指令」，
  按期解冻、按期分账，而不是平台内部搬账。
- **FIN-012** 平台佣金在分账指令中作为**独立收款方**出现，
  由存管方直接划入平台收入户——佣金和用户资金天然隔离，不需要靠代码自律。
- **FIN-013** 退款/取消/纠纷裁决 → **反向分账指令**，同样由存管方执行。
- **FIN-014** ⚖️ 补贴（GRW 优惠券/邀请奖励）出资方是平台自有资金，
  必须走**平台收入户 → 存管账户**的真实划付，不得挪用用户在存管的资金。

## 25.C 分利模式的法律边界（P0，最重要的产品约束）

「早期项目到完成如何分利」在法律上分两类，性质完全不同：

| 模式 | 性质 | 能不能做 |
|---|---|---|
| 按里程碑结算**劳务报酬** | 合同履约 | ✅ 已实现（`Milestone`） |
| 完成后一次性结算 | 合同履约 | ✅ 已实现 |
| 变更单调整报酬 | 合同变更 | ✅ 已实现（`ChangeOrder`） |
| 按项目**收益分成**给执行者 | 视情形可能构成合伙/投资 | ⚠️ 需个案法律意见 |
| **股权/期权式回报** | 涉众性金融 | ❌ 非持牌不得做 |
| 承诺**保本保收益** | 非法集资特征 | ❌ 绝对禁止 |

- **FIN-020** 任务发布时**硬约束**：`pricing` 白名单只允许
  `fixed` / `milestone` / `hourly`，**不接受任何形式的收益分成与股权对价**。
- **FIN-021** 文案风控：任务标题/描述/合约条款命中
  「分红、股权、期权、保本、年化、收益率、原始股」等词 → 拒绝发布并提示原因
  （复用 `ModerationProvider`，独立词表，不与普通违禁词混同）。
- **FIN-022** 合约条款模板明确写入「本合同为承揽/服务合同，
  报酬为劳务对价，不构成任何投资关系」——把定性写进当事人合意里。
- **FIN-023** ⚖️ 若确要做收益分成型任务，必须单独产品线、单独法律意见、
  单独风险揭示，且**不与主站资金流混用**。本 spec 范围内一律禁止。

## 25.D 税务与票据（P1）

- **FIN-030** ⚖️ 个人执行者报酬涉及**个人所得税代扣代缴**义务，
  需与存管方/税务服务商确认代扣方案（劳务报酬所得 vs 经营所得）。
- **FIN-031** 分账指令预留 `tax_withheld_cents` 字段，
  代扣金额作为独立收款方（税务专户）出现在分账里。
- **FIN-032** ⚖️ 发票：平台服务费开具平台发票；执行者报酬发票由
  代开渠道或执行者自行开具，方案需税务意见。

## 25.E 反洗钱与风控（P0）

- **FIN-040** ⚖️ 实名（已有 `KycProvider`）+ 大额/可疑交易监测与上报义务，
  具体阈值与报送格式由存管方与监管要求决定。
- **FIN-041** 现有提现风控（日限额、大额人审、收款人须与实名一致）保留，
  并把「同一收款账户关联多个账号」纳入可疑特征（GRW-013 已有基础）。
- **FIN-042** 资金流向可审计：任一笔钱可回溯到
  「谁付的 → 存管流水号 → 分账指令 → 谁收的」，缺任一环即告警。

## 25.F 迁移路径（P0）

平台不可能等拿到牌照才写代码，所以按这个顺序做：

1. **FIN-050** 把「资金事实来源」抽象成 `LedgerBackend` 协议：
   `InternalLedger`（现状，仅限开发/演示）与 `CustodyLedger`（存管方）。
2. **FIN-051** 全部资金操作改为通过该协议调用，业务代码不再直接改
   `WalletAccount` 字段——这是最大的一块重构，但只做一次。
3. **FIN-052** 生产自检（VND-042 扩展）：`PLATFORM_ENV=prod` 且
   `LEDGER_BACKEND=internal` → **拒绝启动**，并明确打印
   「平台自建账本托管资金涉嫌资金池与二清，不得用于真实交易」。
4. **FIN-053** 演示/沙箱模式显式标注：前端与 API 响应带
   `"sandbox": true`，避免任何人误以为这是真实资金。

## 25.G 验证（P0）

- **FIN-060** 分账指令守恒测试：各收款方金额之和 == 订单金额，无尾差。
- **FIN-061** 反向分账测试：退款/裁决后总账仍守恒。
- **FIN-062** 分利模式白名单测试：收益分成/股权类 `pricing` 被拒。
- **FIN-063** 金融话术拦截测试：含「保本」「年化」「原始股」的任务发布被拒。
- **FIN-064** 生产自检测试：prod + internal ledger → 启动失败并给出合规原因。
- **FIN-065** 沙箱标识测试：非存管模式下 API 响应带 `sandbox: true`。

## 验收标准

- 代码层面：资金操作全部经由 `LedgerBackend`，切换后端不改业务逻辑；
- 产品层面：任何形式的收益分成/股权对价在发布环节即被拒绝；
- 上线层面：未接存管的生产环境**根本起不来**。

## 必须由用户提供（代码无法替代）

- 持牌支付机构/银行的**担保交易或资金存管**产品与签约
- 平台自身的经营资质（涉及人力资源服务、劳务派遣等还需对应许可）
- 税务代扣方案与发票方案的专业意见
- 反洗钱制度与报送通道
