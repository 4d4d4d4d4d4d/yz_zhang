
# 100 响应形状：整条扫除，而不是挑几个抽查（CLI-083）

> 状态：本批实现（V125）
> 依赖：60/64 号（CLI-067/068 请求体与响应形状）、97 号（V122 发现覆盖只有 26/281）

## 0. 起点

V85 建响应形状闸门，docstring 原话是「类型对不上，却没有任何东西会红」。
V122 为了用 `knowledgeCards` 才撞见它的声明是错的（写着服务端从没给过的
`body`），顺手量了一下那个闸门实际管多少：

```
this.request< 调用点           281 个
_assert_shape 真的比过的         26 个
```

**覆盖 26/281，而响应侧没有任何记账说这件事。**

手写案例要造真数据、一个端点一个端点地跑，覆盖面天然很窄。
换一个来源：**服务端 handler 里 `return {...}` 的字面量本身就是契约**。

```
321 个 handler 的最后一个 return
  字面量 dict          161
  字面量 dict 的列表推导  37
  调用 _dump/dump_task 等  ~80
  变量 / 其他           ~40
```

## 1. 做法

| 步骤 | 内容 |
|---|---|
| 读 SDK | 每个 `this.request<T>(verb, path)`：方法名、动词、归一化路径、响应类型 |
| 读服务端 | 递归走进 include 进来的子路由，拿到 handler；读出它所有 `return` 的字面量键 |
| 比 | **给了没声明**（客户端看不见）＋**声明了没给**（客户端读到 undefined） |
| 多分支 | 必选字段必须**每个分支都给**；任一分支给的字段都要声明 |
| 记账 | 静态比对 / 真实响应断言 / 豁免（写理由）/ **未验证（棘轮，只许降）** |

覆盖：**26 → 178/281**（静态比对 153 + 真实响应 23 + 豁免 2），未验证 103。

## 2. 第一次跑扫出来的

**10 处 SDK 与服务端对不上**，外加扫描器自己的两个盲区。

| 方法 | 不一致 | 后果 |
|---|---|---|
| `exportEvidence` | 服务端给 `evidentiary_notice` / `integrity`，SDK 没声明 | **见第 3 节——法律后果** |
| `verifyIdentity` | 转人工那支带 `status`，SDK 没声明 | **见第 4 节——网页说「成功」** |
| `trip` | SDK 声明 `{shared, points[]}`，服务端给的是**最近一个点** `{lat,lng,at}` | 任何读 `trip.points` 的客户端拿到 undefined |
| `addTeamMember` | SDK 声明 `spend_limit_cents`，服务端不回 | owner 设下的花钱上限，界面上无从确认 |
| `removeCircleMember` | SDK 声明 `removed`，服务端回 `ok` | 读到 undefined |
| `finalReport` | 服务端多给 5 个字段（计划预算、工期、状态…），`deliverables` 元素无形状 | 结项报告最有用的「计划 vs 实际」看不见 |
| `apply` / `proposeChange` / `askSupport` / `resolveReport` / `listProgress` / `apiScopes` | 服务端多给的字段 SDK 没声明 | 客户端看不见报名状态、变更金额、工单号、处置效果、进度图片、Webhook 事件表 |

修法的判据：**服务端给了而 SDK 没声明 → 补 SDK**（客户端应当看得见）；
**SDK 声明了而服务端不给 → 看哪边是对的**。`addTeamMember` 改服务端
（回显额度是 owner 需要的确认）；`trip` 与 `removeCircleMember` 改 SDK
（服务端的形状是对的，且两端都没有调用者依赖错的那个）。

## 3. 证据包丢了它的证明力说明

服务端的证据包带着 `evidentiary_notice`——V50 特意做的「诚实标注证明力边界」，
其中一句是：

> 本文所载「平台处理决定」系依当事人事先约定作出的合同履行调整，
> **不是法律意义上的仲裁裁决**，不具有强制执行力。

SDK 没声明这个字段，于是网页下载证据包时写的是：

```ts
JSON.stringify({ ...pack.package, sha256: pack.sha256 })
```

**用户交给律师的那份文件里，没有任何一句话说明它能证明什么、不能证明什么**，
链完整性与第三方背书覆盖到哪一条也一并没了。而那段代码上方的注释写着
「V50 特意做了诚实标注证明力边界」——写的人知道它的存在，但类型里看不见它。

改成整包原样保存，不再挑字段。

## 4. 实名核验：HTTP 200 不等于通过

服务端两个出口：通过 `{is_verified: true}`，转人工
`{is_verified: false, status: 'manual_review'}`。SDK 只声明了 `is_verified`。

**网页**：`act(() => client.verifyIdentity(...), '实名认证成功')`——
不论返回什么都弹「成功」。接上真实供应商后，转人工是常态结局之一；
用户被告知成功，接下来去接单时被拦住，不知道为什么。

**App 更糟**：那是一个「一键实名认证（模拟）」按钮，**把写死的「测试用户」与
证件号 110101199001011234 提交给服务端**：

- 第一个点它的人，账号上被记下的真实姓名是「测试用户」；
- 之后每一个点它的人都收到 `id_already_bound`（同一证件号只能绑定一个账号），
  而 `onPress` 没有 try/catch——**点了什么都不会发生**；
- 接上真实供应商后，所有人都在提交同一个假身份。

网页那边也有同类的东西：身份证号的 `prompt` **预填了同一个假号码**，
文案写着「模拟 eKYC，任意合法格式即可通过」。

这些都只在模拟供应商下「能用」，所以一直没人发现。

修法：服务端两个出口同形（都带 `status`）；两端改成真实表单（不预填任何号码），
按 `status` 区分「已通过」与「已提交，正在人工审核」，服务端的错误原样显示。

## 5. 扫描器自己的两个盲区（也是这一类的老问题）

- **跨行嵌套类型**：`_inline_fields` 的字段正则没有 DOTALL，
  `integrity: {\n chain_valid: ...}` 这种写法匹配失败 → 整个声明返回 None →
  **悄悄退出闸门范围**。与 V122 的「带注释就解析不了」同一类：不报错，只是不再检查。
- **嵌套模板字符串**：`` `/admin/categories/${id}${qs ? `?${qs}` : ''}` ``，
  正则替换切错位置，把 `updateCategory` 算成打一条不存在的路由——一个假报警。
  改成按括号配平扫描。
- **`async` 方法名**：方法名正则不认 `async`，`apiScopes` 的不一致被算到了
  上一个方法头上。

## 6. 闸门

| 闸门 | 内容 |
|---|---|
| CLI-083a | 扫描器自检：SDK ≥250 调用点、服务端 ≥280 路由、可比 ≥120、已知方法必须可比 |
| CLI-083b | 每个 SDK 调用打的路由服务端都有 |
| CLI-083c | 可比的两个方向都对上（含多分支） |
| CLI-083d | SDK 声明读不出 → 红（解析器盲区不许悄悄算过） |
| CLI-083e | 未验证数只许降不许升（棘轮 103） |
| CLI-083f | 豁免必须真实存在且理由是人话 |
| CLI-083g | 比较器自己的红验：两个方向、可选字段、多分支 |
| ACC-020a | 实名核验两个出口同形 |
| TEAM-010a | 加成员回显额度 |
| 两端 | 证据包文件带证明力说明；转人工不说成功；不预填/不写死证件号；错误原样显示 |

八条红验走过。

## 7. 这一批没做的

- **剩下 103 个未验证的调用点**：handler 返回 `dump_task(...)` / `_dump(...)` /
  变量，静态读不出键。下一步是让那些 dump 函数也被读（它们大多本身就是返回字面量），
  或者给每个补真实响应断言。棘轮钉着它们只许变少。记台账 `CLI-083b`。
- **值类型没比**：这一版只比键，不比 `number` 还是 `string`。
  静态读 Python 表达式推类型容易误报，宁可不比。
