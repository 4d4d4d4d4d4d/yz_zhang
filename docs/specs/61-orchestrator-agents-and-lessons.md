# 61 让 AI 真的参与，并且越做越好（ORC-060~065 / VER-051）

> 两条欠账，各挂了三个批次：
>
> - **AGT-053**：编排器的工具只有 `publish_task`——**编排器只会把活派给人**。
>   一个标榜「AI 驱动」的平台，它的 agent loop 里没有 agent。
> - **VER-051**：`verification_lessons` 表在写，**全仓没有任何地方读它**。
>   需求原话是「能够持续帮助迭代任务完成」，而这张表就是那句话的载体。
>
> 两条合起来才构成需求说的那个闭环：AI 参与执行 → 人核验 → 结论回流 →
> 下一次 AI 做得更好。少任何一半都只是半个循环。

## 1. ORC-060 编排器怎么调 agent：不给它开后门

三条路：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A 新工具 `run_agent` | 步骤直接调 agent，不建任务不走合约 | **绕开托管、评审、纠纷、毛利核算全链路**；编排的预算护栏也看不见这笔支出 |
| B 照常发任务，同时邀请合格 agent 承接 | 保留全部链路，只是执行方是 agent | 选它 |
| C 先问人、没人接再给 agent | 更"自然" | 要等招募超时，编排的收敛速度被拖垮；而且「没人接」与「该给 AI 做」是两件事 |

**选 B。** 理由与 AGT-020 同一条：**agent 走完整合约链路，不开后门**。
托管、验收、评审、纠纷、封禁、毛利统计全部以 `task_id` / `user_id` 为键，
方案 A 等于把它们各写第二遍。

## 2. ORC-061 但是：自动派单给 AI 需要一次显式授权

V73 定过一条规矩：

> `agent-apply` **由发布方主动触发**，不自动派单。理由：让 AI 接自己的活
> 是一个需要知情的选择，静默派单等于替用户做主。

编排里发起人已经授权了「自动花钱」，但他**没有**授权「活由 AI 做」——
这是两件不同的事。一个人可能很愿意让系统自动去市场上找人，
同时完全不接受交付物是机器写的。

所以加 `Mission.allow_agents`，**默认关**，在创建编排时显式选择。

**一次授权覆盖整个 mission，而不是每步再问一次**：编排的价值就是不用
一步一问；把授权粒度放在 mission 上，既保住知情同意，又不毁掉自动化。

这条同时决定了文案：开关旁边要说清楚「交付物可能由平台 AI 助理生成，
平台是其履约的责任主体」——这正是合同里已经写着的那句。

## 3. ORC-062 AI 做不成，自动转人工

agent 执行有三种结局，编排必须分别处理：

| run 结局 | 编排怎么办 |
|---|---|
| `succeeded` | 平台代交付（V81 已有）→ 照常进评审 |
| `escalated`（置信度不足/需人审） | **不等**：本步标记失败并取消该任务，由修复步重新发给人 |
| `failed`（判据/审核没过） | 同上 |

为什么不等人工核验：核验单是**发布方自费或平台自费**的一条人工链路，
它适合「这一单我要一个确定的结果」；而编排是**批量、自动、有预算上限**的，
在这里等一个不确定何时被接单的核验，会把整个编排卡住。
**两条路都在，选哪条取决于是谁在等。**

取消任务会释放托管（AIO-024 的 `committed` 回收已经处理好了），
所以转人工不会白烧预算——这也是为什么必须走方案 B：
如果 agent 在合约体系之外执行，这里根本没有「取消并退款」可用。

## 4. VER-051 经验回流：喂回去，并且**看得见喂了什么**

`VerificationLesson` 存的正是提示词最需要的那种数据：
输入（任务标题 + 判据）→ 人的判断（通过/改成这样/不通过）→ **理由**。

做法：`run_agent` 执行前，按**同类目**取最近若干条**非通过**的核验结论，
拼进系统提示词。

三个限制，每条都有理由：

- **只取 `revised` / `rejected`**：`approved` 的结论没有信息量
  （「这次做对了」不指导下一次），而 prompt 长度是有成本的。
- **按类目取**，不跨类目：保洁的核验结论对写代码没有帮助，
  混进去只会稀释真正相关的内容。
- **有数量与长度上限**：提示词不能随时间无限膨胀，否则今天能跑的 agent
  三个月后会因为超长而失败——**一个会随数据增长而变慢变坏的机制，
  是一个定时炸弹，不是一个功能**。

### ORC-063 喂了什么必须落库

`AgentRun.lessons_used` 记下**这次实际用了哪几条**（id 列表）。

没有它，「经验回流」就是一句无法验证的话——和 48 号 spec 里那句
「agent 产出过内容审核」一样，写着但没接。有了它：

- 测试能钉住「产出确实受了哪条经验影响」；
- 运营能回答「这次 AI 的表现变好，是因为哪几条核验」；
- 出问题时能追：是不是某条错误的核验结论把 agent 带偏了。

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| ORC-060 | agent 承接编排步骤时走完整合约链路（有任务、有合约、有托管） |
| ORC-061 | `allow_agents` 默认关；不开时编排一个 agent 都不会邀请 |
| ORC-061 | 开启后，只邀请**合格**的 agent（到场/类目/预算三条闸门仍然生效） |
| ORC-062 | agent 执行失败或升级 → 该步失败、任务取消、预算占用释放、修复步重发 |
| ORC-062 | 修复步不会再被派给 agent（同一形态失败过一次就换人做） |
| VER-051 | 同类目的非通过核验结论进入 agent 的系统提示词 |
| VER-051 | `approved` 的结论不进（没有信息量）；跨类目的不进 |
| ORC-063 | `AgentRun.lessons_used` 记下实际使用的经验条目 |
| — | 提示词长度有上限，经验条数增长不会让它无限膨胀 |

## 6. 这一批没做的

- **ORC-064**：编排不会**混编**（同一目标里一部分给 AI、一部分给人）。
  现在是「这一步先试 AI，不行转人工」，不是按步骤性质分派。
  按性质分派需要先有「哪类步骤适合 AI」的判据，那是 AGT-011 领域之外的另一层。
- **ORC-065**：agent 之间不串联（一个步骤里多个领域 agent 接力）。
- **VER-052**：经验只喂 agent，不喂**人类执行者**。同一份结论对人也有用
  （「这类任务上人常漏什么」），但那要做成可读的攻略卡，是内容侧的事。
