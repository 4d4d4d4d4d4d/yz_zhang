# 186 有一页坏的人多了，提醒运营

> 状态：本批实现（V214）。编号 APP-097。
> 来源：184 号 spec「没做的」——「某一页一天内坏的人数超过阈值时提醒运营（接入已有告警）」；BACKLOG V214。原记作 APP-095，与 136 号「开票入口」撞号，V213 改号。
> 只增不减：184 号的上报与后台汇总不变；「已提醒」的记号不算进页面出错的次数与人数。

## 0. 要解决的问题

184 号让运营能在后台「页面出错」里看到哪页常坏，但那张表得有人去看。新版本把某一页弄坏了，运营往往要等客服工单才知道。

## 1. 业界怎么做

前端错误监控按「受影响的用户数」而不是事件次数设告警阈值，并对同一问题做提醒去重，避免刷屏（如 Sentry 的 Issue Alert 条件「受影响用户数超过 N」与动作频率限制，<https://docs.sentry.io/product/alerts/create-alerts/issue-alert-config/>）。本批照此：按不同的登录用户数、同一页一段时间内只提醒一次。

## 2. 数据

不加表、不加迁移。「已提醒」记一条埋点：`analytics_events.name = render_alerted:<web|app>`、`ref_type = 页面名`、`user_id` 为空。页面出错汇总只数 `render_failed:` 开头的，不受影响。

## 3. 接口

| 接口 | 说明 |
|---|---|
| `POST /analytics/jobs/render-alerts`（job，`X-Job-Token`，执行锁 `render_alerts`，每小时） | 数近 24 小时每个「端 × 页面」坏过的**不同登录用户**（各错误类型合起来数）；到 `PLATFORM_RENDER_ALERT_PEOPLE`（默认 5）且这一页 24 小时内没提醒过，就给运营发站内信；返回 `{"alerted": [{platform, page, people, notified}]}` |

收件人：有「运营」角色、没被封禁的管理员；没有专职运营时退到能看这块的人（超级管理员）。

站内信：「网页「/wallet」近 24 小时有 5 位用户遇到页面出错（RangeError、TypeError）。去管理后台「页面出错」看是哪类错误；多半是接口返回与页面预期对不上，或刚发的版本有问题。同一页 24 小时内只提醒一次。」

## 4. 两端

不加新界面：提醒走站内信，运营在 Web 与 App 的通知里都能看到；点开后去 Web 管理后台「页面出错」看明细（184 号）。

## 5. 隐私、授权与边界

- 站内信里只有端、页面名（数字已换成 `:id`）、人数、错误类型，没有是谁。
- 没登录的上报不算人数：页面名可以编造，按人数提醒就不能被匿名请求刷出来。
- job 端点要 `X-Job-Token`，执行锁防止多实例重复提醒。

## 6. 闸门与红验

`server/tests/test_render_alerts.py` 5 条；10 处变异全部变红（`scratchpad/mut214.py`）：

| 闸门 | 红验 |
|---|---|
| 到阈值才提醒、各错误类型合起来数人、只提醒运营、同一页 24 小时只一次 | `<` 改 `<=` → 红；按错误类型分开数 → 红；收件人不分角色 → 红；去掉去重 → 红；一个都不提醒 → 红 |
| 按端 × 页面分开数、匿名不算人 | 匿名也算人 → 红 |
| 24 小时窗口：旧的上报不算、新的一波再提醒 | 不看时间窗 → 红 |
| 没有专职运营时提醒超管、封禁的不提醒 | 不退到超管 → 红；不排除封禁 → 红 |
| 「已提醒」记号不进页面出错汇总；job 要令牌 | 记号与上报同名 → 红 |
