# 50 早期合作体：贡献即份额（COOP）

> 需求原话：「早期合作，这个是为了**颠覆公司组织形式**，这个合作方式能够
> 可追溯（有智能合约），而且能够获得相关支持（agent、法律顾问、政策、
> 任务发布给特定人解决），能够持续帮助迭代任务完成。
> 你说的合规啥的，只是路径上的一些需要，例如如果需要那就要生成对应
> 法律效益的文件并且申请资质啥的。」
>
> 这一批按这个定位做。**合规不当否决项，当成工作流里的一步**：
> 系统判定这个合作形态需要哪些文书与资质，生成文书、给出办理路径。

## 0. 与公司股权最本质的区别：份额不是分的，是长出来的

传统公司：**先分股权，再干活**。分的那一刻，谁干多少还不知道；
干到一半有人不干了，股权还在他手里。早期合作最常死在这里。

这一批的模型反过来：**份额 = 已确认贡献的函数，随贡献累积而变。**

```
share_bps(成员) = 该成员已确认贡献的计价总额 / 全体已确认贡献的计价总额
```

后果是三条，每条都是有意的：

1. **不干活的人份额会被稀释**——别人继续贡献，分母变大。
   这正是「早期合作、有风险」该有的样子：风险对应的是持续投入，
   不是一次性的名分。
2. **中途加入的人能公平进来**——他的贡献照样计入分子，
   不需要谁「让出」份额。
3. **份额是算出来的，不是存下来的**。所以没有「份额转让」这个动作——
   那会立刻把它变成一张可流通的权益凭证，性质就变了（见第 3 节）。

## 1. 贡献必须被别人确认，不能自报

COOP-010：`Contribution` 提交后是 `proposed`，**必须由另一名成员确认**
才变 `accepted` 并计入份额。

这条是整个模型能不能成立的前提。自报贡献等于自己发股份——
「我说我干了 1000 小时」和 agent 自报置信度是同一类无效（AGT-030 的同一条道理）。

**确认人不能是贡献人自己**，这一条写在代码里，不靠自觉。

计价（`valued_cents`）也由确认人给，不由贡献人给：贡献人说「我做了什么」，
确认人说「这值多少」。**描述与估值分开**，是防止一个人既当运动员又当裁判。

## 2. 可追溯：贡献与分配全部入哈希链

需求说「可追溯（有智能合约）」。平台已经有存证哈希链（`anchor`），
合约关键动作都入链。这一批把**贡献确认**与**收益分配**也入链：

改一条历史贡献，必须重写整条后继链才不被发现——这就是「可追溯」
在技术上的真实含义，而不是「有一张表存着」。

## 3. 收益分配：只分已实现的，且只在体内

这是让这个模型**落在合伙而不是公开发行**的关键技术手段，
不是法务加的限制，是设计本身。

| 做法 | 性质 | 本批 |
|---|---|---|
| 把**已到账**的收入按份额分给**已实名的成员** | 合作内部分配 | ✅ |
| 承诺未来收益、按预期收益定价份额 | 涉众性金融 | ❌ 不做 |
| 公开招募成员 | 公开募集 | ❌ 不做，**邀请制** |
| 份额可转让给体外的人 | 权益凭证流通 | ❌ 不做 |

COOP-020 分配的钱**只能来自合作体钱包的可用余额**——也就是真的收到了的钱。
没有「预期收益」这个概念，代码里也不存在这个字段。

COOP-021 成员**邀请制**，没有公开报名入口。
COOP-022 **不实现份额转让**。这不是「以后再说」，是**故意不做**：
一旦份额可转让，它就是一张可流通的权益凭证，整个性质变了。

## 4. 合规路径引擎：告诉你需要什么，而不是拦住你

需求说得很清楚——合规是路径上的一步，需要什么文件就生成什么，
需要什么资质就去办。所以 `coop/compliance_path.py` 做的是**判定 + 生成 + 指引**，
不是拒绝。

判定维度（都是合作体的客观属性，不靠人填）：

| 维度 | 取值 | 影响 |
|---|---|---|
| 成员人数 | N | 超过阈值触发「人数较多」提示 |
| 是否有资金池 | 有/无 | 有资金池 → 需要资金管理约定 |
| 是否已产生分配 | 是/否 | 已分配 → 需要分配确认书与完税提示 |
| 累计分配金额 | ¥ | 超阈值 → 建议办理经营主体登记 |
| 行业类目 | 受限/普通 | 受限 → 指向 V76 的资质核验 |

输出三样东西：

1. **必备文书清单**（合作协议、风险揭示书、贡献确认书、分配方案）
   ——其中前两样是**加入合作体的前置**，不签不能加入；
2. **是否触达需要办理资质/登记的门槛**，以及办什么；
3. **每一项的当前状态**（已生成 / 待签署 / 待办理）。

COOP-030 **风险揭示书必须签署才能加入**。
「有风险性」是这个模式的固有属性，不是可以淡化的卖点。
一个不告诉人有风险就拉人进来的早期合作，本身就是纠纷的起点。

风险揭示书里必须写清楚的四条（代码里是常量，不是运营可改的文案）：

- 份额会被后续贡献稀释；
- 合作体可能不产生任何收益；
- 分配只来自已实现收入，平台不承诺任何回报；
- 份额不可转让、不可赎回，不构成任何投资或股权。

## 5. 「获得相关支持」怎么落地

需求列了四样：agent、法律顾问、政策、任务发布给特定人解决。

本批落地的是**资金与主体**这一层——合作体有自己的钱包，于是：

- **发任务给特定人解决**：合作体可以用体内资金池发任务，走既有全链路
  （托管/合约/纠纷一行不改）。
- **调用 agent**：同上，合作体作为发布方邀请 agent 接单（V73 的链路）。
- **法律顾问**：合规路径引擎生成的文书 + 已有的 `legal` 模块文书能力。
- **政策**：本批不做（COOP-052，需要外部政策数据源）。

### 架构判断：合作体也是一行 User

与 V73「agent 是 User」同一条理由，同一个标准：钱包、托管、合约、纠纷、
任务发布**全部以 `user_id` 为键**。合作体要有资金池、要能发任务，
不复用就得把这些各写第二遍。

用 `is_venture` 标记，并在所有「人」的语义处显式排除
（推荐池、核验人资格、实名要求等）——与 `is_agent` 同一套处理。

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| COOP-010 | 贡献自报不计份额；**确认人不能是贡献人自己** |
| COOP-011 | 份额随新的已确认贡献动态变化（不是存量字段） |
| COOP-012 | 份额合计恒为 10000 bps（分配不多不少） |
| COOP-020 | 分配只能来自合作体钱包可用余额；超额被拒 |
| COOP-021 | 成员邀请制；没有公开加入端点 |
| COOP-022 | 全站不存在份额转让端点（用测试钉住） |
| COOP-030 | 未签风险揭示书不能加入 |
| COOP-031 | 风险揭示书含四条必备内容（逐条断言，不是断言「非空」） |
| COOP-040 | 合规路径按合作体实际属性给出清单与门槛，且**不阻断** |
| COOP-050 | 合作体可用资金池发任务，走既有全链路 |
| COOP-060 | 贡献确认与收益分配入哈希链，篡改可被发现 |

## 7. 这一批没做的（明确记账）

- **COOP-051**：**退出机制**。成员想离开时份额怎么办？按当前模型他的
  历史贡献仍在分母里、仍会参与后续分配——这可能是对的（他确实贡献过），
  也可能不是（他不再承担风险）。**这需要一个明确的产品判断，我不替用户定**。
  在定下来之前，退出只是「不再贡献」，份额自然被稀释。
- **COOP-052**：政策支持（补贴/园区/税收优惠对接）需要外部政策数据源。
- **COOP-053**：合规路径引擎给的是**结构化提示与文书模板**，
  **不是法律意见**。文书要不要用、怎么改，必须由执业律师过一遍。
  代码里对此有显式声明，不假装它有法律效力。
- **COOP-054**：分配的个税处理沿用既有 `tax` 模块的劳务报酬口径。
  合作分配的税务定性可能不同（经营所得 vs 劳务报酬），
  **这一条要专业意见**，本批按劳务报酬处理并在文书里标明。
