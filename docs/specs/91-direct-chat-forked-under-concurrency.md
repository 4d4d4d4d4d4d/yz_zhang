
# 91 单聊并发会建出两条会话（IM-052 / CONC-054 / IM-051）

> 状态：本批实现（V118）
> 依赖：09 号（IM）、18 号（并发）、86 号（第一次打开钱包可能 500）

## 0. 这条欠账是 V112 自己记下的

修钱包懒建竞态时顺手搜了一遍同形状的函数，`im.get_or_create_direct`
一模一样，当时记进 72 号台账（`CONC-054`）并写明：

> 那张表上没有唯一约束，所以它不像钱包那样 500，而是**静默重复**——
> 两人各说各话、消息分在两条线上。

探针确认它还在：

```
PROBE 并发 10 次开同一个单聊，拿到的会话 id: [1, 2]
库里的单聊行: [(1, '[1, 2]'), (2, '[1, 2]')]
```

**没有约束的地方，竞态不报错，只把数据悄悄弄错。**
钱包那次是 500——难看，但你知道出事了。这一次没有任何人会看到错误：
两个人各自以为对方没回，而消息分在两条线上。

同一个函数还有第二个毛病：

```python
for conv in db.query(Conversation).filter(Conversation.kind == "direct").all():
    if set(conv.participants) == {user_a, user_b}:
```

**把全平台所有单聊取出来在 Python 里比参与者集合**——每开一次私聊扫一遍
全表。两个毛病同在一行上，所以一起改（`IM-051`）。

## 1. 为什么要加一列

`participants` 是 JSON，数据库没法在它上面建唯一约束。所以加一列
**规范化键** `direct_key`（小 id-大 id），唯一：

- 规范化是关键——`(1,2)` 与 `(2,1)` 必须得到同一个键，
  否则两个人各从自己那一侧点「发消息」就又分叉了；
- 任务会话与群聊留 `NULL`：两个库都允许唯一列里有多个 `NULL`，
  所以这一列只约束它该约束的那一类；
- 有了索引，查找走唯一索引，与表里有多少行无关——`IM-051` 顺带没了。

## 2. 迁移刻意是非破坏性的

存量库里可能已经有重复的单聊对（那正是这个缺陷留下的痕迹）。
直接建唯一索引会被顶回来，所以先回填：

| 存量 | 结果 |
|---|---|
| 同一对里**最早**那条（id 最小） | 拿到键 |
| 重复的那些 | **留 `NULL`** |
| 任务会话 / 群聊 | 不参与 |
| 参与者不足两人的坏数据 | 不给键（硬塞会让唯一约束把两条不相干的行判成冲突） |

**消息一条不动、会话行一条不删。** 两条线上的历史都还在，会话列表按
`participants` 查，所以用户仍然看得到它们；以后的查找收敛到有键那一条，
新消息不再继续分叉。

另一条路是把重复会话的消息并进最早那条再删掉多余的行。**没有这么做**：

> 在迁移里合并用户的聊天记录是**不可逆的**，而且 `ConversationRead` 的
> 已读位点会一起错位。分叉已经发生了，先把它止住；要不要合并是产品决定，
> 不是一次 schema 变更该顺手做的事。

## 3. 冲突照样要接住

索引让库拒绝重复行，但**被拒的那一次请求不能变成 500**。
写法与 V112 的钱包一致：`begin_nested()` 开 SAVEPOINT，
插入失败只回滚这一步，不把外层事务一起带走——
调用方常常正在做发消息、建任务会话这种多步写入。

重读之后仍读不到就照样抛：**把异常吞掉换成 `None` 返回，
是把 500 换成后面某处更难查的 `NoneType` 错误。**

## 4. 一条我自己写歪的测试

第一版的并发用例声称「复现那个竞态」。红验时把修法退回
check-then-insert（去掉冲突恢复）——**它仍然是绿的**。

原因：进程内的线程**复现不了那个窗口**，SQLite 把写串行化了，
等第二个线程查的时候第一个常常已经提交。

所以把保证分成两层，并在测试里把边界写明：

- **唯一索引**（迁移建的）让库拒绝重复行——那是兜底，不靠代码时序；
- 代码接住冲突并重读——由一条**结构断言**钉住（`IntegrityError` /
  `begin_nested` / `raise` 三样都要在）。

一个声称复现竞态而实际没有的测试，比没有测试更糟：
**它让人以为那条路径被覆盖了。** 这和「扫不到等于全绿」是同一件事，
只是出现在并发测试上。

## 4b `alembic check` 抓到的一处漂移

模型第一版只写 `unique=True`，而迁移建的是**具名唯一索引**
（`ix_conversations_direct_key`）。SQLAlchemy 把 `unique=True` 渲染成
`UniqueConstraint`，两边对不上，`alembic check` 当场报漂移。

值得记一笔的是**哪个闸门没看见它**：V109 建的列属性漂移闸门
（`test_migrations_match_column_properties`）刻意把索引与约束名**排除在外**，
理由是 SQLite 批处理模式会重命名它们、噪音太大。那条理由仍然成立——
但它的代价就是这一类漂移只有 `alembic check` 看得见，而那条命令在
CI 的 `migration-drift` job 里（两个引擎各跑一遍）。

**一个有意缩小范围的闸门，要知道自己把什么交给了别人。** 这里交给了 CI，
而 CI 确实会红——我是在推送前手跑那条命令时发现的。

## 5. 闸门

| 闸门 | 内容 |
|---|---|
| IM-052 并发 | 八路并发（两侧交替发起）之后：没人拿到异常、都拿到同一个 id、库里同一对只有一行 |
| IM-052 规范化 | `direct_key(a,b) == direct_key(b,a)`，且两侧调用拿到同一条 |
| IM-052 冲突恢复 | 函数里必须有 `IntegrityError` + `begin_nested` + `raise`（结构断言，理由见第 4 节） |
| IM-051 不扫全表 | 查询里带 `direct_key ==`，且函数里没有 `.all()` |
| IM-052 迁移 | 旧版本建库 → 造存量重复 → 升级：最早那条拿键、重复留 NULL、任务/群聊/坏数据不给键、**行与消息数不变** |

红验五条走过：键不规范化、回到全表扫描、去掉冲突恢复、迁移给重复对也塞键
（被唯一索引顶回来）、迁移删掉重复行（破坏历史）。

## 6. 这一批没做的

- **不合并已经分叉的会话**：见第 2 节，那是产品决定。要做的话应当是
  一个带 `--dry-run` 的一次性脚本（像 `scrub_experience`），逐条打印、
  并且想清 `ConversationRead` 怎么对齐。记在台账（`IM-053`）。
- **群聊没有同类约束**：群聊可以重名、可以有两个成员完全相同的群，
  而那**本来就是允许的**（两群人可以各建一个同样成员的群）。
  所以群聊不进这一列，不是漏了。
- **没有量化性能改善**：去掉全表扫描在本地库上看不出差别（表里几行），
  要有数字得先有量级数据，而压测脚本目前只有两个场景（`DRILL-032`）。
