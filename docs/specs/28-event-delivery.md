# 28 · 事件投递：失败隔离、可重试、跨副本（EVT）

> 覆盖 [18-concurrency.md](18-concurrency.md) 的 CONC-030/031 与
> [23-network-security.md](23-network-security.md) 的 SEC-040。

## 先说清楚现状哪里真的坏了

`app/core/events.py` 十七行，同步派发：

```python
def publish(db, event, payload):
    for handler in _handlers[event]:
        handler(db, payload)
```

三个问题，第一个是**已验证的生产事故路径**：

### 问题一：派生副作用能把资金交易整笔干掉（P0）

`task.completed` 上挂着 **6 个** handler：经验入库、后继子任务发布、
容器母任务结项、数据分析、韧性处理、通知。它们和 `release()`（真正的放款）
**在同一个事务、同一个请求里**。

任何一个抛异常，整笔验收放款回滚。已用探针复现：把知识卡片 handler
改成抛 `RuntimeError`（真实诱因：卡片生成走 LLM，超时很正常），
验收接口直接崩，执行方拿不到钱。

**这是本末倒置**：知识库是锦上添花，放款是这个平台的存在理由。
锦上添花失败了，不能让存在理由跟着一起死。

### 问题二：失败即永久丢失

handler 抛异常没有任何记录，也没有重试。如果哪天改成 `try: ... except: pass`
（最容易想到的「修法」），事故就从「崩掉」变成「静默丢失」——
用户永远收不到那条通知，而没有任何人知道。**后者比前者更糟**。

### 问题三：跨副本（CONC-031 / SEC-040）

事件只在处理请求的那个副本派发。目前所有 handler 都在发布方事务内同步跑完，
所以**并不会漏执行**——但这也意味着：任何想把 handler 挪到后台/异步执行的改造，
都会立刻变成跨副本问题。现在没暴雷，只是因为还没人挪。

## 28.A 设计取舍（写下来，因为每条都可以反着做）

- **不引入 Kafka/Redis。** 事务性发件箱（transactional outbox）写在**同一个库、
  同一个事务**里，天然满足「业务改动与事件同生共死」：业务回滚则事件不存在，
  业务提交则事件必定存在。用 MQ 反而要额外解决两阶段提交问题。
  真要上 MQ，让它从发件箱消费即可，业务代码不用改。
- **保留同步派发作为主路径。** 通知、经验卡片在同一请求内落库，
  用户刷新就能看到，体验更好，测试也更直观。异步只是**失败后的兜底**，
  不是默认路径。把一切都改成异步是过度设计，还会让 436 个测试
  全部要等 drain job。
- **失败隔离用 SAVEPOINT，不用 try/except 吞掉。** handler 在嵌套事务里跑，
  失败只回滚它自己那一段，业务事务完好；同时**必须留下失败记录**，
  否则就回到问题二。
- **重试要机器判定，不靠人自觉。** handler 注册时必须声明失败后能不能自动重试；
  不能的，只挂在死信里等人处理。「哪些事件可重放」写在文档里没人会看，
  写成**必填参数**才拦得住下一个新增 handler 的人。

> **检视时纠正的一处自作聪明**：最初把这个参数叫 `idempotent`，
> 但有了 SAVEPOINT 之后，失败的 handler 写的东西**已经被回滚干净了**，
> 重试是从干净状态重来，纯 DB handler 几乎自动就是安全的。
> 真正的问题不是「幂等吗」，而是「**隔了一段时间再补做，还对吗**」——
> 存证链就不对：几小时后补进去的条目，`seq` 会排在真实发生更晚的事件之后，
> 链所声称的「这些事件按此顺序发生」变成假话，而这条链是要拿去举证的。
> 所以参数叫 `retry`，问的是这个问题。

## 28.B 发件箱与投递记录（P0）

- **EVT-001** `OutboxEvent` 表：事件名、payload、发布时间、发布副本。
  由 `publish()` 在**业务事务内**写入，与业务改动同生共死。
- **EVT-002** `EventDelivery` 表：`(event_id, handler)` 唯一——
  这个唯一约束就是**恰好一次**的实现，跨副本同样成立。
  状态 `done` / `failed`，记录尝试次数与最后一次错误。
- **EVT-003** payload 只放**标识符**（task_id/contract_id），不放业务对象快照。
  重试时 handler 重新读库，拿到的是当下的真实状态，而不是发布时的陈旧副本。
- **EVT-004** 发件箱有保留期（默认 14 天），由清理 job 删除已完成的旧事件；
  **失败与死信记录不自动删除**。

## 28.C 失败隔离（P0）

- **EVT-010** `publish()` 对每个 handler 开 SAVEPOINT（`begin_nested`）：
  失败只回滚该 handler 自己写的东西，业务事务与其它 handler 不受影响。
- **EVT-011** handler 失败时记 `EventDelivery(status=failed)` 并结构化告警日志，
  **绝不静默**。记录写在**业务会话**里（回滚到保存点后会话仍可用），
  于是它与业务改动同生共死：业务最终回滚了，这条失败记录也不该留下——
  因为那件事根本没发生。
- **EVT-012** 例外：声明为 `critical=True` 的 handler 失败**必须**让业务事务失败。
  判定标准不是「重不重要」（那样人人都想标 critical），而是：
  **这个副作用缺失，会不会让已提交的业务事实变成平台无法自圆其说的状态**。
  存证入链属于这一类——签了字却没有链上记录，等于平台对外承诺的证据能力有洞。
- **EVT-013** 单个 handler 的失败不影响同一事件的其它 handler：
  一个订阅者坏了不该拖累其他人。

## 28.D 重试与跨副本（P0，对应 CONC-031 / SEC-040）

- **EVT-020** `subscribe(event, handler, retry=...)`：
  **`retry` 是必填参数**，注册时就要回答「失败后隔一段时间自动补做，还对吗」。
- **EVT-021** drain job `POST /events/jobs/drain`：扫描失败且可重试的投递记录并重试，
  受 `job_slot` 单实例锁保护——**任何副本都能重放任何副本发布的事件**，
  这就是 SEC-040 要的跨副本能力，不需要额外中间件。
- **EVT-022** `retry=False` 的 handler 失败直接进**死信**：
  `GET /events/dead-letters`（管理端）列出待人工处理项，绝不盲目补做。
  当前唯一这样标注的是「周期任务自动续期」——它会**创建一个带预算的新任务**，
  几小时后由后台悄悄补出来一单，比缺这一期更糟。
- **EVT-023** 重试次数上限（默认 5 次）后转死信，避免无限重试打爆日志与数据库。
- **EVT-024** 重试在**独立会话**里执行并单独提交：一条重试失败不影响其它条。

## 28.E 可观测（P1）

- **EVT-030** `/metrics` 暴露待重试数与死信数——
  死信堆积是「有功能已经悄悄坏了」的最早信号。
- **EVT-031** `GET /events/health`（job 令牌鉴权）：按事件名/handler 聚合失败数。

## 28.F 验证（P0）

- **EVT-040** 派生 handler 抛异常 → 验收放款**照常成功**，钱正确到账，
  失败被记录（现状的反面，本 spec 的核心）。
- **EVT-041** critical handler 抛异常 → 业务事务**确实回滚**，钱没动。
- **EVT-042** 一个 handler 失败不影响同事件其它 handler。
- **EVT-043** drain 重试可重试 handler → 补齐副作用，且**重复 drain 不会重复补**
  （唯一约束生效）。
- **EVT-044** `retry=False` 的 handler 失败 → 进死信，drain **不碰它**。
- **EVT-045** 发布事件的事务回滚 → 发件箱里**没有**这条事件（同生共死）。
- **EVT-046** `subscribe` 不传 `retry` 直接报错（防止新 handler 漏声明）。

## 验收标准

- 派生副作用的任何失败都**不能**影响资金与状态机；
- 任何失败都留痕、可查、可重试或可人工处理，**没有静默丢失**；
- 重试与跨副本重放**恰好一次**，由数据库唯一约束保证而非代码自觉。

## 与 MQ 的关系（演进，不在本批次）

发件箱是 MQ 的**前置**而非替代：真要上 Kafka/RocketMQ，让 relay 进程
从 `OutboxEvent` 顺序读取并投递即可，`publish()` 的调用方一行都不用改。
先做发件箱、后接 MQ 的顺序不能反——反过来会掉进两阶段提交的坑。
