
# 410 SDK 入参字段漏发闸门

> 状态：本批实现（V437）。编号 CLI-090。
> 来源：自查。V435 写测试时撞上：`taskDraftProfile(draft: TaskDraftInput)` 的请求体逐个列字段，`TaskDraftInput` 加了 `task_certs`，类型检查全过，请求里却没有这个字段，服务端收不到。已有的形状闸门只查：
> - SDK 发的字段服务端认不认；
> - 服务端返回的字段 SDK 声明没声明。
>
> 它不查「入参类型里有、请求体里没发」。
> 只增不减：只加一道闸门，不改任何接口。

## 0. 要解决的问题

SDK 方法收一个类型化的入参对象、请求体却逐个挑字段发时，往入参类型里加字段的人往往只改类型和调用处，忘了请求体那一行。类型检查发现不了：字段是可选的，调用方传了，SDK 自己丢了。

## 1. 业界怎么做（带来源链接）

常见做法是请求体直接用入参对象（或展开），或者用代码生成保证类型与请求一致；做不到的，就用静态检查兜底。本仓库已有的形状闸门（CLI-067 / CLI-083）就是这种静态兜底。本轮没有引用外部报道链接。

## 2. 数据

不涉及。

## 3. 接口

不改接口。

`server/tests/test_sdk_input_fields.py` 的检查规则：

- **扫哪些方法**：签名是 `name(param: SomeInput…)`、`SomeInput` 是 `types.ts` 里的接口、请求体里用 `param.字段` 逐个取字段的方法。
- **要求**：接口里的每个字段，都要在请求体里出现。
- **不查的**：请求体把整个对象展开（`...param`）或原样发出去的，不会丢字段。

现在扫到 6 个方法：`createNote`、`saveOpcProfile`、`addOpcEntry`、`taskDraftProfile`、`createVouch`、`setGigAvailable`。全部发全了（`taskDraftProfile` 在 V435 已补）。
