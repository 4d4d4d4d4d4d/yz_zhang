# 55 国际化：先把机制做对，不做一次性的机械搬运（I18N）

> 需求回顾里我把这条列为 P2 缺口：「全站零 i18n，所有文案硬编中文，
> 出海要重做一遍」。
>
> 实测规模：服务端 **382 处**中文错误消息、**140 个**含中文的 Python 文件，
> Web 侧约 **1197 处**中文字面量。

## 0. 先说清楚这一批**不做**什么，以及为什么

最容易做的版本是：写个脚本把 1197 个中文字面量抽成 key，生成
`zh-CN.json`，全站替换成 `t('key_1234')`。**我不做这个版本**，三条理由：

1. **没有第二个语种可以验证。** 抽完之后，唯一能证明「没抽坏」的办法是
   人肉点一遍全站。而一次抽错（把动态拼接的句子抽成静态 key、
   把复数/性别形态写死）要等真的上了第二语种才会暴露。
   **一个无法验证的大改动，不是进展，是把风险推到以后。**
2. **机械抽取会把代码变难读。** `t('err_4471')` 比「余额不足」更难维护，
   而收益要等出海那天才兑现。
3. **法律文本不能这么搬。** 合同条款、风险揭示书、协议——
   **机器翻译的合同条款是法律负债，不是国际化。**

所以这一批做**机制**与**最该先做对的那部分**，并把剩下的如实记账。

## 1. I18N-001 真正的关键洞见：错误的稳定契约是 `code`，不是 `message`

平台的错误封装早就是：

```json
{"detail": {"code": "insufficient_balance", "message": "可用余额不足"}}
```

**`code` 已经是一个语言无关的稳定标识符**，全站 393 个。
客户端本来就该按 `code` 决定行为与展示，`message` 只是兜底。

这意味着**用户看到的绝大部分动态文案，不需要服务端翻译**——
把 code→文案的映射放在客户端，换语言就是换一张表。
服务端那 382 条中文消息，退化成「客户端不认识这个 code 时的兜底」。

这条判断把工作量从「翻译 382 条并维护同步」变成「客户端建一张表」，
而且顺带解决了一个既有问题：**同一个 code 在不同端的措辞现在会漂**。

### I18N-002 code↔文案表要双向对齐，且**不许静默兜底成空**

与 SYNC-002（账本科目）同一条规矩：
服务端能抛出的 code，客户端都要有文案；客户端多出的 code 说明服务端删过。

兜底行为：客户端不认识的 code **显示服务端 message**（而不是显示 code
本身或空白）——服务端消息虽然是中文，但至少是一句人话。

## 2. I18N-010 语言协商只有一个解析点

`Accept-Language` 头 + 用户偏好（登录后以用户设置优先），
在**一个函数**里解析成受支持的 locale，其余地方只读结果。

支持列表是**白名单**（`zh-CN` / `en`），不认识的一律回落 `zh-CN`。
不做「尽量匹配」：`zh-TW` 回落到 `zh-CN` 是一个**产品决定**
（简繁差异不只是字形），在没有繁体文案之前，回落到简体比回落到英文好。

## 3. I18N-020 法律文本**不走 i18n 机制**

合同条款、风险揭示书、用户协议、争议处理规则——这些**不进翻译表**。

理由：一份合同的效力取决于当事人对**那一份文本**的合意。
把它交给 key-value 翻译表，意味着有人改一行 JSON 就改了合同内容，
而且没有任何审阅环节。

正确做法是**整份文本按语种单独维护、单独由律师审阅、单独版本化**——
合同上写明「本合同以中文版为准」之类的准据条款。

这一批的做法：法律文本模块标记为 `legal_text`，**有测试禁止它们
被接进翻译表**。这是一条「故意不做」的闸门。

## 4. I18N-030 格式化：金额、日期、数字

- **金额**：平台内部一律整数分，展示层格式化。现有 `fmtYuan` 写死「¥」
  与两位小数——抽成按 locale 的格式化函数。
- **日期**：现有代码用 `toLocaleString()`（跟随浏览器）与
  `isoformat()`（服务端）。服务端**只出 ISO-8601**，展示交给客户端——
  这条已经是对的，写进 spec 免得以后有人在服务端拼中文日期。

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| I18N-001 | 客户端有 code→文案表，覆盖服务端可抛出的错误码 |
| I18N-002 | 双向对齐有测试；客户端不认识的 code 回落显示服务端 message |
| I18N-010 | 语言协商单一解析点；不支持的语种回落 `zh-CN` |
| I18N-011 | 用户偏好优先于 `Accept-Language` |
| I18N-020 | 法律文本**不在**翻译表里（有测试禁止） |
| I18N-030 | 金额格式化按 locale；服务端不产出本地化日期字符串 |
| I18N-040 | 新增错误码时若客户端没有文案，CI 会红 |

## 6. 这一批没做的（明确记账，逐条说清为什么）

- **I18N-050 Web/App 界面 1197 处静态文案没有抽取。** 见第 0 节。
  这不是「忘了」，是**判断它现在做收益为负**。真要出海时，
  正确顺序是：先定第二语种 → 有人能校对 → 再抽取，边抽边验。
- **I18N-051 只建了 `en` 的骨架，没有真正的英文文案。**
  我不产出未经母语者校对的英文界面文案——一份半吊子的英文界面
  比纯中文界面更伤信任。表结构与闸门先立住。
- **I18N-052 没有复数/性别/语序处理。** 中文没有这些形态，
  一旦接入英文等语言需要 ICU MessageFormat。现在引入会增加复杂度
  而无法验证。
- **I18N-053 服务端 382 条中文消息保留。** 按 I18N-001 的判断，
  它们退化为兜底，不是主要展示路径。真要多语种服务端消息时，
  再按 code 补服务端翻译表。
- **I18N-054 时区**：服务端全用 UTC 并出 ISO，但**没有用户时区设置**。
  任务截止时间这类在跨时区场景下会误导，出海前必须补。
