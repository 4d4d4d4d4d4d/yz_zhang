# 444 两端发单页选按结果计价与分档

> 状态：本批实现（V471）。编号 OUT-052。
> 来源：443 号第 7 节记下的欠账 OUT-052。按结果计价（52 号）和分档（443 号）在服务端早就能用，两端的发单页却选不了：
> - 网页的计价方式只有「一口价」「竞价」；
> - App 的发单页根本没有计价方式；
> - SDK 里 `TaskInput.acceptance_criteria` 还声明成 `string[]`，而服务端要的是对象（text / kind / check），照着类型写的请求会被服务端拒掉。
>
> 「做得好多给钱」只有走 API 的集成方用得上，普通发布方用不上。
> 只增不减：一口价、竞价的发单照旧，不选按结果计价时请求一个字段都不多；`acceptance_criteria` 的类型改成「字符串或对象」，原来的写法照样能过类型检查。

## 0. 要解决的问题

让发布方在两端发单页上：
- 选「按结果计价」；
- 写交付说明里必须写明的关键词（每个关键词变成一条平台判定的指标）；
- 写全部达标的加付金额，或者写分档。

规则全在服务端，客户端只做两件事：把填写变成请求体；明显没填完的当场说清，不发一个注定被拒的请求。

## 1. 业界怎么做（带来源链接）

外包、众包平台的「奖励 / bonus」一般在发单表单里填条件和金额，条件写成可核对的交付要求。本轮没有引用外部报道链接。

## 2. 数据

不涉及。

## 3. 接口

不改服务端接口。SDK：
- 新类型 `AcceptanceCriterionInput`（text / kind / check）。
- `TaskInput.acceptance_criteria` 改成 `Array<string | AcceptanceCriterionInput>`。
- 新文件 `packages/core/src/outcome.ts`，两端共用：
  - `outcomeCriteria(keywords)`：关键词按逗号、顿号、换行拆开，去空、去重，每个变成 `{text: 交付说明写明「X」, kind: auto, check: {op: contains, value: X}}`；
  - `outcomePayload({keywords, bonusYuan, tiers})`：
    - 没关键词、分档只填一半、上限和分档都没写，就返回 `{error}`，并说清缺什么；
    - 写了分档带 `bonus_tiers`，不带 `bonus_cents`（服务端取最高一档）；
    - 只写上限带 `bonus_cents`；
    - 整行空着的分档忽略。

## 4. 两端

- **Web 发单页**（`Publish.tsx`）：
  - 计价方式多一项「按结果计价（达标加付）」；选了出现一组输入：关键词、全部达标加付（元）、分档（最多 5 档，可加可删）；
  - 写了分档，「全部达标加付」就不能填；
  - 没填完的在页面上说清，不发请求。
- **App 发单页**（新文件 `app/outcomePublish.tsx`）：
  - 「按结果计价」开关，打开才出现同样的输入；项目型不出现（项目先拆解）；
  - 请求体与网页同一份。

## 5. 隐私、授权与边界

- 钱的规则全在服务端：递增、够得着、上限等于最高一档、不超过基础报酬、托管、退回。
- 服务端拒绝时，两端原样显示服务端的理由。
