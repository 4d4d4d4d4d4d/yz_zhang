
# 401 举报处置队列：最急的在前与处理时限

> 状态：本批实现（V428）。编号 RISK-016。
> 来源：上一批（V426，399 号）「没做的」第一条。举报带了类型以后，诈骗、违法的举报仍和「其他」一起按编号排，审核员要从头翻；也没有任何地方说一条举报等了多久、该在多久内处理。
> 只增不减：`GET /admin/reports` 不传 `sort` 时与以前一样按编号排，每行多四个字段；SDK `adminReports()` 多一个可选参数；后台多一个勾选框，默认不勾。

## 0. 要解决的问题

- 诈骗、违法、色情这三类，拖一天就可能有人受骗或内容扩散，应当先处理；
- 审核员看不出哪条已经等太久；
- 主管看不出队列有没有积压超时。

## 1. 业界怎么做（带来源链接）

- 《网络信息内容生态治理规定》第十六条要求「及时受理处置」。常见做法是按风险分级排队，高风险先处理，并给每一级设内部处理时限，超时标红或升级。客服工单这边平台早就这么做了（ESCA-051/052，150、172 号）。
- 本轮没有引用外部报道链接。

## 2. 数据

不加表、不加列：轻重由举报类型决定，等了多久由提交时间算出。

| 档 | 类型 | 处理时限 |
|---|---|---|
| 急 | 违法违规、诈骗或骗钱、色情低俗 | 24 小时 |
| 一般 | 其余 | 72 小时 |

时限是内部承诺，不对举报人承诺。

## 3. 接口

- `GET /admin/reports?sort=urgent`：急的在前，同一档里先来的在前；`sort` 只收 `id` 或 `urgent`，别的值 422。
- 每行多四个字段：
  - `urgent`：是不是急的那一档；
  - `waited_hours`：已经等了几个小时（服务端算好，客户端不自己解析时间）；
  - `sla_hours`：时限几个小时；
  - `overdue`：没处理且等够了时限。

## 4. 两端

- **SDK**：
  - `adminReports(status, sort?)`，不传 `sort` 时地址与以前一样；
  - `reportSlaLine()`：「已等 5 小时（24 小时内处理）」，超了加「已超时」，字段缺了不显示。
- **Web 后台**：举报处置板块
  - 多一个「最急的在前」勾选框；
  - 「类型」列加「急」标记和时限一行，超时的标红；
  - 有超时的，板块顶上写「有 N 条举报已超过处理时限」。
- **App**：后台只在 Web 上，App 不涉及。

## 5. 隐私、授权与边界

不放宽谁能看队列：仍是客服或合规角色（SEC-061b）。
