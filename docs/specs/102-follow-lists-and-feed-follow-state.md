## 0. 起点

V117 把「关注」从 toggle 改成了两个幂等动作，并给空间页补了读状态的接口。
当时记进台账、没做的两件：

- **CNT-024 内容流里的关注按钮没有状态**：web 的按钮永远写着「关注」，
  已关注的人点了没有任何变化（幂等），也没法从流里取消关注；
  App 的内容流**连关注按钮都没有**。
- **CNT-023 没有关注列表页**：空间页只有「N 人关注」这个数字。
  「这 42 个关注者是谁」答不出来。

## 1. 内容流带上关注状态（CNT-024）

内容响应加一个字段：

| 字段 | 取值 | 含义 |
|---|---|---|
| `author_followed_by_viewer` | `true` / `false` | 当前登录的人是否关注了这条内容的作者 |
| | `null` | 未登录，或**这是自己的内容**——「对自己」这个问题没有意义（与 `follow-stats` 的 `viewer_following` 同一约定） |

列表（内容流、某人的作品）与单条（详情、发布后回显）都带，形状一致。

两端：

- **web 社区页**：按钮有状态（`aria-pressed`），「已关注」点了是取消关注。
  同一作者在这一页的几条**一起变**，不重新拉整页。`null` 不画按钮。
- **App 发现页**：内容卡片补上关注按钮，行为同上。

## 2. 那一页的查询次数（CONC-066，内容流部分）

做第 1 节时撞上一个既有的 N+1：`_dump` 每条内容各查两次（作者、我是否点过赞），
一页 20 条就是 40 多次查询。照原样再加「我是否关注了作者」就是 60 多次。

改成列表接口**一页三次**：作者一次、我点过赞的一次、我关注的作者一次
（`_ListCtx`）。单条接口仍逐条查——那里只有一条。

**钉的是「不随条数增长」，不是一个绝对数字。** 测试在 SQLAlchemy 的
`before_cursor_execute` 上数 SELECT，一页 5 条与一页 20 条必须相等。
绝对数字会因为鉴权、限流这些与这一页无关的东西变动，那会是假报警。

这只是 CONC-066 的一部分：**内容流与「某人的作品」两个列表**。其余列表接口
没有系统性排查，台账里那一行保留并改写成剩下的范围。

## 3. 关注 / 粉丝列表（CNT-023）

```
GET /users/{user_id}/followers?after=&limit=   谁关注了他
GET /users/{user_id}/following?after=&limit=   他关注了谁
→ {"items": [{user_id, nickname, followed_at, viewer_following}], "next_cursor"}
```

### 3.1 谁能看

**关注关系本身就是个人信息**：「谁关注了谁」会暴露一个人的兴趣与社交圈。

| 访问者 | 列表主人 | 结果 |
|---|---|---|
| 本人 | 自己 | 总能看 |
| 别人（含未登录） | 资料公开、未封禁 | 能看（与公开空间同一口径） |
| 别人 | 资料不公开，或已封禁 | **403 `follow_list_private`**「对方未公开资料，看不到关注列表」 |
| 任何人 | 不存在或已注销 | 404 |

专用错误码而不是通用 `forbidden`：通用码会被客户端换成「无权执行该操作」，
看的人就不知道**为什么**看不了。也不复用 `profile_private`——那个码的补救是
「去改**你自己**的隐私设置」，对访客是错的指引。

### 3.2 列表里出现谁

| 谁在看 | 列表里的人 |
|---|---|
| 本人 | 所有未注销的人（包括设了资料不公开的——他选择了关注你） |
| 别人 | 只有资料公开、未封禁、未注销的人 |

后一条与空间、搜索（101 号 PRIV-061）**同一条可见性规则**（`_publicly_listed`）。
不这样做的后果：设了资料不公开的人，因为他关注了一个公开的人，就出现在
那个人的粉丝列表里给所有人看——**隐私设置被别人的公开设置绕过了**。

### 3.3 分页

游标是关注关系的 id，降序（新关注在前），不是页码。列表在翻页时还在变化
（有人刚关注），页码会让同一个人出现两次或被跳过。每页至多 50。

### 3.4 每个人旁边的按钮

`viewer_following` 是**访问者自己**是否关注了列表里的这个人（一次查完，不逐个查），
所以列表里的按钮有状态，点了只改那一个人。未登录或那个人就是访问者自己时为 `null`。

### 3.5 两端

| 端 | 入口 | 行为 |
|---|---|---|
| web | 空间页「N 人关注」→ `/people/:id/follows?tab=followers` | 「关注者 / 正在关注」两个 tab（tab 在 URL 里，能分享能后退）；名字点进空间；加载更多；按钮有状态；403 把服务端的话显示出来 |
| App | 空间页「N 人关注 ›」「他关注的人 ›」 | 同上 |

## 4. 闸门

| 闸门 | 内容 |
|---|---|
| CNT-024a | 内容流对关注的、没关注的、自己的三种作者分别给出 `true` / `false` / `null` |
| CNT-024b | 单条接口走逐条查询那条路，字段与列表一致 |
| CONC-066 | 内容流一页 5 条与 20 条查询次数相等 |
| CNT-023a | 别人看到的粉丝列表里只有资料公开、未封禁、未注销的人 |
| CNT-023b | 本人看得到设了不公开的粉丝，看不到已注销的 |
| CNT-023c | 资料不公开的人的两个列表对别人 403、对本人 200 |
| CNT-023d | 列表带访问者自己的关注状态 |
| CNT-023e | 游标分页不重复、不漏人 |
| CNT-023f | 公开的人的列表未登录也能看，按钮状态为 `null` |
| 形状 | 两个列表接口返回的是函数调用，静态扫描读不到——用真实响应与 SDK 声明比（字面量方法名，CLI-083 的扫描靠它认） |
| 授权记账 | `OWNERSHIP_RULES` 给两个列表单独一条规则，写明隐私判断（不再落进 `^GET /users/` 那条泛规则） |
| 两端 | web 5 条（流里按钮有状态且同作者一起变、自己的不画、列表、403 文案、切 tab 打另一个接口）；App 3 条 |
| 联调 | 真浏览器从空间页点「N 人关注」进到列表（14 项） |

六条红验走过：去掉批量查询 → 查询次数断言红；流里关注状态恒为 `false` → 两条红；
别人看到的列表不过滤 → 红；不公开的人的列表对别人可见 → 红；
web 按钮不看状态 → 红；App 列表点了不更新 → 红。

## 5. 这一批没做的

- **其余列表接口的 N+1 没有系统性排查**：本批只改了内容流与「某人的作品」。
  要系统地做，得在测试里给每个列表接口跑「5 条 vs 20 条」——台账 `CONC-066` 保留，
  范围改写成剩下的部分。
- **不做关注通知**：仍是 `CNT-025`，理由不变（先定骚扰与免打扰策略）。
- **列表里不显示头像与简介**：只有昵称与关注时间。补头像要先定 App 的图片缓存口径，
  不在这一批。
