
# 295 后台板块内的按钮级权限隐藏

> 状态：本批实现（V322）。编号 SEC-061h。
> 来源：165 号 spec「没做的」——「一个板块里有的按钮要另一个角色（例如工单板块里「指派」要客服主管、封禁要合规），现在仍靠服务端 403 的说明」；BACKLOG V322。
> 只增不减：板块按角色显示（165 号）不变；有权限的人看到的按钮一个不少。**改了一处旧行为**：从举报里「封禁」以前客服也能做，现在与直接封禁一样要「合规」（见第 2 节，是一处越权的修复）。

## 0. 要解决的问题

- 客服看得到「用户管理」与「举报处置」两个板块（165 号），里面的「封禁」「解封」按钮也照样显示，点了才 403。
- 做这一批时发现：直接封禁（`POST /admin/users/{id}/ban`）只给合规，可「举报处置」里的「封禁」走的是 `POST /admin/reports/{id}/resolve`（客服与合规都能调），服务端在里面直接封号——**客服能绕过合规封人**。

## 1. 业界怎么做

后台权限通常做到「功能点」一级：界面上按不了的操作不显示或置灰并说明，服务端同一规则再拦一次；同一个操作从不同入口进来，权限必须一致。（本批没有另找外部来源。）

## 2. 规则

- 共享 SDK `ADMIN_ACTIONS`：每个按钮记它调的接口（probe）与角色，规则与板块相同（`canDoAdminAction`，没分配角色的老管理员按超级管理员）：
  - 「封禁用户」`POST /admin/users/{user_id}/ban` → 合规；
  - 「解封用户」`POST /admin/users/{user_id}/unban` → 合规；
  - 「指派工单」`POST /admin/tickets/{ticket_id}/assign` → 超级管理员（原来页面里自己写的 `isSuper` 判断改用这里，行为不变）。
- 按不了的按钮不显示，换成一句「封禁用户要合规来做」（`adminActionHint`）。
- 服务端：举报处置选「封禁」时，处置人必须有合规角色，否则 403 `admin_role_required`，写明「可以驳回或下架内容，封禁请转给合规」；被拒时举报不被标成已处理、用户不被封。客服驳回、下架照旧。

## 3. 数据 / 接口

不新增表与接口。

## 4. 两端

- **Web 后台**：「举报处置」「用户管理」里的封禁 / 解封按角色收起；「客服工单」里的指派照旧只有超级管理员看得到。
- **App**：后台只在 Web，不涉及。

## 5. 隐私、授权与边界

界面收起只是方便，真正的拦截在服务端（两个入口现在同一条规矩）。
