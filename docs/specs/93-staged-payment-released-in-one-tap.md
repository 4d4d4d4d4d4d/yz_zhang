
# 93 分期合约在一次点击里被放光（SC-013 / CLI-076）

> 状态：本批实现（V120）
> 依赖：05 号（智能合约：SC-004 里程碑分期、SC-005 验收触发放款）、
> 66 号（补救入口）、87 号（服务端叫他做而客户端上做不到）

## 0. 台账上那条欠项，和它实际的样子

72 号台账里 `SC-013` 的原话是：

> 定义了分期之后，仍可整单交付、整单验收并一次放完全款，
> **没有测试说明这是有意的**

先去读服务端。`contract/service.py` 的 `release()` 第一行写着：

```python
"""SC-005 整体验收放款：放出全部剩余托管（已分期放款的部分不重复）。"""
```

然后它确实只放 `remaining = amount_cents - released_cents`，并且在放完之后
把所有没放的期一并标成 `released`：

```python
db.query(Milestone).filter(
    Milestone.contract_id == contract.id, Milestone.status != "released"
).update({"status": "released"})
```

**这条路是自洽的**：钱不会重复付，里程碑表不会留下「钱付了、期还 pending」
的脏状态。所以它不是漏判，是有意设计——发布方自己点的验收，
平台没有理由替他拦住。

（我原本以为未交付的期会留下 pending，是测试把我纠正了。
**写断言之前的猜测不如跑一遍。**）

## 1. 那么真正缺的是什么

两件，一件在服务端，一件在客户端，台账把它们混成了一条。

**服务端缺的只是一句说明。** 「没人说过」与「有意为之」在代码里看起来
一模一样——下一个人读到「分期合约可以整单放完」时，无法判断该修它还是
该保留它。docstring 写了，但 docstring 不会在有人改坏它的时候变红。

**客户端缺的是决定点本身。** 这才是这一批的主体：

web 与 App 上那个按钮当时都只写了四个字 ——「验收通过（放款）」。
按下去，剩余所有期一起放完。

发布方当初把一笔钱切成三期，**正是为了不一次付完**。
分期是他给自己设的保护。在一个完全不提里程碑的按钮上一次放光，
他失去的是自己设的那道保护，而且**在点之前屏幕上没有任何东西提到它**。

这与 66 号 spec 是同一条规矩的另一面：不是「平台没这个能力」，
而是「平台把一个后果很重的能力摆成了一个看起来很轻的动作」。

## 2. 服务端：把意图钉住，而不是改行为

**不改 `release()`。** 行为是对的，拦住它反而会让「发布方想一次付完」
变成做不到的事（而那是分期合约里完全合理的一种结局：活干完了，
他不想再点三次）。

补两条测试，钉住两件事：

| 闸门 | 内容 |
|---|---|
| SC-013 | 分期合约上整单验收，放的是**剩余**托管，不重复付已分期放掉的部分 |
| SC-013b | 整单验收**会**付掉尚未交付的期，并把它们全部标成 `released`（不留 pending） |

第二条尤其要写下来：它看起来像个 bug，所以必须有一条测试说
「这是它的含义」，否则下一个人会把它「修」掉，而修掉的后果是
钱放完了、里程碑还显示欠着。

## 3. 客户端：在还有未放期时，把代价摊开

两端的判据相同：**取合约里 `status !== 'released'` 的期**，
多于一期才拦。

- **多于一期**才说明他当初真的分了期、而且现在要一次放掉不止一笔。
- **只有一期**（绝大多数合约、以及分期合约的最后一期）**直接给按钮**。
  一个假报警多的闸门会被人关掉——在用户界面上，它会被人闭着眼点过去，
  那比没有更糟。

说清的内容是三件：**几期、共多少钱、以及替代做法是什么**。
只说「确定吗」没有信息量；他需要知道的是「只想付已完成的那一期，
请用下面分期列表里的『验收本期』」——否则拦住他之后他无路可走。

两端的做法按各自平台的惯用法：

- **web** 用 `confirm()`：浏览器里这是用户认得的模态，取消就什么都不发。
- **App** 做成**两步**：RN 里没有 `confirm()`。第一下只把「剩余 N 期、
  共 X 元」连同替代做法画在屏幕上，**不发任何请求**；
  第二下才是「确认整单放款」。与 92 号 spec 里撤回同意的两步同一形状——
  手机上误触一下的代价太大。

## 4. 闸门

| 闸门 | 内容 |
|---|---|
| SC-013 | 整单验收放的是剩余托管，不重复付已放的期 |
| SC-013b | 整单验收会付掉未交付的期，并把它们全标成 `released` |
| CLI-076 | web：未放期多于一期时，确认文案里必须出现期数与合计金额；取消不发请求 |
| CLI-076b | web：只剩一期时**不得**弹确认（假报警会被人关掉） |
| CLI-076c | App：未放期多于一期时第一下只摊开后果、不发请求；第二下才放款 |

五条红验走过：web 去掉确认（直接放光 → 红）、web 把阈值改成 `> 0`
（单期也问 → 红）、App 去掉两步（→ 红）、服务端把 `remaining` 改成全额
（重复付已放的期 → 红）、服务端放款后不标里程碑
（留下「钱付了、期还 pending」→ 红）。

## 5. 这一批没做的

- **没有在服务端拦住整单放款**：见第 2 节。行为是有意的，
  缺的是说明和客户端的决定点。
- **没有做「只放已交付的几期」的批量动作**：现在要分三次点「验收本期」。
  真要做是个新端点（`accept-delivered-milestones`），
  而它和「整单验收」的语义区别得先在 05 号 spec 里写清楚，
  否则界面上会出现两个长得很像的放款按钮。记在台账（`SC-014`）。
- **文案里的金额沿用 `fmtYuan`，没有千分位**：V119 已经踩过一次
  （`¥4600.00`）。改它会动到两端所有金额显示，属于单独一批。
