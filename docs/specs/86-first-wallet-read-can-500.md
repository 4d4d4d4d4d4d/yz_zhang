
# 86 第一次打开钱包可能 500（PAY-046 / CONC-053）

> 状态：本批实现（V112）
> 依赖：04 号（钱包与资金）、18 号（并发）、84 号（没有人跑的脚本）

## 0. 探针：它是怎么被抓到的

这个缺陷不是查出来的，是**V110 的修复顺手撞出来的**。

修完压测脚本后照例跑一遍 `scripts/smoke.py`，它在倒数第三步红了：

```
✓ 验收放款
✗ 执行方到账（扣 8% 佣金）  None == 18400
```

`None` 说明 `GET /wallet` 的返回里没有 `available_cents`。翻服务端日志：

```
INFO:  127.0.0.1 - "GET /api/v1/wallet HTTP/1.1" 500 Internal Server Error
sqlite3.IntegrityError: UNIQUE constraint failed: wallet_accounts.user_id
```

单独重跑一遍，绿。**一个间歇性的 500。**

先写探针确认它不是环境噪音——新用户并发打 12 次 `GET /wallet`：

```
PROBE 并发首次读钱包的状态码分布: {200: 11, 500: 1}
PROBE 有 500: True
服务端日志里的唯一约束错误: 2 处
```

**稳定复现。**

## 1. 病因：check-then-insert

```python
def get_or_create(db, user_id):
    acct = db.get(WalletAccount, user_id)
    if not acct:
        acct = WalletAccount(user_id=user_id)   # 两个请求都走到这里
        db.add(acct)
        db.flush()                              # 后一个撞唯一约束 → 500
    return acct
```

钱包账户行是**懒建**的：注册时不建，第一次碰钱包才建。
两个并发请求同时看到「没有」，于是都插入。

## 2. 为什么这不是「理论上的竞态」

两条真实触发路径：

- **客户端首屏同时发两个请求**：web 与 App 都登着、或者手抖点两下；
  首屏本来就常常并行拉多个接口。
- **放款后的事件处理与用户请求并发**：用户刚收到「到账」通知就点开钱包，
  **那正是最可能撞上的一刻**——通知到达与钱包首次被碰几乎同时。

而 500 的那个页面是**钱包**。用户看到的是「服务器错误」，
而他刚刚被告知有一笔钱到账。**在钱的页面上报 500，比在别处报 500 更贵**：
用户的第一反应不是「刷新一下」，是「我的钱呢」。

## 3. 为什么 1194 条测试都没抓到

测试套件用 `TestClient`，**串行、单进程**。串行的 check-then-insert 永远
不会撞车——第一个请求已经把行建好了。

`test_conc_hardening.py` 里有真并发的用例，但它们盯的是
「重复接受报名 / 重复托管 / 重复放款」这类**已经想到的**竞态点，
而「第一次读一个只读接口」不在任何人的怀疑名单上。

这条值得记下来：**只读接口也会写库**（懒建、懒迁移、懒初始化），
而一旦它写库，它就有并发问题。「GET 不会出事」是个错觉。

## 4. 修法：SAVEPOINT，不是加锁

```python
acct = db.get(WalletAccount, user_id)
if acct:
    return acct
try:
    with db.begin_nested():          # SAVEPOINT
        acct = WalletAccount(user_id=user_id)
        db.add(acct)
        db.flush()
    return acct
except IntegrityError:
    acct = db.get(WalletAccount, user_id)   # 别人刚建好了，重读
    if acct is None:
        raise                                # 读不到才是真的坏了
    return acct
```

两个选择都值得说明：

**为什么用 `begin_nested()`**：插入失败会让整个事务进入不可用状态。
而这个函数的调用方常常正在做**放款 / 托管这种多步写入**——
外层事务被毒化的代价远大于这一行。SAVEPOINT 让失败只回滚这一步。

**为什么不加锁**：`SELECT ... FOR UPDATE` 在 SQLite 上没有；
即便在 Postgres 上，为了一行懒建去锁住整张表或用顾问锁，
代价和复杂度都比「让唯一约束去做它本来就在做的事」高。
**唯一约束已经是正确的仲裁者，缺的只是接住它的那一手。**

**为什么重读之后仍可能 raise**：如果 `IntegrityError` 不是因为别人先建好，
而是别的约束坏了，那就该炸。**把异常吞掉换成一个 `None` 返回，
是把 500 换成后面某处更难查的 `NoneType` 错误。**

修复后重跑探针：

```
修复后 状态码分布: {200: 36}   有 500: False
日志里的唯一约束错误数: 0
```

## 5. 闸门

| 闸门 | 内容 |
|---|---|
| CONC-053 | 并发 8 次首次碰钱包账户：不许有人拿到异常、不许返回别人的账户、最终只许一行 |

红验：把修法撤回成 check-then-insert，这条当场红。

闸门断言三件事而不只是「没异常」：
「只许一行」防的是**有人改成先删后插或关掉唯一约束**这种「修好了红灯」
的解法；「不许返回别人的账户」防的是重读时把 `user_id` 搞错——
**在钱包上把 A 的账户返回给 B，比 500 严重得多**。

## 6. 这一批没做的

- **同一个形状还有一处，这一批只记不改**：搜了一遍 `get_or_create` 形状的
  函数，`im.get_or_create_direct` 一模一样。但它的后果**不同**：那张表上
  没有唯一约束，所以并发不会 500，而是**静默建出两条单聊会话**——
  两个人各说各话，消息分在两条线上，而谁都不会看到错误。
  **没有约束的地方，竞态不会报错，只会把数据悄悄弄错**，这比 500 难查得多。
  根治要先给「参与者对」一个唯一键（需要迁移），不是一行改动，
  记在 72 号台账（`CONC-054`）。顺带看到同一个函数**把全平台所有单聊取出来
  在 Python 里比参与者集合**（`IM-051`），应当一起改。
- **不改成注册时预建**：那样要为历史用户补一次数据迁移，且「预建」也只是
  把窗口从「第一次读」挪到「注册」——注册本身也可能并发（重复提交）。
  接住唯一约束才是根治。
- **smoke 的失败信息仍然不好读**：它报的是 `None == 18400`，
  而真正的原因要去翻服务端日志。让闭环脚本在断言失败时顺手打印最近的
  服务端错误，是一条独立的改进（`DRILL-034`）。
