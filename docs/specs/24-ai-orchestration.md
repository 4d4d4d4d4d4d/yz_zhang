# 24 · AI 编排增强：模型驱动的验收与迭代（AIO）

> 现状：任务分解**已经在调真实模型**（`decompose/llm.py::AnthropicLLM`，
> claude-opus-4-8 + JSON Schema 强制结构化输出 + 服务端校验 + 失败降级模板）；
> 编排循环（`orchestrator/`，V41）也已跑 plan → dispatch → observe → evaluate →
> 生成修复步的闭环。
>
> **真缺口在验收**：`evaluate()` 只数「任务状态是不是 completed」，
> 不看交付物本身。也就是说这个 agent 能管流程，管不了**成果达标与否**——
> 执行者交一句「做完了」和交一份合格产出，在当前循环里没有区别。
> 本 spec 补的就是这一段。

## 24.A 验收标准显式化（P0）

- **AIO-001** Mission 已有 `acceptance_criteria`（JSON），但目前只存不用。
  改为：规划阶段由模型为**每个子任务**产出可判定的验收要点
  （`checklist: [{item, how_to_verify}]`），随任务一并发布给执行者——
  执行者从一开始就知道「怎样算做完」，这比事后争议便宜得多。
- **AIO-002** 验收要点写入任务描述与合约条款附录，**成为合同的一部分**，
  纠纷时可直接引用（与 11 号 spec 的证据链衔接）。

## 24.B 模型辅助验收（P0）

- **AIO-010** `ReviewGateway` 抽象：`review(criteria, deliverable) -> {verdict, score, reasons, missing}`。
  - `RuleReview`（缺省/离线）：沿用现状——状态为 completed 即通过；
  - `ModelReview`（配 Key 时启用）：把验收要点 + 交付说明 + 进度留痕 + 图片凭证
    的**文本描述**交给模型，产出结构化评审结果。
- **AIO-011** 输出强约束：JSON Schema（verdict ∈ pass/revise/fail、score 0-100、
  reasons 数组、missing 数组），服务端校验不通过即降级为 `RuleReview`。
- **AIO-012** **模型永远不能单独动钱**（第一性约束）：
  - `pass` → 仅作为「建议通过」提示给发布方，**仍由人确认放款**；
  - `revise` → 自动生成整改要点并通知执行者，不改变资金状态；
  - `fail` → 进入人工复核队列，**不自动扣款、不自动罚没**。
  理由：模型会错，而资金操作不可逆。AI 只做「谁该看一眼」的分诊。
- **AIO-013** 评审留痕：`ReviewRecord` 记录模型、提示词版本、输入摘要（脱敏）、
  输出、耗时。没有留痕的自动判定在纠纷里毫无价值。

## 24.C 循环质量提升（P1）

- **AIO-020** `evaluate()` 引入**质量维度**：完成度 = 步骤完成率 ×
  平均验收得分，而不是只看步骤计数；低分步骤触发整改而非直接算完成。
- **AIO-021** 重规划：连续两轮整改仍未达标 → 由模型重新拆解该步骤
  （拆得更细/换技能标签/提高预算建议），而不是无限重试同一形态。
- **AIO-022** 迭代摘要：每轮 tick 产出人类可读的进展摘要（做了什么、
  卡在哪、下一步），写入 Mission 时间线——agent 必须可解释，否则没人敢授权预算。
- **AIO-023** 成本与配额：记录每次模型调用的 token 与耗时；
  Mission 级模型调用次数上限，防止循环把 API 账单打爆。

## 24.D 网关工程化（P0）

- **AIO-030** 统一走 19 号 spec 的供应商框架：模型调用纳入 `VendorCall` 留痕、
  幂等、熔断——LLM 也是外部依赖，不该有特权。
- **AIO-031** 超时与重试：单次调用超时上限、指数退避重试上限，
  重试耗尽即降级，**绝不无限等待**（编排 tick 是 job，卡住会拖垮整条流水线）。
- **AIO-032** 提示词版本化：`PROMPT_VERSION` 常量随留痕落库，
  换提示词后能定位「哪些判定出自旧版本」。
- **AIO-033** 脱敏：送模型的内容剔除手机号/证件号/收款账户，
  与日志脱敏用同一套 `redact`。

## 24.E 验证（P0）

- **AIO-040** 结构化输出校验测试：模型返回不合规 JSON → 降级规则评审，不抛错。
- **AIO-041** **模型不得动钱**测试：`ModelReview` 返回 `fail` 时，
  合约资金状态零变化，仅生成人工复核工单。
- **AIO-042** 降级测试：无 Key / 超时 / 熔断打开三种情况都能正常完成一轮 tick。
- **AIO-043** 配额测试：Mission 模型调用达上限后停止调用并挂起，不静默烧钱。
- **AIO-044** 脱敏测试：送模型的载荷不含手机号与证件号。

## 验收标准

- 不配 Key 时全部测试通过（规则评审路径），配 Key 后行为增强而非改变契约；
- 任何模型输出都不能直接导致资金变动；
- 每一次自动判定都能追到模型、提示词版本与输入摘要。
