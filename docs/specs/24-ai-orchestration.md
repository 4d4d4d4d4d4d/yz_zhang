# 24 · AI 编排增强：让循环真正闭环（AIO）

> ## 检视结论（基于对 `orchestrator/service.py` 的逐行复查）
>
> **已经在跑真模型**：`decompose/llm.py::AnthropicLLM`，claude-opus-4-8 +
> JSON Schema 强制结构化输出 + 服务端校验（预算守恒、依赖不成环）+ 失败降级模板。
> `orchestrator/` 也已跑 plan → dispatch → observe → evaluate → 修复步的循环。
>
> **但这个循环现在闭不上**，有四个具体缺陷：
>
> | # | 缺陷 | 后果 |
> |---|---|---|
> | 1 | `evaluate()` 只数 `task.status == "completed"` | 执行者交一句「做完了」和交合格产出，在循环里**没有区别** |
> | 2 | `_make_remedy_steps` 是**同规格重发**（`args=dict(s.args)`） | 上次没人接/没做好，同样的标题、预算、技能要求再发一次，**凭什么这次会成功** |
> | 3 | 修复步幂等靠**标题字符串匹配** `title == f"[修复] {s.title}"` | 脆弱，且多轮后标题会变成 `[修复] [修复] [修复] X` |
> | 4 | **`spent_cents` 语义混乱**（见下） | 任务取消后额度不释放，几轮迭代必然 `blocked`，循环无法收敛 |
>
> ### 缺陷 4 展开：预算语义把两件事混成了一件
>
> `_dispatch_step` 在**发布任务时**就 `mission.spent_cents += budget`，
> 而任务流单/取消时**从不退还**。字段注释写的是「已承诺预算」，行为却是
> 「累计尝试过的金额」——这两个语义混在一起就必然出错：
>
> - 按「已承诺」理解：任务取消 = 钱根本没花出去（托管从未发生或已退款），
>   额度必须释放，否则 agent 会因为一堆**已经不存在的占用**而饿死；
> - 按「累计尝试」理解：它是 runaway 保护——但这个职责本来就由
>   `max_iterations` 承担，用预算来兼职做迭代上限，代价是把正常的重试也掐死。
>
> 现有测试 `test_budget_cap_blocks_remedy_dispatch` 固化的正是这个错误行为。
> 本 spec 修正它。

## 24.A 预算语义拆分（P0，先修地基）

- **AIO-024** 拆成两个独立的量，各司其职：
  - `committed_cents`（当前占用）：分发时 `+budget`；对应任务进入
    **终态且未花钱**（cancelled / 流单）时 `−budget`。护栏用它判断「还能发多少」。
  - `spent_cents`（真实花费）：任务**实际完成放款**时才 `+`。用于展示与对账，
    与钱包账本可交叉核对。
- **AIO-025** 护栏条件改为 `committed + 本步预算 <= budget_cap`；
  防死循环由 `max_iterations` **单独**承担（本来就是它的职责）。
- **AIO-026** 真·超预算仍必须挂起：单步预算就超过剩余额度时 `blocked`，
  等人工加预算或改规格，绝不静默继续花钱。

## 24.B 验收标准显式化（P0）

- **AIO-001** 规划阶段为**每个子任务**产出可判定的验收要点
  `acceptance: [{item, how_to_verify}]`：
  - `TemplateLLM`：按类目给通用要点（到场凭证、成果说明、双方确认），
    保证**离线可用**、不依赖 Key；
  - `AnthropicLLM`：由模型产出，纳入同一 JSON Schema 强校验。
- **AIO-002** 验收要点写入任务描述**并进入合约条款附录**——
  执行者从一开始就知道「怎样算做完」，这比事后争议便宜得多；
  纠纷时可直接引用（衔接 11 号 spec 的证据链）。
- **AIO-003** Mission 级 `acceptance_criteria`（用户填的总目标验收要求）
  作为规划输入下发给模型/模板，不再是**存了但从不使用**的字段。

## 24.C 模型辅助验收（P0）

- **AIO-010** `ReviewGateway` 抽象：
  `review(criteria, evidence) -> {verdict, score, reasons, missing}`
  - `RuleReview`（缺省/离线）：**基于可观测事实真打分**，不是假装通过——
    有无交付说明、有无图片凭证、进度留痕条数、驳回次数、是否自动验收超时通过；
  - `ModelReview`（配 Key 时）：把验收要点 + 交付说明 + 进度留痕 + 图片凭证的
    **文本描述**交给模型，产出结构化评审。
- **AIO-011** 输出强约束：JSON Schema（`verdict ∈ pass|revise|fail`、
  `score 0-100`、`reasons[]`、`missing[]`），校验不过即降级 `RuleReview`。
- **AIO-012** **模型永远不能单独动钱**（第一性约束）：
  - `pass` → 记为建议通过，**放款仍由发布方确认**（或既有的超时自动验收）；
  - `revise` → 生成整改要点、通知执行者，**不改变任何资金状态**；
  - `fail` → 进人工复核，**不自动扣款、不自动罚没**。
  理由：模型会错，而资金操作不可逆。AI 只做「谁该看一眼」的分诊。
- **AIO-013** 评审留痕 `StepReview`：模型名、提示词版本、输入摘要（脱敏）、
  verdict、score、耗时。**没有留痕的自动判定在纠纷里毫无价值**。

## 24.D 让循环收敛（P0，本 spec 的「闭环」核心）

- **AIO-020** 完成度引入质量维度：
  `completion_pct = done/total`（保持不变，向后兼容），
  新增 `quality_pct = 已完成步的平均评审分`。
  **达标条件 = 全部步 done 且 `quality_pct >= QUALITY_BAR`**，
  低分步不算过关，触发整改而不是直接算完成。
- **AIO-021** 修复步**带整改要点重发**，而不是原样复制：
  - 标题保持稳定（不再层层加 `[修复]` 前缀），用 `attempt` 计数表达轮次；
  - 描述追加上一轮的 `missing` 与 `reasons`；
  - 连续两轮仍不达标 → **重新拆解**该步（提高预算建议、调整技能标签），
    而不是无限重试同一形态。
- **AIO-022** 修复步幂等改用 `parent_step_id` 外键，**不再用标题字符串匹配**。
- **AIO-023** 迭代摘要 `MissionEvent` 时间线：每轮 tick 产出人类可读的
  「做了什么 / 卡在哪 / 下一步」。**agent 必须可解释，否则没人敢授权它花钱**。

## 24.E 网关工程化（P0）

- **AIO-030** 模型调用纳入 19 号 spec 的供应商框架：`VendorCall` 留痕、
  熔断——LLM 也是外部依赖，不该有特权。
- **AIO-031** 超时与重试上限，耗尽即降级，**绝不无限等待**
  （tick 是 job，卡住会拖垮整条流水线）。
- **AIO-032** 提示词版本化 `PROMPT_VERSION`，随留痕落库，
  换提示词后能定位「哪些判定出自旧版本」。
- **AIO-033** 送模型前脱敏：剔除手机号/证件号/收款账户，
  复用日志同一套 `redact`。
- **AIO-034** Mission 级模型调用次数上限，达上限即停止调用并降级规则评审，
  不静默烧 API 账单。

## 24.F 验证（P0）

- **AIO-040** 结构化输出不合规 → 降级规则评审，不抛错。
- **AIO-041** **模型不得动钱**：`ModelReview` 返回 `fail` 时合约资金零变化。
- **AIO-042** 降级三路径：无 Key / 超时 / 熔断打开，都能完成一轮 tick。
- **AIO-043** 配额：达上限后不再调用模型。
- **AIO-044** 脱敏：送模型的载荷不含手机号与证件号。
- **AIO-045** **预算释放**：任务取消后 `committed` 回落，修复步可正常分发
  （修正现有测试固化的错误行为）。
- **AIO-046** **真超预算仍挂起**：单步预算超过剩余额度 → `blocked`。
- **AIO-047** **质量闸门**：全部步 done 但平均分低于门槛 → 不算 succeeded，
  生成整改步。
- **AIO-048** 修复步幂等：重复 tick 不产生重复修复步（按 `parent_step_id`）。
- **AIO-049** 时间线：每轮 tick 有可读摘要。

## 验收标准

- 不配 Key 时全部测试通过（规则评审路径），配 Key 后**行为增强而非改变契约**；
- 任何模型输出都不能直接导致资金变动；
- 一个「首轮全部流单 → 修复 → 完成」的场景能真正走到 `succeeded`，
  而不是因为预算虚耗卡在 `blocked`。
