# 31 · 安全事件落库、跨副本封禁与人机验证（SECEV）

> 落地 [23-network-security.md](23-network-security.md) 的 SEC-021/022/023。

## 先说清楚现在的两个洞

### 洞一：注释在说谎（P0）

`app/core/guard.py` 第 20 行原文：

```python
# 进程内实现；多副本下配 Redis 时由 ratelimit 的 Redis 后端承担共享计数，
# 封禁本身落 DB（SecurityEvent），因此跨副本仍能看到。
_banned_until: dict[str, float] = {}
```

**`SecurityEvent` 这个表不存在。** 全仓库 grep 只有这一行注释提到它。
封禁状态就是一个进程内的 `dict`，跨副本什么都看不到。

三副本部署下的真实后果：

| 场景 | 实际发生的事 |
|---|---|
| 攻击者被封 | 只在处理那次请求的副本上被封，换个连接打到另外两个副本照样过 |
| 有效阈值 | 每副本各自计数，10 次 × 3 副本 = 实际要 30 次失败才可能触发 |
| 管理员看面板 | 只看到当前这个副本的封禁列表，另外两个副本封了谁完全不知道 |
| 管理员解封 | **只解了一个副本**。被误封的公司出口 IP 之后还有 2/3 概率被拒 |

最后一条最恶劣：**时好时坏的故障比稳定的故障难查一个数量级**。
用户报「有时候能登录有时候不能」，客服复现不出来。

而这一切被一行注释掩盖着——写注释的人（我）当时想的是「应该这么做」，
写下的却是「已经这么做了」。**注释比代码更容易骗人，因为没有测试盯着它。**

### 洞二：文档承诺了不存在的抽象（P0）

`docs/OPERATIONS.md` 的「⚠️ 仍需补的」表里写着：

> | **人机验证** | 抽象位已留（SEC-021） | 接第三方验证码，触发风控阈值后要求 |

「抽象位已留」——**没有留。** 全仓库没有任何 `captcha` 相关代码。
读文档的人会以为接入只是换个环境变量，实际要从零写。

## 31.A 安全事件落库（P0）

- **SECEV-001** `SecurityEvent` 表真正建出来：类型、IP、用户、明细、时间、失效时间。
  类型至少覆盖 `auth_failure` / `ban` / `unban` / `captcha_required` / `captcha_passed`。
- **SECEV-002** **封禁状态以 DB 为准**，不再是进程内 dict。
  任何副本读到的封禁列表都一样，管理员解封一次全局生效。
- **SECEV-003** 失败计数同样以 DB 为准——否则 N 个副本把有效阈值放大了 N 倍。
- **SECEV-004 写入量天然有界**：封禁检查在计数**之前**，
  被封的 IP 不会再产生新的失败记录。所以单个 IP 每个窗口最多写入
  「阈值」条，攻击者无法靠刷失败把表撑爆。
  这不是巧合，是把顺序排对了才有的性质，**改动这段代码时不能把顺序换掉**。
- **SECEV-005** 成功登录清掉该 IP 窗口内的失败记录（偶发手滑不该累积成封禁）。
- **SECEV-006** 保留期与清理 job：安全事件默认留 30 天。
  ⚠️ 封禁与解封记录属于**运营处置留痕**，保留期到了也只清理 `auth_failure`
  这类高频噪音，处置记录另计。

## 31.B 人机验证（P0，对应 SEC-021）

- **SECEV-010** `CaptchaProvider` 协议 + 三个实现：
  `NoCaptcha`（直通，开发默认）、`SandboxCaptcha`（形态真实、可测）、
  以及留给真实供应商的注册位。走既有的 `registry.get_provider("captcha")`，
  不另起一套。
- **SECEV-011 验证码是给被误伤的人一条自证的路，不是多加一道墙。**
  这是本节最重要的设计取向：没有验证码时，风控的唯一升级手段是**封禁**——
  一个手滑输错三次密码的真人，和一个撞库脚本，得到的处置完全一样。
  加入验证码后升级阶梯变成：正常 → **要求验证码** → 封禁。
  真人过一下验证就继续，脚本过不去。**误封率下降，拦截率上升。**
- **SECEV-012** 触发阈值 `SEC_CAPTCHA_AFTER_FAILURES` 必须**明显低于**封禁阈值，
  否则这条自证的路等于不存在（还没来得及要验证码人就被封了）。
- **SECEV-013** 验证码校验失败**也计入**失败计数：否则攻击者可以用无限次
  错误验证码把真正的登录尝试藏起来。
- **SECEV-014** `NoCaptcha` 直通时，要求验证码的那一步**依然产生事件记录**，
  这样即使没接真实供应商，风控趋势也看得见。

## 31.C 安全看板（P0，对应 SEC-023）

- **SECEV-020** 看板改读 DB，展示全局封禁列表、观察名单、近期事件趋势。
- **SECEV-021** 解封写 `unban` 事件并记入管理员审计（已有 `record_audit`）。
- **SECEV-022** 看板不得暴露与用户身份相关的多余信息——它是运维工具，
  不是查人的工具。

## 31.D 验证（P0）

- **SECEV-030** **换个进程仍然被封**：清空进程内状态后（等价于「请求打到另一个
  副本」），封禁依然生效。这是洞一的直接反面。
- **SECEV-031** 管理员解封**一次全局生效**：解封后清空进程状态，仍是解封状态。
- **SECEV-032** 失败计数跨副本累计：分散在「不同副本」的失败合并计算，
  达到阈值即封禁（不再是 N 倍阈值）。
- **SECEV-033** 达到软阈值后要求验证码；带正确验证码可继续；错误验证码被拒
  **且计入失败**。
- **SECEV-034** 验证码直通实现下，`captcha_required` 事件依然被记录。
- **SECEV-035** 成功登录清空该 IP 的失败记录。
- **SECEV-036** 单 IP 在一个窗口内产生的 `auth_failure` 记录数**不超过阈值**
  （SECEV-004 的写入有界性，防止被刷爆）。
- **SECEV-037** 看板只对管理员开放。

## 验收标准

- 封禁与失败计数**不再依赖进程内存**，多副本行为与单副本一致；
- 代码注释与文档中关于安全机制的每一句陈述都能在代码里找到对应实现；
- 真人有一条不被封禁的自证路径。

## 必须由用户提供（代码无法替代）

- 第三方人机验证服务（hCaptcha / 腾讯云验证码 / 阿里云 …）的密钥
- ⚠️ 大流量 DDoS 仍需云厂商 WAF/CDN 承担，应用层挡不住
