
# 117 真实演示里看到的粗糙之处（二）：履约上门户、发布不替人选、推荐看相关性

> 状态：本批实现（V142）。来源：V140 真后端 + 真浏览器演示（`docs/STATUS-2026-10-13.md` 第 1 节）。
> 同批发现的 IM-060（会话不显示对方名字）、SC-030（合约写「用户1 / 用户2」）已在 V141 修掉。
> 原则：**只增不减**——新增字段与加分项，不删已有入口、不改后台可配置的权重。

## 1. SPACE-029 履约记录上门户

- **现象**：执行方完成一单、拿到五星，他的个人空间仍显示「这个空间正在慢慢生长」。
- **改法**：公开空间接口 `GET /spaces/{id}` 新增 `track_record`，包括完成单数、平均星级、评价总数、常见标签和最近 3 条评价。
- **评价复用 `/users/{id}/reviews` 的双盲揭晓规则**：只有一方评过时不出现。返回内容**不带评价人**：空间是公开页，谁评的不必让路人知道。
- **两端**：Web 和 App 的空间页新增「履约记录」一段；还没做成过合作的，就写明「还没有在平台上完成过合作」。

## 2. TASK-090 发布页不替人选类目与城市

- **现象**：发一个「咖啡店品牌升级」的项目，默认值把它发成了「保洁 · 上海」。
- **改法**：
  - 没带参数时，类目和城市都是「请选择」；没选就提交，会提示先选，不发请求。
  - 资料里填了城市、且这个城市已开通，就用它（这是用户自己填过的，不是猜的）。
  - 带着参数来的照用参数，包括补救入口、模板，以及从工作台点「找人一起做」带过来的标题和说明。
- 真浏览器联调脚本同步改成显式选择。

## 3. SPACE-023（部分）推荐看「和这一单有没有关系」

- **现象**：一单设计任务的推荐里，做过一单保洁、拿过五星的人（68%）排在报了名、个人空间写着「品牌与包装设计」的人（59%）前面。理由还写着「技能部分匹配」，可那单根本没写技能要求，0.5 只是中性分。
- **改法**：在原有四项加权（后台可配置，不动）之上叠加三项相关性加分。三项一次查齐，查询次数与候选人数无关。

| 信号 | 加分 | 理由写给人看 |
|---|---|---|
| 已报名这一单 | +0.10 | 「已报名这一单」 |
| 在这个类目做成过（平台闭环事实） | +0.15 | 「做成过 N 单「设计」」 |
| 技能或个人空间里写着这个类目（自述，权重更低；做成过的不重复加） | +0.08 | 「擅长「设计」（本人技能或个人空间）」 |

- 任务没写技能要求时，不再写「技能完全匹配 / 部分匹配」。
- 分数上限为 1，避免出现「匹配 112%」。

**没做的（仍在 SPACE-023 里）**：可用时间和回复时长进入撮合；作品与技能的语义匹配（现在是类目名的字面包含）。

## 4. 闸门与红验

| 闸门 | 红验 |
|---|---|
| 空间带履约记录，盲窗内的评价不出现，不带评价人；形状与 SDK 类型一致 | 不带评价 → 红 |
| 设计单里报了名、写着设计的人排在高分保洁师傅前面；没写技能要求不说「部分匹配」 | 去掉加分 / 恢复误导理由 → 红 |
| 做成过比自述更重 | 去掉「做成过」 → 红 |
| 发布页：没选类目不发请求；资料城市作默认；带参数照用（Web） | — |
| 两端空间页显示履约记录；没有记录时如实说 | — |
