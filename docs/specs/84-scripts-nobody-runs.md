
# 84 没有人跑的脚本，和它印在文档里的数字（SCR-010~013 / DRILL-030b）

> 状态：本批实现（V110）
> 依赖：40 号（运维演练与压测）、20 号（部署）、82 号（联调闭环）

## 0. 探针

上一批（V109）我在 `SYSTEM-CHECK.md` 里写了「没有压测」，并往 72 号台账
加了一条 `DEP-023 没有压测`。写完之后去核对，发现 `scripts/loadtest.py`
就在仓里，而 `OPERATIONS.md` 印着它的实测数字。

**我写错了。** 于是去跑那个脚本：

```
$ python -m scripts.loadtest --concurrency 16 --requests 600 --scenario read
压测目标：http://127.0.0.1:8000（read 场景，并发 16，共 600 次）
AssertionError: 发布失败：400

$ python -m scripts.loadtest --scenario write
AssertionError: 注册失败：409
```

两个场景都**起不来**。原因：

| 症状 | 病因 |
|---|---|
| 发布 400 | `ip_assignment_required`——**V77** 把知识产权归属变成发任务的必填项 |
| 注册 409 | 手机号是 `139{秒 % 1e8}`，同一秒跑两次就是同一个号 |

第一条意味着这个脚本**从 V77 起就跑不起来了，坏了 33 个批次**。
而在这 33 个批次里，`OPERATIONS.md` 一直印着：

> **容量基线（V65 首次实测，`scripts/loadtest.py`）**：…读 129 rps…

**一个再也跑不起来的脚本，和它印在文档里被当作现状的数字。**

顺着这条线查「还有哪些脚本没有人跑」，`scripts/` 下 10 个脚本里有 2 个
不在 CI、不在回归、不在部署脚本里：`loadtest.py` 与 `seed_demo.py`。
后者的情况更难看——README 第 97 行让新来的人第一件事就跑它：

```
$ python -m scripts.seed_demo
KeyError: 'id'
```

**新人看到的第一个输出是 KeyError。**

## 1. 为什么 seed_demo 的错在三十行之后才出现

它一次都不看状态码：

```python
c.post(f"{API}/tasks", json={...}, headers=boss)     # 400，继续往下走
r = c.post(f"{API}/tasks", json={...}, headers=boss)  # 400
tid = r.json()["id"]                                  # ← KeyError 在这里
```

四次发布全部 400，脚本毫不知情，直到要用返回里的 `id` 才崩。
**那个位置离病因太远**：读栈的人会去查 `/applications` 附近，
而坏的是 `/tasks`。所以这一批给每一步加了 `_ok()`——
**在出错的那一行报错，是脚本对读它的人最基本的礼貌。**

加完 `_ok()` 之后，它立刻暴露了**第二处腐烂**：

```
报名 失败：HTTP 403 {"code":"verification_required","message":"需先完成实名认证"}
```

三个演示用户**共用一个证件号** `110101199001011234`，而平台后来加了
一人多号检测（同号只能绑一个账号）。于是第二、第三个人的实名静默 409，
他们报不了名，闭环那一段（合约 / 评价 / 经验卡）**一条数据也生成不出来**。

有意思的是：`tests/conftest.py` 早就知道这件事，它的 `verify_user()`
按 user id 派生证件号，注释写着「VND-023：证件号一人一号」。
**测试套件知道，而没有人跑的脚本不会知道**——这就是腐烂的机制本身。

## 1b 我自己的修法第一版是错的

给每一步加上状态码检查之后，**第二次跑这个脚本直接退出 1**：
`already_verified`（已实名）被当成了失败。

**把一个静默 bug 换成正当用法上的硬失败，那不是修好。**
而且顺手想到的那个修法——「409 就放过去」——会把 `id_already_bound`
一起放过，那正是上面刚修掉的另一个缺陷。**同一个状态码底下是两件相反的事，
所以放行只能按 `code` 而不是按状态码**（这也是 `code` 作为稳定契约的用处）。

最后没有走「按 code 放行」，而是想清楚这个脚本的**目标状态**是
「演示数据存在」——已经存在就说清楚并正常退出：

```
$ python -m scripts.seed_demo        # 第二次
演示数据已存在（13900010001 / pass123456）。
要重新生成：删掉库文件（或换 PLATFORM_DATABASE_URL）后再跑。
```

也**刻意不做成可反复追加**：追加一遍就多四条任务、多一份合约，圈层名还会
撞（`name_taken`）。**一个跑两次就得到一份说不清的数据集的演示脚本，
比拒绝跑更糟。** 想清目标状态之后，「按 code 放行」那套机制就走不到了，
于是把它删掉——**留着一个走不到的放行口，正是这一路反复在修的那种东西**。

## 2. 比崩掉更糟的那一种

`loadtest.py` 的 write 场景里有**第二份**任务请求体（与 `setup()` 那份
各写一遍），也漏了 `ip_assignment`。它比 `setup()` 那处更危险：

- `setup()` 会炸，你至少知道出事了；
- write 场景不会炸，它让每次请求被 400 挡掉，然后把**拒绝的速率**
  报成写入吞吐量。

**一个把 400 当吞吐量的压测，给出的数字比没有数字更糟**——它看起来
完全正常，而 400 走的是最短路径（连库都不碰），数字还会特别好看。

这一批把两处合并成一个 `TASK_BODY`（第二份实现必然抄漏），并加了一条
AST 闸门：模块里只许有一份字面量任务请求体。

## 3. SCR-013 两种失败的含义是相反的

原来的判据是「错误率过半就报不可用」。这个阈值抓不住上面那件事，
因为坏掉时错误率是 **100%**——它确实会红。但**部分损坏**（比如 30% 的
请求体不对）会被放过。

所以改成按**语义**分：

| 码 | 含义 | 判 |
|---|---|---|
| 400 / 422 | 请求体与服务端对不上，压的是被拒绝的快路径 | **一次都不容忍** |
| 429 / 503 | 限流与过载 | **不算失败**——这恰恰是压测想看到的东西 |

把 429 算成失败等于不许压测压出结果；把 400 算成容量数据等于自欺。
**同一个「错误率」里混着两种意思相反的东西，是那个阈值抓不住问题的根因。**

## 4. SCR-010 覆盖记账：谁在跑这些脚本

`EXERCISED` 声明表，脚本 → **谁在跑它**（值是方式，不是布尔）。
`「没有人跑」不许出现在这张表里`：那不是一种方式，那是这一篇要修的病。

闸门三条：

1. `scripts/` 下每个脚本都要在表里（新加脚本 → 红）；
2. 表里不许留已删除的脚本；
3. **声明「CI 里跑」的，`ci.yml` 里必须真的有它**——这一条防的是
   「把『有人跑』写进表里就算完」，那正是这一批在修的病，只是换个地方犯。

## 5. 声明「回归里跑」的，就真的跑

`seed_demo.py` 与 `scrub_experience.py` 在 CI 里没有合适的位置
（一个是演示数据、一个是一次性运维脚本），所以回归里**真的把它们跑一遍**，
各给一个空库、用子进程跑，不碰共享测试库。

`seed_demo` 那条**不只断言退出码 0，还数一遍落库的行**——
退出 0 而库里是空的，正是它此前的真实状态（前三次发布失败也照样往下走）。

`loadtest.py` 要真实 HTTP，所以分两层：

- CI 的 `boot-smoke` job 跑**很小的一轮**（并发 4、40 次）：目的不是量容量
  （CI runner 的数字没有意义且每次都不一样），而是证明**这个脚本还能跑**；
- 回归里直接把它的请求体打到服务端看是不是 201：**不用起服务、不用跑负载**，
  几毫秒就红。红得越早越便宜。

## 6. 重测出来的数字

修好之后在**同一个容器**上重测（单 uvicorn worker + SQLite 单文件，并发 16）：

| 场景 | 吞吐 | p50 | p95 | p99 | 错误 |
|---|---|---|---|---|---|
| read（任务详情） | 94.1 rps | 166.8ms | 220.7ms | 244.3ms | 0 |
| write（发布任务） | 65.3 rps | 51.9ms | **1373.2ms** | **2159.2ms** | 0 |

与 V65 的数字并排（V65：read 129 rps / p95 175ms；write 87 rps / p95 769ms）
看起来是**读写都慢了约四分之一，写的 p95 差不多翻倍**。

但这句话要**说到什么程度为止**：两次都是单次运行、在共享的云容器上，
噪声不小，所以这**不足以断言性能回归**。能说的是：方向在两个场景上一致，
且 44 个批次里确实加了不少每请求都要走的东西（鉴权、风控闸门、访问日志、
限流）。真要下结论得多次取样并按中间件分层测——记进 72 号台账
（`DRILL-031`），不在这一批里假装已经查清。

写的 p95 是 p50 的 26 倍，这个形状没变：**SQLite 单写锁的签名**。
生产换 Postgres 后必须重测。

## 7. 文档里的数字要带出处

`OPERATIONS.md` 的容量段此前只写「V65 首次实测」。这一批改成同时写明
**哪一次运行、什么配置、以及「这些是地板不是容量规划」**，并加一句
可复现的命令。理由很直接：**这一批就是被「印着 V65 数字的文档 +
再也跑不起来的脚本」这个组合骗过一次的**（我自己在 V109 写反了两遍：
先说「没有压测」，其实有；文档说「有实测」，其实跑不了）。

## 8. 闸门

| 闸门 | 内容 |
|---|---|
| SCR-010 自检 | 扫得到 ≥8 个脚本，且已知的三个在内 |
| SCR-010 覆盖 | 每个脚本在 `EXERCISED` 里有人跑；表里不留已删除的 |
| SCR-010 诚实 | 声明「CI 里跑」的，`ci.yml` 里必须真的有 |
| SCR-011 | `seed_demo` 真跑一遍且**七类表都非空**；`scrub_experience --dry-run` 真跑且声明不写库 |
| SCR-012 | `loadtest` 的请求体被服务端接受（201）；write 场景不许抄第二份 |
| SCR-013 | 400/422 判死；429/503 不判死 |

红验十条全部走过：去掉 `ip_assignment`、write 场景抄一份请求体、
把 400/422 改成不判死、`seed_demo` 漏必填项、三个人共用证件号、
新增脚本不登记、表里说 CI 跑而 CI 里没有、扫描器被改成扫不到、
`--dry-run` 不再声明它不写库、去掉「数据已存在」的早退（第二次跑就炸）。

另外修了一条**别人的闸门被我改红**：`test_ops_drills.py` 原来断言
`loadtest.py` 里有「不设阈值断言」这**五个字**，我正当改写那句注释时它就红了。
**一个钉住散文的闸门会在正当改动上误报**，而误报多的闸门会被人关掉。
保留那句话的同时给它补了行为断言（契约性失败判死、容量性失败不判死），
让它钉住的是原则而不是措辞。

## 9. 这一批没做的

- **性能回归没查清**（`DRILL-031`）：见第 6 节，要多次取样并分层测。
- **压测只有两个场景**：读任务详情与发任务。搜索、广场分页、钱包这些
  真实高频路径没覆盖——加场景很便宜，但要先决定「哪几条是真高频」，
  而现在还没有线上数据。
- **CI 里那一轮不做容量判断**：runner 的数字没意义。要有趋势就得有
  固定机器与历史库，那是一套基础设施，不是一个脚本。
- **`seed_demo` 的数据仍是三个人一条闭环**：够体验主链路，不够压测与
  分页的真实感。造大规模假数据要先想清楚它会不会被误当成真数据。
