# 29 · 个税代扣代缴与发票（TAX）

> 落地 [25-financial-compliance.md](25-financial-compliance.md) 的 FIN-030/031/032。

## 先说清楚现在缺什么

`contract/service.py::release` 现在是这样分钱的：

```python
_settle(db, contract, "release", [
    (contract.executor_id, remaining - fee, "payout"),
    (wallet.PLATFORM_USER_ID, fee, "fee"),
], "验收放款")
```

**两个收款方，没有第三个。** 平台把钱直接付给自然人执行者，
一分税没扣、没有任何完税记录。

《个人所得税法》第九条：**以支付所得的单位或者个人为扣缴义务人**。
平台是支付方，就是扣缴义务人。不扣不是「以后再补」的事——
《税收征收管理法》第六十九条：应扣未扣，向纳税人追缴税款，
**对扣缴义务人处应扣未扣税款百分之五十以上三倍以下的罚款**。

这不是代码疏漏，是**这门生意的合规底座缺了一块**：
执行者拿到的每一笔钱都是应税收入，而平台一次都没有履行过扣缴义务。

## 29.A 一个代码解决不了、必须先由人决定的问题

执行者的收入按哪种所得课税，**决定了扣多少、怎么扣、谁开票**：

| 路径 | 所得类型 | 谁扣 | 大致税负 | 前提 |
|---|---|---|---|---|
| A | 劳务报酬所得 | 平台预扣预缴 | 20%~40% 累进（每次收入减除后） | 无需执行者办任何手续 |
| B | 经营所得（委托代征） | 代征方按核定征收率代扣 | 通常 0.5%~1.5% | 需与税局签**委托代征协议**，执行者注册个体户/临时税务登记 |
| C | 经营所得（自行申报） | 平台不扣 | 执行者自负 | 执行者是个体户/企业，**且能开票** |

⚖️ **这三条路的选择是税务与法律决定，不是代码决定。** 路径 B 是国内灵活用工
平台的主流做法，但它依赖一纸委托代征协议——没有协议就按 B 扣税，
是另一种违法。路径 C 看似省事，但平台若不校验发票就付款，
企业所得税前列支会被否，是把风险从税务挪到了自己账上。

**因此代码要做的不是替你选，而是：**
1. 把三条路都变成**可配置、可执行、可测试**的实现；
2. **逼你必须显式选一条**——生产环境不选就不让启动；
3. 无论选哪条，**钱的流向都必须守恒可对账**，完税记录都必须能拿出来。

## 29.B 税务模式与扣缴抽象（P0）

- **TAX-001** `PLATFORM_TAX_MODE` ∈ `none` / `withholding` / `self_declared`。
  `none` 是现状（不扣），**生产环境启动自检直接拒绝**——
  和「内部账本不得上生产」（FIN-052）同级的红线：你可以选择不扣，
  但必须是**在知道后果的前提下显式选择**，不能是默认没人管。
- **TAX-002** `TaxProvider` 协议：`assess(income_cents, context) -> TaxAssessment`，
  返回应纳税所得额、应扣税额、适用规则名与说明。
  实现：`NoWithholdingTax`（不扣，诚实命名）、
  `LaborIncomeTax`（路径 A，真实累进表）、
  `CommissionedCollectionTax`（路径 B，核定征收率）。
- **TAX-003** 生产环境拒绝非生产实现，与其它 P0 供应商一视同仁
  （复用 `registry.startup_check` 的机制，不另起一套）。
- **TAX-004** 计税基数取**扣除平台佣金后的净额**——那才是真正归属执行者的收入。
  ⚖️ 这条要税务意见确认：也有按含佣金总额计、佣金另作执行者支出的处理方式。
  代码把基数写在 `TaxAssessment.taxable_cents` 里并落库，
  口径变更时能**说清历史每一笔是按什么算的**。

## 29.C 钱的流向（P0）

- **TAX-010** 新增**代扣税款专户** `TAX_USER_ID = -1`。
  代扣的钱不是平台收入，也不是执行者的钱，是**平台代持、待缴库**的第三方资金——
  混进平台佣金账户是最容易犯也最难查的错。
- **TAX-011** 放款分账变成三个收款方（FIN-031）：
  执行者实收 / 平台佣金 / **税款专户**，`purpose="tax"`。
- **TAX-012** 第五条对账不变量：
  `税款专户余额 == Σ代扣 - Σ已缴库`。
  前四条不变量不动，新增这条——否则代扣的钱进了系统却没人为它负责。
- **TAX-013** 缴库 job `POST /finance/jobs/remit-tax`：把专户余额划出并留痕
  （形态与 `platform_settle` 一致，接真实税务通道后换执行者不换形态）。
- **TAX-014** ⚠️ **已代扣税款不随事后调整自动冲回**。
  申诉改判、纠纷退款发生在申报之后时，正确做法是**更正申报**而不是
  在账上偷偷冲销——与真实税务流程一致。代码保留原记录并标记关联调整，
  由人处理。装作能自动冲回，反而会做出一套和税局对不上的账。

## 29.D 完税记录与发票（P0）

- **TAX-020** `TaxWithholding` 一次支付一条：纳税人、合约、含税收入、
  计税基数、扣缴金额、适用规则、模式、供应商、时间。
  这是**完税凭证的数据来源**，也是执行者汇算清缴时要拿的东西。
- **TAX-021** `GET /finance/my-tax`：执行者查自己的年度合计与逐笔明细。
  ⚖️ 平台出具的是**代扣明细**，不是税务机关的完税证明——
  措辞必须准确，不能让用户拿着它以为可以直接抵扣。
- **TAX-022** 平台服务费发票（FIN-032）：发布方可申请开具**平台服务费**发票，
  金额为平台佣金部分，不含执行者报酬——平台没有为报酬开票的资格。
- **TAX-023** `self_declared` 模式下，执行者报酬发票由执行者提供。
  代码为每笔放款生成待开票义务记录并在放款结果中提示；
  ⚠️ **不假装能校验发票真伪**——那需要接税局验真接口。
- **TAX-024** 管理端可查全量代扣与缴库台账。

## 29.E 验证（P0）

- **TAX-040** `withholding` 模式下走完闭环：执行者实收 = 总额 − 佣金 − 税款，
  三方分账守恒，税款专户余额正确。
- **TAX-041** **五条**不变量全部成立（新增税款专户有据）。
- **TAX-042** 劳务报酬累进表分档正确（含 800 元减除、四千分界、三档税率与速算扣除）。
- **TAX-043** `none` 模式行为与改造前**完全一致**（不扣税、两方分账）——
  向后兼容不能靠嘴说。
- **TAX-044** 生产环境 + `none` 模式 → 启动自检失败并说明原因。
- **TAX-045** 缴库后专户归零且流水可查；重复缴库不重复划账。
- **TAX-046** 执行者能查到自己的逐笔代扣明细与年度合计，且措辞不冒充完税证明。
- **TAX-047** 里程碑分期放款同样扣税（**最容易漏的路径**：只改整体放款
  会让分期合约全部免税）。

## 验收标准

- 生产环境**不可能**在没决定税务方案的情况下启动；
- 任何一条放款路径（整体 / 分期 / 裁决执行）都走同一套扣缴逻辑，不存在绕过；
- 代扣的钱在账上**始终有据可查**，且不与平台收入混同；
- 平台出具的文件措辞准确，不冒充税务机关文书。

## 必须由用户提供（代码无法替代）

- ⚖️ 税务师意见：所得类型选择（劳务报酬 vs 经营所得）与计税基数口径
- ⚖️ 委托代征协议（若走路径 B）
- 税务系统对接凭据（申报、缴库、完税凭证下载）
- 发票系统对接（平台服务费开票）
