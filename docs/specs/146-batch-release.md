
# 146 只放已交付的那几期：分期合约的批量放款；App 补上分期列表

> 状态：本批实现（V174）。编号 SC-014（含 SC-014a~c）。
> 来源：台账 SC-014「没有『只放已交付的那几期』的批量动作：要分三次点『验收本期』……它和『整单验收』长得太像，两者的语义区别得先写清」；BACKLOG V174。
> 只增不减：单期验收、整单验收（SC-013 的确认文案）都不变；新增一个**只放点名的、已交付的期**的动作。

## 0. 要解决的问题

- 分期合约好几期都交付了，发布方只能一期一期点「验收本期」；或者点「整单验收」——而后者会放掉**剩余全部期**，包括还没交付的。
- 两个放款按钮并排时，用户分不清差别，这正是 SC-013 当初要防的事。
- **App 上根本没有分期列表**：App 的整单验收提示写着「请用下面分期列表里的『验收本期』」，指向一个不存在的地方；执行方在 App 上也没法逐期交付。

## 1. 业界怎么做（带来源链接）

- **按里程碑放款、只放已批准的**：Upwork 的固定价合同按里程碑托管与放款，客户只对已提交的里程碑批准付款（<https://support.upwork.com/hc/en-us/articles/211068218>）。
- **二次确认列清金额与对象、以客户端看到的合计为准**：支付系统常用「客户端带上看到的金额，服务端核对后再执行」防止界面过期导致误付（与本平台幂等键的做法同一思路）。

无新表、无迁移。

## 3. 规则与接口

| 编号 | 内容 |
|---|---|
| SC-014a | `POST /contracts/{id}/milestones/release-delivered`，`{idxs, expected_total_cents}`：只放点名的期；每一期都必须已交付（否则说清是哪几期，`invalid_milestone_state`）；合计必须等于客户端看到的（`batch_total_mismatch`）；空、重复、不存在的期分别拒绝；只有发布方；合约冻结时不放（`contract_frozen`）；**整批一个事务**，按期号顺序逐期放，流水、佣金、代扣与单期验收完全一样 |
| SC-014b | 放完最后一期时任务照常闭环（与单期验收共用同一段收尾逻辑） |
| SC-014c | 语义区别写进界面：批量按钮叫「放款已交付的 N 期（共 ¥X）」，确认时列出每一期与合计，并写明「还没交付的期不会动」；整单验收的确认文案（SC-013）不变 |

## 4. 两端

- **Web 任务详情**：两期及以上待验收时，分期表上方多一个批量放款按钮（确认框列清楚）。
- **App 任务详情**：新增「分期」一块：每期的状态；执行方「交付本期」；发布方「验收本期」；两期及以上待验收时「放款已交付的 N 期」，先列清楚再「确认放款」；冻结时都不能点。

## 5. 隐私、授权与边界

- 动钱的动作只有发布方能做；服务端以期的真实状态与金额为准，客户端传的合计只用来核对，不用来计算。
