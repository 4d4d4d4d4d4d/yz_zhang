# 255 提额申请的处理时限与后台按等待时间排序、标红

> 状态：本批实现（V282）。编号 API-059。
> 来源：247 号 spec「没做的」——「提额申请的处理时限（SLA）与后台按等待时间排序、标红」；BACKLOG V282。
> 只增不减：申请、批准、驳回、提醒都不变；后台列表每行多三个只读字段，待批的排序从「按编号」改成「按提交时间」（实际顺序一样，写明依据）。

## 0. 要解决的问题

247 号会催运营，但后台列表上看不出哪笔等得最久、哪笔已经超时：运营打开页面还得自己算。

## 1. 业界怎么做

工单 / 审批队列常见做法：按等待时间排序，显示「已等多久」，超过时限的标红。（本批没有另找外部来源。）

## 2. 规则

- 处理时限沿用 247 号的 48 小时（`QUOTA_REQUEST_REMIND_HOURS`，与催办同一个数）。
- 每行多：`waited_hours`（待批的算到现在，已处理的算到处理时）、`sla_hours`、`overdue`（只有待批且等了 ≥ 时限才算超时）。
- 待批列表按提交时间从早到晚（等得最久的在前）；其他状态按提交时间从新到旧。
- Web 后台在超时的申请前标「超过 48 小时」，每行写「已等 N 小时」。

## 3. 数据

不新增表与字段。

## 4. 接口

| 接口 | 变化 |
|---|---|
| `GET /admin/api-quota-requests` | 每行多 `waited_hours`、`sla_hours`、`overdue`；按提交时间排序 |

SDK：`AdminApiQuotaRequest` 多三个可选字段。

## 5. 两端

- **Web 后台「开放 API 配额」待批申请**：超时标签与「已等 N 小时」。
- **App**：后台只在 Web，不涉及。

## 6. 隐私、授权与边界

不变（只有运营）。

## 7. 闸门与红验

4 处变异（`scratchpad/mut282.py`）：3 处首轮变红；「已处理的也算到现在」首轮存活，补「处理时间固定」后变红。
