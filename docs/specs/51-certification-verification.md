# 51 受限类目资质：从「自己填」到「核过才算」（CERT）

> 需求原话：「受限类目资质需要单独处理，必须要对相关证件，用户身份实名审核才行。」
>
> 现状实测：`POST /users/me/certifications` 的实现是
>
> ```python
> user.certifications = user.certifications + [body.name]
> ```
>
> 注释写着「模拟审核即通过」。也就是说——**任何实名用户 POST 一个字符串
> 就能拿到「电工」资质**，管理后台里连审核队列都没有
> （`admin/router.py` 里搜不到 certification）。
>
> 而 `task/service.py:63` 正是用这个字段拦住电工维修、燃气维修、
> 法律咨询这些类目的接单。**这道门一直是虚的。**

## 0. 这一批为什么优先级高于"功能"

一个无证的人接了电工单，出事的是**人身安全**，赔的是平台的连带责任。
这不是「体验不好」那一类问题，是**这个类目根本不该开放**的问题。

所以本批的完成定义不是「加了个审核页面」，而是：
**在资质被人工核过之前，那个类目的接单准入一次都不放行。**

## 1. 四个必须同时成立的条件

需求说「必须要对相关证件，用户身份实名审核才行」。拆开是四件事，
缺任何一件这道门都还是虚的：

### CERT-001 提交的是**申请**，不是资质

端点语义改变：`POST /users/me/certifications` 从「授予」改为「提交申请」，
返回 `status: pending`。**在管理员通过之前，`user.certifications` 一个字都不加。**

### CERT-002 必须附证件影像

没有影像，审核员看什么？申请必须带至少一张已上传的证件图片。

### CERT-003 证件姓名必须与实名**完全一致**

这条最容易漏，而漏了等于前三条白做：**一张别人的电工证也是一张真证件。**

申请时要求填写证件上的姓名，服务端与 `user.real_name` 严格比对，
不一致直接拒绝，理由明说「证件持有人与实名信息不一致」。

> 这只能挡住「拿别人的证」这一类，挡不住伪造。伪造要靠审核员的眼睛
> 与将来接入的核验机构（CERT-050），这一批不假装能挡。

### CERT-004 人工审核，通过才写入

管理员队列 + 通过/驳回 + 审计留痕。驳回必须带理由——
只说「未通过」，申请人不知道该补什么，只会一遍遍重交。

## 2. CERT-010 证件影像是敏感个人信息，不能走匿名能力 URL

这是写这一批时发现的一个**真实安全缺口**，而且它不只影响资质：

`GET /files/{name}` 是**匿名**的能力 URL（FILE-013），设计前提是
「名字来自 CSPRNG，知道 URL 即有权读」。对任务配图、交付凭证，这个
权衡是对的——`<img src>` 带不了 Authorization 头，CDN 直出更不可能回源鉴权。

**但身份证、电工证这类证件影像属于敏感个人信息。**
一个匿名可读的 URL 一旦出现在日志、浏览器历史、转发的截图里，
就等于把证件交出去了，而 PIPL 对敏感个人信息要求的是单独同意 + 严格保护，
不是「不可猜就行」。

所以：

- `UploadedFile` 加 `sensitive` 标记；
- **`/files/{name}` 对敏感文件一律拒绝**（不是「尽量」，是拒绝）；
- 另开 `/files/{name}/secure`：必须登录，且只有**上传者本人与管理员**能读；
- 敏感文件**不进 CDN 直传路径**（`sign_upload` 不给敏感类型签名）。

顺带把注销处置补上：注销时证件影像必须**物理删除**，不是标记删除。

## 3. CERT-005 资质有有效期，不是发了就永久

电工证要复审，律师执业证要年检。**「发了就永久有效」是错的**，
而且是那种几年后才会伤到人的错——到那时平台上已经有一批实际已失效的资质
在照常接单。

所以：

- 申请必须填 `expires_at`（证件上的有效期）；
- 准入判断读的是「**有效且未过期**的资质」，不是「有没有这个名字」；
- 过期不删记录（要留痕），只是不再满足准入；
- 到期前提醒（job），给人时间去复审。

## 4. CERT-006 存量数据怎么办：这是个必须做的决定

现在库里已经有通过旧端点自助发放的 `certifications`。三个选项：

| 选项 | 后果 |
|---|---|
| 保留 | **那些没核过的资质继续生效**，等于这一批白做 |
| 直接清空 | 门关上了，但用户的资质凭空消失，不知道发生了什么 |
| 转成待补材料的申请 | 门关上了，用户看得到「待补充证件材料」 |

**选第三个。** 迁移把每条存量资质转成一条 `pending` 申请（保留名称），
同时清空 `user.certifications`——**准入立刻收紧，用户不至于一头雾水**。

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| CERT-001 | 提交申请不授予资质；受限类目接单仍被拒 |
| CERT-002 | 不附证件影像的申请被拒 |
| CERT-003 | 证件姓名与实名不一致被拒；一致才受理 |
| CERT-004 | 管理员通过后才写入并放行接单；驳回必须带理由 |
| CERT-005 | 过期资质不满足准入；过期记录仍可查 |
| CERT-006 | 迁移后存量资质不再生效，且以待办申请的形式可见 |
| CERT-010 | 敏感文件匿名读被拒；本人与管理员可经鉴权端点读；他人不可读 |
| CERT-011 | 注销时证件影像被物理删除 |
| CERT-012 | 同一资质不能重复提交待审申请 |

## 6. 这一批没做的（明确记账）

- **CERT-050**：**没有接真实的资质核验机构**。现在是「管理员看图判断」，
  挡得住「拿别人的证」和明显的伪造，挡不住高仿。接机构 API
  （住建/人社/司法行政的执业信息查询）是外部签约的事，
  代码侧留了 `CertificationProvider` 的位置但没有实现——
  **也没有假装有**：默认实现如实上报 `manual_only`。
- **CERT-051**：没有 OCR。审核员要自己看图填有效期，量大了会是瓶颈。
- **CERT-052**：资质与**具体类目**的映射仍是 `Category.required_cert` 一对一。
  现实中一个类目可能接受多种资质（如「法律咨询」可接受律师证或法律职业
  资格证），这需要改成多对多，留待有真实类目数据后再做。
- **CERT-053**：审核员自己没有分级与抽检。审核员放水目前只有审计日志可追溯。
