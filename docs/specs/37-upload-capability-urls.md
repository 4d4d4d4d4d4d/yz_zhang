# 37 上传文件的 URL 是能力，不是指纹（FILE）

> 对应 `app/vendors/storage.py`、`app/modules/files/router.py`，
> 以及 19 号 spec 的 VND-031。

## 0. 这一批修的是什么

`GET /api/v1/files/{name}` **完全匿名**——没有登录，没有鉴权。

这本身不是错误。这套设计的意图写在代码注释里：

```python
"""本地实现的读取端点。接真实对象存储后，URL 直接指向 CDN，此端点不再被访问。"""
```

CDN 直出就意味着读取端不可能做鉴权，业界的标准做法是**能力 URL**
（capability URL）：URL 本身就是凭证，知道它就等于有权读它。
这个模式成立有且只有一个前提——**URL 不可猜**。

而这里的 URL 是：

```python
digest = hashlib.sha256(data).hexdigest()[:32]
name = f"{digest}{ext}"
```

**文件名就是文件内容的指纹。** 探针实测：

```
A url: /api/v1/files/04523bfdcb1918b37b179fd3010ceabb.png
B url: /api/v1/files/04523bfdcb1918b37b179fd3010ceabb.png
same object across users: True
offline-computed name matches: True
anonymous GET: 200 208 bytes
cache header: public, max-age=31536000, immutable
```

三件事同时成立，各自是一个独立的问题。

### FILE-001 能力 URL 的前提不成立：拿到原图就等于拿到 URL

能力 URL 的不可猜性必须来自 **CSPRNG**，而不是来自内容。
`sha256(内容)` 对任何**持有这份内容的人**都是公开的。

于是这个端点变成一台**存在性预言机**：任何人手里有一张候选图片，
就能离线算出它的 URL 并去问平台「这张图在不在你这儿」。
200 就是「在」。不需要登录，不需要任何线索，不留下任何可归因的痕迹。

这不是理论问题。一个骚扰者手里有受害者在别处公开过的照片，
就能确认这张照片被上传到了本平台；一份在别处流传的文件，
可以被确认曾作为某笔纠纷的证据提交。**平台原本承诺的私密性直接归零，
而攻击成本是一次 sha256。**

顺带说明我**没有**声称的事：32 个十六进制字符是 128 位，
不存在暴力枚举风险。问题从来不是长度，是**这个值不是秘密**。

### FILE-002 跨用户去重把两个人的数据物理合成了一份

`same object across users: True`：甲和乙上传同一份文件，拿到**同一个 URL、
同一个磁盘对象**。注释把这写成优点——「同一张图重复上传不会占两份空间」。

省空间是对的，**但省的应该是磁盘，不是 URL**。这两件事被混成了一件，
后果是：

- 甲能凭手里的文件拿到乙那条证据的 URL，反之亦然；
- **删除权无法执行**。V60 刚刚建立了「注销时逐字段决定删除/脱敏/保留」的
  机制，但它管不到这里：甲注销要删的那个对象，可能同时是乙的证据。
  删了破坏乙的证据链，不删就是没执行删除权——内容寻址在一个**有删除义务**
  的系统里是个结构性错误。

### FILE-003 这个能力无法被吊销

名字由内容决定，所以**重新上传还是同一个名字**。URL 一旦泄露
（浏览器历史、工单里粘的截图、Referer、转发的聊天记录），
没有任何办法换一个——而响应还带着 `public, max-age=31536000, immutable`，
CDN 与浏览器会把它缓存一年。

一个不能轮换的凭证不是凭证。

### FILE-004 平台答不出「这张违规图片是谁传的」

上传要求登录，但**没有任何地方记下是谁传的**。
`VendorCall` 只记 kind / provider / operation / request_digest，不含用户。

所以举报一张违规图片、或内容安全供应商回报一个问题对象时，
平台没有任何途径追溯到上传者。一个有举报流程、有 `MODERATION_PROVIDER`、
要对内容负责的平台，**连归属都不记**，处置就无从谈起。

### 一个佐证：沙箱的直传实现本来就是对的

```python
def sign_upload(self, content_type: str) -> VendorResult:
    token = uuid.uuid4().hex          # ← 随机
```

真实对象存储的形态（签发直传 URL）用的是随机令牌。
**只有实际在跑的那条本地路径跑偏了**，而它才是所有测试与冒烟走的路径。

## 1. 设计判断

**判断一：修的是命名，不是鉴权。**
给 `GET /files` 加登录态很有诱惑力，但它解决不了问题也不符合架构：
`<img src>` 带不了 Authorization 头，CDN 直出时更不可能回源鉴权。
真正错的是「用内容当名字」，所以把名字改成随机令牌——
让这套设计一开始就假定成立的那个前提**真的成立**。

**判断二：磁盘去重保留，URL 去重取消。**
两件事本来就该分开：blob 按内容哈希存一份，命名条目按上传次数各给一个
随机名，用硬链接指过去。省空间的收益一分不少，而每次上传得到独立的、
可单独删除的、可单独吊销的 URL。硬链接的引用计数顺带解决了 FILE-002 的
删除困境——删掉甲的名字，乙的名字仍指向同一个 blob。

**判断三：归属落库，且必须在 V60 的处置表里做一次决定。**
V60 定的规矩是「新增一列就逼作者做一次决定」。现在真的新增了一张含个人
信息的表，那条规矩第一次被真正使用——`uploaded_files` 必须进处置表，
不进就红。

## 2. 条目

- **FILE-010** 文件名改为 `secrets.token_hex(16)`（128 位 CSPRNG），
  与内容无关。同一份内容重复上传得到**不同的** URL。
- **FILE-011** 磁盘仍按内容哈希去重：blob 落 `blobs/<sha256>`，
  命名条目用 `os.link()` 硬链接；跨设备等 `OSError` 时退化为复制
  （退化只损失空间，不损失正确性）。
- **FILE-012** 新表 `uploaded_files`：`name`（主键）/ `owner_id` / `sha256` /
  `content_type` / `size_bytes` / `created_at`。上传即落库。
- **FILE-013** `GET /files/{name}` 维持匿名，但注释必须写明这是**能力 URL**，
  以及它成立的前提是名字来自 CSPRNG——把这个前提从「碰巧」变成「写下来的约定」。
- **FILE-014** `uploaded_files` 进 `USER_DISPOSITION` 同级的处置表
  （`UPLOADED_FILE_DISPOSITION`），并纳入 V60 那条逐列覆盖的反射测试。
  本批的决定是**全部 `RETAIN`**：上传物是交付凭证与纠纷证据，属于
  **交易对手方的凭证**与法定可追溯性，不是注销者独有的画像数据。
  这是一个明确的决定，不是默认值。

### 不变量

- **FILE-020** 同一份内容由不同用户上传，两条 URL 必须不同，
  且**互相取不到对方的名字**。
- **FILE-021** 名字不得可由内容推导：断言 `sha256(内容)[:32]`
  不出现在返回的 URL 里。
- **FILE-022** 去重仍然有效：两次上传后 blob 目录里只有一个内容对象。
- **FILE-023** 上传后能查到归属：`uploaded_files` 里有一行指向上传者。

## 3. 已知缺口

- **FILE-030 存量文件仍是内容寻址的名字。** 迁移只建表，不重命名历史文件——
  重命名会让已经写进 `ProgressLog.images` / 纠纷证据里的 URL 全部失效。
  存量对象的 URL 仍可被持有原图者推导；上线前若已有真实数据，
  需要一次性重签名 + 回写引用，本批不做。
- **FILE-031 上传内容不过审核。** `POST /files` 不调 `MODERATION_PROVIDER`。
  归属落库后处置才成为可能，但「主动发现」仍然缺失。
- **FILE-032 没有按 owner 的删除入口。** 表建好了，删除动作（含 V60 注销
  流程里的联动）留到有真实对象存储再做——本地实现删了硬链接，
  CDN 上的副本还在。
