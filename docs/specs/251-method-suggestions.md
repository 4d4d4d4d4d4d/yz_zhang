# 251 编排复盘起草方法备注的修改建议

> 状态：本批实现（V278）。编号 AGT-100。
> 来源：245 号 spec「没做的」——「编排复盘时把『哪一步失败过、整改了什么』起草成方法备注的修改建议（确认后写回方法）」；BACKLOG V278。
> 只增不减：复盘、存知识库、蒸馏成方法（133 / 134 / 154 号）都不变；新增两个接口与一个入口。

## 0. 要解决的问题

245 号让修复步读方法里的备注；反方向还缺：这次哪一步整改过、缺了什么，没有回到方法里。下次再按这个方法做，照样踩同一个坑，只能靠发起人自己记得去改方法。

## 1. 业界怎么做

复盘（retrospective）的产出通常落到「下次怎么做」的清单 / 模板里；自动化工具会把失败原因作为对模板的修改建议提出来，由人确认后合并。（本批没有另找外部来源。）

## 2. 规则

- 只对用了「我的方法」的编排，只看按方法拆的步骤（按标题对上）。
- 一步「整改过」= 这个标题下有失败或被修复步接续的记录。对每个整改过的步骤起草：
  - 有评审缺项：「上次这一步没做到：<缺项>」；没有缺项：「上次这一步没做成：<观测前 60 字>」。
  - 建议的备注 = 现在的备注 +「；」+ 上面这句；已经写进备注的不再建议。
  - 理由：「试了 N 次才做成」或「试了 N 次仍没做成」。
- **只出草稿**：看建议不改方法；发起人勾选后「写回我的方法」才改，只改勾了的步骤的备注；写回算一次修改（升一版、旧版进历史，239 / 244 号）。
- 只有发起人能看、能写回（管理员能看编排，但不能改别人的方法）。
- 没用方法、方法已删：返回空建议并说明。

## 3. 数据

不新增表：读 `mission_steps`（状态、评审缺项、观测）与 `nb_methods`。

## 4. 接口

| 接口 | 说明 |
|---|---|
| `GET /missions/{id}/method-suggestions` | `{method_id, method_name, method_version, suggestions: [{title, current_note, suggested_note, reason}], note}` |
| `POST /missions/{id}/method-suggestions/apply` | `{titles}`（1~10）；返回方法（与列表同形状）；没有可写回的 409 |

错误码：`method_suggestion_none`（进 `i18n.ts`）。SDK：`missionMethodSuggestions`、`applyMissionMethodSuggestions`、`MissionMethodSuggestions`。

## 5. 两端

- **Web 编排复盘**：用了方法的编排多「用这次的问题改进我的方法」：列出每步「现在的备注 → 建议的备注（理由）」，默认全勾，可取消，「写回我的方法」后提示现在是第几版。
- **App 编排复盘**：同样的内容与操作（☑ / ☐ 切换）。

## 6. 隐私、授权与边界

方法只属于本人；写回前必须本人确认（AI 只出草稿）。
