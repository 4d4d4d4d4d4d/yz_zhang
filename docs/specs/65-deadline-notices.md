# 65 错过就无法挽回的通知，不能被一个开关关掉（NTF-060~064 / AGT-070/071）

> 三天后，发布方的钱会自动放给执行方。提醒他这件事的那条通知，
> **现在可以被用户在设置里关掉**，而且它**没有说「三天」**。

## 0. 现状

```python
def _on_task_pending_acceptance(db, payload):
    notify(db, task.creator_id, "task", "待验收提醒",
           f"任务《{task.title}》已提交验收，超时将自动通过")
```

`AUTO_ACCEPT_DAYS = 3`。这条通知的类别是 `task`，而 `notify()` 的规则是：

```python
if category != "funds" and not force:
    # 查用户的通知偏好，关了就不发
```

于是两件事同时成立：

1. **它可以被关掉。** 用户在设置里关掉「任务通知」之后，三天后钱自动放出去，
   他一次提醒都收不到。
2. **它没说三天。** 「超时将自动通过」——多久？用户无从知道该什么时候回来看。

## 1. 这条规矩平台自己立过

V61 给纠纷开案通知加 `force=True` 时的理由，写在代码注释里：

> 此前只有 `funds` 类是必达的。但「有人对你发起纠纷，你有 48 小时答辩，
> 逾期缺席裁决」同样是错过就无法挽回的——把它归到 `task` 类，
> **等于允许用户用一个通知开关放弃自己的陈述权**。

待验收提醒是同一件事：**等于允许用户用一个开关放弃自己的验收权与驳回权**，
而后果是钱。

V61 还修过另一半：纠纷通知里的 `48` 曾是硬编码字面量，
「运维改了配置，这句话会继续理直气壮地说 48」。
待验收通知连字面量都没有——它干脆不说。

## 2. NTF-060 必达通知要有一张**声明表**，并被测试钉住

补这一条容易，问题是**下一条怎么办**。全仓 33 处 `notify()`，
只有 3 处 `force=True`；哪些该必达，现在只存在于写的人当时的脑子里。

所以这一批不只改那一行，还立一张表：

```python
MUST_REACH = {
    ("task", "待验收提醒"): "不发就等于默认同意：N 天后钱自动放款",
    ("task", "纠纷已受理"): "错过答辩期 = 缺席裁决",
    ("task", "答辩期即将届满"): "同上",
    ("contract", "合约签署超期作废"): "错过就要重新走一遍成交",
    ("task", "任务已逾期"): "逾期直接影响违约判定",
    ...
}
```

判定标准写死在表的注释里，只有一条：

> **错过它，用户会失去一个他本可以行使的权利，或者失去一笔钱。**
> 不满足这条的，就不该是必达——把所有通知都做成不可关，
> 等于把这个开关变成摆设，用户会连真正重要的那几条一起屏蔽掉。

测试从表里逐条取出来，**真的把用户的偏好关掉**，然后确认这些通知照样送达。
不是检查 `force=True` 这个参数写没写——那只是实现细节，
**要验的是关了开关之后它到底还到不到**。

## 3. NTF-061 期限必须说出来，且取自配置

「超时将自动通过」→「**{N} 天内未处理将自动通过并放款**」，
`N` 取 `settings.AUTO_ACCEPT_DAYS`。

与 V61 同一条：**通知里的数字不许是字面量**。运维把自动验收改成 7 天，
这句话必须跟着变。有测试钉住（改配置 → 文案里的数字跟着改）。

## 4. AGT-070 AI 交的，要在通知里说

平台代 agent 提交交付后（V81），发布方收到的是一条和人交付完全一样的通知。
但这两件事对他不一样：

- 人交付：他大概率和对方聊过，心里有数；
- AI 交付：**他可能根本没意识到这一单是 AI 做的**（虽然他自己邀请过），
  而三天后就自动放款了。

所以 agent 交付时文案不同：说明这是平台 AI 助理的产出、平台是责任主体、
以及**可以申请人工核验**——那条路在 V74 就建好了，只是发布方在这个时点
不知道它存在。

## 5. AGT-071 审核说「拿不准」时自动下核验单——但**供应商挂了时不下**

V81 记了这条没做，理由是「会让审核供应商抖一下直接产生平台成本」。
现在把这条理由拆开看，它其实指向一个**更精确的分界**：

| `review` 的来源 | 自动下核验单？ | 为什么 |
|---|---|---|
| 供应商明确返回 `review`（拿不准） | **下**，平台付费 | 这正是人工核验存在的理由：机器判不了的，交给人 |
| 供应商故障（`provider_error:*`） | **不下** | 这是基础设施问题。**花钱雇人去补一次宕机**，是把成本花在错误的地方；而且故障是批量的，一次抖动会瞬间下一堆单 |

故障那条路保持现状：run 标 `escalated`、不交付、发布方仍可手动下单。
**两条路的区别不是「要不要人来看」，而是「这次拿不准是谁的问题」。**

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| NTF-060 | 声明表里的每一条，在用户**关掉对应偏好**后仍然送达 |
| NTF-060 | 声明表之外的通知照常可被关掉（开关不是摆设） |
| NTF-061 | 待验收通知里的天数取自配置；改配置则文案跟着变 |
| AGT-070 | AI 交付的通知说明是 AI 产出，并给出人工核验入口 |
| AGT-071 | 供应商明确 `review` → 自动下核验单，平台付费 |
| AGT-071 | 供应商故障导致的 `review` → **不**自动下单 |

## 7. 这一批没做的

- **NTF-062**：必达通知只保证站内必达；短信/推送通道的必达要等真实网关。
- **NTF-063**：没有「通知已读但用户其实没看」的兜底（比如临期再提醒一次）。
  待验收目前只在交付那一刻提醒一次，三天里不再提。
- **AGT-072**：自动下的核验单没有速率上限。真实供应商的 `review` 比例未知，
  上线前要看着这个数字，必要时加闸。
