# 207 已签的名额改时段时一键发变更单

> 状态：本批实现（V235）。编号 SCN-139。
> 来源：202 号 spec「没做的」——「已签的名额改时段时一键起草合约变更单」；BACKLOG V235。
> 只增不减：按天改时段（V234）不勾新选项时请求与行为不变（`kept` 每项多一个 `change_order_id: null`）；变更单的规则（只有当事人能提、同一时间只有一张待处理、对方接受才生效、接受后条款追加附录并为双方记新版本签署留痕）全部不变。
> 写明的行为变化：`change_orders` 加两列 `new_shift_start` / `new_shift_end`（迁移 c1d220260044）；变更单被接受时，带了这两列的会把名额的时段与标题一起改。

## 0. 要解决的问题

V234 让发单人在那一天上改时段：还在招的名额直接改；已经有人接的不动，只写明「改时间要和对方走合约变更单」。发单人要自己去每个名额的合约页，一张张写变更单、写清楚是哪天、由几点改到几点——而且就算对方接受了，名额上的时段也不会跟着变（变更单原来只改金额、截止时间与范围说明）。

## 1. 业界怎么做

排班类平台对已确认的班次改时间，通常由发起方提交改班申请、对方确认后才生效；未确认前保持原班次。本平台的合约变更单（SC-007b）正是「一方提、对方确认」的机制，本批把「改哪天的时段」做成变更单里的一项结构化改动，并在发单人改时段时替他起草好。（本批没有另找外部来源。）

## 2. 数据

`change_orders.new_shift_start` / `new_shift_end`（`String(5)`，可空）：`None` = 这张变更单不改时段；`""` = 改成不限时段。只是合约记录的一部分，不含个人信息；注销与导出按合约原有处置。迁移在 SQLite 与 Postgres 上 `upgrade head` + `check` 通过。

## 3. 接口

| 接口 | 变化 |
|---|---|
| `PATCH /tasks/{id}/days/{date}/shift` | 可选 `propose_change`（默认 false）。勾了时，对那天已经有人接的名额：合约已签或已托管、没冻结、没有待处理变更单的，替发单人发一张变更单（事由「发单人改了这一天的时段」，范围写「YYYY-MM-DD 的时段由 09:00–18:00 改为 10:00–16:00」，带上新时段），`kept` 那一项写 `change_order_id` 与「已给对方发了改时段的变更单，对方同意后生效」；还没签好合约的写「先和对方商量好，签约后再发变更单」；已有待处理变更单的写「等对方处理完再发」 |
| `POST /contracts/{id}/change-orders/{order_id}/accept` | 变更单带了新时段时，名额的时段与标题里的「（MM-DD 时段）」一起改；拒绝则什么都不改 |

SDK：`changeDayShift(..., proposeChange)`（不勾时请求体与 V234 一样）；`DayShiftKept.change_order_id`；`dayShiftChangeLine` 分开说「已发变更单、对方同意后生效」与「要走变更单」。服务端名额改时段的写法收成一个 `retime_slot`（按天改时段与接受变更单共用）。

## 4. 两端

- **Web** 任务详情「改某天的时段」里多一个勾选「已经有人接的，顺带给对方发变更单」。
- **App** 子任务进度的改时段里同一个勾选。
- 接单的人在合约页的变更单列表里看到这张单，照常接受或拒绝（原有入口）。

## 5. 隐私、授权与边界

- 签署相关：变更单是发单人自己勾选后才发的提案，**对方确认才生效**（「签署：AI 只出草稿，人确认」）；平台不替任何一方接受。
- 只给发单人（原接口的授权不变）；变更单的提案人是发单人本人。
- 不碰钱：改时段的变更单不改金额；要加价另提变更单或补招（196 号）。
