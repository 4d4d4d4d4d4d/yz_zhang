# 78 没有人盯的队列（QUEUE-010 / CS-031 / CERT-032 / TEAM-032 / UMOD-031 / PAY-045）

> 状态：本批实现（V103）
> 依赖：75 号（催办与超时兜底）、76 号（人审队列的出口）、32 号（定时任务）

## 0. 探针

V101 给六个人审队列装了出口，V102 给三个装了入口。这一批问第三个问题：
**东西进来了、出口也有了，那谁会去看？**

把四个队列里的东西都推到 30 天前，跑一遍全部 job：

```
PROBE SUPPORT_SLA_HOURS = 24（全仓只有定义，没有任何使用）
PROBE 管理员通知条数：跑 job 前 0 条，跑完 0 条
PROBE 管理员收到的通知：[]
PROBE 提单人收到的通知：[]
PROBE 工单仍在队列： [1]
PROBE 资质仍在队列： [1]
PROBE 团队仍在队列： [5]
PROBE 图片仍在队列： ['old-review.png']
```

顺手再问一句「队列长了怎么办」：

```
PROBE /admin/tickets 带 offset=10 → 200，返回 list（offset 被忽略）
PROBE /admin/certifications/pending 带 offset=10 → 200，返回 list
PROBE /admin/teams/pending 带 offset=10 → 200，返回 list
PROBE /admin/uploads/pending 带 offset=10 → 200，返回 list
PROBE /wallet/withdraw-requests?status=pending 带 offset=10 → 200，返回 list
```

五个队列都**接受 `offset` 然后忽略它**。这比报错更糟：翻页的人会看到
第一页无限重复，而且不知道自己在原地。

## 1. 三件事，一个形状

这一批要修的其实是同一个形状的三个面：

- **SLA 是一句没人核对的话**。`SUPPORT_SLA_HOURS = 24` 定义在配置里，
  全仓**没有任何地方使用它**——既不用来排序、不用来告警，也不用来
  告诉用户「我们承诺 24 小时内回」。这是 V96/V99/V101 那条规律的第四次：
  **写下来的承诺，没有任何东西核对它**。
- **积压是静默的**。队列里躺着的东西不会主动发声，而运营是「想起来才去看」。
  V100 已经证明过一次：只在开始时响一次的闹钟等于没有闹钟；
  现在这几个队列**连开始那一次都没有**。
- **等的人不知道自己在等什么**。提交资质的人、提工单的人，
  在超过 SLA 之后仍然一个字也收不到。沉默比慢更伤人：慢可以理解，
  沉默让人以为自己被忽略了。

## 2. QUEUE-010 队列声明表

这一批的主产出是一张表，和 65 号 `MUST_REACH`、76 号 `ADMIN_EXEMPT` 同类：

| 队列 | 看什么 | SLA | 超了谁被催 | 提交方是否被告知 |
|---|---|---|---|---|
| 工单 | `Ticket.status == open` | `SUPPORT_SLA_HOURS`（24h） | 全部管理员 | 是 |
| 资质核验 | `CertificationApplication.pending` | `REVIEW_SLA_HOURS`（48h） | 全部管理员 | 是 |
| 团队企业核验 | `Team.verify_status == pending` | `REVIEW_SLA_HOURS` | 全部管理员 | 是（通知 owner） |
| 图片人审 | `UploadedFile.moderation_status == review` | `REVIEW_SLA_HOURS` | 全部管理员 | 是（通知上传者） |
| 提现人审 | `WithdrawRequest.pending/awaiting_second` | 见 75 号（已有专门的催办与超时退回） | 全部管理员 | 是 |
| 可疑活动复核 | `SuspiciousActivity.status == pending` | `REVIEW_SLA_HOURS` | 全部管理员 | **否** |

最后一行的「否」是**故意**的，而且必须写清理由：AML-030/031 的保密义务
不允许告诉当事人「你被标记了、正在复核」。这一列如果只写 true/false，
下一个人会顺手把它改成 true——所以表里存的是**理由**，不是布尔值
（V90 立下的做法：声明表的值是原因，不是开关）。

提现那一行同样特殊：75 号已经给它做了专门的催办与**超时退回**，
所以这一批不再给它加第二套催办（两套催办等于每小时两条通知，
运营会把整类通知关掉）。它仍然在表里，因为表要能回答
「这个队列有没有人盯」——答案是「有，在 75 号那里」。

## 3. QUEUE-011 一张概览，而不是四条通知

新端点 `GET /admin/queues`：每个队列的**待处理数、最久等了多久、SLA、
是否已超**。三个地方共用它：

1. **催办 job** 用它判断哪些队列超了；
2. **管理后台**首屏用它显示积压概览——运营不该靠往下滚才发现有东西积压；
3. **测试**用它断言，而不是各自去数库。

催办发**一条汇总通知**，不是四条。理由：四个队列各发一条，运营一天收到
四条相似的通知，很快就会把 `system` 类整个关掉——而那一类里还有别的东西。
汇总里逐行写「哪个队列、几件、最久几小时」，这比四条分散的通知更可执行。

## 4. QUEUE-012 等的人也要收到一句话

超过 SLA 时，给**提交方**发一条：「你的 X 已超过 N 小时未处理，我们已催办」。

- 每件只发一次（落 `sla_notified_at` 一类的标记），否则每小时一条比不发更糟。
- 可疑活动复核**不发**（上一节的理由）。
- 文案里的小时数取自配置（V61/V90）。

这条通知的价值不在于加快处理，而在于**把沉默变成有据可查的等待**：
用户知道自己没被忘记，客服也少一通「我的申请怎么样了」。

## 5. PAY-045 队列分页

五个队列端点加 `offset`，并且：

- `offset` 必须**真的生效**（测试断言第 2 页与第 1 页不同）；
- 待处理总数从 `/admin/queues` 拿，不塞进列表响应里改形状；
- 后台在列表末尾给「加载更多」，只在还有剩余时出现。

**接受一个参数然后忽略它**是这一批要消灭的东西：它让调用方以为自己
在翻页。要么支持，要么拒绝（400），不许假装。

## 6. 验收点

| 编号 | 验收点 |

| QUEUE-010 | 表里「不通知提交方」的行必须写明理由，不能是布尔值 |
| QUEUE-011 | 超过 SLA 的队列进入汇总通知；未超的不出现 |
| QUEUE-011 | 一轮只发一条汇总，不是每个队列一条 |
| QUEUE-011 | 汇总里有队列名、件数、最久等待时长，数字取自配置 |

| PAY-045 | 后台只在还有剩余时显示「加载更多」 |

## 7. 这一批没做的

- **没有按人分配**（谁负责哪一单）。汇总通知发给全部管理员，
  也就是 TEAM-064 那条「谁都收到＝谁都不负责」的同一个毛病，
  只是换了个场景。要做分配得先有角色与值班表。
- **没有升级阶梯**：超了 SLA 只是催办，不会升级到更高一级。
  与 75 号留下的那条相同。
- 汇总通知只走站内信与推送，**没有走短信/邮件**：运营不登录后台，
  积压仍然只能靠日常巡检发现。卡在渠道成本与值班制度上。
- 分页只做 `offset`，**没有做筛选与排序**（按等待时长倒序会更实用）。
- `/admin/queues` 的数是**实时算的**，队列很大时会变慢；
  真要做大盘应当落一张物化表。现在的量级不值得。
