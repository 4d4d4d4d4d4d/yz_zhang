# 159 全站公告按城市与人群定向、阅读率

> 状态：本批实现（V185）。编号 NTF-066、NTF-067。
> 来源：151 号「没做的」NTF-066「公告按城市 / 角色 / 类目定向」、NTF-067「公告阅读率」；BACKLOG V185。
> 只增不减：不填城市与人群时行为与 151 号完全一样（全体 / 仅已实名）；预览原有的 `audience`（人数）不变；公告记录多四个字段。

## 0. 要解决的问题

- 公告只能发全体或仅已实名：上海的线下见面会通知发到了全国；「接单规则调整」发给了只发单、从不接单的人。不相干的通知多了，用户会把公告当噪音。
- 发出去以后不知道有多少人看了——无从判断该不该再发一次、要不要换个说法。

## 1. 业界怎么做

- **按人群分组推送（segmentation）**：Braze、Firebase Cloud Messaging 等按属性与行为分组（<https://firebase.google.com/docs/cloud-messaging/android/topic-messaging>）；按最近活跃度划分人群是常见做法。
- **打开率**：站内信与推送的基本指标是送达与打开（opened / delivered）。

## 2. 数据（迁移 `c1d220260032`，SQLite 与 Postgres 都验过）

| 表 | 字段 |
|---|---|
| `announcements`（加列） | `city`（空 = 不限）、`audience`（all / publishers / workers） |

阅读率不加表：按通知的 `announcement_id` 与已读位汇总。

## 3. 规则与接口

| 编号 | 内容 |
|---|---|
| NTF-066-1 | 预览与发布可带 `city`（与用户资料里的城市完全一致）与 `audience`：`publishers` = 近 180 天发过单的人，`workers` = 近 180 天报过名接单的人；与「仅已实名」可以叠加；不认识的人群 400 `bad_audience` |
| NTF-066-2 | 预览多 `city`、`audience_kind`；按条件一个人都发不到时提醒「检查城市名是否写对」 |
| NTF-066-3 | 定时公告保留定向条件，到点按当时的人群发出；审计里写明发给了谁（城市、人群） |
| NTF-067-1 | `GET /admin/announcements` 每行多 `read`（点开过的人数）与 `read_rate`（已读 / 送达，还没发出的为空） |

## 4. 两端

- **Web 管理后台「全站公告」**：城市输入框、「发给哪类人」下拉（全体 / 近 180 天发过单的人 / 近 180 天报过名接单的人）；预览写明发给谁；「发过的公告」表多「已读」一列（人数与百分比）。
- **App**：管理后台只在 Web，不涉及；用户侧照常收到通知。

## 5. 隐私与边界

- 人群只按平台内行为（发单、报名）粗分，不用任何个人画像；预览只返回人数。
- 城市取自用户自己填的资料；没填城市的人不会被按城市定向的公告覆盖。

- **NTF-068 按类目定向**：例如只发给近期接过「保洁」单的人；要先定类目与人的关系口径。
