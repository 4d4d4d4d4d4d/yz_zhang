# 60 形状也要对上（CLI-067）

> V82 建的客户端覆盖闸门只看**路径**：端点在不在 SDK 里。
> 两批之内，它没管的那一半就出事了两次——而且第二次是我自己刚写的代码。

## 0. 两次现成的病历

**一：请求体。** `addCertification(name, licenseNo)` 发的是
`{name, license_no}`，而服务端从 V76 起要的是
`{name, holder_name, cert_number, images, ...}`。**这个调用必 422**，
从 V76 到 V82 一直躺在 SDK 里；而且有一条 SDK 测试**正在断言那个错的请求体**——
它打的是 mock fetch，只验证「我发出的请求长这样」，从不验证「服务端认不认」。

**二：响应体。** V82 给 `CompliancePath` 写的 TS 类型声明了 `items`，
服务端返回的是 `documents` / `registrations` / `notices`。
类型对不上，**没有任何东西会红**，直到 V84 要用它时人眼看出来。

写这一批时闸门立刻抓到了第三条，是我在 V82/V84 亲手写的：
`TeamView` 声明了 `company_status` 与 `created_at`，服务端给的是
`tax_number` / `verify_status` / `verify_reason` / `active`。
于是 V84 团队页上那行「企业信息状态」**在运行时恒为 undefined**。

> 这一条最值得记：那页的 web 测试是绿的，因为**测试桩是照着那个错类型写的**。
> 桩与类型互相印证，两个都错，闭环自洽。
> **在 mock 里自洽，不等于对。**

## 1. 判断：比什么

| 要比的东西 | 拿什么当真相 | 为什么 |
|---|---|---|
| 请求体 | **OpenAPI 的 requestBody schema** | 它就是服务端的校验规则本身（pydantic 模型生成），不是二手描述 |
| 响应体 | **真实响应** | 大量端点返回手写字典，FastAPI 只知道它返回 `dict`，OpenAPI 里**根本没有 schema** |

第二行是这一批唯一需要想一下的地方：直觉会想「都比 OpenAPI 不就统一了」，
但那样只能覆盖有 `response_model` 的少数端点，而出事的恰恰是手写字典那批。

> **能拿到真东西的时候就别去比声明。**

代价是响应侧的比对必须**跑一遍真实业务流程**（建合作体、发密钥、跑 agent…），
测试变重。值得：它顺带证明了那些端点确实能跑通。

## 2. CLI-067 两道比对

### (a) 请求体

扫 `client.ts` 里 `this.request<...>(VERB, PATH, BODY)` 的第三个参数，
取**字面量对象**的顶层键，与 OpenAPI 的 `properties` / `required` 比：

- 多发的键 → 服务端不认（pydantic 默认忽略未知字段，但字段名写错就等于没发）
- 漏发的必填键 → 422

**动态请求体跳过**（透传的 patch 对象、带展开的字面量）：
它们的键在运行时才确定，硬比会得到一堆假警报，而**满口假警报的闸门会被人关掉**。
跳过的部分记在「没做的」里，不假装覆盖了。

### (b) 响应体

解析 `types.ts` 的 `export interface`（含 `extends` 展开），与真实响应的键集合
**双向**比对：

- 声明了服务端没给的 → 客户端 `x.foo` 编译通过、运行时 undefined（就是那个团队页）
- 服务端给了没声明的 → 客户端根本看不见这个字段，写代码时不知道它存在

**两个方向都要红**：只查一边的闸门，另一边就是自由的。

### 自检

沿用 V72 的规矩：解析不出接口、扫不到调用，闸门就恒真。
所以两条都断言下限（≥30 个接口、≥150 个调用、≥40 个请求体真的被比过），
并且钉住几个已知成员（`extends` 必须真的被展开）。

## 3. 验收点

| 编号 | 验收点 |
|---|---|
| CLI-067 | SDK 字面量请求体的键与 OpenAPI schema 一致（多发/漏必填都红） |
| CLI-067 | 六条线的响应形状与 TS 接口双向一致 |
| CLI-067 | 接口解析器能展开 `extends`；解析/扫描数量低于下限时自己先红 |
| TEAM-060 | `TeamView` 按服务端真实字段修正，团队页显示 `verify_status` 与驳回理由 |

## 4. 这一批没做的

- **CLI-068**：字段**类型**不比，只比键名。`amount_cents: string` 这种错仍然抓不到。
  要比类型得把 TS 类型表达式解析出来，或者反过来从 OpenAPI 生成 TS——
  后者是更彻底的方向，但会改掉全部手写类型，是单独一批。
- **CLI-069**：动态请求体（透传 patch、带展开的字面量）跳过。
- **CLI-070**：响应比对只覆盖 V73~V79 那六条线与资质。老模块（任务/合约/钱包）
  的类型是逐步长出来的，没有一次性对齐过，先不动它们——
  这一批要的是**让新写的东西不能再错**，不是一次把历史全洗一遍。
