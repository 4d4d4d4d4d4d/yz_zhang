# 73 盲封与查不到的那笔钱（ADMIN-060 / MOD-060 / FIN-060）

> V96 的测试能断言「批准提现写下了一行审计」。
> 而**谁批了那笔三万块**这个问题，直到这一批之前只能靠查数据库回答。

## 0. 剩下的四条

V96 把提现复核台与可疑活动接上了，管理后台仍有四条只有端点、没有界面
（71 号 spec 的「没做的」里记着）。探针逐条打，**服务端全都是通的**：

```
AUDIT : []                              ← 通，只是没人读
IMPACT: {"in_flight_contracts":[{"contract_id":1,"status":"funded","amount_cents":20000,
         "counterparty_id":1}],"in_flight_count":1,"escrow_at_risk_cents":20000,
         "open_task_ids":[],"open_task_count":0,"wallet":{...}}
FIN   : {"balance_cents":0,"total_fee_cents":0,"settled_cents":0,"fee_count":0}
ANN   : 200 {"delivered":3}
```

其中两条不是「少个页面」的量级。

## 1. MOD-060 管理员在盲封

V58 那一批专门算了封禁的**影响面**：这个人手上有几笔在途合约、
多少托管资金会受影响、几个招募中的任务会被下架、钱包三态各是多少。
算得很细。

而管理后台的封禁按钮长这样：

```tsx
<button className="danger" onClick={async () => { await client.banUser(u.id); await load(); }}>
  封禁
</button>
```

**直接封。** 影响面一次都没被调用过。

封禁是不可逆的处置，而且它的代价不只落在被封的人身上——
对手方的在途合约、已报名执行方的任务，都会跟着受影响。
**代价必须在按下之前摆在眼前**，不是按下之后从工单里慢慢发现。

所以这一批不是「加一个影响面页面」，是**把它接进封禁流程**：
点「封禁」先拉影响面并要求确认，确认之前**一个封禁请求都不发出去**。

这条要靠**行为测试**钉，不能靠源码扫描：
扫描闸门只能看出「`banImpact` 被调用了、组件挂上了」，
它看不出按钮到底是先弹确认还是直接把人封了——
而那正是盲封的要害。（红验证实了这一点：把按钮改回直接封，
源码闸门照样绿，而行为测试四条全红。）

## 2. ADMIN-060 审计日志读不到

审计行一直在写（V58 建的 `record_audit`，V96 给提现批准也接上了）。
读不到的后果很具体：**谁批了那笔三万块**、**谁解封了那个账号**，
这两个问题在界面上答不出来，只能开数据库。

那不是合规底线该有的样子——留痕如果只能事后取证时才用得上，
日常复核就等于没有。

补上：按动作过滤（不然一屏全是登录记录）、显示管理员、对象、明细。
顺手把明细钉住：批准提现的那一行**必须带金额**，
不然回溯时还得再查一次。

## 3. FIN-060 平台自己的钱

佣金收了多少、结算走了多少、账上还剩多少——三个数在界面上看不到。
结算（把佣金从平台账户划走）是个**动钱的动作**，
因此它属于后台、要留痕，而不是一条脚本。

> 代扣税款在独立专户，不与佣金混同（V54 的第五条不变量），
> 界面上要把这句话说出来——否则看数的人会以为账上的钱都是可分配收入。

## 4. 公告

发出去收不回来，所以按下之后要**回显送达人数**：
让发的人看到自己刚影响了多少人。

## 5. 顺手掉出来的一条漂移

`banImpact` 在 SDK 里是行内匿名类型，而它**漏了 `open_task_ids` 与
`open_task_count`**——服务端一直在返回，类型里没有，于是界面
显示不出「几个招募中的任务会被下架」。

又一次「声明了却不给 / 给了却不声明」（V89 那一类）。
这几个响应因为在 `/admin` 下，V89 的形状闸门整体跳过了它们——
V96 已经把管理端两个形状纳进闸门，这一批再纳三个。

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| MOD-060 | 点「封禁」先显示影响面；**确认之前不发任何封禁请求** |
| MOD-060 | 影响面显示在途合约、受影响托管资金、会被下架的任务编号 |
| ADMIN-060 | 审计日志可读、可按动作过滤、显示是谁做的 |
| ADMIN-060 | 批准提现的审计明细里带金额 |
| FIN-060 | 平台财务四个数可见；结算留审计且不破资金不变量 |
| FIN-060 | 结算金额不得超过平台余额 |
| — | 公告回显送达人数 |
| CLI-077 | 四条都进 `ADMIN_CONSOLE`，缺任何一条即红 |

## 7. 这一批没做的

- **封禁仍是一个人点**。与提现的四眼原则（PAY-042）同一个缺口：
  不可逆的处置应当双人确认。
- 审计日志**没有分页**，只取最近 50 条；也不能按管理员或时间范围筛。
- 审计日志**不可导出**。真正的合规审计会要一份可归档的文件。
- 平台财务**没有按期间的报表**（本月佣金、本季结算），只有累计数。
- 公告**不能撤回，也不能定时**；没有预览。
- 管理后台整体**仍未纳入路径覆盖闸门**（`_server_paths` 仍跳过 `/admin`），
  只有 `ADMIN_CONSOLE` 里声明的那几条被钉住。
