
# 384 驾驶舱的时间线：步骤带工期估计，按依赖排出预计完成日（AI-DEC-021c）

> 状态：本批实现（V411）。编号 AI-DEC-021c。
> 来源：368 号「没做的」：驾驶舱只能指出截止排错的地方，看不出整条线什么时候能做完；步骤也没有工期估计字段。BACKLOG V411。
> 只增不减：任务多一个可空字段 `est_days`；驾驶舱响应多 `timeline`、节点多 `est_days`、预警多两种。原有字段、关键路径（按剩余步数）、排期冲突都不变。

## 0. 要解决的问题

一个项目拆成十几步、分给几个人以后，发单人最常问的是「这件事哪天能做完」。驾驶舱原来答不了：
- 关键路径按「还剩几步」算，不知道每一步要几天；
- 截止是一步一步分别填的，填完看不出整条线排下来会不会晚；
- 排期冲突（368 号）只抓明显填错的两种，抓不到「每一步截止都对，可是前面的加起来已经超了」。

## 1. 业界怎么做

项目管理工具的甘特图都是「每个任务一个工期，按前置关系往后推，最晚的那个结束就是项目完成日」，前置没完成的任务从前置的结束开始。这是通行做法，本轮没有引用外部链接。

## 2. 数据 / 接口

- `tasks.est_days`（整数，可空，1~365 天），迁移 `c1d220260094`。
- 拆解步骤可以填工期：`PATCH /decompositions/{id}/nodes/{node_id}` 多收 `est_days`（1~365）；确认时叶子的工期带到子任务上。
- 发单人在发布前可以改：`PATCH /tasks/{id}` 多收 `est_days`（1~365），属于非实质字段，不受防调包保护；任务详情多回 `est_days`。
- `GET /tasks/{id}/cockpit`：
  - 节点多 `est_days`；
  - 多 `timeline`：`rows`（每一步的 `start / end / basis / late`）、`projected_finish`、`unknown_steps`；
  - 预警多两种：`estimate_past_deadline`（这一步按工期排下来赶不上它自己的截止）、`projected_late`（整件事排下来晚于截止）。两种都标红。

### 怎么排

- 每一步最早从「现在」开始；要等的前一步没完成，就从前一步的预计完成时间开始（要等几步取最晚的）。
- 长度按工期估计。
- 没填工期但填了截止：排到截止为止（`basis = deadline`）。
- 两样都没有，或者截止已经过了，或者它要等的步骤排不出来：这一步排不出来（`basis = unknown`），整件事的完成日也不给（`null`），并写明几步没填。不拿猜的数字充数。
- 进行中的步骤不知道做了几成，按整段工期从现在算：宁可估晚，不估早。
- 已完成、已取消的步骤不画条，也不拖后面的步骤。
- 依赖成环的脏数据不死循环。

## 4. 两端

- **网页**：
  - 驾驶舱的「每一步」表多一列「工期」。还没开工（未开始 / 招募中）的步骤可以直接填、存完重新取驾驶舱；开工以后只读（改期走合约变更单）；
  - 表下面画「时间线」：上面一句「按各步工期排下来，预计 X 做完」或「有 N 步没填工期也没填截止……」；
  - 每一步一条：从最早开始的那步画到最晚结束的那步；没填工期按截止排的用灰色，赶不上自己截止的标红并写「赶不上截止」；
  - 拆解页编辑一步时可以填「要几天」，已填的写在这一步下面。
- **App**：驾驶舱同样有时间线（预计完成日、每步一条、赶不上截止的用警示样式），没开工的步骤就地填工期；拆解页编辑一步时可以填「要几天」。
- 两端共用 SDK 的 `timelineBars`（算每条的位置与长度，很短的一步至少占 2%，畸形数据少画不报错）、`projectedFinishLine`、`timelineBasisLabel`，以及扩充后的 `isUrgentCockpitAlert`。

## 5. 隐私、授权与边界

- 驾驶舱只给发布方（原有授权不变）；`est_days` 是任务的公开字段，和截止一样。
- 只给估计，不动截止、不动钱、不自动改期：改不改截止由发单人决定。
