# 43 好友、群聊与第三方登录（IM / ACC-003）

> 补需求回顾查出的另外三条降级实现：独立群聊、好友体系、第三方登录。
> 原始 spec（09 / 02 号）里都写着，实现里只有圈层自带的群聊。

## 0. 三条各自的分量不一样

| 条目 | 原 spec 的说法 | 为什么它不是「锦上添花」 |
|---|---|---|
| IM-020 加好友 | 「**双向同意**」 | 单向加好友＝给任何人开一条无需对方许可的私聊通道，而这个平台上陌生人之间本来就有真金白银的往来 |
| IM-003 群聊 | 「上限**可配**」 | 写死数字意味着不同规模的部署只能改代码 |
| ACC-003 第三方登录 | 「**App 端 Apple 登录为上架合规必需**」 | App Store 规则：提供了任何第三方登录就必须同时提供 Sign in with Apple。这是**上架前置条件**，不是体验项 |

## 1. 设计判断

**判断一：群成员资格就是 `participants`，不另起一张表。**
发消息的鉴权（`_get_conv`）本来就按 `participants` 判断，把群成员放进同一个
字段，群聊的发言权限**自动**被既有鉴权覆盖。另起一张表就要再写一遍鉴权——
而「同一条规则两份实现」是这一路反复踩的坑（V58 的两条封禁路径、
V61 的申诉按钮）。

**判断二：IM-022「合作过的人」是查出来的，不是存出来的。**
存一张表就要在每次闭环、每次取消、每次注销时同步维护它，漏一处就是一条
永远错着的记录。直接查已结算合约的对手方——它不可能过时。

**判断三：`subject` 是身份，邮箱和手机号不是。**
邮箱会变，Apple 还允许用户隐藏真实邮箱。拿它们认人迟早认错人。

**判断四（最重要）：第三方登录不等于实名。**
微信认证的是「这是同一个微信」，不是「这是张三」。所以 OAuth 建出来的账号
`is_verified=False`、没有真实手机号，接单与提现仍然要走实名闸门；
响应里 `needs_phone` / `needs_verification` 如实告诉客户端还差什么。
把两者混为一谈，等于给实名开了一条后门。

**判断五：两个人互相发好友申请不能变成死锁。**
各发一次却互相等待，谁都点不到「接受」——所以第二次发送实质是同意。

## 2. 本批查出的一条真实认证绕过

给 OAuth 账号分配的占位手机号是 `oauth:wechat:xxx`（不可拨打、收不到短信，
这是有意的）。但我自己写的测试发现：

```
POST /auth/login-sms  {"phone": "oauth:wechat:xxx", "sms_code": "123456"}
→ 200 OK
```

`login_sms` 只按 `User.phone` 查人，而模拟通道的固定验证码**不要求先请求
验证码**。任何知道这串占位符的人都能直接登进那个账号。

修法不是在 `login_sms` 里补一个 if，而是把校验放在**短信链路的公共入口**
（`sms_service.assert_dialable`，`send_code` 与 `verify_code` 都过）：
注册、找回、换绑、短信登录共用这一道，漏掉任何一个端点的可能性就此消失。

`verify_code` 也必须校验——只挡发送侧等于没挡，因为模拟通道下固定码直通，
根本不经过 `send_code`。

## 3. 条目

### 好友（IM-020/021/022）

- **IM-020** `POST /friends/requests` → `pending`；
  `POST /friends/requests/{id}/decide?accept=` 仅被申请方可处理。
  ACC-033 拉黑优先于加好友——否则拉黑就是个能被绕过的摆设。
- **IM-021** `GET /friends` / `PATCH /friends/{user_id}`：
  备注名**各自看各自的**，按方向存在同一条关系行上。
- **IM-022** `GET /friends/worked-with`：查已结算合约的对手方，带合作次数。
- 唯一约束 `(requester_id, addressee_id)`：一对人只能有一条记录，
  否则双方同时发起会攒出两条，接受哪一条都对而另一条永远悬着。

### 群聊（IM-003）

- **IM-003** `POST /conversations/groups`、`POST/DELETE .../members`、
  `PATCH /conversations/{id}`（群名/公告/禁言）。
- 成员上限 `PLATFORM_GROUP_MEMBER_LIMIT`（默认 200）。
- 群主不能移出自己（群主位空悬），也不能禁言自己（把自己锁在群外）。

### 第三方登录（ACC-003）

- **ACC-003** `POST /auth/oauth/{provider}`（wechat/apple/google）+
  `GET /auth/oauth/providers`（客户端据此画按钮，不硬编码）。
- `oauth_identities` 表，唯一约束 `(provider, subject)`：
  一个第三方账号只能绑一个本站账号。
- 复用 `_issue_token`：新设备提醒、会话可吊销这些行为不该因为「换了个登录
  入口」就消失。
- **`oauth` 列入 `P0_KINDS`**：`MockOAuth` 等于「客户端说自己是谁就是谁」，
  与支付/实名同一等级的风险，生产自检拒绝它。

## 4. 已知缺口

- **ACC-050 没有「绑定到已有账号」的入口。** 现在第三方登录只做
  「找到或新建」。已有手机号账号的用户想再绑一个微信，需要一个登录态下的
  绑定端点，本批未做。
- **ACC-051 真实通道未验证。** `HttpOAuth` 的形状按微信 `code2Session` /
  Apple id_token 校验 / Google tokeninfo 写的，但本环境无法真连；
  接入时必须在 `verify()` 里按 provider 做字段映射并补一次真机验收。
- **IM-030 群聊没有进 Web/App 界面。** 端点与 SDK 就位，UI 未做。
- ~~**IM-031 禁言只存名单，未在发消息处生效**~~ —— 写到这里时发现它正是我
  这一路一直在批的「建好了没接上」，于是当场补掉：`send_message` 读 `muted`
  并返回 403 `muted_in_group`，有测试钉着「禁言前能发 / 禁言后不能 /
  解除后恢复」。**把它记成缺口比修它还费事。**
