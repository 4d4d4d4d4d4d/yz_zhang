
# 148 大额平台结算的四眼：两位不同的财务先后确认

> 状态：本批实现（V176）。编号 SEC-061c、PAY-042b（平台结算部分）。
> 来源：141 号「没做的」SEC-061c「提现审批与结算的四眼按角色」；台账 PAY-042b「结算与税款缴库仍是一人操作」；BACKLOG V176。
> 只增不减：小额结算照旧一步完成、响应不变；大额提现的两人确认（PAY-042）不变。
> 写明的行为变化：达到 `PLATFORM_SETTLE_DUAL_APPROVAL_CENTS`（默认 ¥1 万）的结算不再立刻划出，而是先记成「等第二位财务确认」。

## 0. 要解决的问题

- 提现从 V99 起就有「超过 ¥2 万要两个不同管理员先后确认」；而**平台结算**——把平台账户上的佣金划出去——一个人点一下就完成了。
- V169 之后两步都只能由财务角色做，所以提现那条已经满足「两位财务」；平台结算还差这一道。
- 税款缴库是调度器按调度表跑的 job（`/jobs/remit-tax`），不是人点的，不在本批范围。

## 1. 业界怎么做（带来源链接）

- **四眼原则 / maker-checker**：资金划拨由一人发起、另一人复核后才执行，是支付与银行内控的基本要求（例如中国人民银行《非银行支付机构监督管理条例实施细则》对资金划转的岗位分离要求；COSO 内部控制框架的职责分离，<https://www.coso.org/guidance-on-ic>）。
- **执行时再核一次余额**：复核时以当时的余额为准，避免发起后余额已经变化。

## 2. 数据（迁移 `c1d220260026`，SQLite 与 Postgres 都验过）

| 表 | 字段 |
|---|---|
| `platform_settle_requests` | 金额、备注、发起人、状态（等确认 / 已划出 / 已驳回）、处理人、理由、时间 |

配置：`PLATFORM_SETTLE_DUAL_APPROVAL_CENTS`（默认 1000000 分）。

## 3. 规则与接口

| 编号 | 内容 |
|---|---|
| SEC-061c-1 | `POST /admin/platform-finance/settle`：达到阈值时先查余额（不够照旧 `insufficient_platform_balance`），记一条等确认的申请、进审计，返回 `status=awaiting_second` 与说明；不动钱 |
| SEC-061c-2 | `GET /admin/platform-finance/settle-requests`：按状态列出 |
| SEC-061c-3 | `POST …/{id}/approve`：发起人自己不能确认（`same_approver`）；确认时再查一次余额；已处理过的不能再处理（`settle_already_decided`）；进审计（写明发起人） |
| SEC-061c-4 | `POST …/{id}/reject`：驳回别人发起的要写理由（`reason_required`），发起人可以直接撤回；不动钱 |
| — | 三个接口都是财务角色（141 号角色总表已登记） |

## 4. 两端

- **Web 管理后台「平台财务」**：大额结算后说明「要另一位财务确认后才会划出」；下面列出待确认的结算（金额、备注、发起人、时间、「钱还没划出」），确认划出 / 驳回或撤回。
- **App**：管理后台只在 Web，不涉及。

## 5. 隐私、授权与边界

- 只涉及平台自己的账；所有动作进审计。

## 7. 没做的

- **SEC-061f 四眼按金额分级**：例如 ¥10 万以上要超级管理员作为第二人；现在只要「另一位财务」。
- **PAY-042c 提现的第二人也按角色核对**：提现两步都已要求财务角色（141 号），但第二人与第一人「同一角色以上」的等级比较还没做（与 SEC-061f 一起做）。
