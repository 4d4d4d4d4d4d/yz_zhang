
# 327 经验时效窗口按类目可配

> 状态：本批实现（V354）。编号 KB-062b。
> 来源：323 号 spec「没做的」：「时效窗口按类目可配（有的行业一季度一变，有的几年不变），在后台由运营调」；BACKLOG V354（第三十三轮排期，分数 18）。
> 只增不减：没设的类目照旧 365 天（323 号的行为一字不变）。类目接口只在设了的类目上多一个 `experience_fresh_days`。

## 0. 要解决的问题

V350 给所有经验定了统一的 12 个月。可行业的节奏不一样：装修材料价、平台规则一季度一变，三个月前的经验就可能带偏；翻译、家教的做法几年不变，一年前的经验还很好用。这个数应该由懂行业的运营按类目调。

## 1. 业界怎么做

内容与知识管理系统常给不同栏目设不同的「过期提醒周期」，由栏目负责人维护。本批没有另找外部来源。

## 2. 规则

- 运营在后台「城市与类目」给每个类目设经验时效：30~3650 天；填 0 回到平台默认 365 天，库里存空值。
- 超出范围的拒绝（400 `fresh_days_out_of_range`），提示写明范围和「填 0 回到默认」。
- 每次改动进审计，写明前后（「装修：默认 → 90」）。
- 生效范围：
  - 喂给 agent 的核验经验，按这个类目自己的窗口取；
  - 经验单元的「新 / 旧」，按单元的适用类目判断，没写适用类目时看所在子类的类目。拆解第一层的排序、助手引用的「可能已过时」都跟着变。
- 价格参考的 180 天（KB-013）不受影响：价格变得快，是另一条规则。

## 3. 数据 / 接口

- `categories.experience_fresh_days`（可空）；迁移 c1d220260083，SQLite 与 Postgres 都验过。
- `PATCH /admin/categories/{id}?experience_fresh_days=N`（ops 角色，沿用原接口）：设了才在返回里带这个字段。
- `GET /categories`：设了的类目才带 `experience_fresh_days`。
- 共享 SDK：
  - `Category.experience_fresh_days?`
  - `updateCategory` 多一个参数
  - 新错误码进 i18n
- 服务端：`knowledge.units.fresh_days_for(db, category)`。

## 4. 两端

- **Web 后台「城市与类目」**：每个类目显示「经验时效 N 天」，没设的写「（默认）」；「经验时效」按钮输入天数，填的不是整数就当场说清、不发请求。
- **App**：没有管理后台，不涉及。

## 5. 隐私、授权与边界

只有 ops 角色能改（沿用类目管理的角色），改动进审计。
