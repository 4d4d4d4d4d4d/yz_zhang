这一批本来只是「把搜索接上两端」。接之前读了一遍服务端，发现两处

## 1. 热词与联想公开的是原始搜索串（PRIV-060）

改造前：

```python
def log_search(db, term):            # 谁搜的不记，搜了什么原样存
    db.add(SearchQuery(term=term))

@router.get("/search/trending")      # 不要登录
@router.get("/search/suggest")       # 不要登录
    # 按次数排序，没有门槛，不过审核
```

两个后果：

- **隐私**：有人搜过「张三 13800001234」，任何人在框里打「张」，联想里就是它。
  **一次就够**——没有门槛。搜索词按 PIPL 是个人信息，原样公开就是泄露。
- **投毒**：任何人反复搜同一句「加微信 xxx」，就能把它推上所有人看得见的
  热词榜。搜索是 GET，写路径限流管不到它。

改法照业界的做法，四层：

| 层 | 内容 | 为什么 |
|---|---|---|
| 写入时：不记身份标识 | 手机号、身份证号、邮箱**根本不存** | 数据最小化在写入时做——存下来的东西迟早会从别的口子出去 |
| 写入时：不记过不了审核的 | 复用 `machine_review()`（不写第二份违禁词表） | 防投毒 |
| 读取时：人数门槛 | 至少 `PLATFORM_SEARCH_PUBLIC_MIN_USERS`（默认 3）个**不同的人**搜过才公开；返回的计数是人数 | k-匿名：一个人的搜索永远不公开；次数可以被一个人刷出来，人数不行 |
| 读取时：再过一遍审核 | 公开前按**当前**规则再审一次 | 词是很久以前记下的，而审核规则会更新 |

**两层审核都各自钉住了。** 红验时发现：把写入时那层去掉，原来那条测试仍然是绿的——
读取时那层把它挡在了公开结果外面。可 `log_search` 的 docstring 写着「不记的两类」，
那一半的承诺就没有任何东西在检查。所以补了「它根本没被存下来」的断言；
读取时那层另用一条「规则更新之前就已经存下的词」来钉。

### 存量数据

迁移 `c1d220260006` 加 `user_id` 列，并**删掉已经存下的身份标识类搜索词**。

这是不可逆的，而 V118 那次我拒绝在迁移里合并聊天记录，理由也正是不可逆。
区别在于对象：那是**用户的聊天记录**，是他们的东西；这是**平台内部的统计日志**，
里面的身份标识本来就不该被存下来——留着它们没有任何正当用途，只是一份负债。

存量行没有 `user_id`，不计入任何人数——它们从此不会再被公开。

## 2. 搜人不看隐私设置（PRIV-061）

改造前用户搜索只排除了封禁：

```python
.filter(User.nickname.contains(q), User.is_banned.is_(False))
```

于是**设了「资料不公开」的人照样被搜出来，连同技能与信用分**；
已注销的「已注销用户」也会出现在结果里。而同一个平台的空间列表
（SPACE-005）与公开资料页（ACC-030）早就按隐私设置过滤了——
**同一个人的可见性，在三个入口有两套规则**。

改成与空间同一条：未封禁、未注销、未设资料不公开。

顺带：四类搜索的 `contains()` 与联想的 `startswith()` 都加 `autoescape`——
用户打一个 `%` 不该匹配到全站所有人（空间搜索早就这么做了）。

## 3. 两端

| 端 | 入口 | 行为 |
|---|---|---|
| web | 导航栏常驻 ⌕ → `/search` | 空框显示热词；边打边联想（防抖 + 过期响应丢弃）；四类结果分组，任务与人可点进去；**查询词在 URL 里**——结果能分享、能后退回来 |
| App | 「发现」页第二个分段「搜索」 | 同上；点人打开空间，点任务取完整详情后打开 |

## 4. 闸门

| 闸门 | 内容 |
|---|---|
| PRIV-060a | 一个人搜十次也不公开 |
| PRIV-060b | 第 3 个不同的人才公开；计数是人数 |
| PRIV-060c | 身份标识根本不存 |
| PRIV-060d | 过不了审核的词不进热词榜，**且根本不存** |
| PRIV-060e | 规则更新之前存下的词，读取时照样被挡 |
| PRIV-060f | `%` 不是通配符 |
| PRIV-060g | 迁移清掉存量身份标识、其余不动；迁移与服务里的模式一致 |
| PRIV-061 | 资料不公开的人、已注销的人搜不到；正当结果仍在 |
| 两端 | 热词可点、结果分组可点、URL 承载查询词、空结果说清、导航常驻入口 |

九条红验走过（服务端七条、客户端三条中的代表）。真浏览器联调新增一步，13 项全绿。

**联调闸门的一个盲区**：V107 的页面覆盖扫描要求路径后面紧跟引号，于是
`/search?q=…` 这种带查询串的访问对它**不可见**。改了扫描并加自检——
与 V116 只认双引号同一类。

## 5. 这一批没做的

- **门槛是全局一个数**：小城市、小众类目的热词天然达不到 3 人，会显得空。
  那是正确的结果（宁可空也不公开个人搜索），但运营可能想按城市调。不做。
- **没有按时间衰减**：去年的热词与上周的同权重。要做得先定窗口。
- **搜索仍是 SQL LIKE**：规模化要换 ES/OpenSearch（模块 docstring 早就写着）。
- **内容与圈层结果不可点**：内容详情与圈层详情两端的路由形态不一致，
  先只列出。记台账 `SRCH-010`。
