# 58 时间是一条契约（TZ-060~068）

> 缺口的证据不是推理出来的，是**代码里现成的两行补丁**：
>
> ```tsx
> // web/src/DisputePanel.tsx:19
> const left = new Date(iso + 'Z').getTime() - Date.now();
> // app/App.tsx:304
> (new Date(dispute.response_deadline + 'Z').getTime() - Date.now()) / 3_600_000
> ```
>
> 有人在这两个地方发现了「服务端给的时间被当成本地时间解析」，于是就地补了个
> `+ 'Z'`。**补丁本身就是缺陷报告**：同一个问题在全仓还有 7 处没补，
> 而且是在两个端上各自独立补了一次。

## 0. 问题的两半

### 半个：出去的时间没有时区

服务端所有时间都是 UTC（`utcnow()` 返回的是 `datetime.now(timezone.utc)`
去掉 tzinfo 的朴素值），响应里一律 `x.isoformat()`——出来的是
`2026-09-20T08:00:00`，**没有 `Z`，没有偏移**。

而 JavaScript 的规矩是：ISO 8601 的**日期时间形式**不带偏移时，
按**本地时间**解析（带偏移或只有日期时才是 UTC）。于是

```
new Date('2026-09-20T08:00:00')   // 东八区用户：本地 08:00 → 实际 UTC 00:00
```

**全站每一个时间显示都偏了用户所在时区的偏移量。** 东八区看到的「刚刚」
其实是 8 小时前；夏威夷用户（UTC-10）看到的时间比真实的晚 10 小时。
账单流水、进度留痕、通知、会话、优惠券有效期，全部如此。

倒计时那两处之所以被发现，是因为**倒计时错了会算成负数**，肉眼可见；
而「这条流水是几点」错 8 小时，没有人会立刻察觉。

### 另外半个：进来的时间偏移被**静默丢弃**

探针实测：

```
POST /tasks  {"deadline": "2030-01-01T10:00:00+08:00"}  → 201
库里存的是                datetime(2030, 1, 1, 10, 0)     ← 偏移没了，也没换算
```

`+08:00` 的 10:00 是 UTC 02:00，正确的存法是 `02:00`。现在存成 `10:00`，
**整整差了 8 小时**，而且没有任何报错。

反过来更糟：

```
夏威夷用户（UTC-10）选「2 小时后」，客户端发本地朴素时间
→ 400 {"code": "deadline_in_past", "message": "截止时间必须晚于当前时间"}
```

**他根本发不出这个任务**，而报错信息说的是一件他知道不对的事。

## 1. 判断：契约定在哪一层

三种做法：

| 方案 | 做法 | 取舍 |
|---|---|---|
| A 存用户时区，按用户渲染 | `users.timezone` 字段，服务端出本地时间 | 服务端要为每个读者渲染一遍；缓存、导出、对账各有一份口径，**同一条记录会有多个"正确"的字符串** |
| B **出入都是带时区的 UTC，本地化只在展示层** | 服务端恒出 `...Z`，客户端按浏览器时区渲染 | 选它 |
| C 全部用时间戳（毫秒整数） | 客户端自己格式化 | 契约最干净，但**改掉全部 74 处输出与所有客户端解析**，收益只是少一个字母 |

**选 B。** 它与平台已有的两条判断是同一条线：金额用整数分、只在展示层转元
（I18N-030），时间用 UTC、只在展示层转本地。**业务层永远只有一个口径，
歧义留在最外面那一层。**

它也决定了「用户时区」这个字段**不做**：浏览器已经知道用户在哪个时区，
多存一份就多一个会过期、会不一致的事实。真要做（比如发邮件提醒需要在
服务端渲染本地时间），那时再加，而不是现在先加一个没人读的字段。

## 2. TZ-060 出去的时间一律带 `Z`

新增 `app/core/timefmt.py::iso(dt)`：朴素值视为 UTC 并补 `Z`，
带时区的先换算到 UTC 再补 `Z`，`None` 原样返回 `None`。
74 处 `.isoformat()` 全部改用它。

### TZ-061 两道闸门，一道管源码一道管出口

**源码闸门**：`app/modules/**` 里不许再出现裸的 `.isoformat()`。
这条能挡住新写的代码。

**出口闸门**（更重要）：跑一遍真实业务流程，把**若干真实响应**递归走一遍，
凡是长得像 ISO 日期时间的字符串，必须带 `Z` 或 `±HH:MM`。

为什么两道都要：源码闸门挡不住**没经过 `iso()` 的路径**——FastAPI 会把
字典里的裸 `datetime` 自己序列化掉，那里没有 `.isoformat()` 可扫。
出口闸门看的是用户真正收到的东西，它不关心中间是怎么生成的。

这是 V72 那条规矩的延续：**扫描器要么看最终产物，要么自己先会红。**

## 3. TZ-062 进来的时间换算而不是截断

新增 `UtcDatetime`（带校验器的 `Annotated[datetime, ...]`）：

- 带偏移 → **换算到 UTC** 后去掉 tzinfo（与 `utcnow()` 同一口径）
- 朴素值 → 视为 UTC（并在接口文档里说明）

用在全部用户提交的时间字段：任务截止时间（发布与编辑两处）、
资质证件有效期。

「朴素值视为 UTC」是个明确的选择：另一种做法是**拒收**朴素值，
逼客户端必须带偏移。拒收更严格，但会把所有既有集成方（包括开放 API 的
第三方）一次性打断，而他们发的朴素值**多半就是 UTC**（我们自己的文档
一直这么写）。换算比拒收温和，且不会把已经对的用法判成错。

## 4. TZ-063 客户端只用一个入口解析

`packages/core/src/time.ts`：

- `parseServerTime(s)`：没有偏移的字符串按 **UTC** 解析（防御既有数据），
  有偏移的照常
- `formatDateTime(s, locale?)` / `formatDate(s, locale?)`：按浏览器时区渲染
- 两处 `+ 'Z'` 的手工补丁删掉，改调这里

**客户端闸门**：`web/` 与 `app/` 的源码里不许出现带参数的 `new Date(...)`
（`new Date()` 取当前时间可以）。理由就是这一批的病历——一个能直接
`new Date(服务端字符串)` 的代码库，迟早会有人这么写，然后错 8 小时。

## 5. TZ-064 顺带补上：网页上根本没有「截止时间」

查这一批时发现的：服务端有截止时间校验、有到期下架 job、有临期提醒，
而 **`Publish` 页面上没有任何地方能填截止时间**。
也就是说线上所有任务的 `deadline` 都是空的，那个 job 从来没有活可干。

补一个输入框，并且**发出去的是带偏移的 ISO**（`toISOString()`），
这样上面两半的修复在真实路径上闭合。

## 6. 验收点

| 编号 | 验收点 |
|---|---|
| TZ-060 | 真实响应里的每个 ISO 日期时间都带 `Z` 或 `±HH:MM` |
| TZ-061 | `app/modules/**` 里没有裸 `.isoformat()`；扫描器扫不到时自己先红 |
| TZ-062 | `+08:00` 的 10:00 存成 UTC 02:00，不是 10:00 |
| TZ-062 | 东八区/夏威夷用户各自发「2 小时后到期」都能成功，且落库是同一时刻 |
| TZ-063 | `parseServerTime` 对带 Z 与不带 Z 的字符串给出同一时刻 |
| TZ-063 | `web/`、`app/` 源码里没有带参数的 `new Date(...)` |
| TZ-064 | 网页能设置截止时间，且发出的是带偏移的 ISO |

## 7. 这一批没做的

- **TZ-065**：不存用户时区（见第 1 节的判断）。服务端渲染的邮件/短信里
  如果要出现本地时间，那时才需要这个字段。
- **TZ-066**：夏令时。按 UTC 存、展示层用 `Intl` 渲染，DST 天然正确；
  但**跨 DST 的「每周同一时间」类重复日程**需要存时区名而不是偏移——
  平台目前没有重复日程。
- **TZ-067**：历史数据不回填。既有行本来就是 UTC，加 `Z` 只是把真相说出来，
  不需要迁移。
- **TZ-068**：导出的 CSV/PDF 里的时间仍是 UTC 字面量，没有标注时区名。
