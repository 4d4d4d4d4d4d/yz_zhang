# 38 被诉方真的收得到、也真的开得了口（DSPR）

> 补 36 号 spec 自己留下的两条缺口：DSPC-050（App 侧没有答辩界面）与
> DSPC-052（答辩期届满前没有提醒）。

## 0. 为什么这两条要一起补

V61 修好了「被诉方在客户端上是哑的」——但只修了 Web。

这留下一个很难看的分布：**线下服务的执行方主要在 App 上**。
`app/App.tsx` 的任务详情里，纠纷相关的按钮只有一个：

```tsx
{actions.includes('open_dispute') && (
  <Button title="发起纠纷（冻结资金）" color="#dc2626"
          onPress={() => act(() => client.openDispute(task.id, '双方对交付结果有分歧，申请平台介入'))} />
)}
```

能开，不能答。也就是说 V61 之后，**最可能坐在被告席上的那一群人，
恰恰是唯一仍然开不了口的那一群人**。这个分布比原来「所有人都开不了口」
更糟，因为它看起来已经修好了。

而 DSPC-052 是另一半：开得了口不等于知道要开口。
现在只有开案时一条通知，答辩期 48 小时静默过去，就变成缺席裁决。
**一个只在开始时响一次的闹钟，和没有闹钟差别不大。**

两条合起来才构成「被诉方真的有机会陈述」。分开做，任何一条单独完成
都只是看起来完成。

## 1. 设计判断

**判断一：App 不重画一套，复用同一批 SDK 方法与同一组服务端事实。**
V61 已经把 `response_deadline` / `respondent_id` / `respondent_spoke` /
`appealable` 放进了 `_dump()`，理由就是「客户端算不出来的事实由服务端给」。
App 直接用这些字段，不自己算 48 小时、不自己判断能不能申诉——
否则就是同一条规则的第三份实现。

**判断二：提醒必须是幂等的，且只提醒真正没说话的人。**
已经答辩过的人不该再被催；催过一次的不该反复催。
所以需要一个持久化的标记（`response_reminded`），而不是靠「离截止还有几小时」
这种会在每次 job 运行时反复成立的条件——那会变成每小时一条骚扰。

**判断三：提醒的时机由答辩期长度按比例算，不写死。**
`DISPUTE_RESPONSE_HOURS` 是可配置的。写死「截止前 12 小时」在答辩期被
调成 6 小时的部署里就永远不会触发。按 **1/4 答辩期**（默认 48h → 提前 12h）
计算，改配置时提醒自动跟着走。这是 DSPC-012 那个硬编码 `48` 的同类错误，
不能再犯一次。

**判断四：提醒同样 `force=True`。**
理由和 DSPC-013 一样：允许用一个通知开关放弃自己的陈述权，
是把公平交给了默认设置。

## 2. 条目

### App 侧（DSPR-01x）

- **DSPR-010** App 任务详情在存在纠纷时渲染纠纷区块：状态、事由、
  双方陈述时间线、答辩输入框、和解提案与接受、结案后的申诉入口。
- **DSPR-011** 被诉方尚未答辩且未结案时，显著提示「你尚未答辩，
  逾期平台可仅凭对方陈述作出处理决定」，并显示剩余时间。
- **DSPR-012** 纠纷区块通过 `disputeByTask(taskId)` 进入——App 和 Web 一样，
  被诉方只知道任务 id。
- **DSPR-013** 结案后答辩输入框消失（服务端本来就会 409，
  但不该让人在手机上打完一段话才被拒）。

### 提醒 job（DSPR-02x）

- **DSPR-020** 新 job `POST /disputes/jobs/remind-response`，
  周期 1 小时，锁名 `remind_response`，登记进 `app/core/jobs.py`
  （JOB-001 的唯一事实来源）。
- **DSPR-021** 触发条件：`status == "open"` **且** 被诉方没有任何陈述
  **且** 距答辩截止不足 `DISPUTE_RESPONSE_HOURS / 4` **且** 尚未提醒过。
- **DSPR-022** `Dispute.response_reminded` 布尔列保证幂等（迁移）。
- **DSPR-023** 提醒文案给出剩余小时数与可执行动作，`force=True` 必达。
- **DSPR-024** 已答辩的被诉方**不会**被提醒；已结案的纠纷不会被提醒。

### 不变量

- **DSPR-030** job 连跑两次，只产生一条提醒。
- **DSPR-031** 新 job 必须同时出现在调度表、`/jobz` 与真实路由里
  ——这条由 V57 的 JOB-002 双向一致测试自动覆盖，不需要新写断言。

## 3. 已知缺口

- **DSPR-040 提醒仍只走站内通知。** 没有短信/推送通道，用户不打开 App
  仍然收不到。`SmsProvider` 已在册，接上是配置工作，但「哪些通知值得花钱
  发短信」是运营决策，不在本批范围。
- **DSPR-041 App 侧仍无附件上传。** 与 DSPC-051 同源，Web 侧也只读。
- **DSPR-042 App 仍未被真正 typecheck。** `app/` 不在 npm workspaces 里、
  没有 `tsconfig.json`，CI 也不碰它——**这正是本批这个缺口能一直躺着的原因**。
  本批加的是字面量闸门（DSPR-010~013 那四条测试），可靠但不是类型检查。
  真正补上需要把 `app` 纳入 workspaces 并在 CI 装 expo/react-native，
  那会改变整个仓库的 `npm install` 与 `npm test` 行为，我在本环境里无法
  完整验证——**与其推一条自己没跑过的 CI 步骤，不如把它写在这里。**
