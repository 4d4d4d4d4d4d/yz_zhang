
# 334 资质别名在后台维护（四眼）

> 状态：本批实现（V361）。编号 SCN-213。
> 来源：332 号 spec「没做的」：「运营在后台维护资质别名（现在写在代码里、配测试）」；BACKLOG V361（第三十六轮排期，分数 18）。
> 只增不减：代码里写死的别名（「电工」=「低压电工作业操作证」）照旧生效、后台收不回；`cert_aliases(name)` 不给数据库时只看写死的几组，老调用行为不变。

## 0. 要解决的问题

V359 把同一张证的两个叫法写在代码里。可叫法是不断冒出来的：「焊工证」与「熔化焊接与热切割作业操作证」、证上的新旧写法……每出一个就要发版。反过来，别名配错等于放松准入：把两张不同的证当成一张，没证的人就能接受限类目的单。所以要能在后台配，而且要四眼。

## 1. 业界怎么做

涉及准入的配置变更（权限、白名单、资质映射）通常走「提出 + 另一人复核」的四眼流程，留痕可查，收回即时生效。本批没有另找外部来源；做法与本平台已有的四眼（V176 结算、V342 临时提权）一致。

## 2. 规则

- **提出**：运营提出「甲 = 乙」，写理由（至少 4 个字）。两个名字去空白、按字典序存（顺序不同算同一对）。
  - 两个名字一样：400 `cert_alias_same`。
  - 已经是同一张证（含代码里写死的、已生效的、经由别的别名连起来的）：409 `cert_alias_exists`。
  - 同一对已有在等确认的：409 `cert_alias_pending`。
- **确认**：另一位运营确认后才生效。自己不能确认自己提出的（403 `cert_alias_self`）；处理过的不能再确认（409 `cert_alias_decided`）。
- **收回**：任何一位运营都可以收回待确认或已生效的一对，收回立刻失效。收紧准入一个人就够。
- **连通块**：甲 = 乙、乙 = 丙，则甲 = 丙（代码里写死的与后台配的一起算）。
- **生效范围**：准入、重复申请判断、拦下时的「持另一个名字的也可以」都认后台配好的别名。
- **审计**：提出、确认、收回都进审计。

## 3. 数据 / 接口

- 新表 `cert_aliases`，迁移 c1d220260086，SQLite 与 Postgres 都验过。
- 接口（都只给运营，已登记进角色表与后台入口表）：
  - `GET /admin/cert-aliases`：返回 `{builtin, items}`
  - `POST /admin/cert-aliases`：请求体 `{a, b, reason}`
  - `POST /admin/cert-aliases/{id}/approve`
  - `POST /admin/cert-aliases/{id}/revoke`
- 共享 SDK：
  - 类型：`CertAliasItem`、`CertAliasList`
  - 方法：`certAliases` / `proposeCertAlias` / `approveCertAlias` / `revokeCertAlias`
  - 五个新错误码进 i18n。

## 4. 两端

- **Web 后台「城市与类目」**：类目表下面多「资质别名」。
  - 列出系统内置的几组和后台配的每一对（待另一位确认 / 已生效 / 已收回）。
  - 自己提出的看不到「确认」，别人提出的可以确认。
  - 都能收回。
  - 两个名字和理由写全了才能点「提出」。
- **App**：没有管理后台，不涉及。

## 5. 隐私、授权与边界

- 只给运营角色；四眼；全程审计。
- 收回不影响已经成交的单（准入只在报名、接单时判断）。
