
# 94 经验按子类生长，而不是按样本堆积（KB-070~KB-079）

> 状态：**设计，未实现**。本篇是可实现规格，不表示已交付。
> 依赖：06 号（知识库，KB-010~013）、83 号（经验数据清洗）、
> 88 号（经验资产是五个核心对象之一）
> 承接用户 2026-10-10 的设计意见：
> 「知识图谱体系不可能把每个样本都添加，需要类似聚类一样，
> 把额外信息或者经验加到具体某个子类里，或者如果没有新建子类」

## 0. 现状（量过的，不是读文档得来的）

起一个实例、跑完一笔真实闭环（`scripts/smoke.py`），然后问知识库：

```
GET /api/v1/knowledge/cards
[{"id":1,"category":"跑腿","city":"杭州","title":"跑腿·杭州",
  "price_actual_cents":20000,"duration_days":0,"outcome":"completed"}]

GET /api/v1/knowledge/search?q=跑腿&kind=card
{"results":[{"id":1,"score":1.0,"text":"跑腿 杭州 跑腿·杭州"}],
 "semantic":false,"degraded":true,"model":"local-bow-256"}
```

**积累是真的**：一笔闭环 → 一张卡。问题在结构：

1. **一条闭环 = 一行**。`knowledge_cards` 是平铺表，检索是对**全部样本**
   算余弦。样本从 1 涨到 10 万时，这条路不是变慢，是**变没有意义**：
   同城同类目的 3000 条「跑腿」各自是一个独立向量，Top-5 返回的是
   其中最像的五条，而用户想知道的是**这一类通常怎么做、通常多少钱**。
2. **KB-012「类目知识图谱（轻量）」是 P2，没有实现**。现有的「类目」
   是发任务时从固定表里选的那个字符串（`task/service.py` 里的类目表），
   它是**运营预设的 20 来个大类**，不随经验生长。
3. 所以今天的知识库只有两层：**大类（人定的）** 与 **样本（机器攒的）**，
   中间那层——真正能被复用的那层——是空的。

## 1. 要加的那一层：子类

> 子类是**知识图谱的节点**；样本只是挂在子类下面的证据。

一个子类回答的是「这一类活儿是什么样的」：

| 字段 | 含义 | 为什么必须有 |
|---|---|---|
| `category` | 所属大类（沿用现有类目表） | 子类不跨大类合并，避免「搬家」与「法律咨询」因为措辞相近被并到一起 |
| `label` | 子类名（如「跑腿·代取快递·同城当日」） | 要给人看，也要能被 Agent 引用 |
| `centroid` | 质心向量 + `embedding_model` | 归并判定的依据；换模型后旧质心不可比（KB-011 已立的规矩） |
| `sample_count` | 样本数 | **样本量必须跟着一起给**，否则「参考价」会变成一个无从判断的数字（KB 的 D 节已立） |
| `price_p50` / `price_p90` | 价格分布 | 单点均价会被一笔异常成交带偏 |
| `duration_p50` / `duration_p90` | 工期分布 | 同上 |
| `outcome_mix` | 完成 / 纠纷 / 取消 的占比 | **失败率是子类的属性**，不是可以被平均掉的噪音 |
| `consensus_steps` | 该子类的共识流程（步骤序列 + 出现频率） | 这是「分解模板」的真正来源（AI-DEC-012），而不是取最近一条的快照 |
| `dissent` | 分歧记录：与共识流程显著不同、但成功闭环的做法 | **把分歧平均掉等于把知识抹平**，见第 4 节 |
| `freshness` | 最近样本时间、近 N 月样本占比 | KB-062（经验没有时效）这条欠账在子类上才有地方落 |
| `status` | `active` / `merged_into` / `retired` | 子类会分裂与合并，历史引用不能悬空 |

样本行（`knowledge_cards`）保留不动，只多一列 `cluster_id`：
**样本是证据，子类是结论，结论必须能回溯到证据。**

## 2. 一条新经验进来时发生什么（KB-070）

```
闭环任务 → 经验卡（已有，83 号 spec 的清洗管线）
         → 向量化（已有，KB-011）
         → 找同大类下最近的子类
         → sim ≥ τ_merge ?  是 → 并入该子类，增量更新统计
                            否 → sim ≥ τ_near ? 是 → 进「待定区」
                                                否 → 新建子类
```

三条判定，对应三种**不同的错**，所以必须是三条而不是一条阈值：

- **并入（`sim ≥ τ_merge`）**：这条活儿和那个子类是一回事。
  增量更新质心、样本数与分布——**不重算全表**。
- **新建（`sim < τ_near`）**：平台第一次见到这种活儿。新建子类，
  `sample_count = 1`，并且**明确标注「单样本子类」**：
  一个样本的 P50 不是统计量，是那一个数字。
- **待定（τ_near ≤ sim < τ_merge）**：像又不够像。
  **这一段刻意不让机器自己定**——它既可能是子类该分裂的信号，
  也可能是子类该放宽的信号，而这两个方向的处置完全相反。
  待定区进运营队列（沿用 V103 的 `QUEUE-010` 声明表与催办机制），
  积压到阈值就催办。

> **为什么不做成「永远自动归并」**：自动归并的失败模式是**子类漂移**——
> 每次都「差一点点」地并进去，二十次之后这个子类已经不是它的名字说的
> 那个东西了，而中间没有任何一刻会报错。这与 V118 那条教训同形：
> **没有约束的地方，错误不报警，只把数据悄悄弄错。**

## 3. 阈值怎么定，以及它不许是一个写死的数字（KB-071）

τ 不是常数，按**大类分别标定**：法律咨询的措辞差异远小于工业共创。

标定方式必须可复现：
1. 取该大类下已有样本，**人工标注若干对**「是不是一回事」（运营动作）;
2. 在标注集上扫 τ，取使「误并」与「误分」代价之和最小的值；
3. **把标定时的样本量、日期、模型名一起存**——换 embedding 模型后
   τ 必须重标，否则就是拿新模型的相似度去套旧模型标出来的阈值。

闸门：`knowledge_clusters` 的每个大类都必须有一条 τ 记录，
且记录里的 `embedding_model` 必须等于当前 provider 的模型名，
否则归并直接拒绝并报警——**宁可不归并，不要用错的阈值归并**。

缺省态要说清：默认 embedding 是词袋哈希（`semantic=false`），
**在这种模式下不做自动新建子类**，只归并进运营已确认的子类、
其余全部进待定区。理由见 06 号 spec 自己写下的那句话：
一个悄悄退化成关键词的「语义检索」比没有更糟。用它去自动生长知识图谱，
得到的是一张按字面相似度长出来的图，而**没有人会发现**。

## 4. 分歧不许被平均掉（KB-072）

这是本篇最重要的一条设计约束。

子类统计天然倾向于「把多数做法当成唯一做法」。但平台要积累的恰恰包含：

- **失败与返工**（KB-004 已要求入库）：某种做法成功率低，必须能查到；
- **例外条件**：同一类活儿在「老小区没电梯」「甲方要当天出图」这类条件下
  流程完全不同；
- **过期条件**：去年的做法今年不合规了。

所以子类里 `consensus_steps` 之外必须有 `dissent`：
与共识显著不同、**但确实闭环成功**的做法，按出现次数与条件标签保留。
对外展示时，共识与分歧**一起给**，并各自带样本量。

**不给单点确定值**是 06 号 spec 的 D 节已立的规矩，这里把它落到结构上：
一个只能返回「通常这么做」的知识库，会在例外情形下给出自信的错答案。

## 5. 对外怎么用（KB-073~075）

| 编号 | 接口 | 用途 | 替换掉今天的什么 |
|---|---|---|---|
| KB-073 | `GET /knowledge/clusters?category=&q=` | 子类检索：返回子类及其统计与样本量 | 今天对全部样本算余弦的 `/knowledge/search` |
| KB-074 | `GET /knowledge/clusters/{id}` | 子类详情：共识流程、分歧、价格/工期分布、证据样本（脱敏） | 今天的 `/knowledge/cards` 平铺列表 |
| KB-075 | `GET /knowledge/price-reference`（改造） | 按**子类**而不是「类目+城市」取分布 | 今天命中不到就返回「暂无同类闭环数据」 |

`/knowledge/cards` 与 `/knowledge/search` **保留**：样本层仍需可查
（取证、运营核对、以及"结论回溯到证据"）。新接口不是替换，是补上中间层。

## 6. 商业上线要求（这一条线上必须先成立的）

| 要求 | 为什么是上线门槛 | 判据 |
|---|---|---|
| **复用授权分级** | KB-002 要求「引用具体案例需双方授权」。子类统计是聚合信息，个案证据不是。**聚合可用 ≠ 个案可引用** | 子类详情里的证据样本必须逐条检查授权位；未授权的只计入统计、不展示 |
| **去标识在入子类之前** | 83 号 spec 的清洗管线必须跑在聚类之前，否则质心里带着姓名与地址 | 聚类输入只接受已清洗字段；原文不进向量 |
| **第三方姓名** | KB-065 已记：核验人打的字里的第三方姓名去不掉 | 未解决前，自由文本**不进**聚类输入 |
| **样本量门槛** | 单样本子类的"参考价"会被用户当成行情 | `sample_count < 5` 的子类对外必须标注「样本过少，仅供参考」，且不进 `price-reference` |
| **刷单不入库** | KB 的 D 节已要求；聚类会放大污染（一次刷单进了质心就一直在里面） | 风控标记的任务不进聚类；已进的要能按 task_id 撤回并重算该子类 |
| **可解释** | 用户问「为什么说这类活儿两千块」，要答得出来 | 子类统计必须能列出参与计算的样本数与时间范围 |

## 7. 闸门（实现这一批时必须同时立的）

| 闸门 | 内容 |
|---|---|
| KB-070a | 并入后子类统计是**增量**算出来的，与全表重算结果一致（随机样本对比） |
| KB-070b | 大类不同的样本**永不**并入同一子类 |
| KB-071a | 当前 embedding 模型与 τ 记录的模型不一致时，归并被拒绝并报警 |
| KB-071b | `semantic=false` 时不自动新建子类（退化模式不生长知识图谱） |
| KB-072a | 成功闭环但偏离共识的做法必须出现在 `dissent` 里，不被平均掉 |
| KB-072b | 子类的 `outcome_mix` 包含纠纷与取消，不只统计 completed |
| KB-073a | 对外的任何价格/工期结论都带 `sample_count` 与时间范围 |
| KB-076 | 风控标记任务可按 task_id 从子类里撤回，撤回后统计重算 |

红验要求：每一条都要能被「改回错的做法」弄红——
尤其 KB-071b，**退化模式下还自动建子类**必须红。

## 8. 这一篇没做的

- **不做跨大类的自动合并**：大类表是运营维护的，合并大类是产品决定。
- **不做层级子类（子类的子类）**：先把一层做对。多层的归并判定要先回答
  「一个样本该进父类还是子类」，而这个问题在样本量小的时候没有好答案。
- **不做在线增量聚类的并发安全**：第一版把归并放在闭环后的 job 里**串行**跑
  （沿用 32 号调度表）。并发归并会出现两个请求同时给同一子类更新质心，
  而那正是 V112/V118 那类静默错误的温床——先串行，有量了再谈。
- **不自己训练 embedding 模型**：接哪家是供应商决定（见 GO-LIVE 红线）。
