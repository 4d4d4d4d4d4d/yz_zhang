第 5、6 两条——正是用户这次特别点出的「AI 协助不懂领域解决」与
「平台能够累积成功经验」——**后端是真的，前端一个入口都没有**。
起实例跑一笔闭环确认过不是空壳：

```
跑完 smoke.py 之后
GET /knowledge/cards
[{"id":1,"category":"跑腿","city":"杭州","price_actual_cents":20000,
  "duration_days":0,"outcome":"completed","has_decomposition":false}]

POST /legal/ask {"question":"对方验收后不付钱怎么办"}
{"answer":"平台任务资金采用先托管后放款机制…可依合同争议解决条款提请约定的
 仲裁机构，或向有管辖权的法院起诉，平台可提供证据包导出。",
 "disclaimer":"…不构成法律意见…","refused":false}
```

**积累是真的、问答是真的，而两件事都没有人读得到。**
用户自己写的 `PRODUCT-DIRECTION.md` 第 53 行画的那条循环
（`合作结果 → 复盘 → 去标识 → 验证 → 案例检索 → 下一次使用 → 修正`）
断在最后一个箭头上。

## 1. 服务端真正缺的那一件：三种结局只有一个布尔位

`/legal/ask` 有**三条**出口，含义完全不同：

| 情形 | 回答 | 正确的下一步 |
|---|---|---|
| 命中知识库 | 真实答案 | 读完就完了 |
| 超出知识库 | 「建议通过『找律师』发布法律咨询任务」 | 在平台上发一单 |
| 命中人身安全/刑事关键词 | 「请立即拨打 110 报警或联系专业机构」 | **立刻走外部紧急渠道** |

而改造前三者只由 `refused: bool` 区分——也就是说后两种在客户端眼里
**一模一样**。界面只能把它们渲染成同一段话，于是：

**一条安全升级通道会被显示成「机器人没答上来」。**

这不是文案问题。第二种的正确反应是在平台上发一单生意，
第三种的正确反应是放下手机打电话——把两者画成同一个样子，
等于让界面在最要紧的那一次给出错的暗示。

所以补两个字段：

- `refused_reason`: `'' | 'high_risk' | 'out_of_scope'` —— 判别位。
- `remedy`: 机器可读的补救，`{action, category, label}` 或 `null`。

**`high_risk` 那一支的 `remedy` 刻意是 `null`**：这里唯一正确的去处是外部
紧急渠道，在它旁边摆一个「发布咨询任务」的按钮，是把紧急情况降级成一笔生意。

`out_of_scope` 的 `category` **从类目表里取**（`SEED_CATEGORIES` 里
`required_cert == '律师'` 的那一条），不在任何一端写死字符串：
写死的那个会在类目改名时静默地把人送到一个空下拉框前面。
这是「第二份实现必然抄漏」的又一次应用。

## 2. 客户端：两端各补一页「不懂就问」

| 闸门 | 内容 |
|---|---|
| LAW-051 | 三种结局必须**不读文案**就能分辨；各自的去处不同 |
| LAW-051b | `high_risk` 不给平台内补救——**即使服务端错给了 `remedy` 也不画** |
| LAW-051c | `out_of_scope` 的补救要真的把人送到发布页，**并带上服务端给的类目** |
| LAW-051d | `disclaimer` 三种结局都原样显示（平台给的是一般性法律信息，不是法律意见） |
| KB-023a | 检索退化（`semantic: false` / `degraded: true`）必须说出来 |
| KB-023b | 经验卡必须显示 `outcome`——**失败案例同样入库**（KB-004） |
| KB-023c | 空结果说清「没有闭环就没有经验」，不说成出错 |
| CLI-079 | `legalAsk` 进 `MUST_BE_REACHABLE`（判定标准第一条：人身风险） |

两条值得单独说明：

**KB-023a 退化提示。** `/knowledge/search` 的 `semantic` / `degraded` 是
服务端**有意暴露**的，它的 docstring 写着「一个悄悄退化成关键词的
『语义检索』比没有更糟——你不会去修它」。客户端把这两个字段藏起来，
等于把服务端那份诚实在最后一步扔掉。所以退化时界面要说：
换个说法可能就搜不到同一批经验。

**KB-023b 结果好坏。** KB-004 要求失败与纠纷案例同样入库。
于是经验卡列表里混着 `completed` 与 `disputed`——
不显示这一列的话，一笔有纠纷的高价成交会被当成行情，
**参考价系统性偏高**。

`legalAsk` 为什么够得上 `MUST_BE_REACHABLE`：那张表的判定标准是
「按不到这一条，用户会面临人身风险、账号被别人继续用，
或者一笔钱/一个权利落空」。平台已经把人身安全那条识别做出来了，
而没有任何端能问——而问「这事我不懂该怎么办」的那一刻，
人很少坐在电脑前。

## 3. 顺手修掉的一个错类型，和它暴露的闸门缺口

要用 `knowledgeCards` 时一读 SDK，发现声明是**错的**：

```ts
// 改造前
Array<{ id: number; category: string; title: string; body: string }>
// 服务端真给的
{id, category, city, title, price_actual_cents, duration_days, outcome, has_decomposition}
```

`body` 服务端**从来没给过**；而真给的五个字段 SDK 一个都没声明——
想按价格或成败筛经验卡的人，**在类型里看不见这些字段存在**。

这正是 V85 建响应形状闸门时要拦的那一类（它的 docstring 原话：
「类型对不上，却没有任何东西会红」）。为什么这次还是没红：

```
this.request< 调用点            281 个
  响应类型是内联对象字面量        180 个   ← 结构上进不了响应侧闸门
  响应类型是具名/原始类型         101 个
_assert_shape 真的比过的具名接口   26 个
响应里用到的具名接口              58 个（其中 37 个从没被比过）
```

**响应侧闸门覆盖 281 个调用点里的 26 个，而没有任何记账说这件事**——
请求侧有 `DYNAMIC_BODY` 表逐条写明「这个比不了，理由是什么」，
响应侧什么都没有。

本批补的是需要的那一截：`_assert_inline_shape()` 能对内联响应类型做
与具名接口同一套三方向检查（声明了没给的、给了没声明的、类型对不上），
并对 `knowledgeCards` / `knowledgeSearch` / `legalAsk` 三个端点真的比了一遍。
整条线的扫除记台账 `CLI-083`，另立一批。

过程中还修了解析器的一个盲点：内联类型里**带注释是正当写法**，
而带注释后 `_inline_fields` 会解析失败并返回 `None`——于是那个声明
**悄悄退出了闸门范围**，不报错，只是不再检查。先剥注释再解析。

## 4. 这一批没做的

- **`legalDocument` 仍无客户端**：文书生成（催告函/和解协议）是**按任务**的动作，
  该在任务或纠纷详情里，不在一个通用问答页。放这里会让用户在一个问法律常识的
  地方被要求选一个 task_id。仍记 `LAW-050`。
- **全局搜索与联想词仍无客户端**：`search` / `searchSuggest` / `trendingTerms`
  三端零调用，台账 `SEARCH-050` 保留。那是「发现」页的事，不是问答页的事。
- **经验只有样本层可读**：这一页读的是 `knowledge_cards` 平铺表与对全部样本的
  余弦检索。子类层（94 号 spec）与可复用单元（95 号 spec）都还没实现，
  所以现在能回答「平台见过这些活儿」，还回答不了「这一类通常怎么做、多少钱」。
- **响应形状闸门的整条扫除**：见第 3 节，记 `CLI-083`。
- **任务拆解仍只在 web**：`APP-077` 保留。
