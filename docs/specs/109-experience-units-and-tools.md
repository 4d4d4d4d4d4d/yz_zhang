
# 109 经验变成能被调用的单元与工具：实现（KB-080~089 / AGT-080~083）

> 状态：本批实现（V135）。设计见 [95 号](95-experience-as-a-callable-tool.md)，本篇记实现、偏差与验证。
> 承接用户 2026-10-10：「攒经验完全可以作为检索数据库或者 skilltool 工具给后续复用」。

## 0. 改之前

V134 让经验长出了子类（这一类通常怎么做、通常多少钱），但**复用**还停在 V86 的形态：
经验以文本拼进分解提示词，复用的唯一方式是模型读到它；平台不知道哪条经验被用了，
也不知道用了之后那一单做没做成。**单向、不计量、不可验证。**

## 1. 数据

| 表 / 字段 | 内容 |
|---|---|
| `reusable_units` | 从子类蒸馏出的单元：类型、版本、内容、**适用条件（含必填的排除条件）**、来源样本、验证状态、使用范围、**两个独立授权位**（复用 / 训练）、工具权限清单、预估成本、状态（active / needs_review / retired） |
| `unit_invocations` | 每次使用：单元 + **版本** + 场景（decompose / agent_tool）+ 调用方 + 任务 + 输入摘要 + 产出 + 成本与耗时 + 结果（pending / closed / reworked / failed）+ 受益贡献者 + 是否草稿 / 已丢弃 / 来源已撤回 |
| `user_consents` 新 scope | `experience_reuse`、`experience_train`：**选择加入**，各自独立，可撤回 |

迁移 `c1d220260009`，SQLite 与 Postgres 上往返（upgrade → downgrade → upgrade）与 `alembic check` 都干净。

## 2. 蒸馏（KB-080）

`POST /admin/knowledge/clusters/{id}/units`（运营，进审计）。四种类型，风险递增：

| 类型 | 内容来自子类的什么 | 拒绝条件 |
|---|---|---|
| `price_hint` | P50 / P90 / 工期中位 / 样本量 / 截至何时 | 样本过少（`unit_too_few_samples`）：单样本的中位数不是统计量 |
| `checklist` | 共识步骤 → 「确认已完成：X」 | 没有共识流程（`unit_no_consensus`） |
| `procedure` | 共识步骤（或运营给的步骤）→ 每步带交付物、验收标准、预算比例、依赖 | 同上；步骤没名字（`unit_step_title_required`） |
| `skill_tool` | 工具名 + 验收清单；**权限清单由平台工具表给，不由运营填** | 平台没有这个工具（`unit_tool_unknown`） |

注册门槛（KB-080a，缺一不得注册）：

- **排除条件必填**（`unit_exclusions_required`）：只说「适用于什么」的单元，会在不适用的场合被照样调用。
- **两个授权位都要明说**：请求体里缺任何一个直接 422，没有默认值。
- **来源必须可回溯且被同意**：只有**双方**都同意了 `experience_reuse` 的那一单才能作来源；
  一单都没有就拒（`unit_no_consented_source`）。

## 3. 用（KB-083 / KB-086 / KB-087）

- `GET /knowledge/units?category=&kind=&cluster_id=&q=`：**只列在用、且有复用授权的**。训练授权替代不了复用授权。
- `GET /knowledge/units/{id}`：内容、权限清单、预估成本、**贡献者**（只列同意了复用的人）。没有复用授权的单元 404——读内容就是在复用。
- **分解（AI-DEC-012）真的在用它**：逐层拆解第一层先找适用的 `procedure` 单元（已验证的优先），
  拆出来的步骤带交付物与验收标准，`source` 记成 `experience_unit:{id}@v{version}`，**同时记一次使用**。
  找不到才退回原来的模板 / 模型。

## 4. 结果回流（KB-084）

使用记录在任务结项时被结算：

- 用了单元的任务**完成** → `closed`；完成但途中有子步骤被驳回过 → `reworked`；**取消** → `failed`。
- 单元的 `validation` 随之更新；使用次数达到 `KB_UNIT_REVIEW_MIN_USES`（默认 4）且「返工 + 失败」过半，
  单元**自己转待复核**，不再被拿去拆解；少于两成坏结果则标 `validated`。
- 运营复核后重新启用：**版本 +1、验证从头算**——复核前的结果属于上一版。

这一条是 95 号说的「最容易被省掉、也最不能省」的那条：没有它，每次调用都被记成一次成功复用。

## 5. 经验工具（AGT-080~083 / KB-088）

`POST /agent/tools/{unit_id}/invoke`，按顺序拒绝：

1. 不是 `skill_tool`，或单元不在用 → `tool_unavailable`；
2. **退化模式**（缺省词袋哈希，不是语义模型）→ `tool_degraded`：只读单元照常可用，可执行的不行；
3. 预估成本超过 `KB_TOOL_MAX_COST_CENTS` → `tool_over_budget`（不执行）；
4. 调用者不是这一单的发布方或执行方 → 403；
5. 类目、城市、预算不在单元的适用范围 → `tool_not_applicable`。

产出**只是草稿**：文本里与 `label` 里都写着「由经验单元 X（第 N 版）生成，未经人工确认」，排除条件跟着草稿走，
每次调用留痕（版本、场景、调用方、输入摘要、成本、耗时、受益贡献者）。
`POST /agent/tools/invocations/{id}/discard`：只有调用者本人能丢。

第一个内置工具：`acceptance_report_draft`（按验收清单给这一单起一份验收报告草稿，逐项待勾选）。
权限清单：读任务与单元清单、只写草稿、**不花钱、不发消息**。

**AGT-081 是扫出来的，不靠人自觉**：`knowledge/tools.py` 与 `units.py` 不得 import 钱包、合约、支付、财务、协作分账
任何一个模块（AST 闸门）。

## 6. 撤回要真的生效（KB-089）

撤回 `experience_reuse`（个人信息授权页上单列的一项，两端都有）时：

- 他参与过的任务的样本**退出子类**（`retracted`），受影响的子类**重算**；
- 用到这些样本的单元：样本移除、**转待复核**；
- 已生成的草稿**不追回**，但标 `source_revoked`；
- 从没同意过的人也能撤回（选择退出）：服务端记一条即时撤回的同意记录，效果相同。

撤回结果里的 `applied` 由服务端给，客户端原样显示。

## 9. 与 95 号的偏差

- **工具在任务详情里有一个按钮**。95 号写的是「由编排器与个人 Agent 页面调用，不做成用户可以随便点的按钮」。
  这两个调用方今天都还不存在（编排器调用是 `AGT-084`，个人 Agent 是 SPACE-026），而一个两端都够不到的工具等于没有。
  按钮的约束比 95 号担心的情形更紧：只对这一单的双方显示、只出草稿、不花钱不发消息、可丢弃、每次留痕。
- **验证只有线上结果，没有离线评测**：95 号的 `validation` 写的是「离线评测 + 线上结果对照」。离线评测集还不存在。
- **使用范围只开放「全平台」**：95 号的 `scope` 有 private / project / platform 三档，但单元表里没有归属对象
  （谁的、哪个项目的），前两档收下也执行不了——等于把私有单元公开。这一批对前两档直接拒（`unit_scope_invalid`），
  字段保留（`KB-093`）。
- **贡献者只到任务双方**：95 号的 KB-085 还列了核验人与写经验帖的人（`KB-090`）。
- **训练授权没有消费者**：`experience_train` 能同意、能撤回、在单元上有独立位，但平台没有训练管线（`KB-091`）。
  这是有意先立的：授权位要先于用途存在，而不是用途上线后再补一份同意。
