
# 103 另外那些没人核对的数字：前端测试计数与结构计数（DOC-011 / DOC-012）

> 依赖：85 号（DOC-010 后端计数闸门）、72 号台账（DOC-011 / DOC-012）、
> 54 号（job 调度表同源）、47 号（CI）

## 0. 起点

85 号 spec（V111）给后端测试计数立了闸门，把另外两类记进台账：

- **DOC-011 前端测试计数**：权威来源是 vitest / jest 的输出，后端回归里拿不到；
  用 AST 数 `it(` 是第二份实现，`it.each` 一来就漂——会误报的闸门会被人关掉。
- **DOC-012 表数、迁移条数、job 数**：变动频率低，先钉最常漂的那个。

## 1. 第一次跑就查出来的

| 位置 | 写着 | 真实 | 后果 |
|---|---|---|---|
| `GO-LIVE.md` 上线手册第 3 步 | `/jobz   # 18 个 job 在册` | 22 | **上线当天值班的人拿它对照**。对不上时，他只能猜是文档旧了还是 job 丢了 |
| `OPERATIONS.md` 定时任务单实例 | 全部 14 个 job 端点已接入 | 22 | 读者会以为有 8 个 job 没有单实例锁 |
| `OPERATIONS.md` 描述 CI 的那一句 | 后端 850 测试、前端 64 测试 | 1357 / SDK 56 + Web 138 | 后端那个数**从 V111 起一直在，DOC-010 的闸门看不见它** |

最后一行是闸门自己的盲区：DOC-010 认「N 个测试」「N 个后端测试」「后端 N tests」，
而这一句写的是「后端 850 测试」——没有「个」，也不是 tests。与 V113 那次
（「个**后端**测试」）同一类：**它不会报错，它只是什么都不查**。补了第三种写法，
扫描器自检里三种写法各放一个样本。

## 2. 前端计数（DOC-011）：比对放到拿得到权威输出的地方

85 号的理由是对的——后端回归里拿不到前端的真实计数，而自己数是第二份实现。
结论却不必是「不钉」：**拿不到的是后端回归，CI 的前端 job 自己就有。**

```
前端 job：  npm test -w packages/core  → counts/core.json   ┐
            npm test -w web            → counts/web.json    ├→ scripts.check_frontend_counts core web
App  job：  npm test (jest --json)     → counts/app.json    → scripts.check_frontend_counts app
```

- **不数任何东西**：vitest 的 json reporter 与 jest 的 `--json` 写的是同一组键
  （V129 实测），脚本只读 `numPassedTests` 与文档比。
- **「没比」不是「比过了一致」**：结果文件不存在、不像测试结果、或里面有失败，都判不一致。
- **只用标准库**：前端 job 不装服务端依赖，这一步不能逼它装。

### 2.1 「前端 N」不许出现在现状声明里

V111 写的是「前端 161 tests（core 56 + web 84 + App 21）」，OPERATIONS 写的是
「前端 64 测试」。**是哪几套相加？** CI 的前端 job 根本不跑 App。一个说不清
由什么组成的数没有办法核对，所以现状声明只许按套件写（Web / SDK / App）。

### 2.2 这一改动自己引入的风险，自己钉

按工作区分开跑（两个工作区写同一个 JSON 会互相覆盖），意味着**新加一个带测试的
工作区而忘了加进 CI，它的测试一条都不跑**——根上的 `npm test` 此前会自动带上它。
回归里有一条：根 `package.json` 的每个带 `test` 脚本的工作区，CI 的前端 job 里
都要有 `npm test -w <它>`。

### 2.3 回归里钉什么

比对本身在 CI 里，回归钉的是「它真的在那儿、真的会红、真的扫得到」：

| 闸门 | 内容 |
|---|---|
| DOC-011a | DELIVERY 顶上那行三套都认得出；「SDK 266 个方法」不被认成测试数 |
| DOC-011b | 现状声明里没有「前端 N」 |
| DOC-011c | 数字不对 → 红，脚本退出码 1 |
| DOC-011d | 数字对 → 绿，退出码 0 |
| DOC-011e | 没结果文件 / 有失败 / 不像测试结果 → 都不绿 |
| DOC-011f | 两个 job 里每一套都是「测试写 JSON → 之后比对」，比对行列着它，没有 `\|\| true` / `continue-on-error` |
| DOC-011g | 每个带测试的工作区都在 CI 里跑 |
| DOC-011h | 历史豁免表每一条都在文档里、**且真的挡掉了一处匹配**。V129 第一版的表里有两条多余的：一条引的是探针输出原文、而没有任何正则会匹配它；另一条的短语与文档原文差了一个词，根本不在文档里（被「已不在文档里」那条抓到）。一条什么都没挡的豁免会让人以为那里有东西 |

## 3. 结构计数（DOC-012）：回归里算得出来，直接比

| 类 | 文档写法 | 真实值从哪来 |
|---|---|---|
| 表 | 「N 张表」 | 用迁移在临时库里真的建一遍再数（不数模型——迁移是唯一保证建出全部表的路径，DEP-020） |
| 迁移 | 「N 条迁移」 | alembic 的 revision 链 |
| job | 「N 个定时任务 / job」 | `app/core/jobs.py` 的调度表（与 cron 同源，54 号） |

**快照文档整篇豁免，但豁免绑在证据上**：`SYSTEM-CHECK.md` 开头写着
「体检日期：2026-09-30，版本 0.99.0」，它的数字是那一天的实测——而它自己说
「半年后数字变了，重跑一遍就知道」。豁免的条件是那行日期还在；有人把它改成
「当前状态」页而删了日期，它就重新受检。

其余历史引用（DELIVERY / 追溯矩阵里 V109 那一批的实测、冒烟脚本「0 个 job 有记录」
那行输出原文）逐条进豁免表，理由写明。

## 4. 红验

十条：App job 去掉比对 / 比对后加 `|| true` / 比对漏了 web / 前端 job 不跑 web 工作区 /
拿不到结果当一致 / 有失败照样比 / 比对不比数字 / 去掉后端「N 测试」写法 /
体检报告删掉日期 / 结构扫描器正则写歪——每一条都红，恢复后全绿。
另用真实的 vitest / jest 输出跑了一遍脚本：一致时退出 0；把 DELIVERY 的 Web 改成 137
时退出 1，并指出是哪一处。

## 5. 这一批没做的

- **SDK 方法数、端点数**仍由各自的闸门钉（`test_sdk_method_triage` / 端点覆盖），
  不在这里重复。
- **索引数**不比：它随**数法**变。同一个库，SQLAlchemy 的 inspector 数出 176，
  `sqlite_master` 数出 202——差的 26 个是唯一约束背后的自动索引（V129 实测）。
  一个说不清怎么数的数不适合写进文档，
  而文档里唯一一处在快照里。
