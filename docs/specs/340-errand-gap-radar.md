
# 340 发单拦截的复核结果按类别进场景雷达

> 状态：本批实现（V367）。编号 SCN-221。
> 来源：336 号 spec「没做的」：「按拦截类别统计复核通过率，进场景雷达，用来校词表」；BACKLOG V367（第三十八轮排期，分数 12）。
> 只增不减：雷达原有五路信号不变，多一路 `errand_gap`；SDK 的 `RadarSignal.source` 多一个取值。

## 0. 要解决的问题

V363 起，被发单拦截挡下的人可以申请人工复核。复核结果散在一条条记录里：某一类拦截是不是拦得太宽、词表该不该收窄，运营没有依据，只能凭印象。

## 1. 业界怎么做

自动审核规则通常用申诉改判率来校准，改判多的规则要复查。本平台的场景雷达本来就是这个用处：把聚合信号摆在运营面前（V148、V167）。本批没有另找外部来源。

## 2. 规则

- **统计范围**：近 30 天（`RADAR_DAYS`）处理过（通过或维持）的复核，按拦截类别分组；在等的不算。
- **出现条件**：通过的来自至少 3 个不同的人（`K_ANON`，与雷达其他信号同一条隐私线），且通过的占处理过的一半以上（`ERRAND_GAP_RATE`）。
- **只出聚合**：类别名、处理条数、通过与维持条数、比例、不同的人数。不出原文、说明、发单人。
- **落到动作**：信号写明「到『发单复核』看通过的原文，考虑收窄这一类的词表」。

## 3. 数据 / 接口

- 不新增表与接口；`GET /admin/packs/radar` 多一路 `source: "errand_gap"`。
- 共享 SDK：`RadarSignal.source` 多 `errand_gap`。

## 4. 两端

- **Web 后台「服务包 → 场景雷达」**：这一路标「发单拦截可能误拦」。
- **App**：没有管理后台，不涉及。

## 5. 隐私、授权与边界

- 只给能看雷达的运营；只出类别与人数，一个人的复核永远不单独出现。
- 雷达只提示，不自动改词表：改词表要改代码并配测试（与 V321 起的做法一致）。
