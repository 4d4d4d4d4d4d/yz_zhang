
# 107 手机上的逐层拆解（APP-077）

> 状态：本批实现（V133）
> 依赖：96 号（设计）、106 号（V132 服务端与 web 实现）、72 号台账 APP-077

## 0. 起点

用户复述的六条愿景里，「AI 协助任务拆解」是唯一一条**手机上一个入口都没有**的：
`propose` / `confirmDecomposition` / `taskTree` 三个方法 App 零调用（`editDecomposition`
V132 起被逐步编辑取代，见 106 号）。App 的发布页只能发一次性的线上小任务。

## 1. 做了什么

| 位置 | 行为 |
|---|---|
| 合作入口 → 发布 | 多一个选项「这是一个要拆开做的项目」。勾上：建**草稿**（`publish_now: false`），建好后直接打开它的详情页 |
| 「不懂就问」→ 发布 | **不给**这个选项：从那里带着类目来的，是一单具体的活（例如一单法律咨询），不是要拆的项目 |
| 任务详情 | 发布方、项目型、总任务、草稿：「还没拆完：继续拆解 →」；确认之后显示子任务进度，点一步打开那一步 |
| 拆解页 | 与 web 同一套规则与文案（共享 SDK 的 `executorLabel` / `decompositionSourceLabel` / `LEAF_CRITERION_LABEL`）：树按层嵌套、每一步写出谁来做与依据、缺判据写「还差」、停下写原因；「待定」就地给「交给人做」与「需要某资质（类目）」；有没说清的步骤时确认按钮不可用；模型回落模板时明说 |

## 2. 顺带

- 子任务进度块拿到不像预期的响应时**不画**，而不是把整个详情页带崩——测试里一个没有桩的接口
  返回了 `[]`，`tree.children.length` 直接抛错，整页卸载。真实响应不会这样，但一个角落的数据
  不该决定整页能不能用（与 V117 关注计数「读不到不该让整页报错」同一条）。
- web 那一版吃过的亏（`{...props}` 盖掉 `node` 导致无限递归）这里一开始就按正确的顺序写。

## 3. 闸门

App 12 条（`decompose.test.tsx`）：执行主体与依据、嵌套；两种「去处」都是真的修改请求且不要资质的类目
不在选项里；没说清不能确认；说清后确认回到任务；展开一层与只拆一步的请求体；回落明说；
没拆过的草稿进来就开始拆；「继续拆解」只给发布方；进度块不带崩详情页；进度点进子任务；
合作入口发布项目建草稿并交回打开；「不懂就问」的发布页没有项目选项。

`test_vision_checklist` 当场要求把 V-5c / V-9 改成「两端已接」——闸门在数 App 的真实调用。
