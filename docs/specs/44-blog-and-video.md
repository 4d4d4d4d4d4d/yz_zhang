# 44 博客编辑器与视频沉浸流（CNT-003 / CNT-014）

> 需求回顾查出的**最后两条**降级实现。至此五条全部补完。

## 0. 这一批修的是什么

原 spec 写的是：

| 编号 | 原文 |
|---|---|
| CNT-003 | 博客编辑器 · Markdown/富文本，**草稿箱**，**插图**，标签 |
| CNT-014 | 视频沉浸流播放器 · **上下滑、倍速、断点续播、流量提醒** |

而 `contents` 表此前是这样的：

```python
body: Mapped[str] = mapped_column(Text)
status: Mapped[str] = mapped_column(String(12), default="published")  # published/removed
```

**连存媒体的字段都没有，也没有草稿态。** 插图、视频、草稿箱三件事
不是「做得简陋」，是压根没有承载它们的地方。

## 1. 设计判断

### 判断一（最要紧）：Markdown 绝不转 HTML

把用户写的 Markdown 转成 HTML 再塞进 DOM，是一个现成的**存储型 XSS**：
博客正文是别人写的、所有人都会看，一段 `<img onerror=...>` 就能在每个
读者的浏览器里执行。

常见做法是「转 HTML 再用 sanitizer 过一遍」——那要引入两个依赖，
而且安全性取决于 sanitizer 的黑名单跟不跟得上。这里换个方向：
**直接解析成 React 元素**，从头到尾没有一个字符串被当作 HTML 解释。

代价是只支持一个够用的子集（标题/加粗/行内代码/代码块/列表/引用/链接/图片），
收益是**这条路径上不存在 XSS 这个类别**——不依赖任何黑名单是否完备。

链接与图片仍要过协议白名单：`javascript:` 开头的 href 不需要 innerHTML
也能执行。被拒的链接**保留文字**而不是静默吞掉，否则作者不知道自己写错了。

### 判断二：视频不走 base64 JSON

图片可以 base64 过 JSON（客户端压缩后几百 KB）。视频不行——
一个 50MB 的视频 base64 之后是 **67MB 的 JSON 体**，整个读进内存再解码，
几个并发就能把进程打死。

所以视频走 `sign_upload` 直传对象存储，**文件根本不经过这个进程**。
本地存储没有 CDN，于是明确返回 `direct_upload: false` 让客户端失败，
**而不是给一个假 URL 让它传到不存在的地方**——与 FILE-013 同一条原则：
宁可明确失败，不要假装成功。

直传的文件本进程看不到，所以：归属在**签发时**就落库（否则举报一个视频时
同样答不出「这是谁传的」），审核状态直接置 `review`（机审看不到内容）。

### 判断三：发布时必须重跑机审

草稿是随便改的。「先存一段干净的，再编辑成违规的，然后发布」是条现成的绕过，
所以 `PATCH` 与 `publish` 两处都重跑 `machine_review`。

### 判断四：草稿只有作者自己看得见，但作者必须看得见

草稿不是「还没推荐」，是「还没公开」——feed、他人主页、按 id 直取全部拒绝。
但 `GET /contents/{id}` 对**作者本人**放行，否则草稿箱里点进去是 404，
根本没法编辑。

### 判断五：流量提醒是替用户的钱包做决定

这是个 LBS 平台，执行者常在户外用蜂窝网络。一个自动连播的视频流能悄悄
吃掉几百 MB。所以**默认在蜂窝网下不自动播**，由用户按一下再播。
`navigator.connection` 是非标准 API，取不到时按「可能是流量」处理——
宁可多问一次，也不要替用户花掉几百 MB。

### 判断六：断点位置存本地，不占服务端

这是「每个人自己的观看进度」，不该占服务端一张表，也不该跟着账号跨设备——
那会变成「我在手机上看到一半，电脑上也跳过去了」。
快看完了（剩不到 3 秒）就不记，下次该从头开始而不是跳到最后两秒。

## 2. 条目

- **CNT-030** `Content.media_urls`（JSON，最多 9 个）承载插图与视频。
- **CNT-031** `Content.status` 增加 `draft`；`POST /contents` 的 `publish=false`
  存草稿。
- **CNT-032** `PATCH /contents/{id}`（作者可编辑）、
  `POST /contents/{id}/publish`（草稿→发布，**重跑机审**）、
  `GET /contents/mine?status=draft`（草稿箱）。
- **CNT-033** 草稿对他人不可见（feed / 他人主页 / 详情三处），对作者可见。
- **CNT-034** `web/src/Markdown.tsx`：解析成 React 元素，
  **无 `dangerouslySetInnerHTML`**，链接协议白名单。
- **CNT-035** `web/src/BlogEditor.tsx`：Markdown 实时预览 + 草稿箱 +
  插图（PhotoPicker，上传后把 URL 插进正文）+ 标签。
- **CNT-036** `POST /files/sign-upload`：视频直传签名，类型与大小白名单，
  归属签发时落库，审核置 `review`。
- **CNT-037** `web/src/VideoFeed.tsx`：上下滑（触摸 + 键盘）、倍速
  （1/1.25/1.5/2×）、断点续播（localStorage）、流量提醒（蜂窝默认不自动播）。

## 3. 已知缺口

- **CNT-040 富文本仅 Markdown 子集。** 表格、脚注、嵌套列表都不支持。
  扩子集就是往 `Markdown.tsx` 里加分支，但每加一条都要想清楚它会不会
  引入一个能被当作 HTML 解释的字符串。
- **CNT-041 视频直传没有真实存储可验证。** 本地实现只会明确拒绝；
  接对象存储后必须补一次真实直传 + 回调审核的端到端验证。
- **CNT-042 视频没有转码与封面图。** 真实产品要转码成多码率、抽首帧做封面，
  这依赖转码服务，不在本批范围。
- **CNT-043 App 侧没有博客编辑器与视频流。** 与 IM-030 同源——
  端点与 SDK 就位，App UI 未做。
