# 74 一个人不能把不可逆的钱决定做完（DSP-030 / PAY-042 / CLI-078）

> 豁免表里写着：「二审裁决也由平台仲裁岗做，**且必须与一审不是同一个人**」。
> 代码里没有这一行。

## 0. 探针

同一个管理员，先做一审处理决定，再受理并裁决自己的申诉：

```
一审:        200        # 执行方分成 5000bps
申诉:        200
二审(同一人): 200        # 执行方分成 9000bps —— 钱跟着二审动了
最终 arbiter: 3   admin: 3
```

**同一个人，两次决定，中间那笔钱按第二次的结论重新划了一遍。**

而 V82 的豁免表里，这条规则是被明确写下来的：

```python
"/disputes/{x}/appeal-verdict": "二审裁决也由平台仲裁岗做，且必须与一审不是同一个人",
```

这是 V96 那件事的第二次：**豁免表的理由里写着一个承诺，而没有任何东西
核对它**。V96 那次承诺的是「在管理后台做」（后台里没有），
这次承诺的是一条**控制规则**（代码里没有实现）。

一张豁免表如果没人核对它的理由，它就只是一句无人负责的承诺。
第一次发现时我修了那一条；这次要修的是**这类承诺本身没有闸门**。

## 1. 为什么申诉复核必须换人

申诉的全部意义在于**换一个人再看一遍**。让做出原决定的人来复核自己的
决定，等于把申诉做成了一道形式：

- 他要推翻的是自己刚写下的理由；
- 当事人看到的「已复核」三个字，和没复核没有区别；
- 而复核会**真的动钱**（差额纠正性划转，`delta > 0` 补付、`delta < 0` 退回）。

这不是「最好换个人」，是这个流程存在的前提。

## 2. DSP-030 二审换人

`appeal_verdict` 增加一条准入：**复核人不得是原决定的作出人**。

拦截的理由要写清楚（`same_arbiter`），因为这条拒绝对运营来说是
「我明明有权限」——他确实有，只是不在这一案上。

> 平台只有一个管理员时，这条会让申诉无法处理。**这是对的**：
> 申诉复核需要第二个人，这是流程要求，不是代码的不便。
> 报错文案要直接说出来，让运营知道该去加人而不是去改代码。

## 3. PAY-042 大额提现的双人复核（maker-checker）

V96 补了提现复核台，而批准仍是一个人点一下就把钱打出去。
真实风控对大额出款普遍要求 maker-checker：**一个人提交放行意见，
另一个人确认**。

这一批的做法**刻意保守**：不改既有的 `approve` 语义（它仍是一次裁决），
而是在**超过双人复核门槛**的金额上要求两次不同管理员的批准：

| 金额 | 规则 |
|---|---|
| ≤ `WITHDRAW_DUAL_APPROVAL_CENTS` | 一人批准即放款（与现状一致） |
| > 门槛 | 第一次批准记为「已复核，待二次确认」，**钱不动**；第二个管理员确认后才放款 |

第二次必须是**不同的人**（否则就是同一个人点两次，等于没有这条规则）。
门槛走配置，默认值写在 `config.py` 里，并且**通知与文案里的数字取自配置**
（V61/V90 立过：通知里的数字不许是字面量）。

## 4. CLI-078 闸门：豁免理由里承诺的规则，必须真的存在

这是 V96 那条闸门的推广。`CLIENT_EXEMPT` 的理由分两种：

1. **说明这条路给谁用**（「开放 API 给第三方」「支付供应商回调」）——
   无需核对；
2. **承诺了一条规则或一个去处**（「在管理后台做」「必须与一审不是同一个人」）——
   **必须能被核对**。

第二种从此要登记：路径 → 兑现它的东西（一个后台调用，或一条测试）。
没登记就红，登记了但兑现不了也红。

判定标准写下来：**理由里出现「必须」「不得」「只能」「在管理后台」这类
承诺性措辞的，就属于第二种。**

## 5. 验收点

| 编号 | 验收点 |
|---|---|
| DSP-030 | 原决定作出人不能裁决同一案的申诉（`same_arbiter`） |
| DSP-030 | 换一个管理员可以正常复核，且差额划转与原逻辑一致 |
| DSP-030 | 拒绝文案说清「需要第二个人」，不让运营以为是权限问题 |
| PAY-042 | 门槛以下一人批准即放款（现状不变） |
| PAY-042 | 门槛以上第一次批准**不动钱**，状态进入待二次确认 |
| PAY-042 | 第二次确认必须换人；同一人再点一次被拒 |
| PAY-042 | 两次确认都留审计；金额门槛取自配置 |
| CLI-078 | 豁免理由里的承诺性措辞必须登记兑现方式，否则红 |

## 6. 这一批没做的

- **封禁不做双人**。封禁可解封（V98 已把影响面接进流程），
  不属于不可逆；真要做双人应当和「处置分级」一起设计。
- 提现的双人复核**没有超时兜底**：第一次批准后如果没人来二次确认，
  申请会停在那儿。这和 TEAM-063（审批无催办）是同一个缺口，
  留给下一批一起做。
- 没有**按角色**区分 maker 与 checker（现在是「任意两个不同管理员」）。
  真实风控通常要求 checker 的岗位等级不低于 maker。
- 结算（`settlePlatform`）与税款缴库仍是一人操作。
