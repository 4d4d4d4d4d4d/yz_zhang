
# 90 关注是个 toggle，而没有任何接口能告诉客户端当前状态（CNT-022）

> 状态：本批实现（V117）
> 依赖：08 号（内容与关系）、88 号（独立个体网络与公开空间）、66 号（补救入口）

## 0. 从「关系」这个核心对象查起

`PRODUCT-DIRECTION.md` 把**关系**列为五个核心对象之一，
而访问者决定要不要关注的那一刻，正是在别人的公开空间上：

> 访问者先看真实内容，再决定关注、交流、购买或邀请。

上一批我说过「关注 web 和 App 都没有」——**那句话是错的**。
查下来：服务端有 `Follow` 表与两个端点，SDK 有 `followUser` / `followStats`，
web 的 `Community.tsx` 调了 `followUser`。

但接着看就不一样了：

```
followUser    web=True   app=False     ← 只在旧的内容流里
followStats   web=False  app=False     ← 没有任何端调用过
个人空间页    web 0 处   app 0 处       ← 产品的中心没有关注
```

**关系存在，但没有接到它该在的地方。** 而再往下看，问题比「缺个按钮」严重。

## 1. 探针：三件事

```
PROBE 1 关注一次:              {'following': True}
PROBE 2 再点一次（双击/重试）:  {'following': False}   ← 撤销了

PROBE 3 有没有「我是否已关注」的读接口？
   GET /users/2/follow         405
   GET /users/2/follow-stats   200  keys=['followers', 'following']
   GET /spaces/2               （没有 following 字段）
```

### 1a 它是个 toggle

`POST /users/{id}/follow` 第二次调用会**取消关注**。手机上双击一下、
或者弱网下客户端自动重试一次，用户刚关注的人就不见了——
而他看到的是自己点了两次「关注」。

### 1b 没有任何接口能回答「我是否已关注」

于是想在页面上画「关注 / 已关注」，**按钮只能猜**。

两件事合起来才是真正的毛病：**猜错 + toggle = 想关注却取消了关注**。
一个按钮有一半概率做反。

### 1c 同名不同义的陷阱

`follow-stats` 返回 `{followers, following}`，而其中 `following` 是
**「这个人关注了多少人」的计数**；`followUser` 返回的 `{following: bool}`
却是「我是否已关注」。**同一个键名，两件完全不同的事。**

客户端把前者当后者读时，结果随别人关注了几个人而变：
计数非零 → 永远显示「已关注」；计数为零 → 显示「关注」。
**一个按钮的状态取决于一个与它无关的数字。**

## 2. 改法

### 2a 幂等化：关注与取消是两个动作

| | |
|---|---|
| `PUT /users/{id}/follow` | 关注，幂等。已关注再调仍是已关注 |
| `DELETE /users/{id}/follow` | 取消关注，幂等。没关注过也返回「未关注」，不报错 |
| `POST /users/{id}/follow` | **下线**（405） |

旧的 toggle 没有保留。留着它比删掉更糟：两个动作并存时，下一个人会从
两个里挑一个用，而挑到 toggle 的那一半界面会继续出现「想关注却取消了」。

「没关注过也当成功」是有意的：对「取消」这个动作来说，
**「本来就没有」和「刚刚删掉」对用户是同一件事**。

幂等还带来一个附带好处：旧的内容流里那个**无状态的「关注」按钮变安全了**。
它不知道当前状态，但现在最坏的结果是「重复关注一次」，不再是撤销。

### 2b 把状态读出来，而且分清是谁的状态

`GET /users/{id}/follow-stats` 增加 `viewer_following`：

- 键名特意**不叫** `following`——那个名字在同一个响应里已经被计数占了（第 1c 节）；
- 匿名访问时是 `null` 而**不是 `false`**：「没登录所以不知道」与
  「登录了但没关注」是两件事。合成一个 `false` 会给游客画一个
  **点下去才发现要先登录**的按钮；
- 看自己的页面时也是 `null`——自己的空间上不该有关注按钮。

### 2c 可选鉴权：只认人，不放权

公开空间允许匿名浏览，所以 `follow-stats` 需要「如果登录了，顺便认一下是谁」。
新增 `get_optional_user`，**复用** `get_current_user` 而不是另写一遍
（会话吊销、封禁、注销那几道判断抄第二遍必然漏一条）。

它把「token 无效 / 会话已吊销 / 账号被封」统一降级成**匿名**。
这在只读的公开接口上是对的，但边界必须写死：

> 只许用在本来就允许匿名访问的读接口上；
> **绝不能**用它授权任何写操作或私有数据读取——
> 那会把「会话已吊销」悄悄变成「当成游客放进来」。

这条边界配了一条测试：坏 token 读 `follow-stats` 拿到匿名结果，
而同一个坏 token 去写必须照样被拒。

## 3. 两端都接到空间上

web 的 `PublicSpace` 与 App 的 `PublicSpaceScreen` 各加一个按钮，
状态**从服务端读**，关注与取消走各自的动作。关注数读不到不让整页报错——
它是页面上的一个小角落，而空间的正文是人和作品。

## 4. 我自己的测试差点什么都没证明

第一版 App 与 web 的用例都用了 `{following: 7, viewer_following: true}`。
红验「把计数当成我的状态」时，**两条都是绿的**——因为 `!!7` 和 `true`
恰好一致，用例根本分不出两个键。

改成**两个键故意取相反的真值**（他关注了 0 个人，而我已经关注了他）之后，
读错键就会画出「关注」而真相是「已关注」，红验才真的红。

**一个看起来合理的断言，可能对它声称要防的那件事完全无能。**
这和「扫不到等于全绿」是同一回事，只是换到了测试数据的取值上。

## 5. 闸门

| 闸门 | 内容 |
|---|---|
| CNT-022 幂等 | 连关三次仍是已关注且计数为 1；连取消三次都返回未关注 |
| CNT-022 toggle 下线 | `POST` 必须 405 |
| CNT-022 状态可读 | 匿名 `null`、登录未关注 `false`、关注后 `true`；看自己 `null` |
| CNT-022 键名 | `following` 是计数、`viewer_following` 是我的状态，两者取相反真值仍要判对 |
| CNT-022 关注自己 | 两个动作都要拒（只拦一个等于没拦） |
| CNT-022 可选鉴权 | 坏 token 读到匿名结果；同一个坏 token 写必须被拒 |
| 客户端 | 已关注点一下走 DELETE、未关注走 PUT；游客被送去登录而不是给个死按钮；关注数读失败不让整页报错 |

红验八条走过：toggle 放回去、去掉 `viewer_following`、匿名写成 `false`、
可选鉴权被用来放权、`POST` 又被加回来、App 读错键、web 回到「总是调
followUser」、web 读错键。

## 6. 这一批没做的

- **没有关注列表页**：现在只能在某个人的空间上看到「我是否关注他」，
  没有「我关注了谁 / 谁关注了我」的页面。`followStats` 的两个计数是
  现成的，但列表要分页与隐私判断（谁可以看别人的关注者），
  记在 72 号台账（`CNT-023`）。
- **不做关注通知**：被关注是否该收到通知，牵涉骚扰与免打扰策略，
  而 NTF 那套必达清单是按「钱与权利」设计的，关注不属于那一类。
  要做得先定策略，不是加一行 `notify()`。
- **内容流里的按钮仍然无状态**：它现在是安全的（幂等），但按下去没有
  视觉反馈。要有状态就得让 feed 响应带上每个作者的关注状态，
  那是一次响应形状的扩张，与这一批的主题（动作语义）不是一件事。
- **关注不参与推荐**：`discoverSpaces` 的排序仍然是按 user_id，
  不是个性化（Spec 88 §4 已写明）。
