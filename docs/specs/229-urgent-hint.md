# 229 自选加急的滥用提示

> 状态：本批实现（V256）。编号 ESCA-060。
> 来源：172 号 spec「没做的」——「统计每个人自选加急被客服改回的比例，过高时提单页提示」；BACKLOG V256（第八轮排期 18 分）。
> 只增不减：提单、类别、优先级与时限的规则全不变——提示不拦，选了加急照旧按加急处理。
> 写明的行为变化：提单响应多 `priority_note`；新接口 `GET /support/tickets/urgent-hint`；后台工单队列每行多提单人近 90 天自选加急 / 被改回的张数。

## 0. 要解决的问题

V178 让用户自己选「资金 / 账号」类加急，时限更短。有人什么都选加急：客服只能一张张改回一般（ESCA-052 留痕），真正钱没到账的人排在了后面，而这个人自己并不知道。

## 1. 业界怎么做

客服系统常见的做法是先提示、再处理：对频繁误选紧急级别的用户在提交时提醒，客服侧看得到提单人的历史，不直接剥夺选择权。（本批没有另找外部来源。）

## 2. 规则

- 口径：近 90 天里，这个人自选资金 / 账号类的工单数；其中被客服改回一般的张数——以客服改优先级时写的审计「urgent -> normal」为准，同一张改来改去只算一次，把加急再点成加急（没变化）不算。
- 提示条件：自选加急 **≥3 张**（一两张不下结论）且被改回的 **过半**。
- 提示文字：「你最近 90 天选了加急的 N 张工单里，有 M 张被客服改回了一般。加急只留给资金没到账、账号登录或安全这类事：选错会让真正着急的人排在后面。」
- 不拦、不自动降级：照旧按用户选的加急处理，由客服判断。

## 3. 数据

不加表：读 `tickets` 与 `admin_audits`。

## 4. 接口

| 接口 | 变化 |
|---|---|
| `GET /support/tickets/urgent-hint` | `{days, self_urgent, downgraded, message}`；`message` 为空就不用提示 |
| `POST /support/tickets` | 多 `priority_note`：选了加急且满足条件时是上面那句，否则空串 |
| `GET /admin/tickets` | 每行多 `requester_urgent_90d`、`requester_downgraded_90d` |

SDK：`UrgentHint`、`myUrgentHint()`、`createTicket` 响应的 `priority_note?`、`AdminTicketRow` 两个可选字段。

## 5. 两端

- **Web / App 提单**：选「资金」「账号」类别时，满足条件显示那句提示（选「一般」不显示）；提交后写明「已提交（按加急处理）」并附这句。
- **Web 后台工单队列**：提单人被改回过的，写「提单人近 90 天自选加急 N 张，被改回一般 M 张」，没被改回过的不写。

## 6. 隐私、授权与边界

用户只看到自己的统计；客服在队列里看到提单人的这两个数字，不含别的内容。
