## 0. 核对：三个数字相乘，没有人在算

量生产编排文件与池参数：

```
deploy/docker-compose.prod.yml   uvicorn ... --workers 2     replicas: 1
app/core/config.py               DB_POOL_SIZE=10  DB_MAX_OVERFLOW=20
                                 => 2 × 30 = 60 条连接
postgres:16-alpine（未调参）      max_connections = 100
                                 其中 superuser_reserved_connections = 3
worker 容器（scripts/cron.py）    走 HTTP 打 job 端点，**不开池**
```

今天 60 < 100，活得下去。问题是**没有任何地方在算这个乘法**，于是：

- 把 `--workers 2` 调成 8（一个看起来只会「扛得更多」的改动）→ 240 条；
- 把 `replicas: 1` 加到 3 → 180 条。

两种改动都极其自然，而超出之后的表现不是某个接口变慢，是 PostgreSQL
直接拒连（`FATAL: sorry, too many clients already`）——
**每一个接口同时 500，包括健康检查**。于是编排器判定容器不健康并重启它，
重启后它又去抢同样多的连接。

业界的说法一致：先定进程数，再让 `进程数 × (pool_size + max_overflow)`
落在数据库容量之内，否则就在应用与数据库之间放 PgBouncer（transaction 模式）。
有案例是 12 个 pod × pool_size 25 = 300 条打在 `max_connections=200` 的实例上，
最后靠 PgBouncer 解决。另一条常被忽略的是 `max_overflow` 的默认值 10
在生产是危险的——**溢出连接是「悄悄超预算」的那一半**。

### 还量到两件事

**`pool_timeout` 没有设**，用 SQLAlchemy 默认的 30 秒。池满时请求挂 30 秒，
在用户那边等于「这页卡死了」——他会刷新，于是又来一个请求，池更满。

**`max_overflow=20` 是池大小的两倍。** 也就是说稳态 10 条、峰值 30 条，
而预算是按峰值算的。这个比例不是错，但它意味着**预算必须按 30 算而不是 10**，
而这件事此前没有写在任何地方。

## 1. 本批做了什么（V123）

| 编号 | 内容 |
|---|---|
| CONC-060 | `pool_timeout` 设为 10 秒并真的传给引擎；闸门断言引擎上的值与配置一致 |
| CONC-061 | `PLATFORM_API_WORKERS` × (池 + 溢出) ≤ `PLATFORM_DB_CONNECTION_BUDGET`，**启动时拦截**（GO-LIVE 第 14 条） |
| CONC-061a | 编排文件里真实的 `--workers` × `replicas` 必须等于 `PLATFORM_API_WORKERS` |
| CONC-061b | 预算不得超过数据库真实能给的连接数（默认 100 − 超级用户 3 − 运维 10 = 87；当前预算 80） |
| CONC-061c | SQLite 部署不受这条算术约束（**一个假报警多的闸门会被人关掉**，而本地与测试跑的都是 SQLite） |

为什么 `pool_timeout` 定 10 秒而不是 1 秒：太短会把**正常的排队**当成故障。
池满在峰值是会短暂发生的正常现象，10 秒足够让一批请求排完，
又不至于让用户面对一个转圈的页面。

为什么预算定 80 而不是 97：除了超级用户的 3 条，还要留给
**alembic 迁移、人工 psql 排查、监控采集**——
上线当天迁移连不上库，和服务连不上库一样是事故。

## 2. 重复付款：一句没人检查的承诺（FIN-070）

`app/core/idempotency.py` 的 docstring 第一行写着：

> 14.6「所有写操作支持 Idempotency-Key，**资金类强制**」

量一下这句话值多少：全仓只有两处用 `replay_or_run`——`wallet.topup` 与
`wallet.withdraw`。而动钱的函数一共六个（`fund` / `release` /
`release_milestone` / `accept_change` / `cancel` / `execute_verdict`），
**四个没有幂等键**。这是「一个承诺没有任何东西在检查」的第十次。

**但结论不是「补四个幂等键」。** 合约那四条走的是另一种保护：
`lock_contract_funds()` 取行锁，然后判状态，不对就 409。重放
`POST /fund` 得到 `not_fundable`，钱不会动第二次。那是正当的保护，
而且在并发下**比幂等键更强**——幂等键挡的是同一个 key 的重放，
挡不住两个不同 key 的并发重复托管。

反过来，充值与提现**不能**只靠状态机：同一个人连续充两次 100 元是
完全正当的操作，状态机分不出「重试」与「真的又充了一笔」，只能靠 key。

所以真正的毛病是**没有人说过哪条走哪种**。于是读 docstring 的人以为
资金类全有幂等键（不对），而加一条新的动钱接口时，没有任何东西问
「你靠什么防重复」。

本批做法——`MONEY_WRITE_PROTECTION` 声明表（值是机制与理由，不是布尔）
＋ **真的打两次**：

| 闸门 | 内容 |
|---|---|
| FIN-070a | 每一条动钱的函数都要在表里写明机制与理由（AST 扫出动钱的函数，不手抄） |
| FIN-070b | 声称靠行锁的，函数里必须真的有 `lock_contract_funds`；声称靠幂等键的，router 里必须真的接头并走 `replay_or_run` |
| FIN-070c | 同 key 充两次只到账一次；**没带 key 的两次是两笔真充值**（把同额连充误判成重试会吞掉用户的钱） |
| FIN-070d | 同 key 换金额必须 409，不得静默回放旧结果——**把一笔没发生的充值显示成成功，比报错严重得多** |
| FIN-070e | 重复托管、重复放款：钱只动一次 |
| FIN-070f | **合约自己**要拦住重复放款，不能只靠任务状态机在外面挡着 |

FIN-070f 是红验逼出来的，值得记下来：第一版只测 `/accept-delivery` 打两次，
而第二次是被**任务**状态机拦下的（任务已 completed），根本到不了 `release()`。
把合约里的 `status != funded → 409` 删掉，那条测试**仍然是绿的**。
**一个因为别处恰好也拦着而通过的断言，等于没有断言**（V118 同一条教训）。

参照 Stripe 的语义，本批**没有**全部照搬，差异写明：

| Stripe 的做法 | 这里 | 为什么 |
|---|---|---|
| 存首次结果（含失败），重放原样返回 | 只存成功结果 | 失败的结果重放回去会让客户端以为「重试也没用」，而很多失败是瞬时的 |
| 同 key 不同参数 → 报错 | 同（409 `idempotency_key_conflict`） | 一致 |
| key 24 小时过期 | **未实现过期** | 记台账 `FIN-071`：没有过期的幂等表会无限增长 |
| 并发同 key 不存结果，可重试 | **未处理** | 记台账 `FIN-072`：当前靠 `(user, key)` 唯一约束，并发第二个会撞约束而 500 |

## 3. 容量：单次压测不是容量证明（CONC-062~064）

本批实测（本容器 + SQLite 单文件，`scripts/loadtest.py`）：

```
read  concurrency=32  requests=400   69.8 rps  p50 447.6ms  p95 583.5ms  零错误
```

**这个数字不能当容量用**，理由要写清楚：

1. **跑的是 SQLite 单文件**，生产是 PostgreSQL——写路径的并发特性完全不同
   （SQLite 把写串行化，这也是 V118 那条并发测试复现不了竞态的原因）；
2. **单次运行、共享云容器**，与 V110 那次（read 94.1 rps）并排看像是慢了
   四分之一，但两次都不足以断言回归（台账 `DRILL-031` 已记）；
3. **只有 read 与 write 两个场景**（台账 `DRILL-032`），而真实流量里最贵的是
   「发任务 → 匹配 → 合约 → 托管」这条多步写入链。

要变成容量证明，缺的是（都未做）：

| 编号 | 内容 |
|---|---|
| CONC-062 | 压测打 PostgreSQL 而不是 SQLite，并记录连接池等待时间（`pool-wait`）——**池等待是容量的真正指标**，比 rps 更早变坏 |
| CONC-063 | 场景覆盖闭环链路，而不是单接口 |
| CONC-064 | 同一配置连跑三次取分布，才谈「基线」与「回归」 |
| CONC-065 | PgBouncer（transaction 模式）：让应用并发与数据库容量解耦 |

## 4. 还没查的并发问题（诚实记账）

- **N+1 查询没有系统性排查**。V118 顺手修掉一个（每开一次私聊扫全表），
  但那是撞上的，不是查出来的。要做得有工具：记录每个请求的 SQL 条数，
  超阈值在测试里红。记 `CONC-066`。
- **长事务**：每个打开的事务都占着一条连接，包括等外部 I/O 的时候。
  平台调供应商（支付/短信/实名）时有没有把事务一起挂住，没查。记 `CONC-067`。
- **`--preload` 与池**：业界明确提醒，池在 import 时建立的话不要用 `--preload`。
  当前没用 preload，但也没有任何东西拦住以后有人加上。记 `CONC-068`。
- **worker 回收**：没有设 `--max-requests` 与 jitter，长跑进程的内存与
  连接泄漏没有兜底。记 `CONC-069`。
