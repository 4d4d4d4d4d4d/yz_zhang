
# 408 要资质的单只推荐持证的人，画像风险看加选资质

> 状态：本批实现（V435）。编号 SCN-294d。
> 来源：上一批（V434，407 号）「没做的」。查下来不只是新加的「加选资质」，推荐本来就不看任何资质：
> - 空调加氟、电工维修这类类目要证的单，推荐列表里也有没证的人；
> - 发单人照着推荐去邀请，对方去报名才被「该类目需……」挡下，两头白跑。
>
> 写这一批的测试时还发现：SDK 的 `taskDraftProfile` 只发它认得的那几个字段，新加的字段会被悄悄丢掉；已改。
> 只增不减：不要资质的单，推荐与以前完全一样；画像接口多收一个可选的 `task_certs`。

## 0. 要解决的问题

- **推荐**：要资质的单，只推荐张张都有的人（审核通过、未过期、认别名），理由里写明持什么证。
- **画像**：发单时的风险提示，也要说出加选的资质会挡人。

## 1. 业界怎么做（带来源链接）

撮合平台的推荐先过「能不能接」（资质、地区、开关），再排「谁更合适」。本平台已经先过实名、接单开关和黑名单，这里补上资质这一道。本轮没有引用外部报道链接。

## 2. 数据

不改表。

## 3. 接口

- `task_required_certs(db, task)`：接这一单要的全部资质（类目的、未成年人证明、发单人加选的），报名准入与推荐共用这一份。
- `holders_of(db, user_ids, required)`：一次查完这些人的有效资质（认别名），不按人逐个查。
- `GET /tasks/{id}/recommendations`：
  - 要资质的单，只留张张都有的人，理由里多「持「…」」；
  - 不要资质的单不变。
- `POST /profiles/task-draft` 多收可选的 `task_certs`；`GET /tasks/{id}/profile` 带上任务的 `task_certs`。
  - 风险多一条「这一单另外要「…」，没有的人报不了名，能接的人会少一些」。

## 4. 两端

- **SDK**：
  - `TaskDraftInput.task_certs`；
  - `taskDraftProfile` 把它发出去：它只发列出来的字段，原来会丢掉。
- **Web 与 App**：发布页勾了加选资质，边写边提示的画像里就带上；推荐列表的理由由服务端给，两端照常显示。

## 5. 隐私、授权与边界

推荐里不显示别人持什么证的细节（证号、有效期），只写资质名。资质名本来就是这一单公开的要求。
