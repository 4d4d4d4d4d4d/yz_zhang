# 443 浮动对价分档

> 状态：本批实现（V470）。编号 OUT-050（分档加付），OUT-052（两端发单页选浮动对价，记欠）。
> 来源：52 号第 3 节记下的欠账 OUT-050：「浮动对价目前只支持一档 bonus（达标 / 不达标），分档递增没做——先把一档做对。」
> 只增不减：不给分档的老写法一字不变（全部平台判定指标通过付全额，否则全退）；52 号的测试照跑。

## 0. 要解决的问题

一档的问题：三条平台判定指标做到两条的人，和一条都没做的人拿的一样，「做得好多给钱」成了「做到满分才给钱」。发布方想按做到的程度给，只能拆成几单。

分档：「通过的平台判定指标至少 k 条，加付 X 元」，取达到的最高一档、不累加。52 号定下的几条照旧成立：
- **OUT-001**：挂在本任务的客观判据上；
- **OUT-002**：有确定上限，最高一档就是上限；
- **OUT-003**：上限全额先托管；
- **OUT-004**：由平台判定。

## 1. 业界怎么做（带来源链接）

承揽、服务合同里常见「按完成度分档付奖励」，关键是每一档的条件客观、金额确定、总额封顶，并写进合同。本轮没有引用外部报道链接。

## 2. 数据

迁移 `c1d220260102`：
- `tasks.bonus_tiers`：`[{min_passed, bonus_cents}]`，可空，老数据当空；
- `contracts.bonus_tiers`：签约那一刻的快照。与 IPC-003 同理：分档随已签署的合同走，事后改任务不改这一单。

## 3. 接口

**发单**（`POST /tasks`）：多一个 `bonus_tiers`，最多 5 档，只在 outcome 计价时可用（别的计价给了是 400 `bonus_not_allowed`）。

| 规则 | 错误码 |
|---|---|
| 按条数、按金额都严格递增 | 400 `bonus_tiers_not_increasing` |
| 最高一档要求的条数不超过平台判定指标的条数（够不着的一档是空头承诺） | 400 `bonus_tier_unreachable`，消息写明「只有 N 条」 |
| `bonus_cents` 不填就取最高一档；填了必须等于最高一档 | 400 `bonus_tiers_mismatch` |

最高一档同样受「不超过基础报酬」管（`bonus_too_large`）。

**任务详情**：多返回 `bonus_tiers`。执行方报名前就看得到「做到几条拿多少」。

**合同条款**（`clauses.outcome_clause`）写明：
- 按通过条数分档加付，取最高一档、不累加，最多加付多少；
- 每一档的条件和金额；
- 没达到的档位差额原路退回发布方。

条款本身就在规范化合同文本里，所以不用再改规范化字段，已签合同的哈希不变。

**放款**（`contract.service.release`）：
- 新的 `bonus_earned_cents()` 读合同里的分档，按最后一次交付说明上通过的平台判定指标条数，取达到的最高一档；
- 差额退回发布方：一分没挣到写「浮动对价未达标退回」，部分退回写「浮动对价按达到的档位退回差额」；
- 没分档的照旧走 `_bonus_earned()`。

SDK：
- 类型 `BonusTier`，`Task.bonus_tiers`、`TaskInput.bonus_tiers`；
- `bonusLine()` 两端共用：没分档的照旧「达标可加付至多」，分档的逐档写出来；
- 错误码：
  - 文案进 i18n：`bonus_tiers_not_increasing`；
  - 消息里带数字、用服务端原话：`bonus_tier_unreachable`、`bonus_tiers_mismatch`。

## 4. 两端

- **Web 任务详情**：有分档的逐档显示；没分档的照旧显示原来那句。
- **App 任务详情**：以前一个字都不显示浮动对价，现在显示同一句（`bonusLine`）。
- **发单页**：两端都还不能选浮动对价，现在只能走 API / SDK。记为 OUT-052。

## 5. 隐私、授权与边界

- 钱的规则全在服务端；客户端只显示。
- 资金守恒由对账作业核对（测试里分档的三种结果都跑了一遍对账）。
