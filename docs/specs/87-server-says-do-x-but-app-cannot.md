
# 87 服务端叫他交资质，而 App 上交不了（APP-072 / CLI-074 / DOC-010b）

> 状态：本批实现（V113 / V114）
> 依赖：66 号（补救入口）、76 号（受限类目资质核验）、85 号（手抄的数字）

## 0. 这一批的起点：先把「前后端已实现未实现」量出来

不读文档，用闸门自己的扫描器量：

```
端点总览   281 = 用户侧 214 + 运营 45 + 定时 22
SDK↔服务端 用户可达端点 216 / SDK 覆盖 237 / 未覆盖未豁免 0 / 豁免 13
SDK 方法   266：web 调 188 / App 调 81 / 运营台调 33
           三端都没调 73（有意不给端 17 + 台账排期 56），未交代 0
web 路由   16，真浏览器联调走到 6，其余 13 条有豁免理由
```

两个结论：

1. **后端↔SDK 这一层已经没有缺口**（0 未交代），V82/V102 的两个方向都闭了环。
2. **缺口换了位置：两端不齐。** web 有而 App 没有的方法 **79 个**，
   App 只到 web 的四成多。

于是真正要问的不是「还差多少个方法」，而是：**这 79 个里，有哪一个会让人
卡住赚不到钱、或者拿不到法定权利？**

## 1. 探针：服务端说了 12 句「请去做 X」

把服务端所有带祈使句的错误码扫出来（「请先」「请提交」「请绑定」…）：

```
12 个：active_contract / capacity_full / certificate_expired /
certification_required / insufficient_balance / no_payout_account /
owner_cannot_leave / session_revoked / sms_code_expired /
sms_code_locked / sms_code_missing / verification_required
```

逐条核对补救在哪个端做得到。**11 条两端都行，第 12 条不行**：

```
certification_required → 「该类目需「{X}」职业资质，请提交证件影像并通过平台核验后接单」
submitCertification    web=True  app=False
myCertifications       web=True  app=False
```

**App 的主要用户是线下执行方**（保洁、维修、搬家），而受限类目恰恰是需要证的
那些（电工、家电维修）。他点进一个单，被挡下来，然后被告知去做一件
**他的设备上做不到的事**。接不了单就是赚不到钱，而他没有电脑。

## 2. 为什么已有的闸门没抓到

V96 立过 `REMEDY_UI`：服务端每个「请先 X」，X 必须在声明的端上真的有入口。
那条闸门是对的，但它的清单是**手列的**——只有 **4** 条。

`certification_required` 从来没被问过「谁来做」。

这和 V57 的调度表、V111 的文档计数是**同一个病**：
**手列的清单只覆盖有人记得的部分，而漏掉的那部分不会报错。**

所以这一批不只是补一条表项，而是把清单改成**从服务端扫出来**的
（`_remediable_codes()`）：每个祈使句错误码要么在 `REMEDY_UI` 里（并且入口
真的存在），要么在 `REMEDY_BY_NORMAL_FLOW` 里写明「补救就是已有流程」。

第二张表同样要诚实：理由 ≥15 字、不许出现「还没做 / 待补 / TODO / 以后 / 暂时」。
没做就记台账，**不许伪装成「走正常流程即可」**。

## 3. app.json 里那两行声明

```json
"NSCameraUsageDescription": "用于拍摄任务交付凭证与到场照片",
"NSPhotoLibraryUsageDescription": "用于从相册选择任务交付凭证",
"android": { "permissions": ["CAMERA", "READ_MEDIA_IMAGES"] }
```

**权限声明了，功能从未实现。** 全仓 App 侧一处 `uploadImage` 都没有。
这又是「写下来的承诺没有人核对」那个形状——而且它会在应用商店审核时
被问「你要相机干什么」。这一批把那两行变成真的。

## 4. 一个需要正面交代的冲突

`REMEDY_UI` 里 `captcha_required` 的理由写着：

> **App 侧未接**：需要 WebView 承载第三方验证码控件，
> 本批没有真机可验证，**宁可如实记成缺口（APP-071）也不上一段没验过的原生依赖**

而这一批**加了** `expo-image-picker`。这不是忘了那条原则，是判断两者不同——
**失败模式不同**：

| | 装了、而真机上用不了的后果 |
|---|---|
| 验证码控件 | 挂在**登录路径**上 → 把人**锁在账号外面**。比没做更坏 |
| 相册 / 相机 | 挂在一个**新增入口**上 → 退回今天的状态（App 上交不了资质）。**不比现状更坏** |

另外两点：`expo-image-picker` 是 Expo 自家的托管模块，调用面只有
「权限 → 选图 → base64」三步；而集成逻辑（选图→上传→拿 ref→提交）
在 jest 里是**真测了**的，未验的只是「原生选择器会不会弹出来」。

残余风险如实记进台账（`APP-073`），不假装它已经在真机上跑过。

## 5. 实现里的几个判断

- **本地先拦 2MB**：服务端 `MAX_BYTES` 是权威，但手机多半在移动数据上，
  让他把 3MB 传完再被拒绝是在花他的流量。
- **不预填证件姓名**：服务端把证件姓名与实名严格比对（CERT-003：
  一张别人的电工证也是一张真证件），但 `me` 刻意不返回实名姓名（最小必要），
  所以只能把规则写在占位符里，并把服务端的驳回原文显示出来。
- **显示 `decision_reason`**：被驳回而看不到原因，用户只能反复提交同一份材料，
  而每一次重提都要再等一轮人工核验。
- **权限被拒时说清去哪儿开**：「按了没反应」是最糟的失败，用户会反复点同一个按钮。
- **上传拿的是 `ref` 不是 URL**：证件影像不该有一条谁都能打开的链接（37 号 spec），
  服务端据 `ref` 给审核员发鉴权 URL。

### 5b 测试替身上踩的一个坑

两条走失败分支的用例（权限被拒、图太大）第一版**静默测不到东西**：
jest mock 没写 `__esModule: true`，babel 的 `import * as X` 互操作会
**拷一份**导出对象给组件，于是 `jest.spyOn` 改的是另一个对象。
加上那一行之后两条才真的走到失败分支。

**一个 mock 没生效的测试会通过**——这正是「扫不到等于全绿」在测试替身上的版本。

## 6. V114 计数闸门的洞

V111 刚建的计数闸门，正则是 `(\d{3,5})\s*个测试`。而台账写的是
「有 1004 个**后端**测试」——**中间多两个字就瞎了**，真实值是 1200。

而这一页正是 README 里「现状一页看清」指向的那一页。它过期的代价不是排版：
读者用它判断「这套东西有多少保障」，于是**低估已经有的、高估还没做的**。
那一节同时还写着「约 88 个 SDK 方法两端都没有人调用」，而真实是 73 个
**全部已交代、未交代 0 条**。

修法：正则放宽到 `个(?:后端|前端|客户端)?测试`，并把那一节按实测重写。
顺带发现前端计数也漂了（App 从 21 涨到 27，而文档还写 161）——
这正是台账里记着的 `DOC-011`（前端计数没有闸门），它在真实地漂。
