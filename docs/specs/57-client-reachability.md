# 57 端上接得到：客户端契约覆盖闸门（CLI-060~067）

> 缺口来自 V81 收尾时的一次清点：48、49 两号 spec **从头到尾没有一个字提客户端**，
> `packages/core` 里也没有任何 agent / 核验单的方法。
>
> 再扫一遍全仓，结果比预想的严重：**78 个用户可达的服务端端点，共享 SDK 里
> 一个都没有**。V73~V79 六个批次（agent、人类核验、早期合作体、受限类目资质、
> 团队账户、开放 API）的用户侧入口，端上全是空的。
>
> 服务端完整、测试全绿、文档齐备——而用户点不到。

## 0. 这不是「还没来得及做 UI」

把它记成排期问题是最舒服的解释，但事实不支持：

- V76 之后，SDK 里那个 `addCertification(name, licenseNo)` **调用会 422**。
  服务端在 V76 改成了「提交申请 + 证件影像 + 姓名比对」，SDK 还停在
  「POST 一个字符串就拿到资质」的旧契约上。**没有任何测试会红**，因为
  SDK 的测试打的是 mock fetch，它只验证「我发出的请求长这样」，
  从不验证「服务端认不认这个形状」。
- 六个批次连续这样过去了，每一批的验收点都写着「服务端 X 成立」，
  没有一条问过「谁来调它」。

所以这一批的产出不是「补 UI」，而是**一条会红的规矩**：

> **服务端新增一个用户可达的端点，就必须同时给出「端上怎么到达它」
> 或者「为什么不给端」——二选一，不许沉默。**

这与 V60 的注销处置表是同一种做法：新增一列就逼作者做一次决定，
而不做决定时的默认行为不能是「悄悄留下」。

## 1. CLI-060 覆盖闸门

`server/tests/test_client_contract_coverage.py`：

1. 从 `app.openapi()` 取全部路由（这是**服务端自己声明的那一份**，
   不是手抄的清单）；
2. 从 `packages/core/src/client.ts` 扫出所有 URL 字面量；
3. 去掉 `/admin`、`/jobs` 前缀的运营/调度端点；
4. 剩下的每一条，要么在 SDK 里有路径，要么在 `CLIENT_EXEMPT` 里有**一句理由**。

### 扫描器必须自己先会红

老规矩（V72 立的）：正则写错时扫不到任何路径，闸门就变成恒真。
所以扫描器断言「至少扫到 N 条」且「已知的几条必须在里面」。

这里还有一个具体的坑：SDK 里有

```ts
`/tasks/mine${qs ? `?${qs}` : ''}`
```

**模板字面量里嵌了第二层模板字面量**，正则在第一个反引号处就断了。
所以路径提取是手写的字符扫描，不是正则。这类假阴性在覆盖率闸门里
表现为**假报缺失**——比不做还糟，因为一个满口假警报的闸门会被人关掉
（V80 那条法律文本闸门刚教过这件事）。

### CLI-061 豁免要写理由，而且是双向的

`CLIENT_EXEMPT` 的值是一句人话理由，不是 `True`。空理由不算数（有测试）。
反向也要成立：**豁免表里不能留下已经不存在的路径**——否则它会慢慢变成
一张没人敢删的历史清单，而闸门的实际覆盖面悄悄缩小（SYNC-002 同款）。

已豁免的几类，以及为什么：

| 路径 | 为什么不进 SDK |
|---|---|
| `/open/v1/*` | 开放 API 是**给第三方用 API Key 调的**，我们自己的客户端走普通会话 |
| `/wallet/pay/callback` | 支付供应商回调，服务端到服务端 |
| `/wallet/withdraw-requests/{x}/approve`、`reject` | 提现人审，风控岗位在管理后台做 |
| `/disputes/{x}/verdict`、`/appeal-verdict` | 裁决与二审由平台仲裁岗做（`require_admin`） |
| `/events/health`、`/events/dead-letters` | 前者 job 鉴权、后者 admin |
| `/finance/tax-ledger` | admin 台账 |
| `/files/{x}`、`/files/{x}/secure` | **能力 URL**，由 `<img src>` 直读——带不了 Authorization 头正是它存在的理由（FILE-013） |

## 2. CLI-062 补齐 SDK

把闸门指出来的其余端点全部接上，约 60 个方法，覆盖六个批次的用户侧：

- **agent**（AGT）：可用助理与**不可用的理由**、邀请、触发执行、执行记录与交付闸门
- **核验**（VER）：下核验单、可接列表与**不能接的理由**、接单、看产出、提交结论
- **早期合作体**（COOP）：创建、邀请、贡献登记与确认、份额、分配、合规路径、风险揭示
- **团队**（TEAM）：建队、成员与角色、支出申请/审批/执行、开票资料
- **开放 API**（OAPI）：Key 的签发/轮换/吊销、Webhook 的登记与投递记录、scope 列表
- **资质**（CERT）：修正那个会 422 的方法，并补上「我的申请与状态」
- 其余零散的用户侧端点（工单、通知偏好、搜索建议、经验卡、发票、行程分享、SOS…）

**修正 `addCertification` 是这一批里唯一一处「改了既有契约」**，
其余都是新增。旧签名保留会更"兼容"，但它兼容的是一个**服务端已经不接受
的形状**——留着只会让下一个人以为它能用。

## 3. CLI-063 Web 上的两个入口

SDK 有方法而界面上没有入口，等于把洞往下挪了一层。这一批先做**最要紧的两个**，
其余（合作体/团队/开发者）随后批次：

### 任务详情页的「AI 助理」面板（发布方视角）

- 列出可用助理，不可用的**逐条写明原因**（到场任务 / 类目不符 / 超预算）
- 邀请 → 正常走报名、选人、签约、托管（不给 agent 开后门）
- 触发执行 → 显示状态、置信度、逐条判据结果、内容审核结论
- 执行失败或需人工核验时，直接给出「申请人工核验」的按钮，
  并**说明这一单谁付费**（升级是平台付，主动核验是自己付）

### 核验台 `/verify`（核验人视角）

- 可接的核验单列表；不能接的显示**资格原因**而不是空列表
  （「只显示空列表，核验人不知道是资格不够还是真没单」——这是 VER 自己的话）
- 接单 → 看到任务要求、AI 产出、平台判据逐条结果
- 提交结论：通过 / 已修正（必须附修正稿）/ 不通过

### CLI-064 界面必须显示服务端给的原因

两个页面都有一条共同的硬要求：**服务端已经算好了「为什么不行」，界面就得原样显示它**。
`eligible-agents` 和 `verification-orders` 都专门返回了 `reason` 字段，
把它们吞掉、只显示一个空列表，是这一批最容易犯的错——
因为空列表看起来更"干净"。

## 4. 验收点

| 编号 | 验收点 |
|---|---|
| CLI-060 | 服务端每个用户可达端点，要么在 SDK 里有路径，要么在豁免表里有理由 |
| CLI-061 | 豁免理由非空；豁免表里没有已不存在的路径；扫描器扫不到时自己先红 |
| CLI-062 | agent / 核验 / 合作体 / 团队 / 开放 API / 资质 六条线在 SDK 里可达 |
| CERT-060 | `addCertification` 按 V76 的真实契约发送（影像、证件号、持证人姓名） |
| CLI-063 | Web 上发布方能邀请助理并触发执行；核验人能看到、接下、提交核验单 |
| CLI-064 | 不可用的助理与不可接的核验单**显示服务端给的原因**，不是空列表 |

## 5. 这一批没做的

- **CLI-065**：合作体 / 团队 / 开发者三条线只到 SDK，Web 上还没有页面。
  闸门管的是「端上接得到」，不是「界面上找得到」——后者还没有机器可判的定义。
- **CLI-066**：App（React Native）侧同样只有骨架页面。SDK 共享，所以接上去
  不难，但要真机验证，本环境做不到。
- **CLI-067**：闸门只看路径，不看**请求体形状**。`addCertification` 这次是
  人眼发现的；要让它自动红，得拿 OpenAPI 的 schema 和 SDK 的调用参数对，
  那是另一批的事（而且需要先给 SDK 的方法标注出它调的是哪个 schema）。
