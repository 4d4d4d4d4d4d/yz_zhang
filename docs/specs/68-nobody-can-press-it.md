# 68 建好了，可是没有一个人能按下去（GEO-023/022 / ACC-040 / IM-020/021 / APP-067/068 / CLI-075）

> 一键求助的代码里写着：**「让求助按钮卡在合规弹窗上，是把合规做成了事故」**。
> 写这句话的时候，那个按钮在任何一个端上都不存在。

## 0. 探针

V91 量的是「App 比 Web 少什么」。这一批把问题换了个方向：
**这个产品里有多少能力，是两个端加起来都没有人能碰到的？**

```
SDK: 245   web: 137   app: 58
两端都没人调用: 105
['acceptChange', 'changePassword', 'checkin', 'myApplications', 'notificationPrefs',
 'openDirect', 'recallMessage', 'resetPassword', 'sendQuoteCard', 'setNotificationPref',
 'setTripShare', 'sos', 'trip', 'withdrawApplication', ...]
```

**105 个。** 这里面有几条不是「少个页面」的量级：

| 能力 | 服务端 | 客户端 |
|---|---|---|
| `sos` 一键求助（GEO-023） | 已实现：留痕、通知对方、返回指引 | **两端都没有按钮** |
| `setTripShare`/`trip` 行程分享（GEO-022） | 已实现 | 同上 |
| `changePassword`/`resetPassword` | 已实现 | **全产品没有任何地方能改密码** |
| `openDirect` 发起会话（IM-001） | 已实现 | 没人调用——**成交前两个人根本说不上话** |
| `recallMessage` 2 分钟撤回（IM-004） | 已实现 | 发错了收不回来 |
| `myApplications` 我的报名 | 已实现且分页测过 | 报完名就找不到了 |

## 1. 求助按钮

```python
@router.post("/tasks/{task_id}/sos", status_code=201)
def sos(...):
    """GEO-023 紧急求助：留痕 + 通知对方与平台（生产联动 110/紧急联系人）。

    LAW-031 这里**刻意不做**位置同意校验：PIPL 第十三条第(四)项把
    「紧急情况下为保护自然人的生命健康所必需」列为无需同意的处理情形。
    让求助按钮卡在合规弹窗上，是把合规做成了事故。
    """
```

这段注释把最难的那一层想清楚了——为了让按钮**不被一个弹窗挡住**，
特意去查了 PIPL 第十三条。而按钮本身没有被做出来。

探针实测服务端是通的：

```
SOS RESP: 201 {"ok":true,"guidance":"已通知平台与任务对方；如遇危险请立即拨打 110"}
对方收到: [('对方发出紧急求助', '任务《周末大扫除》的另一方发出紧急求助，请立即联系确认安全')]
```

**而 SDK 把这个响应声明成了 `{ id, notified }`。** 服务端返回的是
`{ ok, guidance }`——就算有人去调它，那句「如遇危险请立即拨打 110」
在类型里也不存在，任何界面都显示不出来。`setTripShare` 同样：
SDK 说 `{ enabled }`，服务端给的是 `{ trip_share_enabled }`。

这两条是 V89 形状闸门的漏网之鱼——闸门只覆盖了**有具名 TS 接口**的响应，
这两个是行内匿名类型，够不着（和 V91 的 `LedgerRow` 一样）。

**这一批的 P0 就是它：上门、夜间、独自面对陌生人的那群人，
平台替他们想好了法律依据，却没给他们那个按钮。**

## 2. ACC-040 改密码

`changePassword` 与 `resetPassword` 服务端都在，**两端都没有入口**。
用户怀疑密码泄露时，能做的只有注销账号。这条没有「错过就无法挽回」那么戏剧化，
但它是账号安全的地板。

## 3. IM-020/021 说不上话

任务会话在**合约托管成功**时自动建（IM-002）。也就是说：
**只有钱已经托管了，两个人才能开始说话。**

而 `openDirect` 建好了没人调用，于是成交前——正是要问「你几点能到」
「能不能带工具」的那个阶段——双方在产品里没有任何联系方式。
线下服务尤其吃这一条。

`recallMessage` 同理：服务端给了 2 分钟撤回窗口（IM-004），
**没有任何一个端能点**。发错人、发错内容、手滑把手机号发出去，都收不回来。

## 4. APP-067/068 App 的站内信与邀约

App 至今没有任何会话界面，也收不到/应不了邀约。
后者更硬：服务端**会发**「收到任务邀约」这条通知，
而 `acceptInvitation` 在 App 上不存在——
**又一条「通知把人叫来了，他点进去无路可走」**（CLI-074 正是为此立的）。
所以这条一并进 `NOTICE_ACTIONS` 表。

## 5. CLI-075 闸门：会危及人身、账号与钱的能力，必须有人能按

105 条一次清完不现实，也不该为了清而清——有些确实是管理后台或未来功能。
所以照 `MUST_REACH` / `REMEDY_UI` / `NOTICE_ACTIONS` 的老办法立表，
**只收那些「按不到就有实际后果」的**：

```python
MUST_BE_REACHABLE = {
    "sos": (("web", "app"), "上门/夜间任务的人身安全。服务端连 PIPL 豁免都查好了，却没有按钮"),
    "changePassword": (("web", "app"), "怀疑密码泄露时，用户唯一能自救的动作"),
    ...
}
```

判定标准写死：**按不到这一条，用户会面临人身风险、账号被别人继续用，
或者一笔钱/一个权利落空。** 不满足的不进表——
把 105 条全塞进去，这张表就会变成一份待办清单，而不是一条红线。

## 7. 这一批没做的

- **剩下约 95 个两端都没人调用的 SDK 方法**没有逐条过筛，只挑了会危及
  人身安全、账号安全和钱的那几条。其余逐批清理，**不装作已经清完了**。
- **GEO-023 的生产联动**（110 / 紧急联系人 / 平台值班）仍是注释里的计划：
  这一批只保证「按得到、留痕、通知对方」。**按钮能按不等于有人会来**，
  上线前必须接真实值班流程。
- `sendQuoteCard`（IM-009 报价卡）仍然没有任何端发得出去。
- App 的会话不做群聊、不做图片消息。
- **App 仍然没有单元测试**（APP-070）：这一批的 App 行为由扫描闸门与
  共享 SDK 类型覆盖，**这不等于在真机上按过一次那个求助按钮**。
