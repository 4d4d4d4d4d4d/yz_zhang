## 1. 原话

### 1.1 定位（`PRODUCT-DIRECTION.md`，2026-10-07，用户亲自写）

> 一个以独立个体为中心的开放协作网络：每个人拥有可经营的数字空间，
> 借助 AI 延伸能力，通过可验证的约定与他人及机器形成合作，
> 并把获授权的经验变成下一次合作的能力。

> 对用户的表达：让别人了解你，让想做的事找到一起完成的人。

五个核心对象：**个体、关系、意图、合作空间、经验资产**。

场景跨度（同一篇第 17 行与第 31~36 行）：

> 从"今晚帮忙遛狗"到"做一个机器人"

| 场景 | 直接体验 |
|---|---|
| 邻里帮忙、遛狗、简单交付 | 找到附近合适的人，约定时间和结果 |
| 设计、研究、咨询、内容制作 | 从作品认识人，说明想法，形成合作 |
| 机器人、工业品共创 | 找架构师及各模块负责人，共同推进 |
| 持续经营、复杂公司项目 | 在长期合作空间持续组织资源 |

信任与经验循环（第 51、53 行）：

> 信任分层：身份和能力证据 → 明确约定 → 实际交付记录 → 验收和争议处理
> → 可校验的证据。

> 合作结果 → 获授权的结构化复盘 → 去标识与分级访问 → 专家/参与者验证
> → 案例和流程检索 → 下一次使用 → 对照实际结果修正。

落到工程上的是三件事：
- **门户先管好自己，再对外合作**：门户的根是「助手 + 个人知识库」。个人工作台（V141）是助手的一半；知识库是另一半（V147）。蓝皮书逐章的差距见 [121 号 spec](specs/121-workbuddy-bluebook-gap.md)。
- **工程化迭代**：根目录的 `CLAUDE.md` 写规则，`.claude/skills/` 写做法，`docs/BACKLOG.md` 是活的待办，`server/scripts/harness.py` 负责新建 spec、做检查和列待办。spec 与代码的对应由 `tests/test_harness.py` 钉住。
- **平台能力**：任务画像（V151）；影响力与专家等级（V152，类 PoS，见下表 V-15）；按人群把痛点做成服务包（V149、V150）。

### 1.8 场景靠方法发掘，资产是平台的根（2026-10-13）

> 我只是举例，不局限于这些场景和功能，这些场景和功能的发掘，应该依赖于你基于商业化愿景迭代考虑到的，
> 而不是我提啥就做啥，场景千变万化，可以提炼一些方法或者 skill 或者工作流，对于这些场景也可以总结一套方法
> 快速发掘并部署方法到这个平台上，这样也能快速部署新的功能。本身这些 agent，skill，知识库就是平台重要的资产之一。

落到工程上的是两件事：
- **发掘场景有方法**：skill `scenario-discovery` 给出固定的流程，包括人群、要办的事、痛点的频率与严重度、AI 能做到几成、商业价值和交付成本。打分之后排进 BACKLOG。平台自己的数据也会给出信号（场景雷达）：搜不到的词、没人报名的类目、问答答不了的问题、客服没解决的工单。这些都是**聚合**数据，不看个人内容。
- **部署场景靠场景包**：一个场景就是一组平台资产的组合，包括**助手专家**（人设、方法、工具白名单、人工关口）、**方法**（可执行的清单或 SOP）、**知识条目**（有来源、有有效期）、任务模板和例行任务模板。上新场景主要是写一份场景包数据，审核后上线，用户一键启用；不用每次都写代码。下表 1.7 里的人群只是**第一批**场景包，后面的由雷达和方法持续发掘。

### 1.9 端侧隐私沙箱（2026-10-14）

> 另外，需要一套本地隐私性沙箱模式，能够在端侧手机上跑量化小模型从而信息不上传云端，能够完成一些基本 agent 助理的操作。

落到工程上：
- **沙箱模式是一个开关**：打开后，助手相关的推理只在手机上做（量化小模型，例如 1~4B 参数、4 bit 量化，跑在 llama.cpp / MLC 一类的端侧运行时上），**输入原文不离开设备**；
  关掉才回到云端助手。打开时界面上一直有标识。
- **能做的是基本助理操作**：在本机的笔记、待办、草稿上做摘要、拆清单、改写、抽待办、按模板起草——工具只能动**本机数据**，要联网或要动钱、签署、发布的一律拒绝或交给人。
- **不出网要能证明**：沙箱模式下发往服务端的请求只允许「已脱敏的结果」（用户确认后才同步），闸门钉住「沙箱模式下助手调用不发原文」。
- 模型下载、校验（哈希）与版本是平台资产的一部分；手机算力不够时如实说，不悄悄退回云端。

### 1.12 多模态智能体直接操作其他 App（2026-10-15）

> 支持通过多模态智能体能够直接操作其他app吗，在其他app不提供agent的通信api的情况下

落到工程上（[161 号 spec](specs/161-cross-app-agent.md)）：
- **现状**：还不支持。开放 API、Webhook、机器授权都要求对方提供接口；端侧沙箱只动本机数据。
- **做法按优先级退化**：官方 API → 深链 / Intent / 快捷指令 → 系统无障碍控件树 → 截屏加多模态识别。越往后越容易因为对方改版而失效，只在前面不可用时才用。
- **三端不同**：Android 用无障碍服务，可行；iOS 不允许跨 App 读屏，只接快捷指令和 App Intents；桌面用本机执行器。
- **红线不变**：钱、签署、发布、对外发消息只出草稿，由本人在屏幕上确认；屏幕内容默认只在本机处理（与 1.9 沙箱同一套）；只为本人、在本人设备上、对白名单里的 App 操作，不做批量、不托管别人的账号。
- **排期**：平台侧（授权、计划、逐步确认与叫停、红线拦截、执行记录与回放、统一执行器协议）V190；Android 无障碍执行器与桌面执行器需要原生构建与真机，记为「外」。

## 2. 逐条对照

状态词只有四个，含义固定：

- **两端已接**：web 与原生 App 都有真实调用（闸门会去数）
- **仅 web**：网页有，手机上没有
- **仅后端**：服务端能力存在，没有任何客户端够得到
- **未实现**：没有可交付闭环
