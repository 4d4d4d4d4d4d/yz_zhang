# 远景原话与逐条对照

这一页是**用户自己说过的话**，加上每一条今天到了哪一步。

写它的原因：愿景散在三处——`PRODUCT-DIRECTION.md`（2026-10-07 用户亲自写的
97 行）、会话里的几次复述、以及各批 spec 的开头。于是「平台满足我的需求了吗」
这个问题每次都要重新查一遍，而查的结论没有留下来。

**状态不是手写的。** 下面那张表由 `server/tests/test_vision_checklist.py`
钉着：声称「两端已接」的那些，闸门会去数共享 SDK 里对应的方法在 web 与 App
里有没有真实调用；对不上就红。手抄的状态一定会漂移（V111 的教训），
而一页过期的对照表比没有更糟——它会让人以为某条已经成立。

## 1. 原话

### 1.1 定位（`PRODUCT-DIRECTION.md`，2026-10-07，用户亲自写）

> 一个以独立个体为中心的开放协作网络：每个人拥有可经营的数字空间，
> 借助 AI 延伸能力，通过可验证的约定与他人及机器形成合作，
> 并把获授权的经验变成下一次合作的能力。

> 对用户的表达：让别人了解你，让想做的事找到一起完成的人。

五个核心对象：**个体、关系、意图、合作空间、经验资产**。

场景跨度（同一篇第 17 行与第 31~36 行）：

> 从"今晚帮忙遛狗"到"做一个机器人"

| 场景 | 直接体验 |
|---|---|
| 邻里帮忙、遛狗、简单交付 | 找到附近合适的人，约定时间和结果 |
| 设计、研究、咨询、内容制作 | 从作品认识人，说明想法，形成合作 |
| 机器人、工业品共创 | 找架构师及各模块负责人，共同推进 |
| 持续经营、复杂公司项目 | 在长期合作空间持续组织资源 |

信任与经验循环（第 51、53 行）：

> 信任分层：身份和能力证据 → 明确约定 → 实际交付记录 → 验收和争议处理
> → 可校验的证据。

> 合作结果 → 获授权的结构化复盘 → 去标识与分级访问 → 专家/参与者验证
> → 案例和流程检索 → 下一次使用 → 对照实际结果修正。

### 1.2 复述的六条（2026-10-09）

> 个人独立门户，普通协作例如日常遛狗，也可能高级的协作例如合伙公司，
> 商业活动，智能合约保证可信操作流程，AI协助不懂领域解决或者找合作者和
> 任务拆解，平台能够累积成功经验。

### 1.3 三条设计意见（2026-10-10）

> 攒经验完全可以作为检索数据库或者 skilltool 工具给后续复用。

> 知识图谱体系不可能把每个样本都添加，需要类似聚类一样，把额外信息或者
> 经验加到具体某个子类里或者如果没有新建子类。

> 任务拆解感觉可以借鉴 todolist 生成过程，主要要生成树类脉络够细够具体的
> 任务这样有些 ai 可以闭环有些需要求助其他专家。

### 1.4 商业化要求（2026-10-10）

> 以商业上线要求补全这些功能需求

> 实际商业化的一些问题，例如部署的并发，安全性，也考虑解决一下

## 2. 逐条对照

状态词只有四个，含义固定：

- **两端已接**：web 与原生 App 都有真实调用（闸门会去数）
- **仅 web**：网页有，手机上没有
- **仅后端**：服务端能力存在，没有任何客户端够得到
- **未实现**：没有可交付闭环

| # | 愿景条目 | 关键 SDK 方法 | 状态 | 还缺什么 |
|---|---|---|---|---|
| V-1 | 个人独立门户 | `ownSpace` `personalSpace` `discoverSpaces` `followUser` | 两端已接 | 封面/作品上传、独立域名、SSR 与分享预览（SPACE-021）；内容举报（SPACE-022） |
| V-2 | 日常协作（遛狗、跑腿、上门） | `createTask` `apply` `deliver` `acceptDelivery` | 两端已接 | 真实支付与实名供应商未接（上线红线 1~6），**现在还收不了真钱** |
| V-3 | 高级协作（合伙公司、商业活动） | `createTeam` `myTeams` `confirmContribution` `distributeVenture` | 两端已接 | 团队成员增删仍仅 web（TEAM-065）；持续合作空间不是统一驾驶舱（SPACE-024） |
| V-4 | 智能合约保证可信流程 | `signContract` `fundContract` `acceptDelivery` `openDispute` | 两端已接 | 证据包导出仍仅 web（`exportEvidence`）；可靠电子签名与司法存证需持牌机构（红线 4、5）；链上资产未正式部署 |
| V-5a | AI 协助：不懂领域 | `legalAsk` | 两端已接（V122） | 文书生成仍无客户端（LAW-050）；专业供应商与专家复核闭环未验收 |
| V-5b | AI 协助：找合作者 | `recommendations` `eligibleAgents` | 仅 web | App 上没有推荐与可用 Agent 入口；领域化能力证据与可用时间匹配未实现（SPACE-023） |
| V-5c | AI 协助：任务拆解 | `propose` `confirmDecomposition` `taskTree` | 仅 web | App 一个入口都没有（APP-077）；且一次只产出一层 DAG，无「谁能闭环」判定（AI-DEC-040，设计见 96 号 spec） |
| V-6 | 平台累积成功经验 | `knowledgeCards` `knowledgeSearch` | 两端已接（V122） | 只有样本层可读：缺子类层（KB-070，见 94 号 spec）与可复用单元/工具（KB-080，见 95 号 spec） |
| V-7 | 经验作为检索库与 skill tool | — | 未实现 | 设计已写（95 号 spec）；复用授权与训练授权是两份同意，分成口径未定前不开启 |
| V-8 | 经验按子类聚类生长 | — | 未实现 | 设计已写（94 号 spec）；退化态（词袋哈希）下不自动生长 |
| V-9 | 拆解成够细够具体的树 | — | 未实现 | 设计已写（96 号 spec）；资质类目硬否决 `ai_closable` 是其中最要紧的一条 |
| V-10 | 部署并发 | — | 部分 | 连接预算已有闸门与启动拦截（CONC-061，见 98 号 spec）；未做 PgBouncer、未做容量证明 |
| V-11 | 安全性 | — | 部分 | 安全响应头、写路径限流、跨副本封禁、四眼原则、资金重复保护已有；未做外部渗透测试与授权矩阵穷举（见 99 号 spec） |

**V-1 ~ V-6 是用户复述的那六条。** 其中五条两端已接，一条（任务拆解）仅 web。
V-7 ~ V-9 是 2026-10-10 补的三条设计，都已写成可实现 spec 而未实现。
V-10 ~ V-11 是商业化要求。

## 3. 不在愿景里、但上线前绕不过去的

这些不是用户要的功能，是**做这门生意要有的东西**。
放在这里是为了不让它们在「功能都做完了」的印象下被忘掉。

| 项 | 状态 | 卡在哪 |
|---|---|---|
| 资金存管（持牌机构） | 未接 | 平台自建账本托管用户资金涉嫌资金池与二清，已硬编码为启动拦截 |

| 实名 / 短信 / 内容安全 | 未接 | 注册表里没有正式适配实现 |
| 容量证明与值班 | 未做 | 单次压测不是容量证明；告警没有接收人 |
| App 上架 | 未做 | 原生依赖真机未验，商店检查未过 |

完整清单与判据见 [GO-LIVE.md](GO-LIVE.md)（14 条启动红线）与

## 4. 这一页怎么不过期

`server/tests/test_vision_checklist.py`：

1. 第 2 节那张表的每一行都要有状态，且状态必须是四个词之一；
2. 声称**两端已接**的行，表里列的 SDK 方法必须在 web 与 App 里都有真实调用
   （用 V102 那套客户端扫描器去数，不手抄）；
3. 声称**仅 web** 的行，必须确实 web 有、App 没有——
   **接上了而这里还写着「仅 web」，同样是过期**；
4. 扫描器自检：抽不出行时自己先红（扫不到等于全绿，是最糟的一种绿）。
